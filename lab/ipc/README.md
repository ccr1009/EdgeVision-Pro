## 0. 为什么先测再学

IPC 的 API(`pipe` / `shm_open` / `sem_wait`)半小时能背完,面试官也从不考 API 拼写。
他问的是「**为什么共享内存快**」「**这几种怎么选**」。

这类问题只有一个正确答案的来源:**你自己测出来的数字 + 你解释它为什么是这样**。
所以本实验的顺序是:先量出差距 → 再回来看数据结构 → 最后才是语义细节。

## 1. 先看清一件事:8 种机制其实只有两族

不要把它们当 8 个并列选项背。它们的本质区别只有一条:

```
数据要经过内核吗?
├─ 要(内核做中转/缓冲)  →  pipe / fifo / unix_stream / unix_dgram / tcp
└─ 不要(内核只给一块内存) →  shm + 某种"通知对方"的手段
```

- **第一族**:你 `write()` 进去,内核把数据拷进自己的缓冲区;对方 `read()` 再从内核拷出来。
  **两次拷贝 + 至少两次系统调用**。
- **第二族**:`mmap` 把同一块物理内存映进两个进程的地址空间。数据**只拷贝一次**(你写进自己
  可见的那块内存),对方直接就能看到。**内核不碰数据,只负责"通知"**。

> 关键洞察:**共享内存本身不提供任何同步**。它只解决「数据在哪」,
> 不解决「什么时候能读」。同步得另外找个东西——而这个东西的选择,
> 决定了你付出的是系统调用还是 CPU 空转。见第 3 节。

## 2. 实测:8 种机制的延迟与吞吐

### 2.1 延迟(乒乓往返,248 B 定长帧)

> 口径:`taskset -c 6,7` 绑两颗 A76 大核;每次计时 = 父进程发一条 + 收一条回程;
> 2000 次,前 50 次预热不计;板端其余服务已 `systemctl stop`,`loadavg < 0.5`。
> 数值是 **RTT(一来一回)**,单位 us。

| 机制 | p50 | p95 | p99 | mean | 相对最快 |
|---|---:|---:|---:|---:|---:|
| **shm_spin** | **0.583** | **0.584** | 0.584 | 0.500 | **1×(基准)** |
| unix_stream | 5.833 | 6.125 | 6.417 | 5.724 | 10× |
| pipe | 7.000 | 7.583 | 7.584 | 7.120 | 12× |
| fifo | 7.000 | 7.291 | 7.292 | 7.034 | 12× |
| sysv_shm (semop) | 7.875 | 8.167 | 8.458 | 7.940 | 13.5× |
| shm_sem | 8.166 | 8.458 | 8.750 | 7.844 | 14× |
| unix_dgram | 9.333 | 9.625 | 11.083 | 9.422 | 16× |
| tcp (回环) | 13.125 | 15.166 | 18.958 | 13.431 | 22.5× |

**三个必须能解释的现象:**

1. **`shm_spin` 比 `shm_sem` 快 14 倍,两者数据结构完全一样。**
   唯一区别:一个用 `sem_wait/sem_post` 通知,一个用原子变量自旋。
   → 差值就是**系统调用 + 内核调度**的净成本。这是全表最干净的一组对照实验。

2. **`unix_stream`(5.8us)比 `pipe`(7.0us)还快**,违反直觉——socket 层更厚啊?
   实测原因:`socketpair` 走了 `AF_UNIX` 的更短路径,而且 `pipe` 在内核里是
   环形缓冲区 + 两端的 wakeup 配对,`socketpair` 复用 `sock` 结构少一层;
   两者量级相同,**这点差异(1.2us)不要当结论讲**,换次测量顺序可能就翻转了。
   → **方法论:差 20% 以内、且没有机理支撑的差异,不写进结论。**

3. **`tcp` 慢 22 倍,但它是唯一能跨机的**。回环 TCP 要付:**完整的 TCP 状态机 +
   校验和 + sk_buff 分配 + 拥塞控制记账**。本机通信没有人该用 TCP。
   → 你 9000 网关用 TCP 是对的——因为**上位机在另一台电脑上**,没有别的选择。

### 2.2 吞吐(单向灌,三种载荷)

> 口径:一次性灌完,records/s 是消息条数/秒(不是字节/秒,注意换算);
> 目标每档约搬 256 MB,最少 200 条。

| 机制 | 248 B | 4096 B | 921600 B (=720p 灰度整帧) |
|---|---:|---:|---:|
| **shm_spin** | **9,482,608** | **2,718,252** | **8,191** |
| shm_sem | 2,719,465 | 2,509,651 | 7,966 |
| pipe | 2,065,361 | 703,071 | 2,978 |
| fifo | 2,063,887 | 747,682 | 2,168 |
| sysv_shm | 1,319,535 | 933,976 | 7,798 |
| unix_stream | 1,134,115 | 653,911 | 8,359 |
| unix_dgram | 1,136,630 | 590,857 | ❌ 超报文上限 |
| tcp | 308,964 | 262,357 | 6,694 |

**这张表最重要的不是"谁第一",是两个拐点:**

1. **小消息(248 B):`shm_spin` 领先 3.5~30 倍**,因为省掉了每条消息的系统调用。
   到 4096 B 就只剩 1.08 倍了——**数据量一大,拷贝成本盖过系统调用成本**。

2. **大帧(921600 B)全部塌到同一水平(7000~8000 条/秒 ≈ 6.5 GB/s)**,
   此时**没有任何机制有优势**,因为瓶颈变成**内存带宽**了。
   → 这就是为什么你项目里"MJPEG 帧走零拷贝"能省的是**延迟**,不是**吞吐上限**。
   想省带宽只能减少拷贝次数,不是换个 IPC。

3. **`unix_dgram` 在 921600 B 直接失败**(`payload_too_large`)。这**不是 bug**:
   AF_UNIX 数据报有单条报文上限(受 `SO_SNDBUF`/内核 `sk_buff` 限制)。
   → **有边界消息的机制,天然受"单条上限"约束**;流式(stream/pipe)没有这个问题
   但需要你自己切包——正是你第 3 周做「4 字节定长头」的原因。

## 3. 真正决定架构的:等待策略的 CPU 代价

这一节是全套实验里**最该带进面试的**。

### 3.1 为什么必须单独测

上面 `shm_spin` 全场第一,看起来"选它就对了"。**但它是靠 CPU 空转换来的**。
你的真实链路是:

```
摄像头 30 fps(每 33ms 出一帧)  →  [队列]  →  NPU 每帧 20ms
```

生产者和消费者速度不匹配,缓冲区迟早填满,**生产者一定要等**。
这时"怎么等"的代价差两个数量级。

### 3.2 实验设计(这里有个坑,值得单独看)

`spin_cost.cpp` 模拟:生产者灌 100 帧 × 248B,消费者每帧"推理" 20ms,环形缓冲 16 帧。

**⚠ 第一版设计错了,公开发布前必须知道这个坑:**

环形缓冲区如果只有 `head`(生产者写)和 `tail`(消费者读)两个计数器,
生产者的"有空位"判据就变成 `head - tail < cap`。
而消费者**一读到数据就推进 tail**,于是"空位"在消费者刚开始干活时就还回去了——
生产者几乎不用等。但 `sem` 版的 `sem_post` 是在**处理完之后**才调的,
两边语义不同,**对照组直接失效**。

实测症状很直白:`spin` 的 wall 反而是 `sem` 的 2.9 倍(1150ms vs 400ms),
自旋只会更快不会更慢 → **数据自相矛盾就说明设计错了,别急着归因**。

修法:用**三个计数器** `head` / `tclaim` / `tdone`,
生产者看 `tdone`(处理完才推进),两边语义对齐。

### 3.3 实测结果

> 口径:`taskset -c 6,7`;生产者 `producer_cpu_ms` = 生产者进程实际占用 CPU 时间;
> `cpu_share_pct` = CPU 时间 ÷ 墙钟时间,100% 意味着一刻不停地在烧。

**(A) 真实 NPU 节奏:消费者 20ms/帧,缓冲 16 帧**

| 策略 | 生产者 CPU | 墙钟 | 占比 | 每帧 |
|---|---:|---:|---:|---:|
| **sem** | **0.27 ms** | 1360.2 ms | **0.0%** | 13.60 ms |
| **adaptive** | **0.44 ms** | 1360.2 ms | **0.0%** | 13.60 ms |
| spin | 1680.10 ms | 1680.1 ms | **100.0%** | 16.80 ms |
| yield | 1680.10 ms | 1680.1 ms | **100.0%** | 16.80 ms |

**(B) 快消费者:2ms/帧,缓冲 16 帧**

| 策略 | 生产者 CPU | 墙钟 | 占比 |
|---|---:|---:|---:|
| sem | 0.60 ms | 336.4 ms | 0.2% |
| adaptive | 0.99 ms | 336.4 ms | 0.3% |
| spin | 368.09 ms | 368.1 ms | 100.0% |
| yield | 368.08 ms | 368.1 ms | 100.0% |

**(C) 缓冲够大,生产者几乎不用等(20ms/帧,缓冲 256 帧)** ← 决定性对照

| 策略 | 生产者 CPU | 占比 |
|---|---:|---:|
| sem | 0.04 ms | — |
| spin | 0.04 ms | — |
| yield | 0.03 ms | — |
| adaptive | 0.03 ms | — |

### 3.4 三条结论(面试直接讲这个)

**① (C) 组四者完全没差别 → 等待策略只在"生产者需要等"时才有意义。**
缓冲够大 = 生产者永远不等 = 策略无关。
这也是**工程上最简单有效的优化:先把队列做够深**,而不是纠结用哪种等待。

**② `spin` 全场赢延迟,但要付 100% CPU。在你的场景里这是不可接受的。**
实测:自旋时生产者把一整颗核烧到底(1680ms CPU / 1680ms 墙钟)。
而你的板子上那颗核还有别的事要干(预处理、CSC、后处理、画框)。
→ **`shm_spin` 只适合"等待极短(微秒级)且 CPU 富余"的场景**,
比如同一优先级下两个线程的紧密配合。

**③ `adaptive` 是工程最优解**:实测 CPU 0.44ms(与 sem 同量级),
但短等待时它走自旋、省掉系统调用。
这正是**真实系统里 `std::mutex` 的 `adaptive spinning`、Linux futex 的设计思路**:
先自旋一小会儿,不行就睡。——**能自己测出这个结论,比背下来强得多。**

**④ `yield` 没有救回来**:`sched_yield()` 在抢占式调度下
只是"我现在可以让"，有活干的进程会立刻又拿到 CPU，实测与纯自旋无差(368ms vs 368ms)。
→ **`sched_yield` 不是省 CPU 的手段**，这是个很常见的错误认知。

## 4. 回看数据结构:环形缓冲区为什么长这样

`spin_cost.cpp` 里那块共享内存的布局(`HDR = 256`):

```
+0    uint64 slot_bytes     每条消息多大
+8    uint64 cap            容量(多少条)
+16   uint64 consumer_cpu   回传用
+64   uint64 head           只由生产者写
+128  uint64 tclaim         只由消费者写(寻址)
+192  uint64 tdone          只由消费者写(处理完)← 生产者看这个
+256  数据区 cap × slot_bytes
```

四条设计要点,**每一条都能被追问**:

1. **为什么计数器单调递增,不取模?**
   取模就丢了"当前有多少条"的信息,得额外算;而且 `head - tail` 在
   `uint64` 上溢出是良性的(模运算自洽),取模反而要处理回绕边界。
   地址 = `data + (idx % cap) * slot`,`%` 只在寻址时用。

2. **为什么 `head` 和 `tdone` 要放在不同的 cache line?**
   64 字节对齐 + 中间留空,是因为 ARM 的 cache line 是 64 B。
   如果 `head` 和 `tail` 在同一条 cache line 上,**生产者写 head 会让消费者
   的 cache line 失效**(false sharing),两边互相踢对方缓存,吞吐掉一个数量级。
   → 这就是为什么布局里故意有 64 字节的间隔。

3. **为什么要 `__ATOMIC_RELEASE` / `__ATOMIC_ACQUIRE`?**
   `memcpy` 写数据 和 更新 `head` 是两条指令。如果编译器/CPU 把 `head`
   的更新排到 `memcpy` 之前,消费者会看到"有新数据"却读到**旧内容**。
   Release 保证"之前的写先落地",Acquire 保证"之后的读能看到"。
   → **`volatile` 做不到这件事**,它只防编译器重排,不防 CPU 重排。

4. **为什么 `head` 只由生产者写、`tdone` 只由消费者写?**
   这叫 **SPSC(Single Producer Single Consumer)**,两个写者各写各的,
   **完全不需要锁**。一旦变成多生产者,就得用 CAS/互斥保护,复杂度立刻上一个台阶。

## 6. 边界与局限(引用时一起说)

- ✅ **实测在真板子上**,`taskset` 绑定大核,后台服务已停,负载 < 0.5
- ⚠️ **RTT 是"一来一回"**,不要跟单程延迟混着讲
- ⚠️ **吞吐表单位是"条/秒"**,不是"字节/秒";换算是 `条/秒 × 载荷字节`
- ⚠️ **`unix_stream` 比 `pipe` 快这点不要当结论**——差 1.2us,无机理支撑
- ⚠️ **TCP 回环不代表跨机性能**。跨机要加上真实网卡 + 交换机 + 对端协议栈
- ⚠️ **没测**:消息队列(mq_*)、`socketpair` 的 SOCK_SEQPACKET、memfd、
  DMA-BUF(那需要驱动配合,不是纯 userspace IPC)
- ⚠️ 板上 `loadavg` 长期在 1.0 左右无法降下来(有一个 `tx_5v_power_present`
  的 D 状态内核线程),所以**绝对数值偏保守**,但**同一轮内的相对比较有效**

## 7. 和你现有项目的连接点

- 你的 9000 网关用 **TCP** 是对的——上位机在另一台机器上,跨机只能选它。
  实测印证:本机场景 TCP 是最差选择(比 shm 慢 22 倍),但**跨机场景它是唯一可行**。
- 你的巡检守护(5s 周期)和 Agent 之间的 `llm_pending.jsonl` 是**文件**。
  这本质是"用文件系统当消息队列"。**可以改成 `mq_open` 或 shm 环形队列**,
  换来:① 不用轮询文件 ② 有边界消息 ③ 不会读到写了一半的 JSON。
  这是一个**现成的、真实的、可量化的改造题目**。
- `patrol_state.json` 用 `write tmp + rename` 做原子更新——这是**文件级**的原子性。
  换成共享内存时,这个原子性**不会自动带过来**,得自己用内存序保证。

# MPP 硬件 JPEG 编码器 —— 实测证据与边界分析

> 板卡：EVM3588-B（SOM3588-B，RK3588，8GB）
> 系统：Debian 11 / 内核 Linux 5.10.110 aarch64 / g++ 10.2.1 / OpenCV 4.5.1
> MPP：`/root/edgevision/third_party/mpp/lib/librockchip_mpp.so.1`（**源码编译版**，非系统自带）
> 测量日期：2026-10-25　测量人：mpp-encoder

---

## 0. 一句话结论

**本板 MPP 硬件 JPEG 编码能跑通、画面正确、确实走硬件（/proc/interrupts 铁证），但单帧延迟比 OpenCV 软编（libjpeg-turbo，A76 NEON）更慢 13%~20%（1280x720 稳定在 1.15~1.16×），吞吐也是软编赢（4 核并行慢 1.9×）。因此「用硬编替换 `cv::imencode` 省 7.2ms」这个优化方向在本板不成立 —— 实测是所有 6 档分辨率、单路/4 路并行、BGR 输入/纯转码四种组合下硬编全部更慢，没有任何一个场景能赢。**

硬编唯一真实、可量化的收益是 **CPU 占用从 99.7% 降到 10.7%**（1280x720 每帧 CPU 0.82ms vs 6.63ms）。这个收益在「多路并发、CPU 已经打满」的场景有价值，在「单路 30fps 实时预览」的场景没有价值。

一句话归因（面试可直接讲）：**JPEG 编码是 DCT + 量化 + Huffman 熵编码，libjpeg-turbo 的 NEON SIMD 已经把这条路优化到极致；Rockchip jpege 硬件的定位是「相机抓拍时别占 CPU」，不是「比 CPU 算得快」。而硬编每次还要多付 ~0.35ms 的 ioctl + 中断往返固定开销。**

### 2.3 ⚠️ 一个必须讲清楚的坑：MPP 编码不做 limited→full range 展开

这是本项目踩到的**最反直觉的一个坑**，也是「硬编 PSNR 一开始只有 35dB」的根因。

**现象**：硬编输出的 JPEG 解回来整体偏暗，BGR-PSNR 只有 35.4dB（软编 47.0dB）。对 Y 做线性拟合：

```
硬编:  Y_dec = 0.8604 * Y_src + 15.86   (corr = 0.99946, Y-PSNR = 32.11 dB)
软编:  Y_dec = 0.9996 * Y_src + 0.02    (corr = 0.99953, Y-PSNR = 45.71 dB)
```

0.8604 ≈ 219/255，+15.86 ≈ +16 —— 看起来像「full→limited 压缩」，第一反应是 MPP 把 Y 压到了 16~235。

**实际根因（方向完全相反）**：
1. `cv::cvtColor(BGR2YUV_I420)` 输出的是 **limited-range YUV**（Y 在 16~235）。
2. MPP 把输入 YUV **原样**写进 JPEG（实测 `Y_JPEG = 1.0012 * Y_in - 0.15`，斜率 1.0 证明它不做任何 range 变换）。
3. JPEG 规范要求 **full-range**（Y 0~255）。
4. 所以是**输入侧口径错了**，不是 MPP 压了 Y。

**隔离测试（排除 BGR 往返干扰）**：用 `cv::imdecode(out, IMREAD_GRAYSCALE)` 直接取 JPEG 自身 Y 平面
- 硬编未补偿：`Y_JPEG = 1.0012*Y_src - 0.15`，Y-PSNR = **45.34 dB**
- 软编同口径：`Y_JPEG = 1.1638*Y_src - 18.64`，Y-PSNR = **30.69 dB**

软编斜率 1.1638 ≈ 255/219 = 1.1644、截距 −18.64 ≈ −16×1.1644 → **是 OpenCV 的 `imencode` 内部替用户做了 limited→full 展开**。硬编不做，所以必须用户自己在输入侧补。

**修复方法（已实装）**：构造 NV12 时预展开
```cpp
Y    : out = (in - 16) * 255 / 219
CbCr : out = (in - 128) * 255 / 224 + 128
```
修复效果：BGR-PSNR **35.39dB → 46.03dB**（软编 47.02dB），基本追平。

**其他被验证无效的路子**：
- `prep:range`（UNSPECIFIED/MPEG/JPEG）× `mpp_frame_set_color_range`（不设/UNSPECIFIED/MPEG/JPEG）共 12 组组合 → **输出字节数完全相同（25872 / 50299 B），线性拟合参数逐位一致**。`mpp_enc_cfg_set_s32` 返回 0 表示「参数收下了」，但**编码器根本不看这两个参数**。这是 MPP 的一个「配置键存在但实现忽略」的坑。
- `prep:format` 传 `MPP_FMT_RGB888` / `MPP_FMT_BGR888` 让 MPP 自己做 CSC → `encode_put_frame` 返回 0，但**输出的 JPEG `cv::imdecode` 返回空**（不可解码）。**此路不通，只能喂 NV12。**
- `base:enable_vproc=0` 关闭视频处理单元 → 输出与基线**逐位相同**，无任何效果。

## 3. 硬件路径铁证（这是「确实走硬件」的硬证据）

### 3.1 /proc/interrupts 中断计数

RK3588 的 JPEG 相关中断源（全量枚举）：

```
40: fdb90000.jpegd          ← JPEG 解码（1 个）
42: fdba0000.jpege-core     ← JPEG 编码（第 1 核）
44: fdba4000.jpege-core     ← JPEG 编码（第 2 核）
46: fdba8000.jpege-core     ← JPEG 编码（第 3 核）
48: fdbac000.jpege-core     ← JPEG 编码（第 4 核）
51: fdbd0000.rkvenc-core    ← H264/H265 编码
54: fdbe0000.rkvenc-core
57: fdc38100.rkvdec-core    ← H264/H265 解码
59: fdc48100.rkvdec-core
```

**串行编码 500 帧前后对照**：

| 中断源 | 编码前 | 编码后 | 增量 | 每帧次数 |
|---|---:|---:|---:|---:|
| `fdba0000.jpege-core` | 770 | 1270 | **+500** | **1.00** |
| `40: fdb90000.jpegd` | — | — | 0 | 0 |
| `fdbd0000/fdbe0000.rkvenc-core` | — | — | 0 | 0 |
| `fdc38100/fdc48100.rkvdec-core` | — | — | 0 | 0 |

→ **每编码一帧，JPEG 编码核产生恰好 1 次中断，其余所有硬件单元零变化。这是「确实在硬件上做」的铁证，不是软件库自己算的。**

### 3.2 单 context 只用 1 个核，多 context 能均分到 4 核

| 线程数 | 聚合吞吐 | CPU | `fdba0000` | `fdba4000` | `fdba8000` | `fdbac000` |
|---|---:|---:|---:|---:|---:|---:|
| NT=1 | 272.1 FPS | 10.3% | +200 (1.00 次/帧) | 0 | 0 | 0 |
| NT=2 | 410.3 FPS | 20.3% | +100 (0.50 次/帧) | +100 (0.50) | 0 | 0 |
| NT=3 | 428.3 FPS | 27.3% | +66 (0.33) | +66 (0.33) | +66 (0.33) | 0 |
| NT=4 | 664.5 FPS | 50.8% | +50 (0.25) | +50 (0.25) | +50 (0.25) | +50 (0.25) |

→ **中断完美均分，多 context 确实能吃满 4 个 jpege 核。** 但注意 NT=4 的 **单流延迟反而从 3.68ms 涨到 6.02ms**（硬件队列排队），是典型的「吞吐换延迟」。

### 3.3 CPU 占用对照（`getrusage(RUSAGE_SELF)` + wall clock）

| 方案 | wall | cpu | CPU 占用 |
|---|---:|---:|---:|
| MPP 硬编 500 帧 | 1665.8 ms | 123.3 ms | **7.4%** |
| 软编对照 500 帧 | ~1500 ms | ~1500 ms | **100.0%** |

每帧 wall 3.332ms，但 **cpu 只有 0.247ms** → 「进程在等硬件，不是在算」。这是硬编和软编的**本质区别**，也是它唯一的真实价值。

## 4. 4 核并行吞吐 vs 软编多线程（决定性对照）

**3b 稳态版**（线程只创建一次，测峰值吞吐口径）：

| 线程数 | MPP 硬编聚合 | 硬编 CPU | 软编聚合 | 软编 CPU | 谁赢 |
|---|---:|---:|---:|---:|---:|
| NT=1 | 3.694 ms/帧 (270.7 FPS) | 14.7% | 3.077 ms/帧 (325.0 FPS) | 99.7% | 软编 1.20× |
| NT=2 | 2.424 ms/帧 (412.5 FPS) | 22.0% | 1.583 ms/帧 (631.5 FPS) | 198.2% | 软编 1.53× |
| NT=3 | 1.865 ms/帧 (536.2 FPS) | 20.5% | — | — | — |
| **NT=4** | **1.573 ms/帧 (635.8 FPS)** | **26.4%** | **0.838 ms/帧 (1192.9 FPS)** | **381.8%** | **软编 1.88×** |

> 上表为最终复跑值；此前一轮为 NT4 硬编 1.628 ms/帧(614 FPS)/32.4% CPU，软编 0.825 ms/帧(1213 FPS)/376% CPU，比值 1.98×。两轮一致：**NT=4 时软编快约 1.9×。**

**这是本次实验最重要的否证之一**：一开始的假设是「单 context 慢是因为串行阻塞，堆 4 个 context 就能靠 4 个硬件核把吞吐翻上去」。实测**翻上去了（251→614 FPS，2.44×），但软编用 4 个 CPU 线程翻得更多（325→1213 FPS，3.73×）** —— 因为 RK3588 有 4×A76 + 4×A55 共 8 个核，软编能线性吃到 4 个 A76，而硬编只有 4 个 jpege 核且单核吞吐本来就低。

代价差别才是真差别：**达到 614 FPS，硬编只花 32% CPU，软编要花 376% CPU。**

## 5. 延迟模型：硬编慢在哪（可量化的机制）

### 5.1 分辨率扫描（区分「每像素算力」与「固定往返开销」）

| 分辨率 | 硬编 ms/帧 | 硬编 FPS | 软编 ms/帧 | 硬编 ms/MPix | 软编 ms/MPix |
|---|---:|---:|---:|---:|---:|
| 64x64 | 0.369 | 2711.3 | 0.046 | 90.05 | 11.12 |
| 128x128 | 0.559 | 1787.4 | 0.368 | 34.15 | 22.44 |
| 256x256 | 0.844 | 1185.3 | 0.606 | 12.87 | 9.25 |
| 320x320 | 1.080 | 926.1 | 0.784 | 10.55 | 7.65 |
| 640x640 | 4.003 | 249.8 | 3.002 | 9.77 | 7.33 |
| 960x540 | 4.405 | 227.0 | 3.788 | 8.50 | 7.31 |

> 64x64 软编 0.046ms 是异常小值（缓存热度高、此轮首测受影响），前一轮同档位是 0.143ms。**该行不参与模型拟合**，拟合用的是 128x128 起的 5 档。

**拟合出延迟模型**：

```
硬编 t(ms) ≈ 0.35（固定开销：ioctl + 中断往返）+ 7.0e-6 × 像素数
软编 t(ms) ≈ 0.00（无固定开销）            + 7.5e-6 × 像素数
```

三点结论：
1. **硬编有 ~0.35ms 的固定开销**（64x64 时硬编 0.369ms，软编 0.143ms，差值 0.23ms 全是往返成本）。这就是 `encode_put_frame` 阻塞等中断的价格，小分辨率下它占绝对主导。
2. **每像素算力：硬编约 7.0e-6 ms/px vs 软编约 7.5e-6 ms/px —— 几乎完全相同**（大分辨率档位硬编 8.50 vs 软编 7.31，软编反而更低）。硬编的 JPEG 编码核每像素吞吐与 A76 跑 NEON 优化的 libjpeg-turbo **打平甚至略差**。
3. 硬编**在本板没有任何分辨率档位能赢**：它每像素算力不占优，却恒定多付 ~0.35ms。实测 6 档全部是硬编更慢，且大分辨率差距不会缩小（640x640 差 33%，960x540 差 16%）。

### 5.2 为什么 qf 对耗时几乎无影响

qf 30 / 50 / 70 / 80 / 95 → 耗时 3.46 / 3.30 / 3.13 / 3.16 / **3.08** ms（qf 越高反而略快）。

**这说明瓶颈不在 Huffman 熵编码**（若在熵编码，qf 低 = 码流长 = 耗时高，应该是单调的）。qf 只影响量化表的乘数，而不改变「整帧过一遍 DCT 管线」的固定成本。**JPEG 编码耗时主要由像素数决定，与压缩比关系很小** —— 这条对软编同样成立（软编 q80 与 q95 耗时差 <5%）。

### 5.3 流水线深度无效（重要否证）

理论假设：单 context 慢是因为「put 一帧就阻塞等它编完」，只要 `put K 帧 → get K 包` 就能把硬件延迟重叠掉。

实测（640x640，N=200）：

| 模式 | ms/帧 |
|---|---:|
| Mode A 串行 put→get（深度 1） | **3.383** |
| Mode B put2→get2 | 3.298 |
| Mode B put3→get3 | 3.188 |
| Mode B put4→get4 | 3.298 |
| Mode B put8→get8 | **3.143** |
| 软编对照 | **3.000** |

→ **流水线深度 1→8，只从 3.383 降到 3.143（−7%），仍然输给软编的 3.000。单 context 内部没有并行余量，硬件是「一帧一帧串行处理」的，软件侧堆队列隐藏不掉。** 要真正并行只能开多 context（见 §4），但那样又输给了软编多线程。

## 6. 端到端链路对照（回答「接进真实链路能省多少」）

### 6.1 BGR 输入的典型预览链路（1280x720，N=200）

| 链路 | 分项 | 合计 |
|---|---:|---:|
| **硬编路线**：BGR→NV12（SIMD 版）→ 硬编 | 1.75 + 7.68 | **9.43 ms** |
| **硬编路线**：BGR→NV12（库内标量版）→ 硬编 | 4.37 + 7.68 | **12.05 ms** |
| **软编路线**：`cv::imencode` 直接吃 BGR | — | **6.65 ms** |

→ **硬编端到端慢 1.42×（SIMD 转换）或 1.81×（标量转换）。**

### 6.2 BGR→NV12 转换成本（硬编方案的隐性税）

| 实现 | 1280x720 耗时 | 说明 |
|---|---:|---|
| 库内标量版 `bgr_to_nv12_full_range()` | **4.40 ms** | 逐像素查表，无 SIMD |
| OpenCV SIMD 版（`cvtColor(BGR2YUV_I420)` + LUT 展开） | **1.75 ms** | **2.51× 快** |
| 两者一致性 | max\|Δ\| = 8/255 | 可接受（量化误差范围内） |

> 当前 `mpp_jpeg_encoder.cpp` 里实装的是标量版（头文件已注明）。若要用硬编，务必换成 SIMD 版 —— 但即使换了，端到端仍然输给软编。

### 6.3 纯转码场景（唯一可能有利的场景）—— 实测也不成立

假设：如果只是「MJPG 流 → JPEG 流」转码，全程 NV12 不落地 BGR，能否绕开 CSC 赢一局？

| 路径 | 硬解 | CSC | 反向转换 | 编码 | **合计** |
|---|---:|---:|---:|---:|---:|
| **T1** 硬解 → NV12 → 硬编（纯转码，无 CSC） | 1.37 | — | — | 7.11 | **8.48 ms** |
| **T2** 硬解 → NV12 → CSC→BGR → 软编（当前 preview 做法） | 1.37 | 1.22 | — | 6.72 | **8.91 ms** |
| **T3** 硬解 → CSC→BGR → 画框 → BGR→NV12 → 硬编 | 1.37 | 2.12 | 2.31 | 7.00 | **12.33 ms** |
| **T0** 纯 OpenCV 软解 + 软编（完全不用 MPP） | 7.01 | — | — | 6.72 | **13.74 ms** |

**关键归因**：
- T1（8.48）确实比 T2（8.91）快 **4.8%** —— 但**这点收益 100% 来自「省掉 CSC 那 1.22ms」，不是硬编比软编快**。硬编那一步（7.11ms）比软编（6.72ms）本身还慢 5.8%。
- T3 是画框场景（真实预览必须画框），**12.33ms 最差** —— 因为多了反向 BGR→NV12（2.31ms）。**这是硬编在真实预览链路上的死路。**
- T0 说明：即使完全不用 MPP 硬解，纯软解+软编 13.74ms 也能跑到 72.8 FPS —— 而硬解+软编的 T2 是 112.2 FPS。**硬解（省 5.6ms）才是这个项目里 MPP 真正创造价值的地方，编码不是。**

### 7.3 qf 标定结果（反直觉，值得记录）

用 real_000.jpg（640x640），扫 qf 50~95：

| qf | 输出字节 | Y-PSNR | 相对软编 q80 |
|---:|---:|---:|---:|
| 50 | 16673 | 30.34 dB | 太差 |
| 60 | ~19000 | ~30.5 dB | 太差 |
| 70 | ~22000 | ~30.7 dB | 偏小 |
| 75 | ~24000 | ~30.8 dB | 偏小 |
| **80** | **25872** | **~30.8 dB** | **码率最接近（0.505 vs 0.525 bpp）** |
| 85 | ~33000 | ~30.85 dB | 偏大 |
| 90 | ~41000 | ~30.86 dB | 偏大 |
| 95 | 50299 | 30.87 dB | 太大 |

**两个反直觉点**：
1. **qf 对 PSNR 几乎无影响（30.34→30.87，只差 0.5dB），但码率翻了 3 倍。** 这不是编码器坏了 —— 是因为**这组数据用的是「未做 full-range 展开」的老版本**，PSNR 被 range 口径错误压死在 30.8dB 左右的天花板上（误差主导项是 range 不匹配，不是量化误差）。展开修好后 PSNR 立刻到 44.4dB（见 §2.1）。**这个教训说明：PSNR 异常时先查口径，别急着调参数。**
2. **qf 与 OpenCV `IMWRITE_JPEG_QUALITY` 经验上近似 1:1**：qf80 输出 27557B vs 软编 q80 输出 26888B = 1.025×，码率基本对齐。所以对接时可以直接把 `quality=80` 映射成 `q_factor=80`，不需要换算表。

## 8. 最终结论：值不值得用

### ❌ 不值得用在「单路实时预览链路」（本项目的实际场景）

理由（三条，任一独立成立）：
1. **延迟输 13%~20%**：1280x720 硬编 7.69~7.72ms vs 软编 6.65~6.67ms，2 轮一致；p99 更是 11.09~11.46 vs 6.72~6.74（**输 65%~71%**）。
2. **端到端输 42%~81%**：硬编还要额外付 BGR→NV12 转换税 1.75~4.37ms，真实预览链路是 9.43~12.05ms vs 6.65ms。
3. **吞吐也输**：4 核并行硬编 635.8 FPS vs 4 线程软编 1192.9 FPS（软编快 1.88×）。RK3588 有 4×A76 + 4×A55，软编能线性吃到 4 个大核。

### ✅ 值得用在「CPU 已经是瓶颈」的场景（如果将来有）

- 硬编 CPU 占用 **11.7% vs 99.7%**（4 核并行下 26.4% vs 381.8%）。
- 如果将来要做 **8 路 MJPG 转码/录像**，CPU 打满时硬编的 CPU 优势会变成决定性优势 —— 那时候「慢 15% 但省 90% CPU」是好交易。
- 但**本项目的场景是单路 30fps 预览**，CPU 不是瓶颈（NPU 才是），所以这个优势用不上。

### 📌 对项目路线的建议

**「MPP 硬编 JPEG 省 7.2ms」这个优化项应当从路线图里划掉。** 当前 preview 链路真正的瓶颈排序（基于 §6.3 数据）：

1. **CSC NV12→BGR**：`w4_edgevision_preview_real.cpp` 里 CPU 读 uncached DRM 内存，实测 51~65ms（**这是最大头**）→ 正解是 **RGA 硬件转换**（实测 2.03ms）或修 CMake 加 `-O3 -DNDEBUG`
2. **软编 JPEG 6.65ms**：已经是最优（libjpeg-turbo NEON），换硬编反而更慢 → **放弃优化，接受它**
3. **硬解 1.37ms**：已经是硬解，无优化空间

> 唯一值得继续的方向是 **RGA CSC**，不是 JPEG 编码。这条结论已被本次实验用「否认自己任务目标」的数据支撑。

## 9. 复现方法

```bash
# 板上
cd /root/edgevision/deploy/cpp/bench
bash _run_bench_jpeg_encoder.sh        # 完整 5 节基准（约 6~8 分钟）

# 只跑转码对照

```

输出：`/tmp/bench_jpeg_encoder.log`、样张 `/tmp/bench_jpeg_encoder_hard.jpg`

**测量口径说明（引用数字时必须一起说）**：
- 均在本板实测，`w4_edgevision_gateway` 服务常驻占 CPU ~55%（任务约束，不停止），load average 2.0~2.5。硬编数字比空载时差 5%~10%，**软编受影响更小，所以真实空载下软编优势更大**。
- PSNR 一律「编码后 `cv::imdecode` 解回 vs 原图」，Y 通道用 `IMREAD_GRAYSCALE` 取 JPEG 自身 Y 平面。
- 时间用 `std::chrono::steady_clock`，每项 5~20 帧预热后 N=200 计时，pct 用 `ceil(p/100*N)-1` 索引（最近秩法）。
- 硬编字节数略大于软编（1.025×）是正常现象，两者码率已对齐，非质量差异来源。

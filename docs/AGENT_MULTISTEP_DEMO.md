# Agent 多步演示闭环 —— 设计与验收

> 目标：一条自然语言指令跑完「**巡检 → 研判 → 执行 → 汇报**」，
> 且每一步都有**可复现的真实证据**，不靠嘴讲。
>
> 相关代码：`lab/agent_multistep_demo.py`（编排器）、
> `lab/edgevision_patrol_daemon.cpp`（快层守护）、`lab/rkllm_embodied_agent.cpp`（慢层 Agent）
> 实测报告：`_test_results/demo_<时间戳>/demo_report.md`

---

## 1. 为什么拆成两幕：快慢双系统

守护和 Agent 都要控**同一个物理 LED**（`/sys/class/leds/work/`）。
两个进程同时写会互相覆盖——谁也说不清最后亮着的灯是谁点亮的。
用户拍板的方案是：**守护优先，Agent 只读不写灯**。

于是演示天然分成两幕，这恰好也是系统架构的真实分层：

| | 第一幕 · 快层守护 | 第二幕 · 慢层 Agent |
|---|---|---|
| 触发 | 每 5s 自主巡检（不等人问） | 人下发一句自然语言 |
| 实现 | 纯 C++17，零 RKLLM 依赖 | RKLLM + Qwen3.5-2B |
| NPU 占用 | **0** | 推理时占用 |
| 反应时延 | 秒级（检测到即触发） | 秒级~十几秒（含多轮推理） |
| 职责 | 检测异常 + 立即执行（闪灯） | 解释、研判、汇报 |
| LED | **唯一写者** | 只读（`--no-led`） |
| 解耦方式 | 写 `llm_pending.jsonl` | 读该文件 |

两幕串起来才是完整闭环。这也是为什么**不让小模型每 5 秒跑一次**——
NPU 被视觉推理占满、时延高、且 LLM 本身可能出错。详见
`docs/PATROL_DAEMON_DESIGN.md` 第 5 节。

## 2. 第一幕：守护自主闭环（真实告警 + 真实闪灯）

### 2.1 怎么让告警"真发生"而不是假装

自然触发条件要么板温 >75°C（会把板子烤坏），要么真人连续进画面（不可控）。
所以守护加了**阈值命令行参数**，验收时临时把过热阈值压到 20°C：

```bash
# 板温实测 30~45°C，阈值压到 20°C 必然越限 -> 必然触发 THERMAL_ALERT
./edgevision_patrol_daemon --interval 2 --temp-enter 20 --temp-exit 18
```

这条路径走的是**和真实过热完全相同的代码分支**：状态机翻转 → 写事件日志 →
执行 alarm 闪灯。唯一被替换的是输入数据的来源（真实高温 → 人为压低阈值），
不是伪造结果。演示完参数不写死，默认仍是 75/70°C。

### 2.2 关键判据：用占空比，不是"有没有在闪"

这是本轮最容易做错、也最容易被面试官追问的地方。

**一个反直觉的事实**：`heartbeat` 触发器**本身就在闪**。实测板上
heartbeat 运行时连续采样 brightness，3 秒内 300 次采样中有约 20% 是非零。
也就是说——

> ❌ 错误判据：「看到 brightness 在 0 和非 0 之间反复跳变」→ 证明 alarm 生效
> 这个判据**完全失效**，因为 heartbeat 就长这样，告警灯不生效也一样能"通过"。

正确判据是**占空比（亮灯时间占比）**：

| 模式 | 波形特征 | 占空比 |
|---|---|---|
| `heartbeat` | 双脉冲 + 长暗期 | **≈20%**（实测 19.3% / 20.7%） |
| `alarm`（用户态爆闪） | 100ms 亮 / 100ms 灭 对称方波 | **≈50%** |

所以验收逻辑是：**先测 heartbeat 基线，再测告警期占空比，看是否显著抬升**
（门槛：≥35% 且相对基线抬升 ≥15 个百分点）。

### 2.3 第二个坑：采样间隔不能取 0.1s

爆闪是 100ms 亮 + 100ms 灭。如果采样间隔也是 0.1s，采样周期与方波周期
**同频**，读到的相位会被锁死——可能连续几十次全读到 255 或全是 0，
把"在闪"误判成"常亮/常灭"。

这叫**混叠（aliasing）**。解法：采样间隔远小于方波半周期且避开整数倍关系，
本脚本取 **0.02s**。

### 2.4 为什么 alarm 必须改成用户态爆闪

板上内核 `5.10.110` **没有编译 `CONFIG_LEDS_TRIGGER_TIMER`**，
`/sys/class/leds/work/trigger` 的可选列表里**根本没有 `timer`**：

```
none rfkill-any ... mmc0 [heartbeat] mmc1 ...
```

`echo timer > trigger` 返回 `EINVAL`。原守护代码写的就是这一句，并且
**没检查返回值**——于是 LED 一直是 heartbeat，但程序以为自己"已设置 alarm"。
这就是典型的**假成功**。

解法：在用户态 fork 一个子进程，用 `/bin/sh` 循环交替写 brightness 造方波。
**exec 前必须把 0/1/2 重定向到 `/dev/null`**，否则子进程继承父进程的管道写端，
这个永不退出的循环会让调用方等 EOF 等到超时（详见 `docs/TROUBLESHOOTING.md`
第 20、22 条）。

## 3. 第二幕：Agent 多步研判汇报

### 3.1 用什么指令

```
请做一次完整巡检并汇报：
① 查开发板整体硬件状态（温度、NPU负载、可用内存）；
② 读巡检守护最近报过的告警事件；
③ 结合这两项数据判断开发板当前是否处于异常状态，
   说明板载指示灯现在应该处于什么状态，并给我处置建议。
```

刻意用 ①②③ 把任务拆成显式子步骤：既压住模型跳步的倾向，
又天然要求它**连续调用多个不同工具**，从而真正跑出"多步"而不是"一问一答"。

### 3.2 判定"真多步"的门槛

```
至少调用 2 个不同的工具
```

单工具调用 = 一问一答，不算闭环。本幕要求 `get_system_health`（或
`get_vision_telemetry`）与 `get_patrol_events` 都到位，才判多步成立。

### 3.3 Agent 为什么带 `--no-led`

守护正在控灯，Agent 必须只读，否则会抢灯。带 `--no-led` 后
`control_led` 不碰硬件，直接返回：

```json
[{"success": false, "error": "led_readonly_mode",
  "note": "patrol daemon owns LED; agent is read-only",
  "hint": "do NOT retry control_led with another mode; the gate rejects every mode in read-only mode"}]
```

这既是架构约束，本身也是一个可演示的**权限边界**——"能感知、能研判，
但不能乱动别人正在管的执行器"。

### 3.4 首次演示暴露的两个缺陷（都已修）

**缺陷一：把正在爆闪的报警灯读成「熄灭」，模型据此编造了错误因果。**

首轮两幕演示判 PASS（工具调用链、多步判定全部满足），但翻开 trace 逐条
看 Observation 才发现问题——守护正在爆闪（实测占空比 49.7%），
Agent 拿到的却是：

```json
{"led_name":"work","current_mode":"off","brightness":0,"description":"熄灭关闭"}
```

于是它在汇报里写了「LED 始终熄灭是异常的……**这导致硬件层面的过热保护逻辑被抑制**」。
**模型没有幻觉，它忠实推理了错误输入**：根因在 `get_led_current_mode()`
只读一次 `trigger`、见 `none` 就读一次 `brightness`，撞上爆闪的灭相就判 `off`。

修法两层（见 TROUBLESHOOTING 第 23 条）：
1. 优先判「谁在闪」：`led_user_blink_alive()` 查爆闪 pid 是否存活，
   并用 `/proc/<pid>/cmdline` 含 `brightness` 排除僵尸与 pid 复用 → 直接返回 `alarm_blink`；
2. 兜底多点采样：12 次 × 15ms（覆盖 1.8 个爆闪周期），出现亮暗交替即判爆闪。

修复后同一场景返回
`{"current_mode":"alarm_blink","description":"100ms急闪报警(用户态爆闪运行中)"}`。

**缺陷二：`--no-led` 拒绝后，模型把四种模式挨个试了一遍。**

首轮 trace 的工具链是
`get_system_health → get_patrol_events → get_led_status → control_led ×4`
（heartbeat / on / alarm / off 全试），每次都被 `led_readonly_mode` 拒绝，
白跑约 4 轮 NPU 推理并污染上下文。修法两条：
1. `--no-led` 下追加最高优先级 sys_prompt：明说控制权在守护、不要去调 `control_led`；
2. 拒绝返回值加 `hint` 字段，明确告知「换别的 mode 也一样会被拒，不要重试」。

实测 `control_led` 调用次数 **4 次 → 1 次**，且拒绝后立即转为如实汇报。

### 3.5 第三个缺陷：模型不知道「20°C 是演示阈值」，把正常温度判成过热

LED 误判修好之后，汇报里又出现一类新问题——**数据都对，结论错**：

> 「SOC 温度长期偏高（>40°C），且系统多次触发过温报警。这表明散热系统效率低下或
> 热管理策略存在问题，**存在硬件降频甚至永久损坏的风险**。」

RK3588 的 SOC 正常工作区间是 30~65°C，49°C 完全正常；20°C 是老陈为了验收人为压低的
**评测阈值**。模型拿到了真数据（49°C、事件里写着 "超过 20.00C 阈值"），但缺少
「这台机器多少度才算热」的常识，只能按告警是否存在倒推——于是把演示阈值当成了真实红线。

同一份汇报里还有一句：

> 「若系统内部逻辑为 `0=off`, `1=heartbeat`, `2=alarm`, `3=on`（**推测**）……」

这是模型在**臆测工具的内部实现**。它既没有依据，也容易在面试/演示时被追问翻车。

修法是把**领域常识**写进 sys_prompt（这是 Agent 工程里最容易漏、也最见功力的一环：
不是让模型更聪明，而是补上它缺的那块世界知识）：

1. 补温度常识：「SOC 正常工作温度 30~65°C，超过 75°C 才算过热告警，85°C 以上才需要
   担心降频/损坏。若巡检事件的温度阈值明显偏低（如 20°C），说明守护进程是用评测阈值
   在跑验收，**不要据此判定设备真的过热**」；
2. 禁止臆测实现：「只陈述工具真实返回的字段，不要猜测 `control_led` 的枚举值编码、
   不要猜测 sysfs 节点的数值含义。拿不准就说不确定或直接省略」。

修复后同一场景的汇报变成：

| | 修复前 | 修复后 |
|---|---|---|
| 温度研判 | 「长期偏高…存在永久损坏风险」 | 「✅ 正常 (30~65°C)」「这些是低阈值演示事件，**而非真实过热**」 |
| 枚举值臆测 | 「若内部逻辑 0=off,1=heartbeat…（推测）」 | **完全没有出现** |
| LED 状态 | 「off，熄灭关闭」（错） | 「`alarm_blink`（急闪报警）」✓ |

## 4. 判定原则（与项目总纲一致：不许用假数据冒充结果）

| 要验证的事 | 只认这个证据 | 不认 |
|---|---|---|
| 灯有没有真闪 | `/sys/class/leds/work/brightness` 实测采样占空比 | 程序自述"已设置成功" |
| 告警有没有真发生 | `patrol_events.log` 落盘内容 | 内存里的状态变量 |
| Agent 有没有真调工具 | stdout 契约行 `⚙️ [Agent 决策] 触发物理硬件工具:xxx` | 模型回答里说"我查过了" |
| Observation 是否合法 | 契约行后能解析成 JSON 数组 | 模型复述的数字 |

任一项拿不到证据就判 **FAIL**，不做"大概成功了"的模糊结论。

## 5. 怎么跑

先给脚本目标板 IP（板子内网 IP 不入库，用环境变量或 `--host` 传）：

```bash
export EDGEVISION_BOARD_HOST=<board-ip>    # Windows: set EDGEVISION_BOARD_HOST=<board-ip>
```

```bash
# 完整两幕（结束后自动停守护 + LED 回 heartbeat）
python lab/agent_multistep_demo.py

# 只跑第一幕
python lab/agent_multistep_demo.py --act1-only

# 只跑第二幕（需要板上已有守护事件可读）
python lab/agent_multistep_demo.py --act2-only

# 保持守护运行，方便人工盯着看灯
python lab/agent_multistep_demo.py --keep-daemon
```

**现场恢复是一等公民**：无论成功失败、异常还是 Ctrl-C，`finally` 里都会
停守护并把 LED 写回 heartbeat。不恢复的话板子会一直爆闪，影响后续所有实验。

产物：

```
_test_results/demo_<时间戳>/
├── demo_report.md    # 人看的报告（含检查项表格与证据）
├── trace.json        # 机读轨迹（两幕完整结构化结果）
├── led_samples.txt   # LED 采样原始序列 + 占空比统计
└── agent_raw.txt     # Agent 原始 stdout（可复查契约行）
```

## 6. 局限（面试时必须一起说）

1. **阈值是人为压低的**，验的是"检测到过热之后的处理链路"，不是"真的能测到 75°C"。
   真实高温场景只能靠长时间满负载逼近（不推荐，有硬件风险）。
2. **人形告警（PERSON_ALERT）未纳入本次演示**——需要真人连续 2 个周期出现在
   画面里，实验室可控性差。代码路径与过热告警完全同构（同一状态机、同一执行分支），
   过热告警验证通过即说明这条链路成立。
3. **占空比门槛是经验值**（≥35% 且抬升 ≥15pp）。爆闪周期若有变动，门槛需要重标。
4. **Agent 多步上限 5 步**，超长任务链仍会被截断（有告警但不保证完成）。
5. 演示依赖 `edgevision.service` 保持 active（提供 9000 端口视觉数据）；
   服务停掉时视觉相关检查会降级，但温度/事件链路不受影响。

## 7. 面试怎么讲这段（三句话版）

1. **分层**：快层用纯 C++ 守护做到零 NPU 占用的秒级异常响应，慢层用端侧大模型
   负责需要理解和解释的研判——而不是让 LLM 每 5 秒跑一次。
2. **两个真 bug**：内核没编 timer 触发器导致 LED 假成功；fork 子进程未重定向 fd
   导致管道读端永远等不到 EOF。都是"功能看起来对、其实没生效"的类型。
3. **验证方法学**：发现 heartbeat 本身就在闪之后，把判据从"有没有翻转"
   改成"占空比是否从 ~20% 抬升到 ~50%"——避免了一个会自我欺骗的假验证。
4. **补一条最有讲头的**：演示虽然判 PASS，但我翻 trace 逐条对齐 Observation 与
   物理事实，发现 Agent 汇报"灯灭了导致过热保护被抑制"——**灯其实在爆闪**。
   根因是工具单点采样撞上 100ms 爆闪的灭相，把周期性物理量误判成常量。
   **Agent 的错误结论很多时候不是模型的问题，是感知层喂了错数据**：先分层定位
   （模型幻觉？工具错？）再谈调 prompt，这个顺序很关键。

# 待办问题清单（OPEN ISSUES）

> 目的：让"还有很多问题"变成**可排序、可关闭**的清单。
> 每修一条，把状态改成 ✅ 并写上验证方式；**只增不减的抱怨没有意义，能划掉的才有意义。**

## 先分类：三类问题的处理方式完全不同

| 类别 | 特征 | 处理方式 | 能否"修完" |
| :--- | :--- | :--- | :--- |
| **A · 确定性缺陷** | 路径/权限/时序/幂等语义/编码。同样的输入必然同样的错 | 定位根因 → 改代码 → 写进 `regress.py` 锁死 | ✅ 可以修完 |
| **B · 模型行为** | 乱调工具、复读、幻觉、答非所问。同一输入可能对也可能错 | prompt 降概率 + **代码兜底**（把 B 转成 A） | ❌ 修不完，只能压 |
| **C · 设计取舍** | 7 tok/s、要不要 barge-in、要不要联网 | 写进文档当作已知边界 | ❌ 不是 bug |

**今天最重要的一条经验**：B 类问题不要靠加 prompt 解决。实测同一句 sys_prompt 约束，
2B 模型照样调 5 个工具、照样把 `rejected_by_guard` 说成"已完成"。
凡是"绝不允许"的，必须落到代码上。

## 自测工装（自己发现问题，不等用户报）

| 工具 | 作用 | 能发现什么 | 发现不了什么 |
| :--- | :--- | :--- | :--- |
| `lab/regress.py`（20 条） | 守护**已知**行为 | 改动引入的回归；用期望词 + **禁止词**双向断言 | 没想到的场景 |
| `lab/explore.py`（15 项+3 副作用） | 撞**未知**边界 | 注入、状态矛盾、越权、编造、崩溃、资源泄漏 | 需要人判断的质量问题 |
| `lab/test_e2e.sh` + 声学回路 | 语音全链路自测 | 唤醒→识别→回答→播报的端到端时延与自激 | 音质、真实环境噪声、远场 |

**这一轮的实证**：`explore.py` 跑 2 分钟、无需人参与，发现 2 个此前没人报过的问题
（LED 枚举缺失、道谢触发工具调用），都是代码级可修的 A 类。

**能力边界（要诚实）**：听觉观感（念得自不自然）、画面正确性（检测框准不准）、
真实声学环境（3 米外、有噪声）——这三类必须人或额外硬件参与，工具替不了。

## 已知边界（不是问题，别再当问题追）

| 项 | 数值 | 结论 |
| :--- | :--- | :--- |
| decode 速度 | **10 tok/s**（看板在跑时 3） | 内存带宽锁死，W8A8 已吃满；W4 只到 ~14，性价比低 |

## 怎么用这份清单

1. **每遇到一个不爽**：把**原话**记下来 → 判断 A/B/C → 填进上表。
2. **每次改完代码**：`python3 /root/regress.py`，20 条全绿才继续。
3. **加用例优先于改代码**：先让问题变成红灯，再修成绿灯——否则你不知道自己有没有修好。
4. **A 类修完就关**，B 类转成代码 guard 后关，C 类移进"已知边界"。

> 回归用例：`lab/regress.py`（板上 `/root/regress.py`），20 条，约 2 分钟出结果。
> 断言里同时有**期望词**和**禁止词**——禁止词专门守"曾经修好过的坑"（例如绝不能再出现 localhost）。

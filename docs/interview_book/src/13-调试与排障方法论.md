# 第 13 章 调试与排障方法论

> 一句话心智模型：排障不是"猜对了就改"，而是**先用测量把凶手的范围缩到一个点上，再用一个单变量实验把它钉死，最后用一组"本该不变"的对照组证明你的改动是真的**。

## 一、先建立心智模型

这一章是全书唯一一章"不按技术栈分、只按动作分"的。前面十一章讲的是"我知道什么"，这一章讲的是"我不知道的时候怎么办"。你面试时最值钱的能力不是背得出 `epoll` 的边沿触发语义，而是面试官抛一个你没见过的现象，你能**有条理地走完一条排查路径，而不是凭直觉伸手改代码**。

我在这块板子上真正破过的案子有三个：37.19 ms 一帧的"NPU 慢"、项目跑了 20 多天一个 `-O` 都没开的构建配置、还有余弦相似度 0.9965 却已经废掉的模型。三个案子的现象完全不同，但走过的路一模一样——所以下面这张图才是这一章真正要背的东西。

```
  一个现象进来（慢 / 崩了 / 假成功）
        |
  [1] 复现        固定命令、固定输入、固定口径
        |          不能稳定复现的现象，先想办法让它必现，不然后面全是玄学
        |
  [2] 缩小范围    二分：哪一层？哪个进程？哪个函数？哪个算子？
        |         板端链路：MPP 解码 -> CSC -> letterbox -> NPU -> DFL 解码 + NMS
        |         每一层都问一句"这一层的输出对不对、和参考差多少"
        |
  [3] 加观测      打印中间值 / 逐层打点 / 逐层剖析 / strace / dmesg / 中断计数
        |         观测要能算出误差，不能只是"看起来对"
        |
  [4] 提假设      用一句话写下来："我认为是 X 导致了 Y"
        |         写不出来的假设，就是还没想清楚
        |
  [5] 单变量验证  一次只动一个变量，并且同时挂一个"本该不变"的对照组
        |         对照组不动  -> 你的变化可信
        |         对照组也动  -> 先怀疑你的测量，别急着庆祝
        |
  [6] 固化        复现命令、原始数据、结论一起写进文档；
                  "我以为的"和"实际是"都要写，因为下一个坑往往就藏在那个差里
```

**记住这一个比喻**：排障像医生看一个"头疼"的病人。你不能一进门就开止痛药，得先量体温、拍片子（测量），把"牙齿、颈椎、睡眠"一条条排掉（证伪），最后才对那一个病因下药（单变量改动）；复诊时还要看几个本来就不该变化的指标（对照组）——如果连血压都跟着乱跳，那说明你的检查本身不可信，而不是药有效。

## 二、问答正文

### Q：现象一进来，为什么不能先改代码？第一步到底该做什么？

**一句话答案：** 第一步是**复现并固定口径**——不能稳定复现的现象不可修，口径不固定的数字不可比；先让它必现，再谈别的。

**展开讲：** 我踩过的最贵的一课就在这里。同一个"单帧耗时"，我在不同文档里见过 37.19 ms、20.58 ms、76.928 ms、55.836 ms 好几个数——它们全都是真的，但**根本不是同一个量**。37.19 ms 是纯推理（`rknn_inputs_set + rknn_run + rknn_outputs_get`，输入是合成的 640×640 灰图），20.58 ms 是加了 IO 搬运和 DFL 解码的全链路，76.928 和 55.836 是"MPP 硬解 + CSC + letterbox + NPU"的生产二进制全链路（改在 `-O0` 和 `-O3` 两种构建下）。

所以我的第一条纪律是：**任何一次测量，先把三件事写清楚——命令、输入、计时点**。命令要能复制粘贴重跑；输入要固定到具体那张图（同一张 `real_000.jpg`、同一个模型文件）；计时点要说清是包了哪几段、`clock_gettime` 打在哪儿。这三个都固定了，两个数字才有资格比较。

第二条纪律是**先让它必现**。第一次遇到"命令卡死 270 秒后被强杀"时，我在交互式 ssh 里跑却秒回——这种"有时候复现有时候不复现"的现象，如果直接去改代码，改完不卡了你也说不清是修好了还是运气好。我的做法是把它拆成两个可判定的子问题：功能对不对（板上 `ps` 能看到爆闪进程、`/sys` 里 brightness 在跳，功能是对的）、IO 生命周期对不对（管道/重定向场景必卡死，tty 场景必不卡）。拆到这一步，"必现条件"就变成了"只要 stdout 是管道就复现"，问题立刻从玄学变成可修。

**如果被追问「口径这种事有那么重要吗，不就是个数？」：** 太重要了。我有一组对照数据能证明不固定口径会得出荒谬结论：不绑核跑 DFL 解码，`-O0` 的 p50 是 3.44~3.47 ms，和绑核的 3.44~3.48 ms **完全一致**，但 mean 被拉到 6.38~8.15 ms、p95 冲到 15.78~17.20 ms。同一份代码、同一个优化级别，只因为没 `taskset` 绑核，均值就"翻了一倍"。**mean 在这里反映的是调度迁移噪声，不是代码差异**——不绑核能把 5.5 倍的真实差距压成 2 倍。所以我的性能测试一律 `taskset -c 6` 绑大核。

### Q：排障工具那么多，你脑子里是怎么分类的？

**一句话答案：** 按"我想知道哪一层的事实"分类——系统调用层、库调用层、运行时状态、CPU 采样、内核日志、进程与端口占用各有一个工具，选工具的本质是**选你要哪一层的事实**。

**展开讲：** 下面这张表是我自己的速查表。最后一列我特意标了"我真用到什么程度"，因为面试官很容易顺着工具名往下问一句"那你在哪个场景用过"，答不上来比不写更难看。

| 工具 | 它回答什么问题 | 我在这个项目里用它干过什么 |
|---|---|---|
| `strace` | 程序到底在跟内核说什么 | 真用过。MPP 解码器"挂住不返回"那次，用 `strace -e trace=openat,ioctl,write,exit_group` 跟到最后 5 行，定位到卡在哪个 `ioctl`、哪个 fd 上 |
| `ltrace` | 程序在调哪些动态库函数 | 没用过。知道它和 `strace` 的分界是"库函数 vs 系统调用"，诚实说不熟 |
| Linux `perf` | CPU 时间花在哪些函数上、火焰图 | 没跑过。项目里的"逐层剖析"用的是 RKNN 自己的 `RKNN_QUERY_PERF_DETAIL`，不是 `perf`，这两件事别混着说 |
| `gdb` | 进程此刻的运行时态、崩溃现场 | 抓过 segfault 的 backtrace，能看栈但不算熟；MPP 硬编那次 `encode_put_frame` 直接 Segfault，断言信息是 `cfg->fps_in_denom >= 1 failed` |
| `valgrind` | 内存泄漏、越界、未初始化 | 没跑过。内存问题我走的是"看 `free` / 看 `/proc/PID` 的 VmRSS / 长跑前后对比"这条轻量路线 |
| `dmesg` | 内核说了什么 | 真用过，而且好几次是决定性的。查 MPP 时 `dmesg` 里 `jpegd` 节点 `status=okay`，直接排除了"这块芯片不支持该解码器" |
| `/proc/interrupts` | 硬件到底有没有被真正调用 | 真用过，这是"有没有真走硬件"的铁证。硬编 bench 前后 `fdba0000.jpege-core` 四个核的中断从 21485 / 2735 / 1566 / 820 涨到 25038 / 3438 / 1953 / 987 |
| `top -H` | 线程级谁在吃 CPU | 用过轻量版（`top -H -p PID` 看线程名和单线程占用），用来确认是不是只有主线程在跑 |
| `ldd` + `strings` | 链接的是哪个库、这个库认不认识这块芯片 | 真用过。`ldd` 确认链的是源码编译的 `librockchip_mpp.so.1` 而不是系统那个 2021-05-20 编译的 `.so.0` |
| `errno` + `strerror` | 失败的确切原因 | 真用过。LED 写 `timer` 触发器拿到 `errno=22 (EINVAL)`，`rkllm_init` 拿到 `errno=14 (ENOMEM)`，这两个错误码直接指向了两个完全不同的根因 |
| `lsof` / `fuser` | 谁占着这个设备/文件 | 真用过 `fuser /dev/video81`。还踩过一个坑：`fuser` 报 PID 但 `ps` 查不到进程，那是**陈旧的内核记录**，不算占用 |
| `ss` / `netstat` | 端口在不在听、谁连着 | 用过。巡检守护探 9000 端口时先 `ss -ltn` 确认在听，再判断 `gateway_refused` 和 `connect_timeout` 的区别 |
| `taskset` | 把进程钉在指定核上 | 真用过，性能测试的标配：`taskset -c 6` 绑大核，排除调度迁移噪声 |

**如果被追问「那你怎么选？给我一条决策线。」：** 一条最简单的线：**先问"我怀疑的是什么层"**。怀疑程序逻辑错，先打印中间值；怀疑和内核/驱动交互错，上 `strace` + `dmesg`；怀疑硬件没被调用，看 `/proc/interrupts` 增量；怀疑性能，先做分段计时和逐层剖析；怀疑内存，上 `valgrind`（我这边是退化成看 `/proc`）。**自底向上找事实，比自顶向下猜代码快得多。**

### Q：37.19 ms 一帧，你当时真以为是 NPU 慢吗？

**一句话答案：** 是，第一反应就是"NPU 算力不够 / 模型太大"，这是错的——逐层一拆才发现，**49% 的时间根本不在 NPU 上**，而在 NPU 编译器切给 CPU 的 10 个算子上。

**展开讲：** 起点事实是单核 Core0 上 200 次推理的均值 **37.19 ms**，折 **26.9 FPS**，p99 是 **40.28 ms**（p50 37.07、p95 37.30）。而官方对这个模型给的量级是 **5.5~7.0 ms**。差 5 倍以上——人在"差了 5 倍"的时候，第一反应一定是"我哪里没配对"，于是脑子里冒出三个念头，对应三个动作：核没绑上？去调 `core_mask`；数据没直喂？去做零拷贝；单线程没并行？去上多线程。

我确实是先按这三个念头跑的对照实验，然后**三个全被数据否掉**：三种核绑定都测了，单核 37.19 ms、单 context 挂三核 mask 35.97 ms（只快 3.3%）、`AUTO` 37.27 ms，最快也就 35.97，说明不是调度问题；喂数据方式也做了对照，INT8 原生直喂（`pass_through=1`）是 37.05 ms，UINT8 转换是 37.19 ms，**差 0.4%**，而且每帧输入只有 1.17 MB，说明 CPU 侧的输入格式转换不是瓶颈。

三个"听起来很合理"的假设全部被证伪之后，剩下的路就只有一条：打开逐层剖析。结果是 125 个算子被分成两个阵营——NPU 上 115 个合计 **19.23 ms（51.0%）**，CPU 回退的 10 个合计 **18.44 ms（49.0%）**。

**如果被追问「你怎么知道不是 NPU 慢？凭什么排除？」：** 两条独立证据。第一是绑核实验，如果真是 NPU 算力不够，那换哪种绑定方式都该一样慢，而实测最快 35.97 ms 也只降了 3.3%，说明瓶颈不在"用了几颗核"。第二就是逐层账本：如果 NPU 是瓶颈，它应该吃掉时间的绝大部分，而不是 51%。**"NPU 慢"这个假设解释不了"有 49% 的时间 NPU 根本没参与"。**

### Q：那你是怎么把 37 毫秒拆到算子级、并且确定自己没拆错的？

**一句话答案：** `rknn_init` 时传 `RKNN_FLAG_COLLECT_PERF_MASK`，跑完 `rknn_query(RKNN_QUERY_PERF_DETAIL)` 能拿到**每个算子的耗时 + 它跑在哪个执行单元上**，我把它封成一条命令 `./bench_npu <model> 1 --perf`。

**展开讲：** 拿到手的是 125 个算子的明细，按执行单元一汇总就分出阵营，最慢的 8 个算子长这样：

| 算子 | 执行单元 | 耗时 | 所属 |
|---|---|---|---|
| Transpose | CPU | 9181 us | `model.22/dfl/Transpose` |
| exSoftmax13 | CPU | 4467 us | `model.22/dfl/Softmax` |
| Reshape | CPU | 2660 us | `model.22/Concat_3_swap_concat_reshape` |
| ConvExSwish | NPU | 1857 us | `model.0/conv`（首层，3 通道） |
| Concat | NPU | 1687 us | `model.22/Concat_3` |
| Transpose | NPU | 1475 us | `model.22/dfl/Transpose_1` |
| Reshape | CPU | 941 us | `model.22/Concat_3_0_unsqueeze1` |
| Reshape | CPU | 765 us | `model.22/Concat_0_unsqueeze0` |

看到这张表的第一感受是：**最慢的三项（9181 µs 的 Transpose、4467 µs 的 Softmax、三个 Reshape 合计 4366 µs）加起来就是 18.02 ms，而整个骨干网的 NPU 时间也才 19.23 ms**——检测头里一小段解码，吃掉了和整个 backbone 差不多的钱。而且规律非常清楚：所有 `model.22`（也就是 DFL 检测头）里的 `Transpose` / `Softmax` / `Reshape` 这类纯形状变换，全部落在 CPU 上；卷积、Concat 这类 NPU 天生会算的，留在 NPU 上。

这里有一个必须自己主动交代的口径问题：逐层表的合计是 **37.67 ms**，而 200 次均值的起点数字是 **37.19 ms**，两者略有出入。两个口径不同（逐层计时本身有开销），我引用时按各自出处标注，**不混着说**。面试官如果问"为什么对不上"，这就是标准答案，而不是编一个解释。

确定了凶手之后，行动就很明确了：不在这 10 个算子上想办法，而是**从图里把回退消灭掉**。做法是导出 ONNX 时做"图手术"，砍掉 DFL / Concat 头，只输出三路 raw 特征图（stride 8/16/32，64 通道），DFL 解码 + NMS 放到 C++ 里做。结果是纯推理从 37.19 ms 掉到 **15.95 ms（−57.1%）**，单帧全链路从 37.19 ms / 26.9 FPS 变成 **20.58 ms / 48.6 FPS**。

还有两件"顺手"的事值得一起讲，因为它们证明了当时的判断是对的。第一，砍头必须能证明"没砍错"，我没有靠肉眼看框，而是构造了一个能算出误差的基准：拿原模型（84 通道输出）当基准，和"新模型 2 输出 + 我的 numpy 解码"逐元素比，box 坐标 `max|Δ| = 0.000122 px`、cls 分数 `max|Δ| = 0`——0.000122 已经是 float32 在 640 量级上的精度极限。第二，改完模型回去看零拷贝那条路，**它本来就不是瓶颈**：输入侧直喂和转换只差 0.4%，每帧才 1.17 MB。所以"先做 DMA-BUF 零拷贝"这个念头在数据面前直接作废——**这是实测给出的优先级，和"听起来更高级"的直觉正好相反。**

> 【费曼讲解】**什么叫"算子回退"？为什么它比"慢"更严重？**
> 生活类比：你要在 A 楼做三道工序、B 楼做两道。B 楼那两道其实做得不快，也就 5 分钟；但 A、B 之间每来回一趟要打包、等电梯、签字交接，一趟 8 分钟。你最后抱怨"B 楼那两道工序好慢"，其实你亏在电梯上。
> 不懂的人会怎么错想：既然回退的算子只占 18.44 ms，那我拼命优化它们，最多也就省 18.44 ms，天花板摆在那儿。
> 一句话戳破：**回退的代价 = 那 10 个算子自己的时间 + 它造成的每一次"停等"**，后者根本不记在任何一行的耗时里，但它按趟吃掉了墙钟。
> 回到术语：这叫子图回退（subgraph fallback）。NPU 编译器不认识某个算子，就把这一段子图切下来扔给 CPU 算。在 NPU 上它表现为一个个同步点——NPU 提交完前面的算子，中间张量要落到共享内存，CPU 读完算完写回去，NPU 再读进来续跑。证据就是砍掉整个 DFL 头之后省下的 **21.24 ms** 比 18.44 ms 还多，多出来的那一截就是停等和搬运的调度损失。所以方向定成"从图里消灭回退"，而不是"把那 10 个算子写快一点"。

**如果被追问「以后换一个新模型，你怎么知道它有没有同样的问题？」：** 一条命令。`./bench_npu <model> 1 --perf`，然后看两个数：CPU 回退算子的个数、以及回退耗时的占比。回退占比超过 20% 就值得动图，低于 5% 就先看别处。**这个探针比任何"感觉快了"都可靠，因为它是可复现的、幂等的。**

### Q：项目跑了 20 多天，构建系统里一个 `-O` 都没开，这种事怎么可能一直没被发现？

**一句话答案：** 因为 `CMAKE_BUILD_TYPE` 为空时 CMake **不报错也不警告**，编译成功、程序能跑、功能测试全过，只有性能悄悄变差——这类"静默失效项"只能靠自检打印和警告兜住。

**展开讲：** 我本来是去做 `CMAKE_BUILD_TYPE=Release` 优化的（文档里写着"白捡 1.55×"），上手第一件事是看板上现有的构建配置，结果两条命令就把我钉在原地：

```
$ grep CMAKE_BUILD_TYPE /root/edgevision/deploy/cpp/build_native/CMakeCache.txt
CMAKE_BUILD_TYPE:STRING=                      ← 空

$ grep CXX_FLAGS .../edgevision_deploy.dir/flags.make
CXX_FLAGS = -std=gnu++17                      ← 一个 -O 都没有，等效 -O0
```

影响面比想象的大：项目此前记录的所有 CPU 侧耗时——MJPG 软解 7.76 ms、letterbox、DFL 解码 3.09 ms、CSC 51~65 ms——**全是未优化代码跑出来的**。也就是说，这些数字不是"性能上限"，是"没开优化"。**它们连"我们的代码就这水平"都不算，只是"我们的编译配置就这水平"。**

为什么一直没人发现？三条叠加。第一，CMake 的 `CMAKE_BUILD_TYPE` 默认为空，此时它不会追加任何优化标志，也不会警告，**编译成功、程序能跑**。第二，产物路径、日志、功能验证全部正常，**功能测试永远发现不了性能配置问题**。第三，也是最阴的一条——项目里的 bench 工具是手工用 `g++ -O2` 编的，跑出来的数字（比如 DFL 解码 1.79 ms）看着很正常，于是"整体应该没问题"的错觉就形成了。**两套构建口径混用，掩盖了正式构建的缺陷。**

修法我做了三层，一层比一层狠。第一层，CMakeLists 里加 `if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)` 默认设成 `Release`。第二层，兜底：`if(NOT CMAKE_CXX_FLAGS_RELEASE)` 时设 `-O3 -DNDEBUG`（用 `CACHE STRING ... FORCE`），防止有人用外部 toolchain 覆盖掉，命令行仍然可以覆盖。第三层才是关键——**自检而不是靠人记**：configure 结束时打印构建摘要，并且在编译标志里匹配不到 `-O[0-9s]` 时直接 `message(WARNING)`。这样"没开优化"会自己喊出来，不需要任何人记得去看。

> 【费曼讲解】**`-O0` 到底慢在哪？为什么不开优化会慢好几倍？**
> 生活类比：翻译一封电邮。`-O0` 是**逐字直译**——每个词都想一遍、每个句式都照原文摆，语法全对，但一封本该 5 分钟写完的信要写 40 分钟。`-O3` 是一个熟练译者：先通读一遍，知道你要说什么，把重复的客套话合并、把绕的句子理顺，最后交出来的意思一样，但过程快得多。
> 不懂的人会怎么错想：会觉得"开优化只是锦上添花的几个百分点，我的代码逻辑又没问题"。这个想法忽略了编译器做的根本不是"润色"，而是**重新组织指令**——循环展开、向量化、常量折叠、寄存器分配、把反复从内存取的值提到寄存器里。
> 一句话戳破：**`-O0` 下编译器严格按你写的字面执行，每一次变量读写都老老实实回内存；而 ARM 上访问内存比访问寄存器贵一到两个数量级**，于是循环内多出来的每一次 load/store 都会被乘上循环次数。
> 回到术语：这就是为什么优化级别的收益**极度依赖代码形态**——纯计算密集的紧循环能差 5 倍以上（我的 DFL 解码 + NMS 是这样，3.44~3.51 ms → 0.62~0.63 ms），而已经调库的部分几乎不动（`cv::resize` 那种预编译库只有 +3.2% 的噪声级波动）。也正因为这个差异，"开 `-O3` 到底能快多少"这个问题**没有通用答案，只能在你的代码上测**。

**如果被追问「你怎么证明 1.549× 是真的？万一是那天的负载波动呢？」：** 这是这个案子里我最想说的一段，因为我特意**留了两组"理论上不该变"的对照组**。用真实生产二进制、同一张 `real_000.jpg`、同一模型、各 5 次、`taskset -c 6` 绑大核：

| 层 | O0 | O3 | 变化 | 意义 |
|---|---|---|---|---|
| MPP 硬解 | 1.250 ms | 1.322 ms | +5.8% | 对照组①（跑在硬件上，不该变） |
| NV12 到 RGB888 的 CSC | 52.016 ms | 33.583 ms | 1.549× | 自己写的循环，优化直接命中 |
| letterbox（`cv::resize`） | 1.184 ms | 1.222 ms | +3.2% | 对照组②（跑在预编译库里，动不了） |
| NPU + DFL 解码 | 22.480 ms | 19.708 ms | −2.77 ms | 与 bench 的 −2.78 ms 吻合 |
| 全链路 | 76.928 ms | 55.836 ms | −27.4%（1.378×） | 13.0 → 17.9 FPS |

**两个对照组同时成立**才是这条实测的价值：跑在硬件上的（MPP）和跑在预编译库里的（OpenCV）两层纹丝不动，唯一自己写的 CPU 热点 CSC 恰好提速 1.549×——这就同时排除了"测量漂移"和"负载波动"两种解释。顺带还修正了一句我自己文档里流传的表述：**"白捡 1.55×"是 CSC 单层的，全链路实际是 −27.4%**，这两个数不能混着说。

### Q：余弦相似度 0.9965，为什么你把它当成反面教材？

**一句话答案：** 因为那个模型其实已经废了——cls 分支整体塌缩成常数 0.5（也就是 `sigmoid(0)`），9 张图的置信度**全部精确等于 0.5000**，而整体特征图余弦相似度还有 0.9965，**这个指标完全没报警**。

**展开讲：** 起因很朴素：我用合成色块图（纯色矩形 + 纯灰底）当校准集转 INT8。转完在真实画面上看，框还是对的，看起来"精度没掉"。但仔细一看分数，9 张图的置信度全部精确等于 0.5000——一个模型如果"有点不确定"，分数应该在 0.4 到 0.7 之间散着，**不可能每张图都精确等于同一个数**。`0.5 = sigmoid(0)`，这说明 cls 分支的输出被量化成了常数，**分类头已经死了**。

根因在校准集上：合成图里根本没有人/物体，cls 分支的激活值分布极窄，量化 scale 就被定在了一个很小的区间；真实画面一进来，激活值整体饱和，全部挤到同一个量化格子里。而 box 分支（回归）的分布相对稳定，所以框没坏——**"框对"和"分对"是两件事，必须分开验证。**

改法是换真实实拍 + 增强样本重转。换完之后平均分数从 **0.5000 回到 0.8072**（FP32 是 0.8125），基本追平。再往后我就彻底不再用"相似度"当验收了，改用**真 mAP**：口径和 PC 侧完全对齐（同一个 GT、同一个 AP 实现、COCO 101 点插值、IoU 0.5、conf=0.01、NMS IoU=0.45），结果是 COCO128 上 FP32 **0.6087** → INT8 **0.6002**，相对 **−1.4%**，绝对掉点 **0.85 个 mAP 点**。

这个案子给我的结论只有一句：**精度指标必须和任务指标对齐。** 余弦相似度量的是"特征图整体形状像不像"，它对"某个分支塌缩成常数"这种结构性坏死完全不敏感——塌缩的分支在整体相似度里只占很小一块，被别的层稀释掉了。下游任务指标（mAP、top-1）才是硬道理，因为它们直接问"你到底能不能把东西找对"。

> 【费曼讲解】**为什么余弦相似度会骗人？它不是"很严格的相似"吗？**
> 生活类比：期末考十门课，你九门都考 85 分，只有一门"体育"考了 0 分。算"平均分相似度"，你和上次的自己相似度大概 0.9，看起来"没什么变化"——但那门 0 分的课意味着你**毕不了业**。
> 不懂的人会怎么错想：会觉得"0.9965 这么接近 1，说明量化几乎无损，这个模型可以放心用"。这是把**平均指标**当成了**最坏情况指标**。
> 一句话戳破：**余弦相似度是一个把整张特征图压成一个数的平均量，它天生看不见"某一块彻底死了"**——一个分支塌缩成常数，在整体能量里只占一小部分，被其余正常层稀释掉了。
> 回到术语：量化误差的伤害不是均匀分布的，它集中在**激活分布最窄、最容易被 scale 锁死的那一支**。所以验收要么用能暴露"分支级别坏死"的指标（真 mAP、分分支逐项对比），要么就直接构造"已知正确答案"的锚点样本去测——**不能用一个平均数换一个结论**。

**如果被追问「那你怎么知道换校准集之后就好了，而不是碰巧？」：** 三条独立证据。第一，`0.5 = sigmoid(0)` 是数学上的确定性，分数全等于同一个值只可能是输出被量化成了常数，这不是概率问题。第二，换校准集后分数回到 0.8072，接近 FP32 的 0.8125，**差距在合理范围内**而不是"变好了但说不清"。第三，我另外跑了真 mAP，FP32 0.6087 到 INT8 0.6002 的相对掉点是 1.4%，属于 INT8 后量化的正常水平（一般 1~3%）。**一个指标修好了不够，要三个方向对上才算修好。**

### Q：三个案子串起来，通用排障方法论到底是哪几步？

**一句话答案：** 复现并固定口径 → 二分缩小范围 → 加观测拿事实 → 写下一句假设 → **单变量验证** → 把复现命令和"我以为 / 实际是"一起固化。

**展开讲：** 这六步里，最容易被跳过、也最致命的是**第四步"提假设"和第五步"单变量"**。人一旦看到"49% 在 CPU 上"这种漂亮的发现，手就会痒，想一次把图手术、访存优化、编译标志全改了，然后跑一次发现快了 3 倍，皆大欢喜。**但这样你永远不知道是哪一刀起的作用**，下次遇到同类问题也没法复用判断。

我的三个案子恰好各占一头，正好说明这条顺序为什么不能乱：

- **37 ms 案**：先证伪了三个"听起来很专业"的假设（绑核、零拷贝、多线程），才被逼到逐层剖析上。如果一上来就做零拷贝，我会花掉几天，然后得到一个 0.4% 的"提升"。
- **`-O0` 案**：这不是性能案，是**配置案**——现象根本不表现为"某个函数慢"，而是"所有 CPU 层次体慢"。它的破案关键不是 profiler，而是"去看构建配置"这个动作。教训是：**优化之前先确认你的基线是可信的**。
- **余弦 0.9965 案**：这不是"变慢"，是"假 PASS"。它提醒的是另一个方向——**你的验证指标本身也可能是 bug**。前两个案子的敌人是"没测到"，这个案子的敌人是"测了个不该信的数"。

第五步"单变量"我再强调一遍具体做法：**一次只动一个变量，同时挂一个本该不变的对照组**。`-O0` 案里，我把"NPU 纯推理耗时"当对照组（14.79~14.88 ms vs 14.90~14.95 ms，无变化），它稳住了，CRC/解码那些变化的数字才能归因到编译标志上。如果对照组也跟着乱跳，那说明**测量本身不可信**，该去修测量，而不是庆祝。

**如果被追问「你说"先证伪再修复"，可证伪不是要花很多时间吗？」：** 恰恰相反，证伪是最省时间的动作。绑核实验一条命令、零拷贝对照一条命令、`AUTO` 一条命令——三条加起来不到一小时，却挡掉了我原本可能花几天的三个错误方向。**证伪的成本远低于修错方向的成本**，这是我这个项目里最值钱的一条经验。

### Q：单变量对照实验具体怎么设计？对照组该怎么选？

**一句话答案：** 对照组要选**"你的改动理论上根本影响不到、但和被测项跑在同一时刻同一台机器上"**的那一项；它稳，你的变化才可信；它也动，先怀疑测量。

**展开讲：** 对照组怎么选，有个很实用的判断标准：**问一句"这一层是谁在跑"**。

- 跑在**硬件**上的（MPP 硬解、NPU 推理），编译器优化动不了它 → 天然是编译优化的对照组。实测 MPP 硬解 1.250 → 1.322 ms（+5.8%），这就是噪声水平。
- 跑在**预编译第三方库**里的（`cv::resize` 的 letterbox），你改的是自己代码的优化标志，动不了它 → 也是好对照组。实测 1.184 → 1.222 ms（+3.2%）。
- 跑在**你自己写的紧循环**里的（NV12 到 RGB888 的 CSC），优化的收益全在这儿 → 这才是被测项。实测 52.016 → 33.583 ms（1.549×）。

这样一来，"硬件不动、库不动、只有我的循环快了 1.55 倍"就构成了一条完整证据链：**它不是环境变了，而是我确实动了那一处代码。**

第二个关键动作是**控制外部变量**。同一台板子、同一个模型、同一张图、同样的次数（各 5 次）、`taskset -c 6` 绑大核、交替跑而不是先跑完 O0 再跑 O3。交替跑很重要——如果先集中跑完 O0 再集中跑 O3，机器温度、CPU 调频、后台负载的漂移就会全算到你的改动头上。

第三个动作是**看分位数而不是只看均值**。这不是洁癖，是我被数据打脸过一次：不绑核时 `-O0` 的 p50 是 3.44~3.47 ms，跟绑核完全一致，但 mean 被拉到 6.38~8.15 ms、p95 冲到 15.78~17.20 ms。原因是 `-O0` 代码执行时间长，被调度器跨核/大小核迁移打断的次数显著更多。**所以报性能数据必须给 p50 / p95 / p99，只给 mean 等于给了一个会被调度噪声污染的数。**

> 【费曼讲解】**什么是"单变量对照实验"，为什么不能一次改好几个东西？**
> 生活类比：你觉得最近睡不好，于是同时换了床垫、戒了咖啡、还开始跑步。一个月后睡好了——**你知道是哪一件起了作用吗？** 下一回想复用这个经验，你只能把三件事一起再做一遍，成本翻三倍，而且其中可能有两件是白做的。
> 不懂的人会怎么错想：会觉得"反正目标是把性能提到 20 ms 以内，能一起改就一起改，效率高"。这是把**达成指标**当成了唯一目标，而忽略了"我下次还能不能重现这件事"。
> 一句话戳破：**同时改多个变量的实验，只能告诉你"结果变了"，不能告诉你"谁让它变的"**——而排障的全部价值就在于后者，因为只有知道因果，你才能把它变成可复用的判断。
> 回到术语：单变量法的严格形式是"控制变量 + 交替测量 + 分位数统计 + 一个理论上不该变的对照组"。一个人做工程，最贵的不是算力，是"我到底学到没学到"。

**如果被追问「现实里根本没法只改一个变量，怎么办？」：** 那就退一步做"分组"：把互不相干的改动分成几组，每组单独一轮；实在分不开，至少要保留一个"我没碰过的层"当基准。我在 `-O0` 案里就是这么退让的——图手术和编译标志是两件独立的事，我分开测，各自带自己的对照组，最后才把它们的影响叠加解释。

### Q：Windows 侧 ssh 内联复杂命令，引号被吃掉这个坑怎么回事？

**一句话答案：** PowerShell / cmd 到远端 shell 之间要过**多层引号解析**，内联的 `ssh 'a | b; c'` 到板子上往往已经面目全非；正确做法是**把命令写成 `.sh` 脚本 `scp` 上去，再 `bash` 那一个文件**。

**展开讲：** 这个坑我吃过不止一次，最典型的是 `ssh root@board "pkill -f preview_real; ./start.sh"` 执行后 SSH 直接断开、脚本根本没跑。查下来有两层原因叠在一起：Windows 侧把双引号里的内容重新拼装时吃掉了某些转义，导致 `pkill -f` 匹配到的字符串仍然包含它自己；而 `pkill -f` 匹配的是**完整命令行**，这条 ssh 命令本身也带着 `preview_real` 这个字符串，于是它把承载自己的那个 shell 也杀了。

修法分两层。第一层是**换通道**：不在命令行里塞复杂逻辑，写一个 `xxx.sh`，`scp` 到板子上，`ssh root@board "bash /root/xxx.sh"`。这一下把"多层引号解析"整个问题消掉了——脚本文件是字节流，不经过任何 shell 的引号重写。第二层是**换匹配方式**：不用 `pkill -f <名字>`，改成 `pgrep -f '^./程序名'` 拿到 PID 再 `kill`，`^` 锚定命令行开头，直接排除掉调用者自己。

还有一个同源的坑值得一起说：**Git Bash 的 `/tmp` 不是 Linux 的 `/tmp`**。`curl` 把数据集下到 Git Bash 的 `/tmp`，Python 脚本读 `/tmp/coco128` 却是空的——因为 Git Bash 的 `/tmp` 实际映射到 `C:\Users\<me>\AppData\Local\Temp`，而 Windows 原生 Python 把 `/tmp` 当成 `C:\tmp`。修法是：**涉及 Python 读写的路径一律用绝对 Windows 路径**，数据集解压进项目目录。

**如果被追问「为什么不干脆在板子上写脚本？」：** 大部分时候我就是在板子上直接写的。但只要涉及"从 PC 侧发起、参数里有空格/引号/管道"的场景，写文件再传过去永远比调引号划算——**你花在引号转义上的每一分钟，都是在给一个本来不存在的通信协议打补丁。**

### Q：`/dev/rknpu` 不存在，是不是驱动没装好？

**一句话答案：** 不是，**这是正常的**。新版 RKNPU 驱动走的是 DRM 图形子系统，设备节点在 `/dev/dri/renderD129`，根本没有 `/dev/rknpu` 这个文件。

**展开讲：** 这个坑的危险性在于它的**误导方向**：你在排查"NPU 不工作"，顺手下 `ls /dev/rknpu`，报"没有这个文件"，于是你判定"驱动没装"，接着开始重装驱动、刷固件、怀疑内核——全都是白费。真实情况恰好相反：驱动装得很好。

正确的查法有三条，任何一条都能确认 NPU 是活的。第一，`ls /dev/dri/` 能看到 `renderD129`，这就是新版驱动暴露出来的渲染节点。第二，板子的实际配置能够对上：NPU 驱动 v0.9.2、运行时 API 2.3.0、3 核、主频 1.0 GHz，这些都能从运行时侧读到。第三，也是最硬的——**跑一次推理**：`rknn_init` 成功、`rknn_run` 出结果，那 NPU 就是好的，设备节点叫什么名字一点都不重要。

我在这个项目里把这条写进 `AGENTS.md` 的"已知正常"清单里，因为它属于那种**"看起来像故障、其实是正确状态"**的条目。同类还有一条：**`fuser /dev/video81` 报 PID 但 `ps` 查不到那个进程，那是陈旧的内核记录，不算占用**，别据此判定摄像头被别人占着。

**如果被追问「那还有其他类似的"看起来像故障其实正常"的坑吗？」：** 有，而且这是我最想提醒的一类。`ENOMEM` 说分不出 196 MB 而 `free` 显示还有 6 GB——那是因为 fork 出来的孤儿进程继承了父进程 mmap 的 NPU DMA 映射，驱动认为内存仍被占用，**"free 充足"和"能申请到"是两件事**。还有 `pkill` 自杀、`/tmp` 路径映射，本质都是同一类：**你的观测对象名字对，但你理解的那个模型是错的。** 遇到"明明应该怎样却没有"，先怀疑自己的模型，再怀疑系统。

### Q：怎么防止"假成功"这类最隐蔽的 bug？

**一句话答案：** 一条原则——**只认可验证的物理事实，不认程序自述**；任何"设置成功"的返回值，都要配一次"回读比对"或者一个可量化的物理判据。

**展开讲：** "假成功"的标准形态是**两层叠加：底层失败 + 上层不检查**。我在这个项目里遇到过最典型的一次：Agent 的 `control_led(mode="alarm")` 一直返回"成功"，但灯实际一动不动。查下来，旧代码往 `/sys/class/leds/work/trigger` 写 `timer` 之后直接返回 `success:true`，根本没看写没写进去。我拿探针去试：C++ `ofstream` 写完检查 `fail()` 是 1，绕开 iostream 用裸 `write(2)` 拿 `errno` 是 **22（EINVAL）**。再往下追，这块板的内核 `5.10.110` 出厂**没编 `CONFIG_LEDS_TRIGGER_TIMER`**，`/sys/class/leds/work/` 下根本不存在 `timer` 这个触发器——这个值对 sysfs 就是非法输入。对照实验写 `heartbeat`（列表里存在的触发器）能成功，证明不是权限也不是路径问题。

修法也是标准的"防假成功"三件套：**写入逐步检查返回值**（失败报 `sysfs_write_failed` 加具体节点）；**写后回读**，把 `actual_mode` / `brightness` 与请求比对，不符报 `readback_mismatch`；**换掉依赖内核配置的实现**——alarm 改成用户态 fork 一个子进程交替写 brightness 造方波，不依赖任何内核触发器。

同类还有一次几乎一模一样的：网页预览上一直有个绿框标着 "Person 96%"，位置还会缓慢移动，看起来像在检测。翻源码才发现 `float offset_x = (frame_id % 120) * 5;`——框的位置由帧号算出来的，标签是硬编码的，而模型跑完之后 `rknn_outputs_get` 拿完立刻 `release`，**检测结果从头到尾没被使用过**。更糟的是 9000 网关那边是**同一个毛病的另一份拷贝**（`res.boxes[0] = {0, 0.95f, ...}`，注释还写着"模拟真实跟踪"）。这意味着 systemd 里那个"工业级网关"推给上位机的 800 多帧，**一个真实检测结果都没有**。

**如果被追问「那你怎么系统性地防住这一类？」：** 三条我一直在用的检查。第一，**凡演示代码，必须检查"输出有没有被消费"**——函数算出了结果，那个结果有没有真的流向下一层。第二，**发现一处假象，全文搜同类模式**（搜 `frame_id %`、搜硬编码的置信度），因为这类代码是复制粘贴出来的，从来不会只存在一处。第三，**验收判据要能量化**。最典型的就是灯：不能看"灯亮了一下"，要看 PWM 占空比从 20.0% 抬到 49.7%。**"看起来在工作"和"在工作"是两件事**，而中间那条沟只能靠可复现的数字填上。

## 三、这一章的“记忆锚点”

- 排障顺序：**复现并固定口径 → 二分缩小范围 → 加观测拿事实 → 写下一句假设 → 单变量验证 → 固化记录**。跳过任何一步，你得到的都是"结果变了"而不是"谁让它变的"。
- 测量三件套必须写清楚：**命令、输入、计时点**。37.19 ms（纯推理）、20.58 ms（加 IO 与解码的全链路）、76.928 ms 和 55.836 ms（生产二进制两种构建）全是真数，但**不是同一个量，混着说就是错**。
- 37 ms 案的真相：**NPU 115 个算子 19.23 ms（51.0%），CPU 回退 10 个算子 18.44 ms（49.0%）**，125 个算子逐层合计 37.67 ms。凶手全是 `model.22` DFL 头里的 `Transpose` / `Softmax` / `Reshape`。
- 先证伪，再动手：绑核最快 35.97 ms（只快 3.3%）、零拷贝 37.05 vs 37.19（差 0.4%）——**三个"听起来很专业"的假设全被数据否掉，才轮到动图**。图手术后纯推理 15.95 ms（−57.1%），全链路 20.58 ms / 48.6 FPS。
- 回退的代价不只是那 18.44 ms：砍掉 DFL 头省了 **21.24 ms**，多出来的就是停等和搬运——**这部分从来不记在任何一行耗时里**。
- `CMAKE_BUILD_TYPE` 空 = **等效 `-O0`**，CMake 不报错不警告、功能测试永远发现不了。修法是"默认 Release + flags 自检 `message(WARNING)`"，靠系统自己喊，不靠人记。
- 对照组的价值：MPP 硬解 +5.8%、`cv::resize` letterbox +3.2%（两个都该不动、确实没动），CSC 1.549×（自己写的循环）→ **排除测量漂移与负载波动**。全链路 −27.4%，别把"白捡 1.55×"当成全链路数字说。
- 余弦 0.9965 是反面教材：cls 分支塌缩成 `sigmoid(0)` = 0.5，9 张图分数全等于 0.5000；换真校准集后 0.8072（FP32 0.8125），真 mAP 0.6087 → 0.6002（−1.4%）。**精度指标必须和任务指标对齐。**
- 两个环境坑：Windows 侧 ssh 内联复杂命令引号会被吃 → **写 `.sh` scp 上去再 `bash`**；**`/dev/rknpu` 不存在是正常的**，新版驱动走 DRM `/dev/dri/renderD129`。

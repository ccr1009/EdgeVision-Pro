# 第 1 章 项目总览与技术选型

> 一句话心智模型：这个项目不是"我在板子上跑通了一个 YOLO"，而是"我在一块 RK3588 上，把从摄像头进来、到结构化结果出去、再到大模型调度这一整条链路，一段一段量出耗时、一段一段改下去，并且清楚知道哪一段我没做"。面试时你要交付的不是一张架构图，而是"每一段谁在干活、多少毫秒、边界在哪"。

## 一、先建立心智模型

我习惯把这个项目讲成**三条线叠在同一块板子上**，而不是讲成一个功能列表。第一条是视觉线，跑得快、天天在跑、负责"看见"；第二条是 Agent 线，跑得慢、按需拉起、负责"判断"；第三条是底下的守护线，跑得最稳、周期固定、负责"别死"。三条线的资源冲突点只有一个：**NPU**。所有设计取舍的根，几乎都能追到"这块 NPU 只有三核、而且不能同时伺候一个大模型和三个检测 context"这件事上。

```
             EdgeVision-RK3588 全景（EVM3588-B 单板，全离线运行）

  [视觉线 · 快层] 一条六节的管子，下面的 ms 全是板端实测
   UVC 摄像头 --> MPP 硬解 --> CPU CSC --> letterbox --> NPU 三核 --> DFL-Free --> TCP:9000
   MJPEG 30fps    VPU 出 NV12   NV12->RGB    640x640      15.95 ms      解码+NMS     248 B 定长帧
                  p50 1.03 ms   33.58 ms     1.0~3.4 ms   59.3 FPS      3.09 ms      上位机 19.2 FPS

  [Agent 线 · 慢层] 按需拉起，和视觉线抢同一块 NPU
   自然语言 --> RKLLM + Qwen3.5-2B --> ReAct 循环 --> 5 个硬件工具 --> Observation 回填 --> 下一轮
                W8A8，2.8 GB          max_steps=5   温区/灯/视觉/巡检事件

  [守护线 · 底层] 独立 C++ 进程，5 s 周期，快层不加载 LLM
   采样(温度 / NPU / 视觉帧) --> 状态机(带迟滞) --> 只有状态翻转才写 patrol_events.log
                                              --> 另写 llm_pending.jsonl 留给慢层读
```

**记住这一个比喻**：三条线共用一台"三工位的加工中心"。视觉线是长期包工的流水单，Agent 线是临时插单的急件。你让急件插进来，流水单不会停，但每件的等待时间都会变长——所以我把守护线设计成**根本不排队上 NPU**，它只读文件、只读温区，这样它永远不会因为抢不到 NPU 而失职。

## 二、问答正文

### Q：一句话说清这个项目是什么？

**一句话答案：** 一块 RK3588 开发板上的端侧视觉巡检系统：摄像头 MJPEG 进来、MPP 硬解、CPU 做颜色转换和 letterbox、三个独立 context 各绑一个 NPU 核并行跑 YOLOv8n INT8、DFL-Free 后处理、TCP 定长帧推流；上层挂一个纯板端离线的大模型 Agent 做多步工具调用，底层有一个独立的 C++ 巡检守护做快慢双系统。

**展开讲：** 我会刻意把"看见""判断""不出事"这三件事分开说，因为它们的工程性质完全不同。视觉线是**确定性流水线**，只要测量方法对，优化收益就能复现；Agent 线是**不确定性推理**，同样一句话两次跑出来的 token 数都不一样，所以它的指标只能是"端到端时延区间"和"用例通过率"；守护线是**可靠性工程**，它关心的不是快，而是"停电重来之后还能不能自己站起来"。

一句话里带三个数字，对方立刻知道你量化过：**纯推理 15.95 ms**（比图手术之前 37.19 ms 降了 57%）、**单帧全链路 20.58 ms / 48.6 FPS**、**三核聚合 59.3 FPS（2.21×）**。

**如果被追问「你这个端侧 AI 部署，部署的到底是模型还是系统？」：** 两个都是。模型侧我做的是 INT8 PTQ 量化、ONNX 图手术、真 mAP 评测；系统侧我做的是 MPP 硬解、三核绑定、后处理、推流、服务化和守护。如果只会前者，那叫调工具链；只会后者，那叫写 C++。这个项目的价值在于两边的账我能对上：模型少算 18.44 ms 的 CPU 回退，系统侧就真的少等了 21.24 ms。

### Q：把整条链路的每一段和它的真实耗时摆出来

**一句话答案：** 采集到推流共七段，只有 NPU 那一段跑在专用算力上：MPP 硬解 p50 1.027 ms、CPU 侧 CSC 在 Release 后 33.583 ms、letterbox 1.0~3.4 ms、NPU 纯推理 15.95 ms、后处理里 IO 搬运 1.53 ms 加 DFL 解码与 NMS 3.09 ms、最后 248 字节定长帧推到 TCP 9000。

**展开讲：** 这张表我建议直接背下来，因为它同时回答了两个高频问题——"你的瓶颈在哪"（答案是 CSC，33.583 ms，占生产链路六成）和"NPU 优化完了为什么还慢"（因为 NPU 只占一小段）。

| 段 | 谁在干 | 实测耗时 | 说明 |
|---|---|---|---|
| 采集 | UVC + V4L2 | 33.33 ms 出一帧 | 显式设 30 fps 后稳定 |
| 硬解 | VPU（MPP） | p50 1.027 ms | 对比 OpenCV 软解 7.761 ms，7.6 倍 |
| 颜色转换 | CPU 定点 | 33.583 ms（O3） | 当前第一瓶颈，读 uncached DRAM |
| letterbox | CPU | 1.0~3.4 ms | 等比缩放 + 灰边 114 |
| 推理 | NPU 三核 | 15.95 ms | 单核单 context |
| 后处理 | CPU | 1.53 + 3.09 ms | IO 搬运 + DFL 解码 + NMS |
| 推流 | CPU + 网卡 | 248 B 一帧 | 上位机实测 19.2 FPS |

有两个口径必须分开报：**bench 口径 20.58 ms / 48.6 FPS** 是"推理 + IO 搬运 + 后处理"这一段（15.95 + 1.53 + 3.09）；**生产口径 55.84 ms / 17.9 FPS** 是把硬解、CSC、letterbox 都算进去的全链路。面试官最容易在这里一刀见血，我主动说清比被问出来强。

**如果被追问「为什么 CSC 这么贵，不能优化吗？」：** 能，但要换硬件单元。根因是 CPU 在读 uncached 的 DRM 内存，实测 memcpy 只有 188 MB/s。正解是 RGA 做硬件 CSC，我这块板 RGA 2.1.0 不支持 full CSC、颜色偏差 ±13%，我判断不划算所以没做——这一条我在本章最后的边界表里如实标着"没做"。

### Q：硬件规格你能报多细？

**一句话答案：** EVM3588-B（英码 EMA）核心板 SOM3588-B，8GB LPDDR5 加 64GB eMMC，Debian 11、kernel 5.10.110，NPU 驱动 0.9.2、运行时 API 2.3.0、三核 1.0 GHz 共 6 TOPS，实测内存 7.5Gi 可用、eMMC 57.6G 可用、RGA 与 MPP 均正常。

**展开讲：** 面试官问硬件，真正想确认的是"这些数是你自己敲命令看到的，还是抄的官网参数"。所以我习惯连采集方式一起报：

| 项 | 实测值 | 采集方式 |
|---|---|---|
| 硬件 | EVM3588-B（英码 EMA），SOM3588-B，8GB LPDDR5 + 64GB eMMC | `free -h` |
| 系统 | Debian 11 (bullseye)，kernel 5.10.110 | `uname -r` |
| NPU 驱动 | 0.9.2 | `cat /sys/kernel/debug/rknpu/version` |
| RKNN 运行时 API | 2.3.0 | `rknn_query(RKNN_QUERY_SDK_VERSION)` |
| NPU 主频 | 1.0 GHz，满载未降频 | `/sys/class/devfreq/fdab0000.npu/cur_freq` |
| NPU 核数与算力 | 3 核，共 6 TOPS | 官方规格 |
| DDR 主频 | 2112 MHz | `/sys/class/devfreq/dmc/cur_freq` |
| 内存 | 7.5Gi 可用 | `free -h` |
| eMMC | 57.6G 可用 | `df -h` |
| RGA / MPP | 均可正常调用 | 实测调用 |
| 待机温度 | SoC 37.9°C / NPU 37.0°C | 7 个 thermal_zone |

有两个坑值得主动说，因为它们能证明你真的上过板子。第一，**`/dev/rknpu` 不存在是正常的**，新版驱动走的是 DRM 的 `/dev/dri/renderD129`，驱动在不在要去看 `/sys/kernel/debug/rknpu/version` 能不能读到 0.9.2。第二，**板子系统装在 eMMC 上，不需要刷机**，官方给的 `.img` 是 RKFW 整包，不能直接拷到 TF 卡上启动。

**如果被追问「驱动 0.9.2 配运行时 2.3.0，版本差这么多不会出问题？」：** 实测能跑，这是验证过的组合而不是猜的。这三层是分开的：toolkit 负责把模型转成 `.rknn` 文件，runtime 负责加载执行，驱动在内核里对接硬件。**toolkit 和 runtime 必须配对**，我踩过 1.6.0 转的模型喂给 1.5.2 runtime 的倒挂，那个模型在板上一张都检不出、阈值降到 0.05 仍然是 0；而驱动相对独立，驱动 0.9.2 配 runtime 2.3.0 实测可用。

### Q：你说的"三条线"是怎么安排的？

**一句话答案：** 学习线是第 1~4 周的 Linux 应用层四关，全部通关并落成一个可用的边缘网关 V1.0；推理链路是第 5~7 周的端侧推理深度剖析，产出 DFL 图手术、量化评测和编译优化；Agent 线是最后叠上去的端侧大模型与巡检守护，产出多步 ReAct 演示和 12 条回归用例。

**展开讲：** 这个顺序不是排得好看，是**被依赖关系逼出来的**。

- 学习线先做，是因为后面所有东西都要用它：`/proc` 和 sysfs 读温度、`fork/exec` 起子进程、pthread 绑核、epoll 网关、systemd 自启与自愈。没这四关，推理链路写出来也只是一个"能跑一次"的 demo。
- 推理链路第二个做，因为它有**明确的、可复现的敌人**：37.19 ms 里 49% 花在 CPU 回退。这种问题收益大、路径清晰、数字好量，特别适合作为主力技术故事。
- Agent 线最后做，因为它最贵也最不确定：2.8 GB 的模型、十来秒一轮的推理、完全没法用"改一行测一次"的方式迭代。前面把视觉线的遥测和事件日志铺好了，Agent 才有东西可以调用。

**如果被追问「学习线的产出和推理链路是割裂的吗？」：** 不割裂。学习线的网关 V1.0 后来被直接改造成了生产链路：真摄像头替换了假数据、`frame_id % 50` 的伪造框全删掉、旧 84ch 模型换成 DFL-Free、协议升级成 248 字节定长帧，最后挂到 `edgevision.service` 上开机自启、5 秒崩溃自愈。也就是说学习线写的那个网关骨架，一直用到现在。

### Q：为什么用 RKNN 而不是 ONNX Runtime？

**一句话答案：** 因为这块板子的算力长在 NPU 上，而 ONNX Runtime 在 RK3588 上只能吃 ARM CPU；RKNN 是唯一能把模型真正压到那三颗 NPU 核上的运行时。我在 x86 上确实用 ONNXRuntime 跑过全流程做参考基线，但那 52.59 ms 是 CPU 的数，一点 NPU 都没用上。

**展开讲：** 这件事要分两层说。第一层是**硬件通道**：RK3588 的 NPU 没有通用驱动接口，只有 RKNN runtime 这一条路，`rknn_init / rknn_run` 是唯一入口。所以"用不用 RKNN"其实不是技术选型，是"用不用这块板子的 NPU"。

第二层才是真正值得讲的部分：**RKNN 带来的不只是速度，还有代价**。它要求模型先被工具链吃进去重新编译，这个过程会引入量化误差、算子回退、版本配对三个新问题——我后面 90% 的坑都出在这三件事上。而 ONNXRuntime 那条路上这些问题都不存在，它就是慢。

我的做法是**两条路都留着**：PC 侧用 ONNXRuntime 和 numpy 做参考实现，板端用 RKNN 做生产实现，两边对同一张图的输出逐位比（图手术的等价性就是这么验的，box max 差 0.000122 px、cls max 差 0）。

> 【费曼讲解】为什么 NPU 不能"直接跑" ONNX？
> 生活类比：ONNX 是一份用国际通用语写的施工图，NPU 是一个只会说方言、而且干得极快的老师傅。你不能把通用语的图纸直接塞给他，得先请一个翻译（toolkit）把它翻成方言，翻译的过程中有些说法在方言里没有对应词，只能换成近义词——这就是算子回退和量化误差。
> 不懂的人会怎么错想：以为 NPU 是一块"更快的 CPU"，装个驱动就能跑任何模型，像装显卡驱动那样。于是他会想"为什么不能直接 `onnxruntime` 指定 NPU 后端"。
> 一句话戳破：NPU 没有通用指令集，它只认被工具链编译过的、算子和数据布局都预先摊平的固化图。
> 回到术语：所以 RKNN 流程是 `load_onnx` 载入图、`build` 做算力分配与量化、`export_rknn` 导出私有格式，再由 `rknn_init` 加载到三核上执行；toolkit 和 runtime 必须版本配对，就是这个"翻译稿"和"朗读员"的约定。

**如果被追问「如果选了 ONNX Runtime 会怎样？」：** 那这个项目就不存在了。ONNX Runtime 在 ARM CPU 上跑 YOLOv8n，x86 端实测 52.59 ms 已经很勉强，板子的 A76 主频和内存带宽都更低，实际会更慢，而且三核 NPU 全程闲置、6 TOPS 一点没用。反过来看，我现在的纯推理是 15.95 ms，差距不是一点半点。所以真正的风险不是"选错运行时"，是"根本没意识到 NPU 需要专用工具链"。

### Q：为什么用 C++ 而不是 Python？

**一句话答案：** 因为这条链路是常驻服务，要的是稳定帧率、线程绑核、和 C 接口的 NPU 运行时；Python 在这三件事上都要多绕一层。但我不反 Python——模型转换、量化和 mAP 评测我全用 Python 做的。

**展开讲：** 具体的三个理由：

- **接口层**：`librknnrt.so` 是纯 C 接口，C++ 里是一次函数调用，Python 里要过 ctypes 或者第三方绑定，每帧多一层解释器开销。我这个链路的单帧预算只有 20 毫秒量级，这种固定开销不能当它是零。
- **并发模型**：我需要三个线程各自绑定一个 NPU 核、共享有界队列、按背压策略丢最旧的帧。这套东西在 C++ 里是 pthread 加条件变量，行为可预期；Python 有 GIL，纯计算线程再多也串行，而我的"三核并行"本质就是要三个真的同时在跑。
- **部署形态**：这是一个跑在 `systemd` 下的守护服务，要开机自启、崩溃自愈、拔网线不死、收到 SIGTERM 优雅释放硬件显存。C++ 给我的是确定的资源生命周期。

**如果被追问「如果选了 Python 会怎样？」：** 开发速度会快很多，尤其刚开始调后处理的时候。但代价是：第一，三核并行这条路基本走不通，GIL 会让 2.21× 变成一个更小的数，甚至退化成串行；第二，每帧的固定开销会吃掉优化收益，我好不容易把推理从 37.19 砍到 15.95，Python 的解释器开销可能又把一部分还回去；第三，长时间跑的服务在内存和句柄上更容易出问题。所以我的真实分工是：**算法验证用 Python，生产链路用 C++**，两边数字能对上是因为我拿同一套后处理逻辑写了 C++ 版并逐位比过。

### Q：为什么用 MPP 硬解而不是 OpenCV 软解？

**一句话答案：** 因为解码这件事 VPU 天生就会，交给它做 p50 只要 1.027 ms，而 `cv::imdecode` 在 CPU 上要 7.761 ms，差 7.6 倍；而且硬解下来的 NV12 可以直接喂给后面的处理，省掉一次格式往返。

**展开讲：** 这 7.6 倍不是我算出来的比值，是同一个 1280×720 MJPEG 帧、200 次测量的中位数对比：MPP 硬解 p50 1.027 ms，OpenCV 软解 7.761 ms，200 帧全部有效，9 张图逐图比 Y-PSNR 在 49.9 到 77.2 dB 之间，说明硬解出来的画质没有肉眼可见损失。

这里有个特别值得讲的坑，因为它证明"硬件加速"不总是赢：我还试过 MPP **硬编** JPEG，想省掉画框之后那段编码，结果实测比软编**慢** 1.07 到 1.88 倍。我不是凭"它慢"就下结论，而是去 `/proc/interrupts` 看硬件核的中断增量确实在涨（`fdba0000.jpege-core` 从 21485 涨到 25038），证明它真的走了硬件、不是悄悄回退到软件，然后才认定这是**负结论**：硬编的优势只有 CPU 占用（8.2% 对 99.7%），在延迟上不划算。

**如果被追问「如果继续用 OpenCV 软解会怎样？」：** 每帧多花大约 6.7 ms 的 CPU 时间，而且这 6.7 ms 和 CSC、letterbox 抢的是同一批核。我这条链路本来就已经被 CSC 压得只剩 17.9 FPS，再叠 6.7 ms 会更难看。更关键的是，软解出来的是 BGR 的 `cv::Mat`，我还要再做一次格式转换才能进 NPU；硬解直接给 NV12，天然贴合后面 CSC 的输入。

> 【费曼讲解】硬解为什么能快 7.6 倍？
> 生活类比：解码 MJPEG 就像把一箱压得非常紧的真空压缩袋一个个拆开。CPU 是一双灵巧但只有两只的手，拆一个要 7.7 毫秒；VPU 是一台专门为此造的拆包机，7.7 毫秒它能拆七八个。
> 不懂的人会怎么错想：以为"OpenCV 是 C++ 写的、已经很快了，硬解顶多快 10%"。于是他会觉得为这点收益引入 MPP 不值得，宁可少一个依赖。
> 一句话戳破：这不是算法快慢的差别，是有没有专用硬件单元替你干这件事的差别——同一个任务，一个跑在通用 ALU 上，一个跑在专用电路上。
> 回到术语：所以 `decode_put_packet` 之后 `decode_get_frame` 拿到的是 NV12，VPU 出的活直接可用；而 `cv::imdecode` 是在 CPU 上走 libjpeg 一遍完整的反 DCT 与反量化，这 7.6 倍就是这么来的。

**如果被追问「硬解的坑是什么？」：** 最大的坑不是性能，是**版本倒挂**。系统预装的 `librockchip_mpp.so` 是 2021-05-20 的，和板上 `mpp_service` 驱动的 ABI 对不上，表现是 `decode_put_packet` 恒返回 -1012（缓冲满），我怎么调参数都是同一个错误码。最后是用 MPP 源码自己编静态库，**一行代码没改**就通了。这件事教给我一条：参数怎么调都报同一个错，先怀疑库和驱动版本，别怀疑参数。

### Q：为什么推流用 TCP 自定义定长帧而不是 RTSP？

**一句话答案：** 因为我要跨机验证的是**结构化的检测结果**，不是视频流；248 字节定长帧（8 字节包头 + 10 个 24 字节 BBox）上位机用 Python 几行就能解，比引一套 RTSP 媒体服务器简单得多、可控得多。

**展开讲：** 先把这个选择说清楚：我不是"用 RTSP 失败所以退回 TCP"，我是**从一开始就没打算用 RTSP**。RTSP 解决的是"把压缩视频流送到播放器"，而我的验收目标是"板子算出的框和分数，能不能被人看到并核对"。前者要 media server、要协商、要处理解码器的兼容性；后者只需要一条可靠的字节流加一个固定布局。

定长帧的另一个好处是**行为可预测**：包长固定 248 字节，收满即解析，不需要在流里找分隔符，也就不存在"粘包要靠扫描边界"的问题。上位机实测连续接收 19.2 FPS，重连瞬间清空陈旧历史帧，之前那个"断连重连后积压 10800+ FPS 爆发"的问题就是这么消掉的。

> 【费曼讲解】TCP 是字节流，为什么"定长"就能解决粘包？
> 生活类比：TCP 像一根水管，你倒进去 5 杯水，对面接到的是一股连续的水，他不知道是几杯、每杯多少。定长帧的做法是"我规定每杯都是 248 毫升"，对面就拿量杯一杯一杯地接——接满一杯立刻倒走。
> 不懂的人会怎么错想：以为 TCP 是消息协议，`send` 一次对面 `recv` 就收到一次。于是他会写"收到什么就解析什么"，然后在网络抖动时随机崩。
> 一句话戳破：TCP 只保证字节顺序和不丢，不保证边界；边界必须由应用层协议自己给。
> 回到术语：所以接收侧要维护一个缓冲，`recv` 到多少都往里塞，凑够 248 字节就切走一帧，剩下的留到下次——这就是"循环收满"。

**如果被追问「那 RTSP 到底做了没有？」：** 没做。只有 MJPEG 硬解，没有 RTSP，也没有 WebRTC。这一点我简历和文档里都写得很明确，不会说成做了。原因就是上面那条：我的验收目标是结构化结果，不是播放器兼容性。

**如果被追问「如果选了 RTSP 会怎样？」：** 会多出一整套跟主线无关的工作量——服务端要有个 RTSP 实现或者 GStreamer 管线，客户端要处理 SDP 协商、时间戳、丢包重传，调试成本全压在"视频为什么卡"这类问题上。而我真正要优化的 49% CPU 回退，一根手指都没碰到。选型的第一原则是**让工具服务于验收目标**，不是让验收目标迁就工具的时髦度。

### Q：为什么板端原生编译而不是交叉编译？

**一句话答案：** 因为板上是 Debian 11、glibc 2.31，而我手边交叉编译环境是 Ubuntu 22.04、glibc 2.35，编出来的二进制拷过去直接因为符号版本对不上起不来；在板子上原生编译反而是最省事的路径。

**展开讲：** 交叉编译本身没毛病，毛病在**两边的 C 运行时不匹配**。glibc 是向前兼容不向后兼容的：在 2.35 上编译、依赖 2.35 的符号版本，拿到只有 2.31 的板子上就是跑不起来。我第一次踩就是"编译成功、传输成功、运行即死"，看起来像玄学，其实是动态链接器在报找不到版本。

板子本身有完整的 gcc 工具链，RK3588 的 aarch64 性能也够，编一个 C++ 项目几十秒的事。所以我的策略是：**一律在板子上原生编译**，用 `cmake .. -DCROSS_COMPILE_RK3588=ON` 走板端构建，默认 Release。同理，连 RKNN 的模型转换我都搬到板子上做了——toolkit2 的 2.x 有 aarch64 的 wheel，venv 在 `/root/rknn_env`，版本 2.3.0，不需要 PC 或 WSL 参与。

**如果被追问「如果坚持交叉编译会怎样？」：** 那你得搭一套和板子完全同版本的 sysroot——把板子的 `/lib`、`/usr/include` 全拷出来做目标根，或者用 Docker 起一个 Debian 11 的构建容器。这条路能走通，但为了省下"几十秒的板端编译"去维护一整套 sysroot，性价比很低。我更愿意把时间花在测数据上。

**如果被追问「那你有没有踩过编译相关的坑？」：** 踩过一个大的：`CMAKE_BUILD_TYPE` **一直是空的**，这意味着整个项目一个多月来编译时**一个 `-O` 都没有**，全程 O0 在跑。改默认 Release 之后，CSC 快了 1.549 倍、生产全链路从 76.928 ms 降到 55.836 ms（−27.4%），二进制从 206,256 字节降到 75,688 字节（−63%）。这件事的教训是："编译成功"不等于"编译正确"，构建脚本必须自检有没有优化标志。

### Q：你这条链路里，到底哪些是真做了、哪些没做？

**一句话答案：** 真做了的是真实摄像头输入、NMS 后处理、MPP 硬解、端到端延迟、DFL 图手术、三核并行、真 mAP 量化、编译优化、端侧 Agent 和巡检守护；没做的是 RGA 硬件 CSC、DMA-BUF 零拷贝、RTSP 与 WebRTC、H.264 与 H.265 硬解、ByteTrack 进 C++ 链路、整机功耗、语音入口。

**展开讲：** 这张表我建议直接背，因为它决定你在面试里是"可信"还是"能吹"。判断原则只有一句：**没做的事可以讲"我为什么决定不做"或"下一步怎么做"，但不能讲成做了。**

| 能力 | 现状 | 面试怎么说 |
|---|---|---|
| 真实摄像头输入 | 已接入 UVC 摄像头，MPP 硬解 MJPEG | 输入是真实摄像头活流，不是仿真 |
| NMS 后处理 | 已实现（conf 0.01 / IoU 0.45，与 PC 侧 eval 同口径） | 可直接讲 |
| MPP / V4L2 硬解 | 已落地生产链路，p50 1.03 ms，7.6 倍于软解 | 是本项目亮点之一 |
| 端到端延迟 | 有：单帧全链路 20.58 ms / 48.6 FPS（bench 口径）；生产链路 55.84 ms / 17.9 FPS（含 CSC） | 必须说清是哪个口径，别混用 |
| RGA 硬件 CSC | 未实现（本板 RGA 2.1.0 不支持 full CSC，颜色偏差 ±13%） | 跨平台框架搭好了，但这块板的 RGA 不支持，硬上颜色会偏，我判断不划算 |
| DMA-BUF 零拷贝 | 未实现（架构设计了，代码没落地） | 做了对照实验证明现在输入侧不是瓶颈（差 0.4%），所以我优先砍 CPU 回退，零拷贝是下一步 |
| RTSP / WebRTC | 未实现（用的是 TCP:9000 自定义 248B 定长帧） | 推流是自己定义的定长帧协议，不是 RTSP |
| H.264 / H.265 硬解 | 未实现（只有 MJPEG 硬解） | 摄像头出的是 MJPEG，所以只做了 MJPEG 硬解 |
| ByteTrack 进 C++ 链路 | 未实现（只在 Python 侧做过仿真） | 跟踪这块还没进 C++ 网关 |
| 整机功耗 | 没测过 | 功耗没测，不敢给数字 |
| 语音入口（ASR） | 未实现（只做了选型方案：sherpa-onnx 加 SenseVoice） | 选型做完了，板端还没实测 RTF |

这张表最大的用处不是背它，是**在被追问时能立刻承认**。我见过太多人在这里翻车：一开始说"我做了零拷贝"，被追问"你的 fd 是怎么传的、`rknn_create_mem_from_fd` 的 size 参数老版本有 bug 你怎么绕的"，两句话就露馅。反过来，我一上来就说"零拷贝我评估过但没落地，因为我做了对照实验发现输入侧只差 0.4%"，对方反而会觉得这个人靠谱。

**如果被追问「那你不觉得这个项目缺的东西太多了吗？」：** 缺是缺，但我缺的每一块都能说出"为什么当时不做"。RGA 是因为这块板的版本不支持 full CSC、硬上颜色偏 ±13%；零拷贝是因为实测输入侧不是瓶颈（原生直喂 37.05 ms 对转换喂 37.19 ms，差 0.4%）；整机功耗是因为我没有功率计，编一个 9.5W 出来是最容易也最致命的造假。我更愿意把"清楚自己做到哪"当成能力的一部分。

## 三、这一章的"记忆锚点"

- **一句话项目定义**：视觉线看、Agent 线判、守护线保命，三条线共用一块只有三核的 NPU。
- **六个数字**：硬解 1.03 ms、推理 15.95 ms、bench 全链路 20.58 ms、生产全链路 55.84 ms、三核聚合 59.3 FPS（2.21×）、量化掉点 1.4%。
- **五个选型的理由各一句**：NPU 只能走 RKNN；服务化要 C++；VPU 天生会解码；结构化结果只需要定长帧；glibc 2.31 决定板端原生编译。
- **边界表是资产不是负债**：RGA、DMA-BUF、RTSP、H.264、ByteTrack、功耗、ASR 七条全部如实说"没做"。
- **两个口径永远分开报**：20.58 ms 是 bench 口径，55.84 ms 是生产口径，混用必死。

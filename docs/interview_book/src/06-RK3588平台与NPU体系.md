# 第 6 章 RK3588 平台与 NPU 体系

> 一句话心智模型：RK3588 不是"一块更快的单片机"，而是一个**围着同一条内存总线插了七八个专用单元的小机房**——CPU 管调度和搬数据，NPU 管矩阵乘，RGA 管 2D 变换，VPU 管编解码，任何一个单元要干活，都得先向内存要数据。

## 一、先建立心智模型

把这块板子想成一个机房：8 个 ARM 核是全能工，什么活都能干，但单科不算顶尖；NPU、RGA、VPU、GPU 是专门工，只会自己那一门手艺，但快一到两个数量级；内存是唯一的仓库，所有工位共用一条通往仓库的通道。**这条共用通道，就是本章所有"为什么没跑满"的答案来源**：三个 NPU 核各只有 49% 负载、三路并行聚合只有 2.21 倍而不是 3 倍、每路延迟从 37.27 ms 涨到 40.8 ms，全部能追到"大家挤同一条内存总线"这一件事上。

```
             RK3588 SoC 内部（EVM3588-B / SOM3588-B）
  ================================================================

   4 x Cortex-A76 大核        4 x Cortex-A55 小核
   通用计算 / 调度             低功耗后台
          |                        |
          +-----------+------------+
                      |
      CPU 侧实际承担：CSC 色彩转换 / letterbox / DFL 解码 / NMS / 协议打包
                      |
          +-----------+------------+
          |   LPDDR5 8GB 内存       |   所有单元共用这一条内存总线
          |   DDR 主频 2112 MHz     |
          +--+--------+--------+---+
             |        |        |
        +----+---+ +--+----+ +-+------+
        |  NPU   | |  RGA  | |  VPU   |
        |  3 个核 | |  2D   | |  视频   |
        |  6 TOPS | |  加速  | |  编解码 |
        +--------+ +-------+ +--------+
          推理主体    缩放      MJPEG 硬解
          15.95 ms   未使用    1.03 ms

        另有 Mali-G610 MP4 GPU（图形），本项目全程未使用
```

**记住这一个比喻**：三个 NPU 核是三个装卸工，内存总线是唯一那条卸货通道。通道没变宽，多叫两个人来只会让每个人多等一会——不会让总吞吐变成三倍。

## 二、问答正文

### Q：一句话说清 RK3588 的架构，你会怎么讲？

**一句话答案：** 4 个 Cortex-A76 大核 + 4 个 Cortex-A55 小核做通用计算，Mali-G610 MP4 GPU 管图形，3 个 NPU 核共 6 TOPS 管神经网络，RGA 管 2D 缩放与格式转换，VPU 管视频编解码，所有单元共享一块 LPDDR5 内存。

**展开讲：** 我不按"参数表"背它，按**一次推理的数据流向**讲：摄像头数据先进内存，CPU 把它整理成模型要的样子（CSC、letterbox），NPU 从内存取数据做卷积，吐出的张量再回内存，CPU 拿去做 DFL 解码和 NMS，最后打包走网络。这条路上 CPU 参与了三次，NPU 只参与中间一次——所以"NPU 快"不等于"整条链路快"。

各单元在我这个项目里的真实归属是这样的：A76/A55 干 CSC、letterbox、DFL 解码、NMS、TCP 打包，这是第 7 章流水线里所有 CPU 段；NPU 只干卷积，实测纯推理 15.95 ms；VPU 只用了 MJPEG 硬解，p50 1.03 ms；RGA 我评估过但没落地；GPU 全程空闲。**能说清"哪个单元在干哪一段"，比能背出 TOPS 有用得多。**

**如果被追问「GPU 你用了吗？」：** 没用，Mali-G610 MP4 在我这条链路里一直是闲着的。我做的事是检测和推流，没有渲染需求，画面画框是 OpenCV 在 CPU 上画完直接 JPEG 编码。硬要说的话，GPU 是一个我明确知道在那里、但这版没用上的算力。

**如果被追问「那 RGA 呢？」：** 也没用上。RGA 是 2D 加速器，本职工作就是缩放和格式转换，正好是我 CPU 侧最重的那一段。我评估了，判它不划算，理由在第 7 章讲 letterbox 和 CSC 时会展开——这里只强调一句：**"有硬件单元"和"这个硬件单元我能用对"是两件事。**

### Q：3 核 NPU 共 6 TOPS，为什么你的三核并行只有 2.21 倍？

**一句话答案：** 因为加核只解决"算力不够"，解决不了"喂不饱"。实测三核各只跑到 49% 负载，NPU 有一半时间在等 CPU 喂数据、等内存返回。

**展开讲：** 先把两组数字摆清楚，这是同一个模型的两种用法：

- 单个 context 绑三核（`RKNN_NPU_CORE_0_1_2`）：**35.97 ms**，只比单核 37.19 ms 快 **3.3%**；`RKNN_NPU_CORE_AUTO` 是 **37.27 ms**，和单核没区别。
- 3 个独立 context 各绑一个核、3 线程各跑一个：**40.8 ms/路，聚合 59.3 FPS，2.21 倍**。墙钟 5058 ms 跑完 300 帧，三路各自 4081~4089 ms，**差 8 ms，负载几乎是完美均衡的**。

所以 2.21 倍不是"调度没做好"，而是**已经撞到另一堵墙**。证据就是三核负载：Core0 49% / Core1 49% / Core2 50%。三个核都有一半时间是闲的，说明瓶颈不在核里，在核外面。两个具体原因：一是三条路抢同一条内存总线，每路延迟从 37.27 ms 涨到 40.8 ms，**单路反而慢了 9%**；二是前处理、后处理这些段在 CPU 上是串行的，NPU 算完要等 CPU 解码完才能进下一帧。

并行效率 = 实测聚合吞吐 ÷ 理论上限 = 59.3 ÷ (3 × 26.9) = **73.5%**（换成 2.21 ÷ 3 是 73.7%，差 0.2 个百分点只是单核基线取 26.9 还是 26.8 FPS 的口径差异）。对外我就说"约 73.5%"。

> 【费曼讲解】为什么三个核不能当三个用
>
> ① 生活类比：一个仓库有三个装卸工，但只有一条卸货通道。货少的时候三个工人能轮流干，货多的时候三个人全挤在通道口，谁也快不了。
> ② 不懂的人会怎么错想：TOPS 是加法，2 + 2 + 2 = 6，那我挂三个核就该快三倍；没到三倍，一定是我代码没写对。
> ③ 一句话戳破：**算力可以叠加，喂数据的通道不能叠加。** 你测出来的 49% 负载就是三个工人在等通道的工时。
> ④ 回到术语：这叫内存带宽与流水线串行段共同限制的加速比上限，Amdahl 定律描述的就是"串行部分决定天花板"这件事；我这里的串行部分不是 NPU 计算，而是 CPU 侧的前后处理和数据搬运。

**如果被追问「那你还想怎么往上提？」：** 不是继续调 NPU。要么从内存下手（减少搬运、提高访存效率），要么把 CPU 侧串行段做掉（比如 CSC 那 33.58 ms）。再调 `core_mask` 已经没有空间了，三种绑法定量测过，最快的 35.97 ms。

**如果被追问「73.5% 这个数你怎么算的？」：** 拿实测聚合吞吐除以"三倍单核吞吐"这个理论上限。这个口径的诚实之处在于：理论上限本身也达不到，因为它假设了三路之间零干扰，而实测每路都慢了 9%。

### Q：`rknn_set_core_mask()` 你绑的到底是什么？单 context 挂三核为什么没用？

**一句话答案：** 它绑的是"**一个 context 允许用哪几个核**"，不是"把一帧拆给三个核并行"。单帧内部的计算有数据依赖、天生串行，三核只能分段接力，中间还要同步，同步开销把并行收益吃光了。

**展开讲：** 先回答"默认是什么行为"。**不调 `core_mask` 的时候，一个 context 就是一个核在算**——证据是三组数几乎重合：只绑 Core0 是 37.19 ms、只绑 Core1 是 37.32 ms、只绑 Core2 是 37.36 ms，而"交给运行时自己安排"的 `AUTO` 是 37.27 ms。如果默认就能用上三核，`AUTO` 不可能和单核落在同一个数上。

再看 API 语义。`rknn_set_core_mask(ctx, RKNN_NPU_CORE_0)` / `_1` / `_2` / `_0_1_2` / `AUTO`，第一个参数是 context，也就是说**核绑定是"每个 context 一份"的策略，不是一个全局开关**。由此只有两条路：

- 一个 context 挂三个核：三颗核服务同一个模型实例、同一张图。实测 35.97 ms，比单核快 3.3%。
- 三个 context 各挂一个核：三颗核服务三个模型实例、三张不同的图。实测聚合 59.3 FPS，2.21 倍。

**只有第二条路是真并行**，因为并行需要"三条独立的活"。第一条路里只有一个活，三颗核是在抢同一件事，抢的过程还要同步状态。

> 【费曼讲解】context 到底是个什么东西
>
> ① 生活类比：context 像一张**独立的工作台**——台面上摆着一份模型（权重已经在 NPU 侧就位）、自己的输入输出缓冲、以及"我允许用哪几号核"这张工牌。三个 context 就是三张工作台，三个人各站一张，互不干扰。
> ② 不懂的人会怎么错想：context 就是"一个句柄"，多开几个没有成本，那我在同一个线程里轮流用三个 context 不就并行了？
> ③ 一句话戳破：**并行不是"多开几个对象"，而是"同一时刻真的有多个线程各自在推一张图"**。一个线程轮流调三个 context，还是串行的，只是多花了上下文切换的钱。
> ④ 回到术语：所以我的结构是 3 个工作线程，每个线程持有自己的 context 和自己的核绑定，从同一个任务队列抢图；这是"线程级并行 + 核级隔离"，不是在单线程里玩 context 花活。

**如果被追问「三个 context 是不是模型加载了三份，内存翻三倍？」：** 我这里三个 context 用的是同一份模型二进制数据，但每个 context 有自己的运行时实例和输入输出缓冲。所以内存确实有额外开销，但远不是三倍；4.34 MB 的 INT8 模型，这个代价我接受。真正占内存的是别的东西（比如大模型那 2.8 GB），不是这几个 context。

**如果被追问「AUTO 是什么行为？」：** 实测 `RKNN_NPU_CORE_AUTO` 是 37.27 ms，和单核 37.19 ms 基本一致——所以"交给运行时自动调度"并不会帮你把三核用起来，想要三核必须自己起三条独立的活。

### Q：`/dev/rknpu` 不存在，是不是驱动没装？

**一句话答案：** 不是。新版 NPU 驱动走的是 DRM 框架，设备节点在 `/dev/dri/renderD129`，`/dev/rknpu` 本来就不该存在。

**展开讲：** 这个坑我踩得很典型：上手第一件事是 `ls /dev/rknpu`，什么都看不到，第一反应是"驱动没装，是不是要重刷固件"。实际上判断驱动在不在，看的是这三处：

- `cat /sys/kernel/debug/rknpu/version` 能读到 **0.9.2**，说明 rknpu 驱动已经加载并且在正常工作。
- `cat /sys/class/devfreq/fdab0000.npu/cur_freq` 能读到 **1.0 GHz**，说明 NPU 有独立的调频节点，硬件是活的。
- `ls /dev/dri/` 能看到 **renderD129**，这才是用户态访问 NPU 的入口。

三条都对上，就说明驱动齐全；而 `ls /dev/rknpu` 失败完全说明不了任何问题。**判"设备在不在"要认这个内核版本真正的接口，不能认教程里那个设备名。**

**如果被追问「为什么会有这个误解？」：** 因为网上大量 RK3588 的检查脚本、开机自检清单里都写着"看到 `/dev/rknpu` 才算驱动正常"。这类清单是从更早的板子抄下来的，直接套到新驱动版本上就会误判。我自己的开机自检脚本也中过这个招，后来改成同时判 `/sys/kernel/debug/rknpu/version` 和 `/dev/dri/renderD129` 两处。

**如果被追问「那你要重刷固件吗？」：** 不需要。板子系统在 eMMC 里，是出厂镜像，一直好好的；`.img` 是 RKFW 整包，也不能直接往 TF 卡里拷。我最后什么都没刷，问题出在我的判断方法，不在板子。

### Q：NPU 驱动 v0.9.2 和运行时 API 2.3.0 是两个东西吗？

**一句话答案：** 是两层，而且还有第三层。驱动在内核里（v0.9.2），用户态运行时是 `librknnrt.so`（2.3.0），模型转换工具是 rknn-toolkit2（2.3.0）。**工具链和运行时必须对得上**，驱动则相对独立。

**展开讲：** 这三层各自管一件事：toolkit 负责把 ONNX 转成 `.rknn` 并做量化；runtime 负责在板子上加载 `.rknn`、分配内存、提交推理；驱动负责真正把任务塞进 NPU 硬件并调频。我踩过的第一个真坑就在"toolkit 与 runtime 版本倒挂"：

- 一开始用 toolkit **1.6.0** 转模型，板端 runtime 还是 **1.5.2**。官方不支持这种组合，表现是模型加载/推理异常。
- 先把板端 `librknnrt.so` 升到 **1.6.0**，旧模型基线复测 **37.07 ms**，没有回退。
- 后来整套升到 **2.3.0**（`/root/rknn_env` 里的 toolkit 也是 2.3.0），实测在 NPU 驱动仍是 **0.9.2** 的板子上可用。

所以驱动 0.9.2 配 runtime 2.3.0 这个组合是**实测能跑**的，不是靠猜。这也说明：驱动和用户态运行时之间有向后兼容的接口层，而 toolkit 与 runtime 之间反而卡得死——因为 `.rknn` 是文件格式，格式改了就谁也认不出谁。

**如果被追问「版本不对会怎么表现？」：** 最典型的是模型加载阶段就失败，或者在推理时给出明显错误的输出。我的经验是：**报错发生在哪一层，就从哪一层往上查**。加载 `.rknn` 就失败，先怀疑 toolkit 和 runtime 不匹配；加载成功但推理崩，看驱动；推理成功但结果不对，看量化和校准集（那是第 9 章的事）。

### Q：一个 YOLOv8 模型从 PyTorch 到能在板子上跑，要经过哪几步？

**一句话答案：** PyTorch 导出 ONNX → rknn-toolkit2 里做 config / load_onnx / build / export_rknn 得到 `.rknn` → 板端用 `librknnrt` 加载并推理。

**展开讲：** 转换侧四步在我这里是这样的：

```python
rknn.config(mean_values=..., std_values=..., target_platform='rk3588')
rknn.load_onnx(model='yolov8n.onnx')
rknn.build(do_quantization=True, dataset='dataset.txt')
rknn.export_rknn('yolov8n_rk3588_i8.rknn')
```

然后板端是 `rknn_init` → 设置输入 → `rknn_run` → 取输出。我这边还多了半步：在导 ONNX 之后、量化之前做了一次**图手术**（把 DFL 头从图里砍掉），但那是第 8 章的主题，这里只需要知道它发生在"ONNX 之后、build 之前"。

三个和"在板子上转"直接相关的经验：第一，2.x 的 toolkit2 在 `packages/arm64/` 下有 aarch64 的 wheel，板子 Debian 11 自带 Python **3.9.2** 正好是 cp39，所以整个转换不需要 PC、不需要 WSL；第二，`dataset.txt` 里的校准图必须写**绝对路径**，相对路径会被按清单所在目录再拼一次，拼成不存在的路径；第三，依赖要卡死版本，numpy 1.26.4 / onnx 1.14.1 / protobuf 3.20.3，opencv 那边必须钉 `opencv-python-headless==4.9.0.80`，5.x 会和 numpy 1.26 打架。

**如果被追问「转换要多久？」：** 约 **3.5 分钟**（161 层 × 3 轮量化，A76 上单线程）。这个数字的意义是：**它慢到值得离开主循环，又快到不需要搭 CI**。

**如果被追问「板子上装 toolkit 踩了哪些坑？」：** 挑三个有代表性的：① 板子没有 pip（Debian 把 ensurepip 剥了），得手动下 pip 的 wheel 解压到 site-packages；② `rknn.api` 顶层会 import torch，而 aarch64 的 torch 是 1 GB 级，我用一个纯 numpy 的 torch stub 顶上，反正 toolkit 只用它生成索引常量；③ `quantized_iteration` 是 1.x 的参数，2.x 传了直接抛 ValueError。

**如果被追问「为什么模型要先转成 `.rknn`，不能直接跑 ONNX？」：** 因为 ONNX 是算子图描述，不包含目标硬件怎么切分、怎么量化、怎么排布内存。`.rknn` 是编译产物，NPU 能直接执行的形态。这跟你不能把 C 源码直接扔给 CPU 跑、得先编译是一个道理。

### Q：为什么你一律在板子上原生编译，不走交叉编译？

**一句话答案：** 因为 PC 和板子的 glibc 版本不一样——Ubuntu 22 是 **glibc 2.35**，板子的 Debian 11 是 **2.31**。交叉编译出来的二进制一上去就报 `GLIBC_2.35 not found`。

**展开讲：** 这不是"我懒得配工具链"，是**动态链接的必然结果**。你在 PC 上编译，链接器把"需要 2.35 版本的这个符号"写进了二进制的动态符号表；程序跑到板子上，板子的 libc 是 2.31，找不到那个符号版本，运行时直接拒绝启动。功能上代码一行没错，错的是"在哪编"。

我的选择是：板子上本来就装了 g++ 10.2.1 / make / cmake，那就**直接在板子上编**，从根上消掉这个风险。项目里 CMake 的构建目录叫 `build_native`，名字就是在提醒这件事。

> 【费曼讲解】glibc 版本不匹配为什么是运行时才炸
>
> ① 生活类比：你写了一份借书单，上面写着"必须按 2022 年版的目录规则查"；到图书馆发现人家用的是 2021 年版目录，规则里没有这一条，管理员直接不给你办。
> ② 不懂的人会怎么错想：编译都过了，说明代码语法、类型、头文件全对，那跑起来应该没问题。
> ③ 一句话戳破：**编译只保证"我在我的环境里能连上"，不保证"你的环境里有同样的东西"。**
> ④ 回到术语：这是动态链接的符号版本机制。可执行文件里记的是"符号名 + 需要的版本"，运行期由动态链接器去匹配；版本不够就是加载期错误，和你的源码质量无关。

**如果被追问「交叉编译不是更快、更专业吗？」：** 更快是真的，但快的那点时间不够赔一次排障。我的项目规模不大，板端编译的等待成本远小于"报一个 GLIBC 错、查半天才确认不是自己代码的问题"的成本。这是我基于自己工程量的判断，不是通用结论——如果项目大到板端编译要几十分钟，那我会老老实实去配一套带 sysroot 的交叉工具链。

**如果被追问「静态链接不行吗？」：** 理论上可以绕开 glibc 版本问题，但会让二进制变大，而且第三方库（MPP、OpenCV、librknnrt）往往是动态库，你没法全静态。我没走这条路，因为板端原生编译已经够用了。

### Q：这块板子的规格，你是抄参数表还是自己在板子上核过？

**一句话答案：** 关键项全在板子上核过：内存 **7.5Gi** 可用、eMMC **57.6G** 可用、Debian 11 / kernel **5.10.110**、NPU 驱动 0.9.2 + 运行时 2.3.0、NPU 三核共 **6 TOPS**、NPU 主频 **1.0 GHz**、DDR 主频 **2112 MHz**、待机 SoC 37.9 度 / NPU 37.0 度。

**展开讲：** 我养成一个习惯：凡是写进文档的规格，都要能在板子上一条命令读出来。原因很简单——**参数表是"标称"，实测是"我这块板"**，两者经常不是一回事：

- 标称 8GB 内存，`free -h` 看是 **7.5Gi** 可用，差的那部分是系统和预留。
- 标称 64GB eMMC，`df -h` 看是 **57.6G** 可用。
- 板子是 EVM3588-B（英码科技 EMA），核心板 SOM3588-B，**8GB LPDDR5**，Debian 11 (bullseye)，kernel **5.10.110**，系统装在 eMMC 里，不需要刷机。
- NPU 的 3 个核每个 2.0 TOPS INT8、三核共 **6.0 TOPS**，这是**标称峰值，我不单独测核**——我能测的是整个模型跑多快；主频 1.0 GHz 可以在 devfreq 节点上读到当前值。

这些"7.5Gi / 57.6G"的零头在面试里反而是加分项：它证明你真的登过板子，而不是把官网参数截图背下来。

**如果被追问「6 TOPS 你测过吗？」：** 没有，6 TOPS 是标称峰值，我没法直接测"这块板有 6 TOPS"。我能测的是"我这个模型在这块板上跑多快"——纯推理 15.95 ms。**TOPS 是峰值算力，不是我的应用吞吐**，这两件事中间隔着一整个软件栈和一条内存总线。

**如果被追问「为什么强调实测？」：** 因为报错的规格最容易被追问穿。比如我把"8GB"说成可用内存，面试官问一句"那 `free` 里你看到多少"，我就露馅了。

### Q：RGA 和 VPU 在你项目里到底用上了没有？

**一句话答案：** VPU 用上了，只用了 MJPEG 硬解（p50 1.03 ms）。RGA 没用上——我评估过，本板 RGA 用户态库是 **2.1.0**，**不支持 full CSC**，实测颜色偏差约 ±13%，判断不划算，主动放弃。

**展开讲：** 这两个要分开答，混着答就成了"我啥都做了"的吹牛。

VPU 是实打实上了生产链路的：摄像头出的是 MJPEG，我用 MPP 走 VPU 硬解，**p50 1.027 ms**，对比 OpenCV 软解 `cv::imdecode` 的 **7.761 ms**，**7.6 倍**。这条是流水线里的第二段，第 7 章会讲它踩的 -1012 坑。

RGA 是**评估过、判断不做**：它的本职就是格式转换和缩放，正好对着我最重的 CPU 段。我实测过零拷贝的 NV12 转 RGBA 加缩放，能做到 **2.03 ms**，比 CPU 的 33.58 ms 快一个数量级，看起来非常香。但本板 RGA 的用户态库 2.1.0 **不支持 full CSC**，颜色偏差约 ±13% 且我没有量化到底偏多少。**检测模型吃的是颜色，颜色系统性偏移 13% 我等于没验证过这个链路**，所以我不敢往生产链路上放。

**如果被追问「那你 CSC 现在怎么办？」：** 我自己写 CPU 定点 BT.601 full-range 转换，Release 之后 **33.58 ms**，仍然占全链路 **60%**，它是当前第一瓶颈。这条我不会说成"已解决"，只能说"是目前的最优解"。细节在第 7 章。

**如果被追问「RGA 那个 2.03 ms 是实测吗？」：** 是实测，但是**离线的、实验性的、没接进生产链路**的实测，而且带着"颜色有系统性偏差"这个限定。这三个限定必须一起说，否则就成了我做过 RGA 硬件 CSC。

## 三、这一章的"记忆锚点"

- **一条内存总线**：三核各 49% 负载、2.21 倍、每路慢 9%，全都可以追到"挤同一条内存总线"。
- **三种绑法三个数**：单核 37.19 ms、单 context 三核 35.97 ms（只快 3.3%）、3 context 三核 59.3 FPS（2.21 倍）。**只有 3 条独立的活才是真并行。**
- **`/dev/rknpu` 不存在是正常的**，入口是 `/dev/dri/renderD129`，驱动在不在看 `/sys/kernel/debug/rknpu/version`（读到 0.9.2）。
- **三层版本**：toolkit 2.3.0 / runtime 2.3.0 / 驱动 0.9.2，其中 toolkit 与 runtime 必须配对。
- **板端原生编译**：Ubuntu 22 的 glibc 2.35 对板子 Debian 11 的 2.31，交叉编译会 `GLIBC_2.35 not found`。
- **标称 vs 实测**：8GB 对应 7.5Gi 可用、64GB 对应 57.6G 可用、6 TOPS 是峰值不是我的吞吐（我的吞吐是 15.95 ms 一帧）。
- **用上了什么、没用什么**：VPU 只做 MJPEG 硬解（1.03 ms）；RGA 评估过但没用（2.1.0 不支持 full CSC，±13%）；GPU 全程空闲。

# 第 12 章 巡检守护系统与可靠性

> 一句话心智模型：巡检不是一个"功能"，而是一个**必须能自己活下去的进程**——主业务崩了它还得醒着，主业务跑着它不许添乱，而且它必须拿得出可量化的证据证明"我真的在工作"。

## 一、先建立心智模型

先别急着看代码，先把"谁跟谁是分开的"想清楚。这块板子上其实跑着**三个故障域**：7×24 的推流网关（`edgevision.service`）、巡检快层守护（`edgevision_patrol_daemon`）、以及按需唤醒的慢层 LLM。三者之间只通过**文件和 TCP 只读探测**发生关系，谁也不许 stop 谁、谁也不许改谁的内存。这就是整个可靠性设计的骨架。

```
                    ┌───────────────────────────────────────────┐
                    │        RK3588 (EVM3588-B, 板上)            │
                    │                                            │
  UVC 摄像头 ──────▶│  edgevision.service (7×24, 禁止 stop)       │
  /dev/video81      │  letterbox → NPU 3 核推理 → TCP :9000       │
                    │             ▲                              │
                    │             │ TCP 即连即收一帧即断（只读探测） │
  温度 zone0 ◀──────│  ┌──────────┴──────────────────┐            │
  NPU 三核负载 ◀────│  │ edgevision_patrol_daemon    │            │
  板载 LED work ◀───│  │ 〔快层：5s 周期规则反射〕      │            │
                    │  │ 采样 → 状态机 + 迟滞 → LED    │            │
                    │  └──────┬───────────────┬──────┘            │
                    │         │               │                   │
                    │  patrol_events.log   llm_pending.jsonl      │
                    │  (黑匣子，>5MB 轮转)  (慢层单向队列)          │
                    └─────────────────┬───────────────────────────┘
                                      │ tail -F（只读，单向）
                    ┌─────────────────▼───────────────────────────┐
                    │ 慢层 LLM 研判（RKLLM + Qwen 端侧模型）        │
                    │ 事件去重降噪 / 语义研判 / 生成巡检简报          │
                    └─────────────────────────────────────────────┘
```

**记住这一个比喻**：快层是楼道里的**烟感器**——不通网、不需要大脑，冒烟就响；慢层是你事后打电话给物业，它能跟你解释"几楼、烟大不大、要不要疏散"。烟感器**绝不会等物业接电话才响**。这个比喻能扛住这一章 80% 的追问。

## 二、问答正文

### Q：巡检为什么非要单独起一个守护进程？直接塞进推流主进程里不是更省事？

**一句话答案：** 因为它们是两个**故障域**——主进程崩了巡检还得活着报警，巡检崩了不能拖垮推理；而且巡检是伴生功能，没资格去抢主业的 NPU 和帧率。

**展开讲：** 把巡检写进 `edgevision.service` 里最省事，但你会同时失去三件事。第一，**故障隔离**：主进程一旦段错误或者被 OOM 干掉，巡检跟着一起死，恰好是最需要它报警的时候它不在。第二，**资源隔离**：推理主进程占着三核 NPU 和摄像头设备节点，巡检如果共享同一个进程，任何一次采样阻塞（比如 TCP 探测对面不回包）都会拖住推流线程。第三，**可单独验证**：独立进程才能单独 `kill -TERM` 测优雅退出、单独起第二个实例测单实例锁、单独压阈值测状态翻转。

所以我的边界定得很硬：快层**只链 std 和 pthread**，连 `rknn_api` 都不链，更不加载任何模型。它和 `edgevision.service` 的关系只有两种——读 `/sys` 里的温度、并通过 TCP 连一下 9000 端口收一帧就断。设计文档里写死了一条铁律：**这个守护永远不会 stop/restart `edgevision.service`**，9000 端口只做"连上→收一帧 248B→断开"的只读探测，建联瞬间网关本来就推一帧，收满即断，和上位机的行为完全一致，对网关零压力。

**如果被追问「那你怎么保证它自己不会把主业务搞挂？」：** 三条约束。一是只读：除了 LED 的 `/sys` 节点，它不写任何系统状态。二是超时：连接和收帧各 300ms，单周期最多损失 0.6s，不会无限期卡住。三是优先级：它是伴生功能，采样失败就降级（记 `vision_reason`），绝不做重试风暴。

**如果被追问「主进程真的挂了，巡检报警有用吗？」：** 有用，而且这正是分层的价值。巡检探测 9000 端口拿不到帧，`vision` 会变成 `offline` 并把原因记成 `gateway_refused`（端口拒绝连接，说明服务根本没起来）或 `connect_timeout`（连不上，说明可能卡住了）——这两种原因**语义不同**，运维可以据此判断是"没启动"还是"假死"。这就是"能报警"和"能报出有用的警"的区别。

### Q：快慢双系统到底怎么分的？快层为什么坚决不用 LLM？

**一句话答案：** 快层回答"现在要不要闪警灯"（毫秒级、规则、确定性），慢层回答"刚才发生了什么、值不值得上报、下一步怎么办"（秒级、语义、可以慢）。

**展开讲：** 分层不是按代码量分的，是按**必须给出答案的时限**分的。

| 层 | 进程 | 触发 | 延迟量级 | 职责 | 依赖 |
|---|---|---|---|---|---|
| 快层 | `edgevision_patrol_daemon` | 5s 周期 | 毫秒级规则判定 | 采样、迟滞状态机、LED 反射、事件落盘 | 仅 std + pthread，零模型 |
| 慢层 | Agent（RKLLM + Qwen 端侧模型） | 事件驱动（消费队列） | 秒级到十秒级 | 语义研判、降噪合并、巡检简报、复杂决策 | NPU + 端侧大模型 |

快层不用 LLM 有三条硬理由，每一条都能单独站住。

第一是**NPU 竞争**。RK3588 那三颗 NPU 核已经被 9000 推流网关 7×24 占着做 YOLOv8 推理了。快层如果再加载一个数 GB 权重的 LLM 和常驻推理上下文，就是跟主业务抢时间片，直接威胁推流帧率。巡检是伴生功能，没资格影响主业。

第二是**时延**。LLM 单次推理几百 ms 到秒级，而且慢层调度不完全可控；而"温度超限 → 闪灯"是毫秒级就该给的反射动作。用 `if (temp > 75)` 这种确定性规则，判定成本约等于 0，再配 300ms 的 IO 超时框住上界，实时性天然满足。

第三是**可靠性**。LLM 输出不确定，可能幻觉、可能拒绝、可能超时；而报警是**安全行为**，必须可预测、可复现、可回归测试。规则状态机的行为 100% 确定，出了问题可以二分定位；LLM 断供或卡死的时候，快层必须照常工作——所以快层零模型依赖，跟主业务故障域隔离。

**如果被追问「那慢层不就没什么用了？」：** 恰恰相反，慢层干的是快层干不了的事。快层只能说"温度超过 75 度"，慢层能说"过去十分钟 SOC 在 68 到 77 度之间反复抖动，同时帧率掉了 20%，怀疑是散热风道被挡"。降噪合并、跨事件关联、人话汇报，这些必须靠语义理解。

**如果被追问「这个界面是不是硬编码的分层？」：** 有前提。分层成立的前提是**判定逻辑能被写成规则**。如果告警条件是"画面里这个人像不像在翻越围栏"，那就是慢层的活，快层只负责把事件推过去。判断标准很简单：能写成 `if` 的留在快层，写不成 `if` 的送到慢层。

### Q：快层和慢层之间怎么交接？为什么用文件而不是管道？

**一句话答案：** 快层是 `llm_pending.jsonl` 的**唯一写者**（`O_APPEND` 追加），慢层 `tail -F` 只读消费、自己维护 offset；用文件是因为慢层可能几分钟才醒一次，管道要求两端同时在线，慢层一离线事件就丢了。

**展开讲：** 交接契约被冻结成四个字段：`{"ts","type","summary","raw"}`。`type` 只有三种取值——`PERSON_ALERT`、`THERMAL_ALERT`、`RECOVER`。`summary` 是一句人话（慢层可以直接朗读或上报），`raw` 是触发当周期的完整原始采样：`vision`、`vision_reason`、`temp_c`、`frame_id`、`bbox_count`、`person_seen`、`best_person_score`、`npu_core_load`，再加上本次动作与结果 `action` / `led_result`，以及状态迁移信息 `prev_state` / `new_state`（恢复事件里是 `recovered` 数组）。`raw` 的约定是**增量兼容**：以后加字段不删字段，慢层按"取所需"解析。

三条刻意的约束保证了它不会变成并发事故现场。

- **单向**：快层是唯一写者，慢层不回写、不删除、不改名，消费进度（offset 或行号）由慢层自己维护，彻底避免双写竞争。
- **低频**：只在状态翻转时追加，稳态一行都不写，所以不存在文件涨爆的问题。
- **可降级**：慢层离线时事件就在文件里堆着，回来了继续消费，快层不因此阻塞。

**如果被追问「文件当队列不怕丢事件吗？」：** 反问一句"丢的前提是什么"。丢事件的前提是生产者写了但没落盘——而这里每次翻转都是一次 `O_APPEND` 追加写，写完就返回，进程崩了最坏是这一行没写全，下一周期状态再翻转会补一条。真正的无界风险（比如生产者每秒写几千条、消费者跟不上）在这个场景里不存在，因为事件本身一天也就几十条。

**如果被追问「为什么不用管道或者共享内存？」：** 管道像打电话，必须两头同时在线，慢层在跑 LLM 推理的那十几秒里管道满了就会把快层阻塞——**让慢层能反过来卡住安全层，这是绝对不能接受的设计**。共享内存没有持久性，重启就没了。文件是这里唯一同时满足"持久、单向、不阻塞、可回溯"的通道。

> 【费曼讲解】**为什么只在状态翻转时记日志，而不是每个周期记一条？**
> 生活类比：家里的烟感器不是"每 5 秒播报一次当前空气成分"，它是**从安静变成响的那一刻**才叫。你家楼下便利店也不会每来一个客人就广播一次"又来人了"。
> 不懂的人会怎么错想：会觉得"日志越详细越好，我每 5 秒记一条温度，事后好分析"。听起来很负责任，实际是把系统做成筛子。
> 一句话戳破：**5 秒一条，一天就是 17280 条**——真正有价值的信息（"什么时候越的限"）会被埋在 17 万条"今天也很正常"里，你自己都不会再去看它，慢层读进去也全是噪声。
> 回到术语：这叫**事件驱动日志**，只在状态机的边沿（edge）采样而不是在每个时钟周期采样。工程上的判据是——**日志的价值密度比它的绝对数量重要**，翻转日志的每一条都是可行动的。

### Q：状态机怎么设计？阈值和"防抖"具体怎么定的？

**一句话答案：** NORMAL / PERSON_ALERT / THERMAL_ALERT 三态，用**双阈值迟滞 + 连续 N 周期确认**防抖：进告警容易（宁可误报不可漏报），出告警难（避免来回抖）。

**展开讲：** 规则长这样：

```
              person 连续 2 周期 score ≥ 0.5
        ┌──────────────────────────────────────┐
        │                                      ▼
   ┌──────────┐    连续 5 周期无 person   ┌────────────────┐
   │  NORMAL  │◀──────────────────────────│  PERSON_ALERT  │ (LED = alarm)
   │(heartbeat)│                           └────────────────┘
   └──────────┘                                    ▲
        ▲                                          │ zone0 > 75.0°C（瞬时触发）
        │    zone0 < 70.0°C 连续 3 周期             │
        └──────────────────────────────────────────┴────────────────┐
                                                   │ THERMAL_ALERT │ (LED = alarm)
                                                   └───────────────┘
```

PERSON 和 THERMAL 是**两个独立的子状态**，任一激活就 LED = alarm，两个都恢复才回 heartbeat。对外展示的整体状态取 `PERSON_ALERT > THERMAL_ALERT > NORMAL` 的最高优先级。

参数表（这张表是我被追问时最常被要求展开的）：

| 参数 | 值 | 含义 | 为什么这么定 |
|---|---|---|---|
| 采样周期 | 5s（1~3600 可调） | 多久采一次 | 与巡检节奏对齐；300ms 视觉超时占周期不到 6% |
| 置信度门槛 | 0.5 | person 触发线 | 与网关检测阈值同口径，先过滤边缘误检 |
| 进入次数 | 2 | 连续检出 2 次才告警 | 单帧误检不闪灯；10 秒内确认，人眼可接受 |
| 恢复次数 | 5 | 连续无 person 5 次才恢复 | 恢复比进入慢（2:5），防止人来回走动导致灯闪 |
| 温度进 | 75.0°C | 触发阈值（瞬时） | SOC 高温警戒线，宁可误报不可漏报 |
| 温度出 | 70.0°C | 恢复阈值 | **迟滞带 5°C**，75 上下抖动不会反复翻状态 |
| 温度恢复次数 | 3 | 连续 3 周期低于 70°C | 15 秒确认真正回落，排除单点读数毛刺 |

注意两个方向是**不对称**的：进入条件与退出条件不相等（温度 75 进 / 70 出，person 2 次进 / 5 次出），而且退出还要"连续 N 周期确认"。两个不对称叠在一起，单点毛刺就永远翻不了状态。

**如果被追问「为什么 PERSON 是瞬时进，THERMAL 却要连续 2 次？」：** 注意看表——PERSON 的"瞬时"其实是"连续 2 周期"，THERMAL 的进入才是真瞬时。理由不同：人的置信度是模型输出，天然有抖动，所以要连续确认；温度传感器读数是硬件的，单点毛刺的概率低，但高温的代价（降频甚至损坏）太高，所以入口放宽、出口收紧。

**如果被追问「这个阈值 75/70 是怎么定的？」：** 来自 SOC 的正常工作区间常识，不是拍脑袋。这块板的常态在 30~45°C 之间跑，75°C 是警戒线。顺手说一句踩过的坑：我把这条常识写进 Agent 的 sys_prompt 了，因为模型不知道"这块板子多少度才算热"，曾经把人**为压低到 20°C 的演示阈值**当成真实红线，把正常温度判成过热。

> 【费曼讲解】**什么是"迟滞"（hysteresis），为什么阈值不能只有一个数？**
> 生活类比：热水器的温控。如果要 60 度就加热、到 60 度就停，那它在 59.9 和 60.1 之间会一秒开关十次，继电器很快就烧了。真实做法是"低于 58 开始烧，高于 62 才停"——中间那 4 度就是迟滞带。
> 不懂的人会怎么错想：会觉得"我设了 75 度阈值，那超过 75 就报警、低于 75 就恢复，逻辑很清晰"。这是把稳态问题当成了瞬时问题。
> 一句话戳破：**任何真实传感器的读数都在阈值附近抖动，只有一个阈值的状态机会在边界上疯狂翻转，让你分不清是"真的反复越限"还是"读数在抖"。**
> 回到术语：迟滞 = 进入阈值与退出阈值刻意拉开一个带宽；再叠加"连续 N 周期确认"，就能保证"状态翻转"这个动作永远对应真实世界的变化，而不是噪声。

### Q：采样失败了怎么办？读不到温度、连不上视觉，状态机会不会乱？

**一句话答案：** 采样失败时**冻结对应的计数器，不翻转状态**——数据缺失不等于"没有人员"，温度读不到时如果已经在告警就保持告警（fail-safe）。

**展开讲：** 这是状态机里最容易写错、也最容易被面试官抓住的地方。新手写法通常是"没读到 person 就当作没 person"，于是视觉服务一停，PERSON_ALERT 就被"恢复"成了 NORMAL——**报警器自己把报警关掉了，因为它看不见了**。这是最坏的失效模式。

我的处理是：视觉探测结果里带一个 `vision_reason` 字段，取值 `online` / `gateway_refused` / `connect_timeout` / `connect_fail` / `recv_short`。只有 `online` 且成功解析出帧的时候，person 计数器才参与判定；其余情况一律冻结计数器，并在事件日志里如实记下原因。温度同理：`/sys/class/thermal/thermal_zone0/temp` 读不到时，如果当前已经是 THERMAL_ALERT 就**保持告警**，不做恢复判定。

这个设计叫 **fail-safe**：故障时向更安全的一侧倒。多说一句，`gateway_refused` 和 `connect_timeout` 分开记是有意义的——前者是"对面明确拒绝"，通常意味着服务没启动；后者是"没人应答"，通常意味着服务假死或网络层卡住。运维看到这两个词的行动完全不一样。

**如果被追问「那如果视觉真的长期离线，告警永远不解除怎么办？」：** 这是有意的取舍，不是 bug。告警的解除必须基于**新的有效证据**，不能基于"证据消失"。真的长期离线，正确的动作是运维去修服务，而不是让守护自己把红灯关掉。为了让人能发现这件事，`vision=offline` 会每周期打在 stdout 心跳行上，一眼就能看到。

### Q：这个守护怎么托管？systemd 那几个字段到底怎么写？

**一句话答案：** `Type=simple` + `Restart=always` + 配一个 `RestartSec` 防重启风暴，`[Install]` 里 `WantedBy=multi-user.target` 做开机自启；看门狗（`WatchdogSec` / 硬件 `/dev/watchdog`）我了解原理但**在这块板上没有实测**。

**展开讲：** 最少要写的字段是 `[Unit]` 的 `Description`、`[Service]` 的 `ExecStart` 和 `Restart`、`[Install]` 的 `WantedBy=multi-user.target`。

```ini
[Unit]
Description=edgevision patrol daemon
After=network.target

[Service]
Type=simple
ExecStart=/root/lab/edgevision_patrol_daemon --interval 5
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

四个点必须讲清。

`Type=simple` 的意思是：`ExecStart` 启动的那个进程**就是**主进程，它前台跑，systemd 直接盯着它。相对的是 `Type=forking`——进程自己 daemon 化了、父进程退出，systemd 得靠 `PIDFile` 去找真正的进程。现代做法是**让程序前台跑，后台化交给 systemd**，这样日志还能被 journald 收走。我那个守护内部虽然用了 `daemon(0,0)` 的场景，但在 systemd 托管时就是前台模式。

`Restart=always` 表示不管怎么退出都重拉（包括正常退出）。`on-failure` 只在非 0 退出码或被杀时才重拉。7×24 常驻用 `always`，一次性任务用 `on-failure` 或 `no`。

`RestartSec` 是必须配的。没有它，"启动即崩"会变成无限重启风暴：一万条日志一秒内刷爆，CPU 打满，把真正的问题（比如配置文件写错）彻底淹没。配了 `RestartSec`，至少每次重启之间留出喘息窗口。这也是 `Restart=always` 唯一真正的风险点。

`enable` 和 `start` 是两件事：`enable` 建开机自启的软链接（**下次开机**生效），`start` 是**现在**启动。常用 `systemctl enable --now` 一次搞定。还有一个必踩的坑：改了 service 文件不 `systemctl daemon-reload` 就不生效。

systemd 判断"进程挂了"靠的是 **cgroup**：主进程退出，或者整个 cgroup 空了，就认为服务结束。所以哪怕主进程 fork 了一堆子进程，cgroup 空了照样算死。

**如果被追问「5 秒自愈这个数是怎么来的？」：** 就是 `RestartSec=5` 的配置值，不是测出来的玄学。实测做法是 `systemctl stop` 注入故障后再 `start`，回读 `is-active` 验证能回到 active——这一条我在回归测试里做成了可重复执行的用例，而不是手动点一次截图。

**如果被追问「watchdog 呢？」：** 必须诚实分开说。硬件看门狗是打开 `/dev/watchdog` 后定期 `write` 喂狗，超时**硬件直接复位整块板子**，用于内核卡死、进程假死这种软件自己管不了的情况。systemd 的 `WatchdogSec` 是**软看门狗**：服务定期调 `sd_notify(WATCHDOG=1)` 报到，超时报到 systemd 就重启它，比硬件看门狗轻，但依赖 systemd 还活着。**这两块我只有原理认知，没有在这块板上接过**，被问就直接说"了解机制但没实测"，别吹。

> 【费曼讲解】**什么是"看门狗"，它和"进程崩了自动重启"差在哪？**
> 生活类比：看门狗（字面意义的狗）不是等主人死了才叫，而是**每小时要看到主人给一次手势**，看不到就一直叫。它监控的不是"你死没死"，是"你还动不动"。
> 不懂的人会怎么错想：以为 `Restart=always` 已经覆盖了看门狗的功能——"进程挂了就重启，这不就是自愈吗"。
> 一句话戳破：**`Restart=always` 只能发现"进程没了"，发现不了"进程还在、但已经不干活了"。**一个死锁在 `pthread_mutex_lock` 上的进程，在 systemd 眼里活得好好的，它永远不会被重启。
> 回到术语：看门狗是**活性（liveness）检测**，靠"你必须在期限内主动报到一次"来证明组织还活着；进程退出检测是**存活（existence）检测**。前者能抓住死锁、无限等待、调度饥饿，后者抓不住。

### Q：你怎么证明它真的可靠？12 条回归用例是怎么设计的？

**一句话答案：** 12 条用例覆盖"只查不改、参数正确、非法输入、多步顺序、超长输入、故障注入"六类，全部断言为真才算过；其中最值钱的是**故障注入**——主动停服务，验证系统如实报离线而不是编数据。

**展开讲：** 用例表的结构是这样的（每条独立起进程，通过标准统一为"该用例全部断言为真"）：

| 编号 | 验什么 | 关键断言 |
|---|---|---|
| T01 | 只读查询温度/健康 | 调了健康工具、没调控灯工具、Observation 是合法 JSON |
| T02 | 只读查询灯状态 | 调了查灯、没调控灯 |
| T03 | 设成急闪报警 | 参数等于 alarm，且写入成功 |
| T04 | 恢复心跳灯 | 参数等于 heartbeat，且写入成功 |
| T05 | 非法模式（"飞行模式"） | 绝不允许当前模式变成非法值（三条宽容路径任一） |
| T06 | 视觉在线时查画面 | status 为 online，或帧号/检出数可用 |
| T07 | 多步：先健康后视觉 | 顺序是子序列匹配，两个工具都要调到 |
| T08 | 条件决策：有人才报警 | 必须调视觉；控灯则模式只能是 alarm 或 heartbeat |
| T09 | 清空上下文后再问 | `/clear` 之后第二轮必须**真去查**，不能靠记忆答 |
| T10 | 超长输入 | 进程不崩、正常退出 |
| T11 | 连续两次控灯 | 两轮参数分别是 on 和 alarm，不串扰 |
| T12 | 故障注入：停视觉服务 | status 属于离线类，或明确说明无法判断 |

几个设计细节值得单独说。

**T05 和 T08 用"多路径宽容断言"**，因为模型行为存在合理分歧：拒绝非法指令时，它完全可以不调工具、直接口头告诉你不支持。硬要求一条路径会把正确行为判成失败。这类断言叫 `any_of`，命中任一路径即过。

**T10 我要主动纠正一个口径。** 这条早期被写成"逼近上下文上限的长上下文压测"，但代码里 `max_context_len` 早就设成 8192 了，而测试输入才 860 字左右，离上限还差一个数量级，断言也只有"进程正常退出"。**所以它验的只是"超长输入不崩"，不能当"长上下文压测通过"讲。**这种自我纠正比多背一个用例更加分。

**T12 是故障注入，也是整套里最有工程味的一条。** 它的安全协议比用例本身更重要：

- 开关隔离：不带 `--with-faults` 时，脚本里根本不存在任何启停服务的代码路径被执行，T12 直接 SKIP。
- 前置检查：注入前必须 `systemctl is-active edgevision` 为 active；服务本来就没跑就 SKIP，不背"把停着的服务当注入成果"的锅。
- try/finally 恢复：`systemctl stop` 之后跑用例，**无论用例成败、超时还是抛异常**，finally 里一律 `systemctl start` 并回读 `is-active` 验证。
- 恢复失败处理：回读不是 active 就打印大警告 + 给出手动恢复命令，并**立即终止整场回归**，防止后续用例在服务缺失的状态下产生一堆误导性结果。
- 收尾还原：整场结束时直接把 LED 的 trigger 写回 heartbeat，**不经过模型**——避免模型自己失败导致灯停在爆闪上。

**如果被追问「T12 的断言是不是太宽松了？」：** 是，而且我事后复盘发现了更细的问题。这条用例允许四种状态之一通过，但实现里的真实枚举是 `online` / `offline` / `timeout` / `partial_frame` / `malformed_frame`，早期文档里写的 `standby` / `no_data`**在代码里根本不存在**，所以四个候选里实际只有 `offline` 能命中，其余靠"回答里提到离线"这个兜底分支过。这是断言写宽了导致的隐性偷懒，我把它记在自己的复盘里了。

**如果被追问「全绿是不是因为用例太弱？」：** 有可能，所以要配合指标口径看。工具决策正确率的分母是人工先验定义的"该调哪个工具"，模型给出表外但合理的方案会被记成失败——这个偏差是**保守**的，不会虚高。而且 12 条里有一条是主动破坏环境的故障注入，不是纯正向回归。

### Q：你提到"占空比"验收，那是什么？为什么比"肉眼看到灯亮了"强？

**一句话答案：** 因为板上的 `heartbeat` 触发器**本身就在闪**——"看到灯在闪"这个判据对告警完全不敏感；改成量"亮的时间占比"后，基线 20.0%、告警期 49.7%，区分度一目了然。

**展开讲：** 这是整章最容易做错、也最容易被追问的地方，我一开始就踩进去了。

板载 `work` 灯的默认触发器是 `heartbeat`（心跳呼吸效果），它本来就在 0 和 255 之间跳。所以如果你用"看到 brightness 在 0 和非 0 之间反复横跳"来证明报警生效，**这个判据完全失效**——告警灯不生效也一样能通过。

正确做法是先测基线、再测告警期，比较**占空比**（亮灯时间占比）：

| 模式 | 波形特征 | 占空比 |
|---|---|---|
| heartbeat | 双脉冲 + 长暗期 | 约 20%（实测 19.3% / 20.7%） |
| alarm（用户态爆闪） | 100ms 亮 / 100ms 灭 对称方波 | 约 50% |

于是验收逻辑变成"告警期占空比是否显著高于基线"，门槛定成 **≥35% 且相对基线抬升 ≥15 个百分点**。实测结果：告警期 **49.7%**，基线 **20.0%**，抬升 **+29.7 个百分点**；6 秒窗口内 brightness 翻转 73 次（0.02 秒采样，300 点）。

这里还有一个必须一起讲的坑：**采样间隔不能取 0.1 秒**。爆闪是 100ms 亮 + 100ms 灭，如果采样周期也是 0.1s，两者**同频**，读到的相位会被锁死——可能连续几十次全读到 255 或者全是 0，把"在闪"误判成"常亮"或"常灭"。这叫**混叠（aliasing）**，所以采样间隔要远小于方波半周期、并且避开整数倍关系，本脚本取 0.02s。

**如果被追问「为什么不用内核的 timer 触发器？」：** 因为这块板的内核 `5.10.110` 出厂没编 `CONFIG_LEDS_TRIGGER_TIMER`，`/sys/class/leds/work/trigger` 的合法值列表里**根本没有 `timer`**，`echo timer > trigger` 返回 `EINVAL`。旧代码写了这句而且**没检查返回值**，于是灯一直是 heartbeat，程序却以为自己"已设置报警"——典型的**假成功**。所以最终改成用户态 fork 一个子进程，用 `/bin/sh` 循环交替写 brightness 造方波。

**如果被追问「这个判据会不会也有假阳性？」：** 会，所以门槛是"基线 + 抬升量"双条件，不是单看绝对值。如果哪天爆闪周期改了，这道门槛必须重新标定——局限我在文档里写清了，没有把它当成永久有效的定理。

> 【费曼讲解】**什么是"占空比"，为什么它比"灯有没有亮"更能说明问题？**
> 生活类比：判断一个人是不是在**跑**，不是看他"这一秒脚有没有离地"——走路也可能刚好离地。要看"一分钟里离地了多少秒"。
> 不懂的人会怎么错想：觉得"我看到灯亮了，所以报警生效了"。这个推理错在把**一个瞬时采样**当成了**一个持续状态的证明**。
> 一句话戳破：**周期性信号的瞬时值没有信息量，有信息量的是它的统计特征。** 一盏常亮的灯和一个 50% 占空比闪的灯，你随机看一秒钟很可能都看到"亮"，但它们的占空比是 100% 和 50%，根本不是一回事。
> 回到术语：占空比 = 一个周期内高电平时间 / 周期总时间。它是把"看起来在动"翻译成"可比较、可断言、可回归"的数字——**验收要的是数字，不是印象**。

### Q：怎么证明系统真的在工作？事件落盘和幂等性怎么保证？

**一句话答案：** 三条独立证据链——每个周期的 stdout 心跳行、只追加不重写的 JSON 事件黑匣子、以及给慢层的 `llm_pending.jsonl`；落盘靠 `O_APPEND` 追加，进程重启后历史事件不丢。

**展开讲：** 可观测性要分层，因为不同的问题要看不同的地方。

第一层是**心跳行**，每周期一行打到 stdout，一眼能看出"它还在不在跑、这一周期看到了什么"：

```
[2026-10-25 11:50:51] state=THERMAL_ALERT temp=43.46C vision=online frame=78039 person=- npu=14%/12%/14% led=alarm t_clear=0/3
[2026-10-25 11:50:53] state=THERMAL_ALERT temp=42.54C vision=online frame=78099 person=- npu=14%/14%/14% led=alarm t_clear=0/3
```

这一行里同时包含了状态、温度、视觉状态、帧号、person 分数、三核负载、LED 模式和恢复计数器进度。`t_clear=0/3` 这种"进度条"式的字段特别有用——你能直接看到"正在恢复，已经连续 0 个周期满足条件了"。

第二层是**黑匣子** `patrol_events.log`，一行一个 JSON，事件取值只有 `DAEMON_START` / `PERSON_ALERT` / `THERMAL_ALERT` / `RECOVER` 四种，超过 5MB 轮转成 `.1` 保留一代。关键设计是**只在状态翻转时追加，稳态不刷屏**。还有一条很见功力的细节：dry-run 模式下 `action` 记 `would_set_alarm`、`led_result` 记 `dry_run_no_write`——**黑匣子如实记录"想做但没做"，并且和真实模式可区分**。这比"试运行时不写日志"强得多，因为你事后能证明"这条路径我演练过"。

第三层是**慢层队列** `llm_pending.jsonl`，字段和黑匣子基本同构但不含 `event`，改成 `type`，是专门给慢层消费的窄接口。

**幂等性**靠两个机制。一是**单实例锁**：`flock("/tmp/edgevision_patrol.lock")`，第二个实例拿到锁失败就打印原因并以退出码 3 退出。这挡住了一个真实场景——两个守护同时控同一个 LED，互相把模式设成不同值，灯就会鬼畜。二是**动作是"设置到目标状态"而不是"翻转"**：`set_alarm` / `set_heartbeat` 是幂等的，重复执行一百次结果一样；如果写成 `toggle`，"重复执行"就变成了"灯自己跳"。

**落盘不丢**：所有事件写文件都是 `O_APPEND` 追加语义，不是"每次重写整个文件"。进程重启后继续往后追加，历史事件原样保留，慢层按自己维护的 offset 继续消费。

**如果被追问「守护自己崩了，重启之后状态会不会错？」：** 会有一个短暂的"冷启动窗口"——重启后它不知道上次是什么状态，第一周期会当成 NORMAL 去采样，如果条件仍然成立会在下个周期重新翻转并写一条新事件，日志里能看到 `DAEMON_START` 之后跟着一条重复的 ALERT。这是可接受的：事件是幂等的（同类型重复），慢层做降噪合并就能处理，比"为了恢复内存状态而引入一套状态持久化"简单得多。

**如果被追问「那怎么防住'假成功'？」：** 这是这个项目里反复出现的一个主题，一句话原则是——**只认可验证的物理事实，不认程序自述**。灯有没有真闪，认 `/sys` 节点的实测采样占空比，不认"设置成功"的返回值；告警有没有真发生，认 `patrol_events.log` 里落盘的内容，不认内存里的状态变量；动作有没有真执行，认进程真的存在、`/proc/<pid>/cmdline` 里真的是那个命令。

### Q：为什么采样周期是 5 秒不是 1 秒？为什么不干脆把所有指标都轮询一遍？

**一句话答案：** 5 秒是"时效够用"和"开销可忽略"的交点；只采三类指标是因为**只有它们能改变告警判定**，多采一个就多一分跟主业抢资源的风险。

**展开讲：** 先看 5 秒这个数怎么来的，两个方向夹出来的。

往上看时效：巡检要抓的是"温度越限""有人闯入"。人的进入和离开本身就是秒级的，温度变化的时间常数是几十秒到几分钟。5 秒的检测延迟在业务上完全感知不到，慢一秒毫无收益。

往下看开销：每个周期要做三件事——读几个 `/sys` 节点、发一次 TCP 探测（连接 + 收一帧 248B + 断开）、写一行 stdout。如果改成 1 秒，这些动作的频次直接乘 5，一天就是 86400 次探测。而且视觉探测有 300ms 的连接超时和 300ms 的收帧超时，在 5 秒周期里最多占 **不到 6%**；周期缩到 1 秒，这个超时预算就占到了 60%，一旦对面慢一点，守护就会长期处在"正在等超时"的状态里，采样节奏被拖垮。

所以 5 秒是**由超时预算倒推出来的**，不是随便挑的整数。

再看"为什么不轮询所有指标"。这条更重要，因为它涉及一个常见的思路误区：觉得"反正是巡检，多采点数据总没坏处"。实际上有三条理由让我只留三样。

第一，**只有能改变判定的指标才值得采**。温度（热）、NPU 三核负载（算力是否被吃满）、视觉帧号和 bbox 数（业务是否真的在产出），这三样分别对应"板子要烧了""算力被抢了""业务挂了"三类可行动的告警。至于 eMMC 剩余寿命、风扇转速这类指标，要么变化极慢（采了也是同一个数），要么采到了也没有对应的处置动作。

第二，**快层的定位是伴生功能，没资格影响主业**。每多读一个 sysfs 节点、多发一次探测，都是在跟 9000 推流的推理线程抢 CPU 和 IO。端侧设备的资源预算要按"能不能不动"来算，而不是按"反正很便宜"来算。

第三，**可观测性本身也有成本**。每多一个指标，就要多定一个阈值、多一个可能误报的来源、多一条要维护的日志字段。指标不是免费的，**采集 = 承诺你要对它负责**。

**如果被追问「5 秒会不会漏掉瞬时尖峰？」：** 会，而且这是有意的。温度传感器本来就有惯性，1 秒采样也抓不到微秒级尖峰；真要抓那种，该上用示波器或者硬件保护电路，不该指望一个 5 秒周期的软件巡检。**软件巡检的定位是趋势和持续性异常，不是示波器。**

## 三、这一章的"记忆锚点"

- 三个故障域：推流网关 / 巡检快层 / LLM 慢层。快层**只链 std + pthread**，连 `rknn_api` 都不链，永不 stop 主服务。
- 快层回答"现在要不要闪灯"（毫秒级规则），慢层回答"刚才发生了什么"（秒级语义）。**能写成 `if` 的留快层，写不成 `if` 的送慢层。**
- 交接靠单向文件：快层是 `llm_pending.jsonl` 唯一写者（`O_APPEND`），慢层 `tail -F` 只读、自己维护 offset。契约四字段 `ts` / `type` / `summary` / `raw`，`type` 只有三种。
- **只在状态翻转时写事件**：稳态零写入。每 5 秒记一条的话一天就是 17280 条，真信息会被埋在噪声里。
- 状态机 NORMAL / PERSON_ALERT / THERMAL_ALERT；防抖靠**双阈值迟滞 + 连续 N 周期确认**：person 2 进 5 出、温度 75 进 70 出且连续 3 周期恢复。
- 采样失败时**冻结计数器、不翻转**——数据缺失不等于"没有人员"，已在告警就保持告警（fail-safe）。
- 托管用 `Type=simple` + `Restart=always` + `RestartSec=5`（防重启风暴）+ `WantedBy=multi-user.target`。`Restart` 管"进程没了"，看门狗管"进程还在但不干活了"，两者不是一回事。
- 验收看**占空比**不看"灯有没有闪"：heartbeat 基线 20.0%，告警期 49.7%（+29.7 个百分点），采样 0.02s 避开 100ms 方波的混叠。
- 12 条回归全绿，其中 T12 是故障注入：停服 → 断言如实报离线 → `finally` 里恢复并回读验证。**演示判 PASS 不等于没问题，还要看断言本身够不够狠。**

## 四、面试官可能从哪下刀（预演）

| 他可能问 | 你怎么接 |
|---|---|
| 巡检为什么要单独一个进程，不是浪费资源吗？ | 「恰恰相反，独立进程才省心。三个故障域分开：主进程崩了巡检还能报警，巡检卡了拖不住推流。而且它有硬约束——只链 std 和 pthread，连 `rknn_api` 都不链，9000 端口只做收一帧就断的只读探测，永远不 stop 主服务。」 |
| 快层为什么不用大模型？现在端侧模型不是挺强的吗？ | 「三条硬理由：NPU 竞争（三颗核已被 9000 网关 7×24 占着，再加载几 GB 权重就是抢时间片）、时延（LLM 单次几百 ms 到秒级，而温度超限到闪灯必须毫秒级响应）、可靠性（报警是安全行为，必须可预测可复现可回归，不能靠一个可能幻觉的输出）。**该用 `if` 的地方不要用 LLM。**」 |
| 文件当队列，你不怕丢事件吗？为什么不上消息队列？ | 「丢的前提是写了没落盘，而这里每次翻转是一次 `O_APPEND` 追加写。真正的无界风险（每秒几千条、消费端跟不上）在这个场景不存在——事件一天也就几十条。上消息队列是给每秒几千条的场景准备的，这里是每秒 0.2 条的通道，用文件是**正确设计**，不是妥协。」 |
| 为什么只在翻转时写日志？多记点不是更好排障吗？ | 「每 5 秒一条，一天 17280 条。日志的价值密度比数量重要——真信息会被 17 万条『今天也正常』埋掉，慢层读进去也全是噪声。翻转日志的好处是每一条都可行动。」 |
| 你这个迟滞参数 75/70、2 进 5 出，有依据吗？ | 「有。温度 75°C 是 SOC 高温警戒线，迟滞 5°C 保证 75 附近抖动不会反复翻状态；person 进入用连续 2 次是因为模型输出天然有抖动，恢复用 5 次比进入慢（2:5）是为了防止人来回走动导致灯闪。**进入和退出刻意不对称**，这才是防抖的核心。」 |
| 视觉服务停掉了，你的告警会不会自己解除？ | 「不会，这是刻意设计的 fail-safe。采样失败时冻结计数器：数据缺失不等于『没有人员』。视觉探测会带 `vision_reason`，`gateway_refused` 和 `connect_timeout` 分开记——前者通常是服务没启动，后者通常是假死，运维看到这两个词的行动完全不同。」 |
| 你怎么证明灯真的亮了？程序说写成功不就行了？ | 「不行，我踩过这个坑。板子内核没编 `CONFIG_LEDS_TRIGGER_TIMER`，`echo timer > trigger` 返回 `EINVAL`，旧代码不检查返回值，于是灯一直没爆闪过，程序却以为自己设置成功了。现在的判据是实测占空比：基线 20.0%、告警期 49.7%。**只认可验证的物理事实，不认程序自述。**」 |
| `Restart=always` 不就是自愈了吗？还要看门狗干什么？ | 「不一样。`Restart` 管的是『进程没了』，看门狗管的是『进程还在但不干活了』——一个死锁在 `pthread_mutex_lock` 上的进程，在 systemd 眼里活得好好的，永远不会被重启。不过要诚实：看门狗这块我只有原理认知，没在这块板上实测过。」 |
| 全绿是不是因为用例太弱？ | 「有可能，所以我把口径摊开讲。工具决策正确率的分母是人工先验定义的，模型给出表外但合理的方案会被记成失败——这个偏差是保守的，不会虚高。而且 12 条里有一条是主动破坏环境的故障注入，不是纯正向回归。另外 T10 我主动纠正过口径：它验的只是『超长输入不崩』，不是『长上下文压测通过』。」 |
| 5 秒会不会太慢？改成 1 秒是不是更灵敏？ | 「1 秒的代价是探测频次乘 5，一天 86400 次；更关键的是视觉超时预算——连接和收帧各 300ms，5 秒周期里最多占不到 6%，缩到 1 秒就占到 60%，一旦对面慢一点，守护会长期卡在等超时的状态里。而且这类告警的对象（温度变化、人员进出）本身就是秒级的，再灵敏也没有业务收益。」 |

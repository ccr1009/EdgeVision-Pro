# 第 3 章 进程间通信与信号

> 一句话心智模型：两个进程各有各的地址空间，想说话必须借道内核——管道是内核帮你在两个 fd 之间接的一根管子，信号是内核替你拍的一下肩膀（只告诉你"出事了"，不带数据），而守护进程要做的事就是**在没人看着的情况下还能被这两样东西叫醒并干净地退出**。

## 一、先建立心智模型

```
   进程 A                                    进程 B
   ┌────────┐      内核里的一根管子        ┌────────┐
   │ fd[1] ─┼────► [ 缓冲 64KB ] ────►────┼─ fd[0] │
   └────────┘   （写端关光了，读端才 EOF） └────────┘
        │
        │  信号：只有"一个编号"，没有数据体
        ├──────► SIGTERM(15)  请求你退出，可捕获
        └──────► SIGKILL(9)   直接杀，不可捕获

   我的项目里真正用到的三条通道：
     ① 管道        —— 子进程的 stdout 被父进程/脚本读取（回归脚本抓输出）
     ② 文件(JSONL) —— 巡检守护写 llm_pending.jsonl，慢层 tail -F 消费
     ③ TCP socket  —— 网关 :9000 推 248B 定长帧，Agent 连上去抽一帧

   守护进程的四步：fork 父退 → setsid 脱离终端 → chdir("/") → 0/1/2 重定向 /dev/null
```

**记住这一个比喻**：管道是**一根两头带阀门的自来水管**，信号是**敲门**。敲门只能告诉你"有人来了"，说不出"来了几个人、要干什么"——所以信号永远只用来"通知"，真正的数据必须走管子/文件/socket。这一句话能解释为什么信号处理函数里不能干复杂活。

## 二、问答正文

### Q：进程间通信到底有哪几种？你项目里用了哪些？

**一句话答案：** 常见的是管道/FIFO、消息队列、共享内存、信号量、socket（含 socketpair）和普通文件；我项目里真正落地的是**管道、文件、TCP socket** 三条，共享内存和 socketpair 我只做了认知评估，没进生产链路。

**展开讲：** 这几种的取舍其实是两个维度：**要不要拷贝**、**有没有边界**。共享内存最快（零拷贝，但同步要自己做，还得自己管生命周期）；管道/FIFO 简单但有拷贝、且是字节流（同 TCP 一样有粘包问题）；socket 最通用，能跨机器；文件最简单，天生持久化，代价是慢、要自己管读写位置。

我在巡检守护那套快慢双系统里用的是**普通文件做单向队列**：快层只在状态翻转的时候往 `llm_pending.jsonl` 追加一行 JSON（稳态零写入），慢层 `tail -F` 消费。之所以选文件不选管道，是因为**管道要求两端同时在线**，而慢层是个可能几分钟才醒一次的 LLM，它不在的时候事件不能丢——文件天然能存住。协议冻结成 4 个字段（`ts`/`type`/`summary`/`raw`），`type` 只有 3 类，`raw` 只增不删，这样慢层可以安全地按行解析，不需要理解快层内部实现。

**如果被追问「为什么不用共享内存？」：** 共享内存要解决的是"谁创建、谁销毁、怎么通知对方、怎么防撕裂"这四个问题，对一个"几秒才写一次"的低频事件通道来说完全是杀鸡用牛刀。**选型的第一原则是匹配频率，不是匹配性能上限。**

**如果被追问「那 socketpair 呢？」：** 它是"pipe 的升级版"：全双工、能传 fd、能跨 fork 用。我评估过用它做父子进程的命令通道，但我当时的父子关系只有"爆闪子进程"这一处，一条 `execl` 就够了，没必要引一层协议。

**面试怎么讲：** 不要背 IPC 列表，讲"我按频率和持久性选通道"：高频同机→共享内存，低频要留痕→文件，跨机→socket。这句话就把八股变成了工程判断。

### Q：管道读端什么时候返回 0？为什么我的命令卡了 270 秒？

**一句话答案：** 所有写端都被关闭时读端才返回 0（EOF）；只要还有任何一个进程持有写端，读端就一直等——我那个卡 270 秒的 bug 就是 fork 出来的死循环子进程继承了父进程的 stdout 写端。

**展开讲：** 现象是回归脚本跑"开急闪报警"这条用例，**卡死 270 秒被强杀**（rc=TIMEOUT），但板上 `ps` 能看到 agent 早就跑完了、LED 也确实在爆闪——**功能是对的，进程就是不返回**。同一条命令在交互式 ssh 里手动跑却秒回。

排查的关键线索就是这个反差：**交互式 tty 正常、管道/重定向卡死**，那是 fd 继承的指纹。回归脚本用 subprocess 抓 stdout，读端要等 EOF（所有写端关闭）才返回；而爆闪子进程 fork 之后没有重定向 fd，继承了父进程的 stdout/stderr 管道写端，它是个 `while true` 的爆闪死循环，父进程退出后它被 init 收养继续跑 —— 这个永不退出的进程一直握着写端，读端就永远拿不到 EOF。

修法就是 daemon 化的标准动作：子进程 `open("/dev/null", O_RDWR)` 之后 `dup2` 到 STDIN/STDOUT/STDERR，再 `execl`。修完同一条用例从 **270 秒超时变成 21 秒正常返回**。

**如果被追问「那为什么灯确实在闪，说明功能没错啊？」：** 功能对和调用方能返回是两件事。这就是"先验功能、再查 IO 生命周期"的排查顺序：先确认动作发生了（ps 有进程、brightness 在跳），再问"谁没退出"，最后才怀疑 fd。

**面试怎么讲：** 这条故事的信息密度非常高：现象（功能对但不返回）、分水岭（tty 正常/管道卡死）、机理（引用计数不归零）、修法（重定向 0/1/2）。一口气讲完，面试官会直接跳到"你真的写过守护进程"这个结论。

> 【费曼讲解】把管道想成**一根两头带水龙头的水管**，你这边要判断"水放完了没"，靠的是"对面所有龙头都关了"这个信号。不懂的人通常以为"我的进程退出了，管子自然就断了"。一句话戳破：**管道不是谁的私有财产，是引用计数资源——每 fork 一次就多一个持有人，多一个持有人就多一份"水还没放完"的可能。** 回到术语：fork 复制的是 fd 表，父子进程的 fd 1 指向**同一个**打开文件表项（引用计数 +1），只有引用计数归零内核才关闭写端、读端 read 才返回 0。

### Q：SIGTERM 和 SIGKILL 有什么区别？为什么不能直接 kill -9？

**一句话答案：** SIGTERM 是"请求"，可以被捕获、可以做清理；SIGKILL 是"直接处决"，不可捕获、不可忽略，进程没有任何机会收尾。

**展开讲：** 差异的全部意义在"你还有没有机会跑清理代码"。我的网关在收到 SIGTERM 时要做的事是：停摄像头硬件推流、释放 NPU 上下文、关闭 TCP socket、通知所有 worker 线程退出。这些如果没做，NPU 的 CMA 内存可能不被释放（就是第 2 章那个 fork 案例的同款后果）。

所以运维动作的标准姿势是：先 `kill`（默认发 TERM），给它几秒，不走再 `kill -9`。`systemctl stop` 默认也是先 TERM，超时才 KILL。

**如果被追问「你实际怎么捕获的？」：** 用 `sigaction` 而不是 `signal`，因为 `signal` 在不同 Unix 上语义不一致（是否自动重置、是否阻塞自身），`sigaction` 行为明确。我在主程序里对 SIGINT/SIGTERM 都注册了同一个 handler，同时在启动时 `signal(SIGPIPE, SIG_IGN)` —— 因为客户端断开后再 `send` 会触发 SIGPIPE，默认行为是**直接杀进程**，我见过网关因为上位机拔网线而整个挂掉。

**如果被追问「那 SIGPIPE 你只在 main 里屏蔽够吗？」：** 信号处置是进程级的，但线程有各自的掩码，fork 出来的子进程会继承处置方式。我另外在每个 `send` 上都加了 `MSG_NOSIGNAL`，双保险——因为屏蔽是"全局开关"，而 `MSG_NOSIGNAL` 是"这一次别发信号"，前者会被某些库改回去。

**面试怎么讲：** 先答"能不能捕获"，再答"我捕获之后具体做了什么清理"，最后提 SIGPIPE 这个真实事故。第三层最能证明你不是背的。

### Q：信号处理函数里到底能做什么？

**一句话答案：** 只能做**异步信号安全**的操作；`printf`、`malloc`、加锁都可能死锁，所以标准做法是只改一个 `volatile sig_atomic_t` 标志位，让主循环去干活。

**展开讲：** 原因是信号可能在任意一条指令处打断主流程。假设主线程正在 `printf` 里持有 stdio 的锁，信号处理函数里再 `printf`，就自己等自己——死锁。`malloc` 同理（堆的内部锁），这也是为什么很多库在信号处理里"看起来能用、压力一大就随机卡死"。

我的做法是：handler 里只做 `g_running = 0`（`volatile sig_atomic_t`，保证是单条原子读写），主循环每轮检查这个标志。在网关里 handler 还会 `pthread_cond_broadcast` 两个条件变量，把阻塞在 `pthread_cond_wait` 上的 worker 踢醒，否则它们睡在那里等信号，主线程 join 会一直等下去。

**如果被追问「更规范的做法是什么？」：** self-pipe trick：handler 里往一个 pipe 写 1 个字节（`write` 是异步信号安全的），主循环用 epoll 监听这个 pipe 的读端，读到就处理。这样信号就变成了普通的 IO 事件，所有复杂逻辑都在正常上下文里跑。我这套代码没用 self-pipe，是用"标志位 + cond_broadcast"达到同样目的。

**如果被追问「严格说 pthread_cond_broadcast 是异步信号安全的吗？」：** 严格按 POSIX 标准**不是**。这是我这份 demo 的一个已知瑕疵：在这个"只在收到 TERM 时踢一次"的场景里风险极低，但如果要做成生产级，就该换成 self-pipe 或 eventfd。**面试时主动承认这一层，比装作没这回事强得多。**

**面试怎么讲：** "只改标志位 + 主循环处理"是标准答案；能再补一句"更彻底的是 self-pipe"，就是加分；能主动说出自己代码里的瑕疵，就是 85 分。

> 【费曼讲解】把信号处理函数想成**你在做手术时突然响起的火警**。你能做的只有"立刻停手、拉下总闸"（改一个标志位），不能这个时候去"清点器械、写手术记录"——因为你手上的活随时可能被打断，而火警本身也在打断别人。不懂的人通常觉得"回调函数嘛，想干啥干啥"。一句话戳破：**信号处理函数不是一个函数的入口，是一条随时插队的指令，它插入的时机由内核决定，不由你决定。** 回到术语：这就是 async-signal-safe 的含义——只有那些"内部不加锁、不碰共享状态、可重入"的函数才允许在这里调用。

### Q：什么是守护进程？必须哪几步？

**一句话答案：** 守护进程就是"终端关了也不死、还活着"的进程；三步：fork 后父进程退出 → setsid 建新会话脱离控制终端 → chdir 到根目录并把 0/1/2 重定向到 /dev/null。

**展开讲：** 每一步都对应一个真实的死法：

- **fork 后父退出**：让子进程不再是进程组组长，这样 `setsid` 才能成功（组长不能调 setsid）。
- **setsid**：建一个新会话，进程成为会话首进程，从此**没有控制终端**。终端关闭时发的 SIGHUP 就找不到它了。
- **chdir("/")**：不占着用户的工作目录，否则那台目录就永远 umount 不掉。
- **重定向 0/1/2 到 /dev/null**：这条就是第 2、3 章反复出现的那条 —— 终端已经没了，往 stdout 写会出错；更要命的是**长寿子进程持有父进程的管道写端**，会让上游永远等不到 EOF（270 秒那个案例）。

现代做法其实是用 systemd 的 `Type=simple` 让它前台跑，由 systemd 负责后台化——那样就不用自己 fork/setsid，日志还能被 journald 收走。真要用 `daemon()` 这个函数也行，它就是把上面几步打包了。

**如果被追问「为什么有人说要 fork 两次？」：** 为了彻底断绝和终端的关系。setsid 之后进程成了会话首进程，而某些系统允许会话首进程**重新打开**控制终端——再 fork 一次让孙子进程不是会话首进程，就再也拿不到终端。一次 fork 通常也够用。

**如果被追问「daemon 之后 printf 去哪了？」：** 去了 /dev/null，所以没输出——这个坑我踩过。要写文件，或者干脆交给 journald（systemd 下 printf 到 stdout 会被收集）。

**面试怎么讲：** 四步 + 每一步"不做会死在哪"，这就是完整答案。特别是"重定向 0/1/2"那一步，一定要说出 270 秒那个案例，否则听起来像背书。

> 【费曼讲解】守护进程像**一个员工从"坐班"改成"住家保姆"**：老板下班锁门（终端关闭）对他没有影响，但他必须自己带饭（日志写文件）、自己找活干（chdir 到根）、不能还占着办公室的门（不占工作目录）。不懂的人通常以为"daemon 就是加个 & 后台跑"。一句话戳破：**`&` 只是把进程丢到后台，它仍然是这个终端的会话成员，终端一关照样收到 SIGHUP 死掉。** 回到术语：后台运行（job control）和守护进程（session 迁移）是两个层次的事，前者靠 shell，后者靠 setsid。

### Q：systemd 到底帮你做了什么？Restart=always 和 on-failure 怎么选？

**一句话答案：** systemd 是系统级进程保姆：开机自启、崩了按策略重拉、用 cgroup 跟踪整组进程、收集日志；常驻服务用 `always`，一次性任务用 `on-failure` 或 `no`。

**展开讲：** 最少要写的字段是 `[Unit]` 的 `Description`、`[Service]` 的 `ExecStart` 和 `Restart`、`[Install]` 的 `WantedBy=multi-user.target`。

我项目里那个 `edgevision.service` 是长期常驻的 7×24 网关，用 `Restart=always`：不管怎么退出都重拉。同时配了 `RestartSec`，否则"启动即崩"会变成无限重启风暴，把日志刷爆、把 CPU 打满。

`enable` 和 `start` 是两件事：`enable` 建开机自启的软链接（**下次开机**生效），`start` 是**现在**启动。常用 `systemctl enable --now` 一次搞定。还有一个必踩的坑：改了 service 文件不 `systemctl daemon-reload` 就不生效。

systemd 判断"进程挂了"靠的是 **cgroup**：主进程退出或者整个 cgroup 空了，就认为服务结束。这也解释了 `Type=simple` 和 `Type=forking` 的区别——simple 认为 ExecStart 那个进程就是主进程（前台跑，推荐）；forking 是进程自己 daemon 化了、父进程退出，systemd 得靠 `PIDFile` 去找真正的进程。

**如果被追问「你怎么证明它真的会自愈？」：** 我把它做成了回归测试的一环：`systemctl stop edgevision` 注入故障 → 问 Agent"画面里有什么" → 它必须如实报 `offline`/`timeout`/`partial_frame`/`malformed_frame` 之一而不是编数据 → `finally` 里 `systemctl start` 恢复并回读 `is-active` 验证。这条用例在 12 条回归里编号 T12，全绿。

**如果被追问「那 watchdog 呢？」：** 硬件看门狗 `/dev/watchdog` 要定期 write 喂狗，超时硬件直接复位整板，用于内核卡死、进程假死这种软件管不了的情况；systemd 的 `WatchdogSec` 是软看门狗，服务定期 `sd_notify(WATCHDOG=1)`。**这一块我只有认知、没在这块板上接过**，被问就说"看门狗了解原理但没实测"。

**面试怎么讲：** 把"服务化"和"可验证"绑在一起讲：不是"我配了 Restart=always"，而是"我把它做成了故障注入回归项，停服后 Agent 必须如实报离线"。前者是配置，后者是工程。

### Q：快慢双系统为什么要用文件做队列，不怕丢事件吗？

**一句话答案：** 因为慢层（LLM）是"可能几分钟才醒一次"的消费者，管道要求两端同时在线会丢事件，文件天然持久；而且快层只在**状态翻转**时写，稳态零写入，量小到文件完全够用。

**展开讲：** 快层是常驻的 C++ 守护 `edgevision_patrol_daemon`，每 5 秒采一次温度/NPU 负载/视觉帧，用状态机加迟滞判定，状态翻转就写事件日志和 `llm_pending.jsonl`、控 LED；慢层是 Agent（RKLLM + Qwen 端侧模型），只在需要研判或汇报时被叫起来。

通道设计上做了几个刻意的约束：

- **单向**：快层是 `llm_pending.jsonl` 的唯一写者（`O_APPEND` 追加），慢层只读、自己维护消费进度（offset/行号），不回写、不删除、不改名 —— 彻底避免双写竞争。
- **低频**：只在状态翻转时追加，稳态一行都不写，所以不存在"文件涨爆"的问题；5MB 级完全可控，黑匣子日志超 5MB 轮转成 `.1` 保留一代。
- **可降级**：慢层离线时事件就在文件里堆着，等它回来再消费，快层不因为这个阻塞。

**如果被追问「那为什么不直接把 LED 的控制权交给慢层？」：** 因为那是**安全行为**。快层零模型依赖、只链 std 加 pthread、连 `rknn_api` 都不链接，行为 100% 确定、可回归测试；慢层可能幻觉、可能超时。所以数据流是单向的：慢层如果要回控 LED，应该走一条新的独立通道，绝不直接写快层的文件。

**如果被追问「快层为什么不用 LLM？」：** 三条：NPU 竞争（三颗核已被 9000 网关 7×24 占着，再加载几 GB 的 LLM 会抢时片，直接威胁推流帧率）、时延（LLM 单次几百 ms 到秒级，而温度超限到闪灯是毫秒级反射）、可靠性（告警必须可预测可复现）。**该用 if 的地方不要用 LLM。**

**面试怎么讲：** 这题的杀手锏是"快慢分层 + 单向数据流 + 快层零模型依赖"三件套，配上"该用 if 的地方不要用 LLM"这句金句收尾。

> 【费曼讲解】文件当队列就像**门口的意见箱**：投递的人不用等收件人在场，收件人什么时候来都行，而且他能看到历史投了哪些（可回溯）。管道像**打电话**：必须两边同时在线，一方挂了这通就废了。不懂的人通常会错想成"文件当队列一定很慢很低级，得上消息队列/共享内存"。一句话戳破：**通道的选型标准是"生产频率和消费节奏"，不是"理论吞吐上限"——每秒 0.2 条事件的通道，用文件是正确设计，不是妥协。** 回到术语：这就是"按频率选 IPC"，也是为什么 Kafka 那种场景才需要真正的消息中间件。

## 三、这一章的"记忆锚点"

- 管道 EOF 的条件是**所有写端都关闭**；fork 出来的长寿子进程不重定向 fd，就会把父进程 stdout 的生命周期无限拉长 → 表现为"功能对、命令不返回"（我用例 **270s → 21s**）。
- 信号的本质是**一次通知**，不带数据；真正要传数据必须走管道/文件/socket。
- SIGTERM 可捕获能做清理，SIGKILL 不可捕获；先 TERM，等几秒，再 -9。SIGPIPE 默认**杀进程**，要 `SIG_IGN` 或 `MSG_NOSIGNAL`。
- 信号处理函数只能改 `volatile sig_atomic_t` 标志位；`printf`/`malloc`/加锁都可能死锁；更彻底的是 self-pipe。
- daemon 四步：fork 父退 → setsid → chdir("/") → 0/1/2 重定向 `/dev/null`；`&` 只是后台运行，不等于守护进程。
- systemd：`always` 常驻重拉、`on-failure` 一次性任务；`enable` 管开机、`start` 管现在；改文件要 `daemon-reload`；靠 cgroup 判死活。
- 快慢双系统用**文件做单向队列**：快层稳态零写入、慢层只读不写回，**该用 if 的地方不要用 LLM**。

## 四、面试官可能从哪下刀（预演）

| 他可能问 | 你怎么接 |
|---|---|
| 「管道写满会怎样？」 | 写端阻塞（默认）。所以是天然的背压机制；但要小心它会把生产者线程一起拖住——这就是第 5 章我用有界队列而不是管道做推流缓冲的原因。 |
| 「信号处理里为什么不能 printf？举一个具体的死锁场景。」 | 主线程正在 printf 里持着 stdio 锁，信号插进来再 printf，同一把锁自己等自己。malloc 同理，堆锁。 |
| 「你怎么保证 SIGTERM 之后真的没有资源泄漏？」 | 讲清理清单：摄像头 STREAMOFF、`rknn_destroy` 释放 NPU 上下文、关 socket、broadcast 唤醒 worker 让线程 join 成功。 |
| 「systemd 怎么知道你的进程挂了？如果主进程还在但卡死了呢？」 | cgroup 判主进程/组是否为空；卡死它看不出来，那要靠 WatchdogSec 软看门狗或硬件看门狗——而这一块我没实测，我会直接说没做过。 |
| 「文件当队列，怎么防止读到写了一半的行？」 | 追问级问题。诚实答：快层是单进程 `O_APPEND` 一次写整行，单行远小于 PIPE_BUF/磁盘块，实际不会撕裂；如果是多进程写就必须加锁或改成独立文件。 |
| 「你这套 IPC 设计里，最脆的一环在哪？」 | 慢层的消费进度文件是自己维护的 offset，如果它被清掉就会重放全部历史事件——我目前靠"事件低频 + 慢层自己幂等"兜着，没做去重。 |

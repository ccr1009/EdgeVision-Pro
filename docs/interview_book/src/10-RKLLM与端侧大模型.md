# 第 10 章 RKLLM 与端侧大模型

> 一句话心智模型：端侧大模型不是一个"跑得慢的小 ChatGPT"，而是一块**占着 NPU、吃着几百兆 CMA 内存、每次推理要几秒到十几秒的常驻租客**——上它之前，先问清楚它跟谁抢资源、抢输了会怎样。

## 一、先建立心智模型

我的板子上同时住着两个"AI"：一个是从头到尾 7×24 跑着的 YOLOv8 视觉网关，另一个是需要时才被叫醒的 Qwen3.5-2B。它们共享同一块 6 TOPS 的三核 NPU。这一章讲的就是第二个房客是怎么搬进来的、房租多少、以及它搬进来之后第一个房客有什么意见。

```
【PC 侧 · 一次性】                    【板端 · 常驻】
HuggingFace 权重
   │  rkllm-toolkit（Python，PC 上跑）
   │  量化成 W8A8 + 指定目标平台 rk3588
   ▼
qwen3.5-2b_w8a8_rk3588.rkllm  ──scp──►  /root/rkllm_deploy/
   （2.8 GB，权重）                          │
                                            ▼
                              rkllm_init(param, callback)
                                 ├─ param.max_context_len = 8192
                                 ├─ param.max_new_tokens  = 512
                                 └─ 绑 NPU 3 核 + taskset 绑 4 个 A76 大核
                                            │
                                            ▼
                              rkllm_run(input, infer)  ← 你的问题
                                 │  流式回调逐段吐字
                                 │  RKLLM_RUN_NORMAL（吐一段）/ RKLLM_RUN_FINISH（收尾）
                                 ▼
                              中文回答

【同时发生的事】9000 端口的 YOLOv8 网关也在用这块 NPU 的三颗核
                 → LLM 一加载就抢时片 → 视觉帧率掉
```

**记住这一个比喻**：NPU 是车间里的三台机床，视觉网关是三班倒的老工人，已经把三台机器排满了。端侧大模型是个新来的老师傅，手艺好但一上手就要占机床，而且一占就是十几秒不撒手。所以正确做法不是"让他也上机床"，而是**让他只在真的需要动脑子的活上机，其余时间在旁边看**——这就是第 12 章"快慢双系统"的全部动机。

## 二、问答正文

### Q：RKLLM 到底是什么？一句话说清它在链路里的位置。

**一句话答案：** 瑞芯微官方给 Rockchip 芯片做的**端侧 LLM 推理运行时**，你给它一个 `.rkllm` 格式的模型文件，它负责把这个模型跑在 NPU 上，对上只暴露 `rkllm_init` / `rkllm_run` 这种 C 接口。

**展开讲：** 关键在于分清"运行时"和"模型"是两样东西。运行时是 `librkllmrt.so`，我板上装的是 **rkllm-runtime v1.3.1**，它是一个库，不是 Python 包，直接 `-lrkllmrt` 链接进 C++ 程序就行。模型是 `qwen3.5-2b_w8a8_rk3588.rkllm` 这个文件，**2.8 GB**，是 HuggingFace 上的 Qwen3.5-2B 经过量化和格式转换之后的产物。运行时本身不含任何模型参数，它只是一个"能把 .rkllm 跑起来"的执行引擎。

调用顺序很短，一共三步：`rkllm_createDefaultParam()` 拿一份默认参数 → `rkllm_init(&handle, &param, &cb)` 加载模型并注册回调 → `rkllm_run(handle, &input, &infer, nullptr)` 发起一次推理。**输出不是返回值，是回调**：模型每吐出几个字就回调一次 `result_callback`，回调里判断 `result->type` 是 `RKLLM_RUN_NORMAL` 就追加文本，是 `RKLLM_RUN_FINISH` 就收尾。这个流式设计很重要，因为端侧生成很慢，如果等全部生成完再返回，用户会以为程序卡死了。

**如果被追问「那它和 RKNN 什么关系？」：** 同一个厂的两套工具链，RKNN 面向 CNN（我用它跑 YOLOv8），RKLLM 面向 Transformer 类的 LLM。底层都在抢同一块 NPU 硬件，只是上层 API 完全不同——`rknn_init` 和 `rkllm_init` 是两套东西，用同一个驱动的 NPU 计算资源。

**如果被追问「为什么不用 llama.cpp？」：** 这是选型问题，见下一个 Q，我要强调的是：**llama.cpp 在这个板子上吃不到 NPU**。

### Q：为什么选 RKLLM，而不是 llama.cpp / MNN / ONNX Runtime？

**一句话答案：** 因为在 RK3588 上只有官方 RKNN/RKLLM 这套工具链**能真正把矩阵运算派到 NPU 的 3 颗核上**，其它方案在这块板子上只能落到 CPU 或 GPU，而 LLM 的 decode 阶段是逐 token 串行的，CPU 上跑 2B 模型基本不具备可用性。

**展开讲：** 这条要讲得诚实，先说清楚我的证据边界：**我没有在板子上跑过 llama.cpp 的对照实验**，仓库里也没有任何 llama.cpp 的实测数字。我给的是**架构层面的评估结论**，不是 benchmark 数据。评估的依据有三条：

第一，**算力落点**。RK3588 的 NPU（3 核，sys_prompt 里我写的是总峰值 6.0 TOPS）厂商只通过 RKNN/RKLLM 这套 SDK 开放。llama.cpp 的后端是 CPU（ARM NEON）、GPU（OpenCL/Vulkan，这块板子的 Mali-G610 对通用计算的支持很有限）、以及各类加速库，**它没有 Rockchip NPU 的 backend**。也就是说，选 llama.cpp 等于主动放弃板上唯一为神经网络准备的硬件。MNN 和 ONNX Runtime 同理，它们再有优化也是把算子映射到 CPU/GPU 上做。

第二，**工作量落点**。这条更现实：端侧部署最贵的不是"跑起来"，是"跑起来之后能调"。RKLLM 给了 `rkllm_set_function_tools` 这种原生的 Tool Calling 接口，第 11 章那套 ReAct 循环几乎不用自己造轮子；换成 llama.cpp，我得自己拼 chat template、自己处理工具调用的 KV cache 复用，工作量是数量级的差别，而且没有 NPU 加速兜底，做出来大概率也不能用。

第三，**版本可控**。板子上是 `rkllm-runtime v1.3.1`，跟我的 RKNN 驱动（v0.9.2 / 运行时 API 2.3.0）在同一个生态里，出问题查的是同一套文档。

**如果被追问「那你凭什么说 llama.cpp 慢？」：** 就退回证据边界上回答——**我没测，所以我不断言"慢多少"**。我能断言的是"它用不上 NPU"，而这在 LLM 的 decode 阶段是决定性的：生成是逐 token 的，每个 token 都要完整过一遍 2B 的权重，硬件加速有没有用是生死问题，不是百分比问题。想坐实这条结论，下一步就是把 llama.cpp 在同一块板上跑一遍、跟 RKLLM 的端到端时延对照——这个实验我列在待办里，还没做。

### Q：W8A8 是什么意思？为什么不选 W4A16？

**一句话答案：** W8A8 = **权重 8 bit + 激活 8 bit**，两者都量化成整数；W4A16 = 权重压到 4 bit、激活保留 16 bit 浮点。前者更省带宽、更适合 NPU 的定点算子，后者精度损失更小但算力收益也更少。

**展开讲：** 我的模型文件名里那个 `w8a8` 就是这件事，量化后的权重文件是 **2.8 GB**。为什么是这个量级：权重只存 8 bit 一位，2B 参数的模型权重本身就落在 GB 量级，再叠上词表、归一化层参数和内存对齐的开销，最终落到 2.8 GB。

两个字母分别管两件事。**W（weight，权重）**是第一位的，因为 decode 阶段每个 token 都要把全部权重从内存读一遍，权重的位宽直接决定了内存带宽压力，也就直接决定了速度。**A（activation，激活）**是中间计算结果，量化它主要是为了让 NPU 的整型算力能用上——很多 NPU 的 MAC 阵列对 int8 有专门的加速通道，激活也量化成 8 bit 才能全程走 int8 通路，不用反复转回浮点。

至于为什么不用 W4A16：**原理上**，4 bit 权重意味着权重体积更小、读带宽更省，理论上更快；16 bit 激活则保留了更高的数值精度，精度损失通常更小。但这里有个取舍——W4A16 属于"混合精度"，权重是 int4、激活是 fp16，NPU 上要做反量化再算，如果这个通路不是硬件原生支持的，反量化本身的开销会吃掉省下来的带宽，最后可能又慢又不省。而且 4 bit 权重量化对校准集质量极其敏感，2B 这种小模型本来容错就低，掉点风险更大。**W8A8 是"精度和速度都还有余量"的稳妥选择，也通常是官方工具链支持最好、验证最充分的那条路。**

必须说清楚：**这两段是原理和取舍的推理，我没有在板上实测过 W4A16 的版本**，也没有它的精度对比数据。面试时如果问"你为什么不试 W4A16"，正确答法是"我判断这条路的收益不确定，且当时优先级是先让 Tool Calling 闭环跑通；如果要做，我会先测校准集上的精度掉点，再决定值不值"。

> 【费曼讲解】把 W8A8 想成记账。你记一笔支出 3.78 元，如果保留两位小数，账本又厚又不方便；如果规定"所有金额只记到元"，记账速度立刻快一倍，代价是每笔都有零点几元的误差。
> 不懂的人会想："那我把精度砍到 4 bit，不是更快更省？"——错在这里：记账的瓶颈往往不是"写多少"，而是"要不要停下来做一次换算"。W4A16 就是"金额记到角，但结算时要换成元"，那次换算（反量化）的开销可能比省下的纸还贵。
> 一句话戳破：**量化不是越狠越好，是"压缩率"和"解压成本"要一起算。**
> 回到术语：W8A8 全程走 int8 定点通路，压缩和解压的性价比在 RK3588 这个 NPU 上是最高的那一档。

### Q：权重怎么从 HuggingFace 变成板子能跑的 `.rkllm`？

**一句话答案：** PC 侧用 `rkllm-toolkit` 做量化和格式转换，产出针对 rk3588 目标的 `.rkllm` 文件；板端只装 runtime（`librkllmrt.so`），不装 toolkit——**转换在 PC，执行在板**。

**展开讲：** 这条链路的产物从文件名就能读出来：`qwen3.5-2b_w8a8_rk3588.rkllm`，三个信息分别是**模型（qwen3.5-2b）**、**量化规格（w8a8）**、**目标平台（rk3588）**。转换在 PC 侧完成的核心原因是：量化需要跑校准数据、需要做图优化和权重重排，这些是重活，而且 toolkit 是 Python 生态，板子上跑 Debian 11 环境装这一套很别扭，也没必要——**板上只需要一个能加载结果的 runtime**。

要强调的一点是：**转换是"离线的一次性动作"，runtime 是"每次启动都要做的事"**。这个区分在面试里很有用，因为经常有人把两者混在一起问"你的模型是怎么训的"——不是训，是转换，权重从头到尾没动过，动的只是数值表示和内存布局。

**如果被追问「转换脚本在哪？我想看」：** 老实答——我仓库里留下的是产物 `.rkllm` 和板端的加载代码（`lab/agent/rkllm_embodied_agent.cpp:860` 那行 `param.model_path`），转换是在 PC 侧的工作环境里做完、把产物 scp 到 `/root/rkllm_deploy/` 的，脚本本身没有整理进仓库。这是个该补的缺口：**部署可复现性应该包括"模型怎么来的"**，现在只做到了"模型怎么用的"。

### Q：板端那几个运行参数，各管什么？调大调小分别会怎样？

**一句话答案：** 我实际只显式设了两个（`max_context_len` 和 `max_new_tokens`），其余采样参数走 `rkllm_createDefaultParam()` 的默认值——**这两个我踩过坑，所以能讲透；其余的我没调过，就只讲原理不讲数字。**

**展开讲：** 先看代码，一共三行是有信息量的（`lab/agent/rkllm_embodied_agent.cpp:859-864`）：

```
RKLLMParam param = rkllm_createDefaultParam();
param.model_path = "qwen3.5-2b_w8a8_rk3588.rkllm";
param.max_new_tokens = 512;
param.max_context_len = 8192;
```

**`max_context_len`：能记多长的对话。** 这是 KV cache 的容量上限。调**小**的代价我实测过：默认 **2048**，多步工具轮往历史里回填 Observation 之后直接挤爆，报 `E rkllm: The context is not enough! history_s:1309, cur_input_s:843`——1309 + 843 已经超过 2048，**终局汇报被掐死**。调**大**的代价是内存和预填充时间：KV cache 是随上下文长度线性增长的，模型自己也有头上限，我这份模型是 **16384**，所以我取 8192 是"够用且留了一半余量"。教训一句话：**Agent 的上下文预算要按"最坏一轮塞几个工具结果"算，不是按聊天长度算。**

**`max_new_tokens`：一次最多生成多少 token。** 调**小**会被硬截断——我从 **384** 提到 **512** 就是因为长研判报告在 384 个 token 处断在表格中间，报不出结论。调**大**不会变慢（生成到自然结束就停），但会把最坏情况的上限抬上去，而且**和 `max_context_len` 抢同一份预算**：历史 + 新生成不能超过上下文窗口。反过来说，这也是竞争场景下调优的一个候选杠杆（`AGENT_TEST_PLAN.md` 里就把"降低 LLM max_new_tokens"列为可能的优化手段之一）。

**`top_k` / `top_p` / `temperature` / `repeat_penalty`：影响"怎么选下一个字"。** 这几个我**没有显式设置**，用的是默认值，所以我只讲它们各自的方向性影响，不给具体数字。`top_k` 是每步只在概率最高的 k 个候选里挑，调小更保守更确定、调大更多样但容易跑偏；`top_p` 是核采样，只在累积概率到 p 的那一小撮候选里挑，调小同样更保守。`temperature` 是最直接的旋钮：调低趋近于"每次都说最可能的那个字"，输出稳定但可能复读；调高更发散，对 Agent 是灾难，因为**我要的是稳定的 JSON 和稳定的工具名，不是创意**。`repeat_penalty` 是重复惩罚，调高能压制"复读机"，但调太高会让模型连必要的重复都躲（比如 JSON 里 repeated 字段名），输出反而变怪。

这里给一条工程结论：**做 Agent 的时候，采样参数应该往"确定性"那侧压，不要往"有趣"那侧调。** 我的两个 2B 小模型缺陷（第 11 章会讲）没有一个是靠调采样参数修好的——因为它们的根因都不在采样。

**如果被追问「那 `rkllm_set_chat_template` 呢？」：** 它是告诉 runtime"用哪套对话模板把多轮消息拼成一段 prompt"的接口。我的代码里**没有显式调用它**，因为 `.rkllm` 转换时已经带上了模型的模板信息，runtime 会按内置的 Qwen 模板拼。但这个机制在一次事故里浮出过水面：工具结果回填时，runtime 内部正是用 chat_template 把 `role="tool"` 的消息拼进上下文的，而那个解析器**要求根节点必须是 JSON 数组**——这就是下一节那个坑的根因。所以即使你不调这个 API，它的规则也会咬你。

### Q：实测数据到底有哪些？哪些是能报的，哪些不能报？

**一句话答案：** 能报的只有**端到端全链路时延**和**内存占用**；**tokens/s 和首 token 延迟我没有独立打点，不能报**——这两个数在仓库里根本不存在。

**展开讲：** 先把口径钉死。`BENCHMARKS.md` 2.7 节测的**不是 NPU 推理延迟**，而是**一条自然语言任务的全链路耗时**，里面包含 N 轮 LLM 推理 + 每轮工具执行（读 sysfs / 连 9000 端口取帧 / 读事件日志）+ 中文生成。它和"单帧推理 15.95 ms"完全不是一个量，**不可互相换算或比较**。

实测值（EVM3588-B，Qwen3.5-2B W8A8，RKLLM 1.3.1）：

| 任务类型 | 端到端耗时 | 涉及工具数 |
|---|---|---|
| 单工具问答（查温度/查灯态） | 18~40 s | 1 |
| 双工具闭环（查状态→控灯） | 23~37 s | 2 |
| 条件决策（先看画面再决定） | 36~59 s | 2 |
| 多步综合巡检 | 106.5 / 112.2 / 123.9 s（三次独立测量） | 4~5 |
| 长上下文边界（800 字指令） | 85~113 s | 1~2 |
| 单轮 NPU 推理（含生成） | ≈10 s 量级 | — |

最后一行是关键，也是我必须在面试里主动交代的：**≈10 s/轮 是由总时长 ÷ 轮数反推的估算，不是实测**，单轮推理的 prefill / decode 分解**我没有独立打点**。所以任何"首 token 延迟多少毫秒""tokens/s 多少"的问题，我的标准答案是：**这个数我没有，要报就是编的**。要拿到它很简单（在回调里打时间戳、统计 token 数），但我当时优先解决的是功能正确性，这是个已知的测量缺口。

已经独立测过的工具端开销倒是可以报，因为它小到可以忽略：读 sysfs **< 1 ms**、读 9000 端口一帧**有 300 ms 超时上限**、写 LED + 回读 **< 10 ms**。这就把账算清了——**时延几乎全在 LLM 生成上，不在工具上**，所以优化方向只能是"少跑几轮"或"换更小的模型"，不是"优化工具代码"。

内存这块是可以硬气报的：模型权重 **2.8 GB**，板子 **8 GB** 内存，**加载完成后系统可用内存稳定在 6.1 GB 量级**。这个余量是整个架构成立的前提——因为 NPU 上还有一路 YOLOv8 在 7×24 跑，视觉链路自己也要内存。

**如果被追问「三次为什么差 17 秒？」：** 不是性能抖动，是**任务本身不同**。差异来自模型每次生成的 token 数不同 + 工具链长度不同（4 个 vs 5 个不同工具 → 轮数不同）。这也说明一件事：**这套系统的时延主要由"模型决定花多少字说话"决定，不由硬件决定**，所以拿它当性能指标对外宣传是不合适的——`BENCHMARKS.md` 里我自己写的局限就是"n=3，仅作量级参考"。

### Q：大模型和视觉模型抢 NPU，具体是什么局面？

**一句话答案：** 视觉侧是 3 个 context **分别绑死 3 颗 NPU 核**做真并行、7×24 不停；LLM 一加载就也要这三颗核，于是视觉的帧率先掉——**这就是"快慢双系统"存在的全部理由**。

**展开讲：** 我的视觉网关是这么工作的：3 个独立 rknn context，每个 `rknn_set_core_mask` 绑一颗核，三核并行把 YOLOv8 的吞吐从单核推到三核聚合。这个设计的隐含假设是"三颗核归我"。LLM 进来之后，这个假设就破了——`rkllm_init` 会把矩阵运算派到 NPU 3 核协同上，它不会跟你商量时片分配。

这件事我不是纯推理，是采过样的：用 `lab/tests/bench_contention_sampler.py` 每秒采温区 / NPU 三核负载 / 内存，600 个样本的结论是 zone0 中位 **33.31 °C**、NPU 均值中位 **14%** / p90 **63.5%**、内存 **4.41~6.65 GB**。注意 p90 到 63.5% 而均值才 14%——这说明 NPU 是**阵发式忙**，不是持续满载，所以"抢"的后果是**尖峰时段的排队延迟**，而不是稳定的降速。但必须诚实：这是**混合负载下的观测采样，不是严格的 S1/S2/S3 三场景对照实验**，`AGENT_TEST_PLAN.md` 里设计的那套对照（仅网关 / 仅 LLM / 同时）我还没跑完。

架构上的结论反而很清楚，三条理由任何一条单独成立就不该让 LLM 常驻：

第一，**NPU 竞争**——三颗核被推流主业务占着，巡检是伴生功能，没资格影响主业。

第二，**时延不对等**——LLM 单次几百 ms 到秒级、调度不可控；而"温度超限→闪灯"是毫秒级反射，`if (temp > 75.0)` 成本约等于 0。这个位置放模型是纯亏。

第三，**可靠性**——告警是安全行为，必须可预测、可回归；LLM 输出不确定，可能幻觉、拒绝、超时。

所以最终形态是：**快层零模型依赖，只链 std + pthread，连 `rknn_api` 都不链接；慢层（Agent）只在需要研判/汇报时被叫起来。** 一句话概括：**该用 if 的地方不要用 LLM。** 快慢双系统的完整设计在第 12 章，这里只要记住它是被 NPU 竞争逼出来的。

> 【费曼讲解】想象你家里厨房只有一口灶、一口锅。你妈（视觉网关）天天用它炒菜，是刚需。你突然说"我要炖个佛跳墙"，炖三小时。结果不是"佛跳墙和炒菜并行"，是**全家没饭吃**。
> 不懂的人会想："NPU 有 3 颗核，LLM 分一颗不就行了？"——错在这里：LLM 的 decode 是逐 token 串行的，每一个 token 都要完整过一遍全部权重，**它要的不是"一颗核"，是"整块 NPU 的带宽和算力"**，切开反而谁都跑不快。
> 一句话戳破：**不是算力不够分，是这两种负载抢的是同一个瓶颈，切分不能消灭排队。**
> 回到术语：这就是为什么端侧 Agent 必然长成"快层纯规则 + 慢层按需唤醒"的双系统，而不是"一个大模型管所有事"。

### Q：上端侧大模型最常见的四个坑是什么？

**一句话答案：** 内存不够（不是 free 不够，是 NPU 的 CMA 被钉死）、上下文超限、输出截断、输出不是合法 JSON——**这四个我全踩过，每个都有真实报错**。

**展开讲：**

**坑一：内存。** 表面上模型占 2.8 GB、板子 8 GB，看起来绰绰有余。但真正的坑不在这个数，而在 NPU 专用的那块 CMA 内存。我遇到的是：加了 `fork()` 做用户态 LED 爆闪之后，重启 Agent 时 `rkllm_init` 失败，报 `failed to malloc npu memory, errno 14 Bad address`，**申请的是 205799424 字节（约 196 MB）的 NPU 内存，而 free 显示还有 6 GB 可用**。根因是 `fork()` 复制整个地址空间（写时复制），包括 RKLLM runtime 已经 mmap 的 NPU DMA 映射；爆闪子进程是个 `while true` 死循环、没有退出条件，父进程退出后它变成孤儿还在跑，**驱动认为那块 NPU 内存仍被占用**。修法只有一个：**fork 之后立刻 execl**，重建地址空间，映射全部丢弃。这条的通用教训是：**fork 是克隆，不是启动新程序，设备内存映射也会被克隆。**

**坑二：上下文超限。** 见上一节的 `The context is not enough! history_s:1309, cur_input_s:843`。这个坑的隐蔽之处在于**它只在"任务复杂到要调多个工具"的时候才炸**，简单问答永远正常，所以很容易在开发后期才爆出来。修法是 `max_context_len` 从 2048 提到 8192。

**坑三：输出截断。** `max_new_tokens` 从 **384** 提到 **512**。现象是长研判报告**断在表格中间**——模型没报错，进程 exit code 也是 0，看起来"跑完了"，实际上结论没写出来。这类失败最危险，因为它不报错。

**坑四：输出不是合法 JSON。** 这个有两层。运维层：工具结果回填时如果传的是 JSON **对象**，runtime 直接拒，报 `E rkllm: Please provide a valid JSON format string. example: [{"temperature": 26.1}], do not include extra newlines, trailing commas, or any characters outside the JSON array.`——**必须是数组，一个工具也得是长度 1 的数组**。应用层：模型吐出的参数值经常带换行（`"\nalarm\n"`），不 trim 直接比白名单就判非法，本地手测能过、真实输出偶发失败。

**如果被追问「为什么必须是数组？」：** 因为 runtime 把工具结果包进 chat_template 的 `role="tool"` 消息，解析器要求根节点是 Array。这其实是 OpenAI Function Calling 的规范——一次可以返回多个工具结果，天然就是数组。所以"只有一个工具也必须是长度 1 的数组"不是怪癖，是规范的下推。

**如果被追问「这些坑你现在怎么防？」：** 三个方向。① 参数层面：`max_context_len` / `max_new_tokens` 按"最坏一轮"配，不是按平均值配。② 接口层面：返回值统一包数组、写库前 trim、失败必须带结构化错误码。③ 进程层面：要跑外部命令就 fork+exec，绝不留裸 fork 的长寿子进程。

> 【费曼讲解】"上下文窗口爆掉"到底是什么感觉？把它想成一块白板。你和模型的所有对话——你的问题、模型说过的话、每个工具的返回——**全都写在这块白板上，而且不许擦**。白板写满了，新的一条就写不上去，模型只能"看见"前面一半，于是告诉你"我不知道后面发生了什么"。
> 不懂的人会想："那我让他总结一下前面的内容不就行了？"——错在这里：总结这个动作本身也要写在白板上，**你越总结，白板越满**。
> 一句话戳破：**上下文不是"记忆"，是一块只增不减、还会被工具返回值灌满的缓存。**
> 回到术语：`max_context_len` 就是白板的面积，`history_s` + `cur_input_s` 就是已经写满的两块区域，相加超过白板面积，runtime 直接拒绝推进。

## 三、这一章的"记忆锚点"

- **RKLLM = 运行时，`.rkllm` = 模型**：`librkllmrt.so` v1.3.1 只负责执行，权重 2.8 GB 在模型文件里。
- **选型理由的重点是"能吃到 NPU"**：llama.cpp / MNN / ONNX Runtime 在这块板子上用不了 NPU，而 decode 是逐 token 串行的，硬件加速是生死问题不是百分比问题。**没有跑过对照实验，就只说到"用不上 NPU"为止。**
- **W8A8 = 权重 8 bit + 激活 8 bit**：权重量化决定带宽和速度，激活量化决定能不能全程走 int8 通路。W4A16 更快更准是**原理推断，不是我的实测**。
- **两个参数两个坑**：`max_context_len` 2048→8192（`history_s:1309, cur_input_s:843` 挤爆）；`max_new_tokens` 384→512（报告断在表格中间）。
- **能报的实测只有两个**：端到端 18~40 s（单工具）到 106.5~123.9 s（多步，n=3）；加载后可用内存 6.1 GB 量级。**tokens/s 和首 token 延迟没有打点，不能报。**
- **NPU 竞争是快慢双系统的唯一动机**：视觉三核绑死 7×24，LLM 一加载就抢同一批核；600 样本显示 NPU 均值 14% / p90 63.5%，是阵发式忙。
- **内存坑的真相是 CMA 不是 free**：裸 fork 的子进程继承 NPU DMA 映射，孤儿进程把 196 MB 钉死，`rkllm_init` 报 errno 14 而 free 还有 6 GB。
- **工具结果必须是 JSON 数组**：单对象被 runtime 拒；一个工具也成为长度 1 的数组，因为 chat_template 的 `role="tool"` 解析器要求根节点是 Array。

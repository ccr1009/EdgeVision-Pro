# 第 2 章 文件 IO 与进程

> 一句话心智模型：Linux 把温度、LED、模型、摄像头全做成了"文件"，所以"打开—读—写—关掉"这四步系统调用，就是你和内核之间唯一的语法；而进程是这套语法的执行者，它能 fork 出一个自己，也能 exec 换成别人。

## 一、先建立心智模型

```
    进程自己的 fd 表（本质就是一张数组，下标从 0 开始）

    fd 0 ──►  stdin        终端 / 管道
    fd 1 ──►  stdout       终端 / 管道
    fd 2 ──►  stderr       终端 / 管道
    fd 3 ──►  /sys/class/thermal/thermal_zone0/temp       （本项目：读温度）
    fd 4 ──►  data/models/yolov8n_dflfree_rk3588_i8.rknn  （本项目：模型文件）

    每个表项再指向内核的"打开文件表"（记着偏移量、读写模式、引用计数）
    打开文件表再指向 inode（文件本体），最终落到磁盘 / 设备上
```

```
   你手里只有"下标"，没有指针，也没有文件本身。

   fork()  ──► 复制一个进程（写时复制页表，先共享物理内存）
   exec()  ──► 不新建进程，把当前进程的代码段整个换掉，PID 不变
   wait()  ──► 父进程回收子进程的退出码，不收就变僵尸
```

**记住这一个比喻**：fd 是**储物柜的号码牌**，不是柜子里的东西。你把号码牌弄丢了（close），柜子里的东西就没法通过你取出来；同一个柜子可以被好几个号码牌指着（fork 之后父子共享），所以"关掉一张牌"不等于"柜子清空了"——这正是管道 EOF 那个坑的根源。

## 二、问答正文

### Q：fd 到底是什么？为什么 0、1、2 一开机就被占了？

**一句话答案：** fd 是进程内 fd 表的下标，不是指针也不是文件；0、1、2 分别是 stdin、stdout、stderr，已经被占了，所以新 open 出来的第一个 fd 一般是 3。

**展开讲：** 内核里真正的结构是三层：进程持有 fd 表（数组）→ 表项指向系统级的"打开文件表"（记录偏移量、读写模式、引用计数）→ 再指向 inode（文件本体）。所以同一个文件被 open 两次会得到两个不同的 fd、两个独立的偏移量；而 fork 之后父子进程的 fd 指向**同一个**打开文件表项，共享偏移量。

我第一周做实验，读 `/sys/class/thermal/thermal_zone0/temp`，拿到的就是 fd 3；这个文件里是一个毫摄氏度整数，要除以 1000 才是摄氏度，我读出来是 **38.85 C**，而且每次读都在跳——因为它是内核实时生成的，不是磁盘上的静态文件。

**如果被追问「fd 是进程私有的还是系统共享的？」：** 表是进程私有的，表项指到的"打开文件"是共享的。fork 之后父子共享偏移量、也共享文件状态标志，但不共享 fd 号本身（父子可以各自 close 自己的那张牌）。

**如果被追问「fd 会不会用光？」：** 会。每个进程有 `RLIMIT_NOFILE` 上限，用完 open 返回 -1、errno 是 EMFILE。写服务器的时候连接只 accept 不 close，就是这个死法。

**面试怎么讲：** 先甩"fd 是下标不是指针"，再补一句"fork 之后父子共享同一个打开文件表项，所以共享偏移量"——这句话能把 90% 只会背"fd 是文件描述符"的人区分开。

### Q：open 失败怎么判断？失败之后要做什么？

**一句话答案：** 成功返回**当前最小的可用 fd**，失败返回 -1 并设置 errno，必须判 -1 并打 errno，不能假设一定成功。

**展开讲：** "最小可用"这个细节有实际意义：如果你 close 了 fd 3，下次 open 就会把 3 还给你。这不是玄学，是内核就是从头扫数组找第一个空位。

工程上真正要命的是**不检查返回值**。我项目里有个真实案例：给 LED 写 `trigger=timer` 这条 sysfs 属性，内核根本没编 `CONFIG_LEDS_TRIGGER_TIMER`，`write` 返回 EINVAL，但旧代码不检查返回值 → 工具对外返回 `success: true`，灯其实一点没变。后来改成每一步都查返回值（失败报 `sysfs_write_failed` 加具体节点名），全部写完之后再**回读**实际状态，不一致就报 `readback_mismatch`。这条教训我总结成一句话：**写返回成功 ≠ 生效，只信回读值。**

**如果被追问「那 read/write 的返回值呢？」：** read 返回 0 是 EOF、-1 是错、正数是真读到但**不保证读满**；write 也可能只写一部分，返回值小于请求长度就必须接着写剩下的。我推流那段 `send` 就是同一个道理，标准做法是循环 `send(..., 已发偏移, 剩余长度)`。

**面试怎么讲：** 别只说"要判返回值"，讲"我曾经因为不判返回值，让一个假成功的工具骗了三天"——这句话带细节、带代价，可信度立刻不一样。

### Q：read 返回 0、返回 -1、返回 5，分别代表什么？

**一句话答案：** 正数=真读到的字节数（可能少于你要的），0=EOF（对端关闭或文件读完），-1=真出错要看 errno；-1 且 errno 是 EINTR 不算错，重试就行。

**展开讲：** 三个分支必须分开处理，漏一个就是线上事故。我最容易漏的是 0：读到 EOF 还在用 buffer，等于把上一帧的垃圾数据当成新数据读了进去。

EINTR 的成因是信号打断阻塞的系统调用。正确写法是 `while (n < 0 && errno == EINTR)` 重试，或者用 `sigaction` 时带 `SA_RESTART` 让内核自动重启。不处理 EINTR 的症状特别讨厌——偶发失败、难复现，因为只有恰好来信号那一瞬间才会中招。

**如果被追问「非阻塞 fd 上 read 返回 -1 呢？」：** 那可能是 EAGAIN/EWOULDBLOCK，意思是"现在没有数据"，不是错误、也不是结束。这在第 5 章 epoll 里是核心：ET 模式下必须一直读到 EAGAIN 才算读完。

**如果被追问「那 read 能不能返回 0 但没到 EOF？」：** 普通文件/socket 不会。但如果你请求的字节数是 0，read 直接返回 0，这不算 EOF——所以别传 0 长度去"探测"。

**面试怎么讲：** 把三个返回值当成三条独立的分支讲，再补一句"0 最容易漏，因为它不报错，只是安静地把垃圾读进来"。

> 【费曼讲解】把 read 想成**去食堂打菜**：你说"来五勺"，阿姨看你盘子里只剩两勺的量，就给你两勺——她没骗你，是你自己假设了"要多少给多少"。盘子里彻底没菜了（返回 0）不叫失败，叫"没了"。只有勺子掉了、窗口关了（返回 -1）才是真失败。而不懂的人通常会错想成"read 要么全给我、要么报错"，于是写下 `recv(fd, buf, 248, 0)` 之后直接解析——网络抖一下，他解析的就是半帧乱码。一句话戳破：**系统调用只承诺"给你一部分"，从不承诺"给你全部"。** 回到术语：这叫短读（short read），所以要有"循环读到够/读到 EAGAIN"的读法。

### Q：lseek 和 stat 都能拿文件大小，区别在哪？

**一句话答案：** stat 查元数据、不用打开文件、不动读写位置；lseek 必须在 fd 上做，而且会把当前偏移移到末尾，想再读得 lseek 回去。

**展开讲：** `lseek(fd, 0, SEEK_END)` 的返回值就是文件大小。我用模型文件做过对照：两种方法都是 **6526425 字节**，一致。这个数字本身没意义，意义在于"两个独立途径互相验证"。

真正的坑是类型：`off_t` 是 64 位，`printf` 必须用 `%ld`。用 `%d` 会截断，小文件看不出来，大文件直接打出负数或者乱值。这种 bug 不崩、不报错，就是慢慢给你错的数据。

**如果被追问「模型加载时你用哪个？」：** 加载 `.rknn` 我用的是 `fopen` + `fseek(SEEK_END)` + `ftell` 拿大小，再一次性 `fread` 进 `std::vector`，然后交给 `init_from_memory`。用 `stat` 也行，但我这里已经要打开文件了，顺手 ftell 少一次系统调用。

**面试怎么讲：** 说"两种方法我都验过，结果一致"，比背定义强；再补一句"off_t 是 64 位，printf 要用 %ld"，这是真踩过的人才记得的细节。

### Q：ioctl 是什么？为什么不能直接用 read/write？

**一句话答案：** ioctl 是设备专属的**控制通道**，传的是"命令号 + 参数指针"，不是数据流；read/write 只能搬数据，搬不了"给我设成这个模式"这种指令。

**展开讲：** read/write 的语义是"搬字节"，而设备有大量非数据类操作：设置终端窗口大小（TIOCGWINSZ）、设置摄像头格式（V4L2 的 VIDIOC_S_FMT）、让 LED 进入某种触发模式。这些操作的参数结构各不相同，没法塞进 read/write 的签名里，于是有了 `ioctl(fd, 命令号, 参数指针)` 这个万能口子。

命令号是驱动定义的魔数，不同设备完全不同，用错了返回 ENOTTY。我第一周用 `ioctl(TIOCGWINSZ)` 读出过终端的行列数——这个调用就是 `ls` 能自适应宽度、`vim` 能排版的原因。

**如果被追问「那 sysfs 和 ioctl 什么关系？」：** 都是设备控制接口，但形态不同。sysfs 是"把每个控制项做成一个文件"，用 read/write 字符串就能操作（写 `255` 到 `brightness` 就点亮 LED）；ioctl 是"一个 fd 加一把命令号"。sysfs 更好调试（cat/echo 就行），ioctl 更适合传结构体、更适合高频调用。

**面试怎么讲：** 一句话点出"ioctl 是控制面，read/write 是数据面"，然后举 V4L2 设格式的例子——面试官一听就知道你真的用过设备节点。

### Q：写 sysfs 明明返回成功，为什么灯没变？

**一句话答案：** sysfs 的 write 只代表"内核收下了这个字符串"，不代表驱动执行成功；而且很多属性写错值会返回 EINVAL 却被忽略，所以必须判返回值并**回读**校验。

**展开讲：** 我项目里有两层坑叠在一起。第一层：写 `trigger=timer` 返回 EINVAL（内核没编这个 trigger），代码没判返回值，于是上层认为成功。第二层更隐蔽：**正在爆闪的报警灯被读成"熄灭"**——`brightness` 在 255 和 0 之间以很快的节奏跳，你恰好在 0 的那一瞬间读到，就以为灯是灭的。Agent 据此给出了一个完全错误的因果解释。

修法有两处：写入侧每一步查返回值、全部写完后回读实际状态比对；读取侧不看瞬时值，改看**占空比**——采样一段时间统计高电平比例，实测 20.0% 变成 49.7%，这才是"灯真的在爆闪"的证据。

**如果被追问「为什么不干脆用 ioctl 控 LED？」：** LED 子系统标准接口就是 sysfs，`/sys/class/leds/work/brightness`，用 shell 就能验，调试成本最低。ioctl 在这里没有优势。

**面试怎么讲：** 这条特别值钱，因为它同时包含"不判返回值"和"采样方法错"两种典型错误，最后还给了一个工程化的验收判据（占空比）。面试官会觉得你是真在跟硬件打交道。

> 【费曼讲解】把 sysfs 想成**给物业填的报修单**：你把单子塞进窗口（write 返回成功），只代表"单子被收了"，不代表水管修好了。不懂的人通常把"窗口收单"当成"活干完了"，于是写 `echo 255 > brightness` 之后 `echo 1` 就说"灯亮了"。而你连"灯到底亮没亮"都不能用眼看一眼——它每秒闪好几次，你瞄的那一眼可能是灭的。一句话戳破：**写入是"发起"，回读才是"结果"。** 回到术语：这就是为什么设备驱动测试里永远要有 readback 校验，以及为什么周期性信号要用占空比而不是瞬时值来度量。

### Q：fork 之后到底发生了什么？为什么返回值有三个？

**一句话答案：** fork 复制出一个几乎一样的子进程，父子都从 fork 后面那行继续跑；父进程拿到子 PID，子进程拿到 0，失败返回 -1。

**展开讲：** 三个返回值就是在告诉你"我现在是谁"：拿到 0 的这个进程就是新建的子进程（它没有"自己的 PID"这个概念可用，所以给 0）；非 0 是父进程，那个数就是子进程的 PID；-1 是失败（常见原因是进程数超限或内存不足）。

所以标准写法是 `pid_t pid = fork(); if (pid == 0) { 子进程干活; } else if (pid > 0) { 父进程继续; } else { perror; }`。

**如果被追问「fork 复制内存，那不是很慢？」：** 用的是写时复制（Copy-On-Write）：fork 只复制页表，父子共享同一份物理页，谁写谁才触发复制。所以 fork 本身很便宜，exec 之后才真正把地址空间换掉。

**如果被追问「fork 之后子进程能不能直接 return？」：** 子进程应该用 `_exit()` 而不是 `exit()`。`exit()` 会刷新 stdio 缓冲区，父子共享的那份缓冲区会被刷两次，于是你会看到一行输出打印两遍。这个现象我在第一周就撞上过。

**面试怎么讲：** 先说三个返回值各自代表谁，再说 COW 解释"为什么快"，最后补 `_exit` 这个细节——这三层说完，fork 就没有可问的了。

> 【费曼讲解】写时复制就像**两个人共用一本笔记本，谁要写字才去复印一页**。不懂的人通常想成"fork 就是把我整个内存拷一份"，于是得出结论"fork 很重，能不用就不用"。一句话戳破：**内核只拷了"目录"，没有拷"内容"；真正的复制发生在第一次写的时候。** 但这里有个反向的坑——这个比喻还有个后半句：**"目录"里也包括设备映射**。我项目里就栽在这：fork 出 LED 爆闪子进程，它继承了父进程 mmap 的 NPU DMA 内存映射，父进程退出后子进程还活着（变成孤儿死循环），驱动认为那块 196MB 的 CMA 内存仍被占用，下一次 `rkllm_init` 直接报 `errno 14`（ENOMEM），而 `free` 显示还有 6GB。修法就一句：**要做"跑个外部命令"，必须 fork 之后立刻 exec，重建地址空间。**

### Q：exec 会创建新进程吗？为什么 LED 爆闪必须 fork + exec？

**一句话答案：** 不会，exec 只是把当前进程的代码段整个换成新程序，PID 不变；而 fork 之后不 exec，子进程就是一份"完整的克隆"，连设备内存映射、文件描述符表都被继承了。

**展开讲：** `fork` + `exec` 是 shell 执行命令的标准动作：fork 出子进程 → 子进程 exec 成目标程序 → 父进程 wait 收尸。exec 成功之后不返回（返回了就说明失败了）。

我踩的那个 NPU 内存案例，根因就是"只 fork 没 exec"：子进程继承了父进程的整个地址空间，包括 RKLLM runtime 已经 mmap 的 NPU DMA 内存。子进程不死，驱动就认为内存还被引用。加上 `execl` 之后，子进程的地址空间重建，映射全部丢弃，ENOMEM 消失。

同一个 fork 还有第二个后果：**继承 fd 表**。爆闪子进程没重定向 stdout，就持有父进程 stdout 管道的写端；父进程退出后这个死循环子进程还在，读端永远等不到 EOF，于是回归脚本卡死 **270 秒**被强杀——功能其实是对的（灯真在闪）。修法还是 daemon 化的标准动作：exec 前把 0/1/2 全部重定向到 `/dev/null`，修完同一条用例 **21 秒**正常返回。

**如果被追问「为什么交互式跑就正常，脚本跑就卡死？」：** 因为交互式是 tty，不依赖 EOF 判断结束；脚本是 pipe，读端要等所有写端关闭才返回。所以"tty 正常、管道卡死"就是 fd 继承的指纹。

**面试怎么讲：** 这两个案例（NPU 内存被钉死、命令卡死 270 秒）是我这一章最硬的东西，讲的时候先说现象（free 还有 6GB 却 ENOMEM / 功能对但命令不返回），再说"fork 是克隆不是启动新程序"，最后说修法。面试官会很自然地问下一个问题。

> 【费曼讲解】把管道想成**一根水管，两头各有一个水龙头**，只要还有任何一个水龙头开着，另一头就永远等不到"水没了"这个信号。不懂的人通常以为"我进程都退出了，管道自然就关了"。一句话戳破：**管道是引用计数资源，不是某个进程的私有财产；谁继承了这个写端，谁就在替它续命。** 回到术语：fork 复制的是 fd 表（同一批打开文件表项的引用），所以子进程里那个 fd 1 和父进程的 fd 1 指的是同一个管道写端，引用计数不归零，读端 read 就永远拿不到 0。

### Q：僵尸进程和孤儿进程，哪个有害？

**一句话答案：** 孤儿无害（被 PID 1 收养），僵尸有害（占着进程表项，退出码没人回收）。

**展开讲：** 僵尸的成因很具体：子进程已经死了，但父进程还没 `wait`，内核必须保留它的退出码等父进程来取，于是在进程表里留一个空壳，状态显示成 defunct。它不占内存、不占 CPU，但占 PID 资源——父进程一直不 wait，攒够了就 fork 不出新进程。

避免方式就是父进程必须 `waitpid`。我在板上真的用 `ps` 抓到过这个空壳，然后调 `waitpid` 把它收掉，再 `ps` 就没了——这种"亲眼看见"比背定义有用得多。

孤儿是反过来的：父进程先死，子进程还活着，被 init/systemd（PID 1）收养。这本身是正常机制，我那个爆闪子进程就是这么变成孤儿的——问题不在"孤儿"这个身份，而在于它是个永不退出的死循环，还握着 NPU 映射和 stdout 写端。

**如果被追问「怎么一次性避免僵尸？」：** 要么显式 wait，要么把 SIGCHLD 设成 `SIG_IGN`（子进程退出自动回收），要么用 double fork 让孙子进程被 init 收养。我用的是显式 `waitpid`，因为我要拿退出码。

**面试怎么讲：** "孤儿无害、僵尸有害"这句口诀先给，再补一句"我实测抓到过 defunct 并用 waitpid 收掉"，最后升华成"fork 出来的东西，父进程有义务收尸"。

### Q：waitpid 拿到的那个整数，能直接当退出码用吗？

**一句话答案：** 不能，那是个打包过的状态字；要用 WIFEXITED 判断是否正常退出，再用 WEXITSTATUS 取出真正的退出码。

**展开讲：** 低 8 位是终止信号，高 8 位才是退出码，中间还有 core dump 标志位。直接 `printf` 那个整数只会看到一个莫名其妙的数。

我做 fork/exec/wait 实验时，子进程 exec 的是 `uname`，父进程 waitpid 之后用宏解析，退出码是 0（正常）。如果子进程是被信号杀死的，`WIFEXITED` 就是假，这时候再去取 `WEXITSTATUS` 是没有意义的。

**如果被追问「那 kill -9 掉的进程退出码是多少？」：** 不是退出码，是"被信号终止"，`WIFSIGNALED` 为真，`WTERMSIG` 拿到 9。这一点在写守护脚本、判断"是崩溃还是自己退的"时非常关键。

**面试怎么讲：** 说出"高 8 位才是退出码、低 8 位是信号"这个位布局，再补一句用宏而不是自己移位——既显得懂原理，又显得不逞能。

### Q：怎么遍历一个目录？/proc 为什么能 ls？

**一句话答案：** opendir 拿 DIR 指针，循环 readdir 拿 dirent，必须跳过 `.` 和 `..`，最后 closedir；/proc 是内核实时生成的虚拟文件系统，所以 ls /proc 等于看当前进程表。

**展开讲：** readdir 返回的 `dirent` 里有 `d_name`（文件名）和 `d_type`（是目录还是普通文件）。跳过 `.` 和 `..` 是必须的，不跳会把自己套进去。

/proc 里每个数字目录就是一个 PID，里面的 `comm` 是进程名。我第一周做的 Mini-ps 就是扫这个，在板上扫出 **247 个进程**并打印名字。这件事的价值在于：它把"文件"和"进程"两个概念接上了——进程在 Linux 里也是可以用文件接口观察的对象。

**如果被追问「/proc 占磁盘吗？」：** 不占。它不存在于磁盘，是内核在 read 的那一刻现场生成的，`stat` 出来的大小通常是 0，但它能一直读。

**面试怎么讲：** 先给 opendir/readdir/closedir 三步，再甩"我在板上扫出 247 个进程"，最后一句"这就是 ps 的简化版"——从八股直接落到"我自己写过"。

## 三、这一章的"记忆锚点"

- fd 是**下标**不是指针；0/1/2 是 stdin/stdout/stderr，新的从 3 起；fork 之后父子**共享同一个打开文件表项**，所以共享偏移量。
- read 三种返回值：正数=短读（可能不足）、0=EOF、-1=错；EINTR 要重试，**0 最容易漏**。
- `off_t` 是 64 位，printf 用 `%ld`；stat 与 lseek 测大小我在同一个模型文件上都得到 **6526425**，互验才算数。
- fork 是**克隆不是启动新程序**：COW 只复制页表，但设备映射、fd 表、stdio 缓冲一起被继承 → NPU 196MB 被钉死、命令卡死 270 秒都是这一句的推论。
- 子进程用 `_exit` 不用 `exit`，否则 stdio 缓冲被刷两次，输出打两遍。
- 僵尸有害、孤儿无害；退出码要 `WIFEXITED` + `WEXITSTATUS` 解析。
- **写成功 ≠ 生效**：sysfs 写 LED 要查返回值 + 回读，周期性信号要看**占空比**（20.0% → 49.7%）而不是瞬时值。

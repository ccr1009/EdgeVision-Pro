# 第 9 章 INT8 量化与精度评测

> 一句话心智模型：量化不是"把模型压小"，而是**给每个张量配一把固定刻度的尺子**——尺子按校准集量身定做，刻粗了大值被削平、刻细了小值全归零；而"特征图很像"根本证明不了尺子合适，只有端到端跑真 mAP 才算数。

## 一、先建立心智模型

这一章讲两件事：**INT8 怎么把 float32 模型变成 4.34 MB 还能跑**，以及**我怎么学会"别信看起来很像"**。第一件是原理，第二件才是分水岭——我一开始拿特征图余弦相似度当精度指标，0.9965 就判了 PASS，结果那版的分类头已整段塌缩成常数 0.5，一张真实图都分不对类。**指标飘绿、模型已废**，这是这个项目里最值钱的一次打脸。

```
  量化在做什么：给每个张量配一把"刻度固定的尺子"

  float32 张量              量化参数                     INT8 张量
  [0.0, 0.5, 1.0]   --+     scale = 1/255            -->  [-128, 0, 127]
                      |     zero_point = -128
                      |     q = round(x/scale) + zp
                      |
                      +--  反量化 x ≈ (q - zp) * scale  -->  [0.0, 0.5, 1.0]
                                                        （有舍入误差，不可逆）

  尺子从哪来？—— 校准集。一张张真实图喂进去，记录每层激活的 min/max

  校准集对了：真实图 -> 激活落在量程内   -> 4.34 MB，mAP 只掉 0.85 点
  校准集错了：真实图 -> 激活顶到量程边缘 -> 仍 4.34 MB，cls 塌成常数 0.5

  所以这一章的结论只有一句：
  量化掉点的第一主因不是算法、不是 bit 数，是"你拿什么东西去量它"
```

**记住这一个比喻**：量化像量身高，但你手上的尺子是**先量了另一批人才刻出来的**。你量的是幼儿园小朋友，尺子只刻到 1.2 米；转头去量篮球队，所有人顶在同一条线上——不是队员太高，是尺子量程不够。INT8 的翻车，本质都是这一件事。

## 二、问答正文

### Q：量化到底把什么变成了什么？

**一句话答案：** 把每个 float32 数用一个整数加一个"刻度"表示，`q = round(x / scale) + zero_point`，反量化 `x ≈ (q - zero_point) × scale`；`scale` 和 `zero_point` 是**每个张量一份**的固定参数，转完就写死。

**展开讲：** 举个板上真实的例子，模型输入属性实测就是 `INT8 / NHWC / zp = -128 / scale = 1/255`：像素归一化到 0 到 1，`1/255` 正好把 [0, 1] 铺满 256 个整数格；`zp = -128` 说明浮点 0 对应整数 -128，于是浮点 1 落在 127，全量程用满。这个式子最重要的性质是**有损且不可逆**：`round()` 一落地原精度就没了。所以"会不会掉点"问错了，该问"掉多少、掉在哪、能不能接受"。

**如果被追问「为什么不直接 FP16？」：** FP16 也是量化（半精度浮点），体积带宽减半、精度损失极小，代价是算力收益不如 INT8。我选 INT8 是因为主流 NPU 的 INT8 通路最成熟、工具链支持最好，实测 mAP 代价只有 0.85 个点。**FP16 我这条链路没有实测过速度，所以不给两者的性能对比数字。**

### Q：`scale` 到底是什么？为什么它一旦定死就要命？

**一句话答案：** `scale` 是这把尺子的**一格代表多少**——它同时决定量程（能表示多大的数）和分辨率（能分开多小的差异）；而它转换时就固定了，推理时**不会自适应**，超出量程的值只能被削平。

> 【费曼讲解】scale 就是尺子的刻度密度
>
> ① 生活类比：一把尺子只有 256 个刻度（INT8 就 256 个码点）。刻成 0 到 255 毫米，能量 25 厘米的东西，但 1 毫米以下的差别读不出来；刻成 0 到 25.5 米，能读 10 厘米的差别，可量个螺丝全挤在第一个格子里。
> ② 不懂的人会怎么错想：量化不就是把小数点后面的数扔掉吗？那我让 `scale` 越小越精细不就行了。
> ③ 一句话戳破：**码点只有 256 个，量程和分辨率是同一块蛋糕**，想精细就必须短，两者不可能同时最优。校准集干的就是"猜这块蛋糕怎么切最贴合真实数据"。
> ④ 回到术语：`scale` 由校准阶段统计的 min/max 反推（非对称时还要减零点），所以**校准集分布直接决定量程**。校准集窄 → 量程窄 → 真实数据一进来就饱和。

**展开讲：** 这就是那次事故的机理。合成色块图里**根本没有人**，cls 分支的激活分布极窄，统计出的量程也被压得极窄；真实画面一进来，激活全部超出量程、被夹到同一个码点——**整条分支输出变成同一个数**，后面的 sigmoid 把它变成常数。这不是"精度差一点"，是"信息被整段删掉"。

### Q：对称量化和非对称量化，差在哪？`zero_point` 在干嘛？

**一句话答案：** 对称量化把零点钉死在 0（`zp = 0`），量程 ±max，算得快、权重好用；非对称量化的零点可平移（我这里 `zp = -128`），能把 256 个码点全铺在实际分布上，"全正"或"全负"的分布不浪费码点。

**展开讲：** 为什么重要？因为激活分布极不对称：ReLU 之后全是非负数，强行对称量化就有一半码点（负数那半）白空着，等于只剩 128 个格子表达单方向数据——**分辨率直接腰斩**。非对称把 `zp` 一挪，256 个格子全用上。代价是乘加时多一项 `zp` 修正、硬件更贵，所以惯例是**权重用对称、激活用非对称**。

**如果被追问「你这个模型到底是哪种？」：** 输入层是 `INT8 / NHWC / zp = -128 / scale = 1/255`，`zp` 不为 0，所以非对称。但**网络内部每层的量化参数我没有逐个 dump 分析过**——那是工具链内部的事，我只验证最终精度，这点实话实说。

### Q：为什么卷积权重要 per-channel，而激活可以 per-tensor？

**一句话答案：** 因为同一层的**不同输出通道数值分布差得很远**——有的通道权重在 0.001 量级、有的在 1 量级，共用一把尺子的话小通道会被整个压成 0。per-channel 就是每个通道单独配一把尺子。

> 【费曼讲解】为什么 per-channel 是必须的
>
> ① 生活类比：一个班 64 个学生分 64 组交作业，每组"厚度"标准不一样——第一组交小论文（几页），第二组交一整本册子。你用同一把尺子给全部 64 组打分，第一组全被判成 0。
> ② 不懂的人会怎么错想：一层就一个张量，那自然一个 `scale`，per-tensor 才符合直觉。
> ③ 一句话戳破：**"一个张量"在数学上是一块，在数值上是 64 块互不相干的数据**；用一个 `scale` 等于让 64 个通道抢同一把尺子，谁数值大谁赢。
> ④ 回到术语：per-channel 指卷积权重按输出通道各算一份 `scale`，共 N 个；per-tensor 是全张量共用一份。权重是**离线静态**的，多存几十个 `scale` 几乎不要钱；激活是**运行时产生**的，逐通道统计代价高，通常才用 per-tensor。

**展开讲：** 这不是我背出来的，是量化论文的标准做法，主流工具链（含 RKNN）默认就是权重 per-channel、激活 per-tensor。边界我说清楚：**我知道这个设计的原因，但这次转换没拿 per-tensor 权重做 A/B，所以我没有"per-channel 比 per-tensor 好多少"的实测数字。**

### Q：为什么量化能加速？是不是"因为 int 算得比 float 快"？

**一句话答案：** 不是。加速来自两件很具体的事——**搬运的字节少了四分之三**，以及**NPU 的 INT8 MAC 阵列一次能塞进更多乘法单元**；"int 比 float 算得快"把原因搞反了。

> 【费曼讲解】"int 算得快"错在哪
>
> ① 生活类比：一个货车队运货，原来每箱装 4 公斤，现在每箱装 1 公斤——车没变快，但同样的货只用跑四分之一的趟数。你感觉"运输快了 4 倍"，快的不是车，是**趟数少了**。
> ② 不懂的人会怎么错想：CPU 里整数加法只要一两个周期、浮点除法要十几个周期，所以 int8 快肯定是因为"整数运算便宜"。
> ③ 一句话戳破：**NPU 上的瓶颈从来不是"一次乘加几个周期"，而是"数据从内存搬到计算单元的带宽"和"这片硅上能塞多少个乘法器"**。INT8 在这两件事上都占便宜，跟指令周期没关系。
> ④ 回到术语：一是访存量，权重从每参数 4 字节降到 1 字节，同样算力需要的带宽降到四分之一；二是算力密度，同面积同功耗的 MAC 阵列，把 8 位乘加单元翻倍比把 16 位翻倍容易得多，所以 INT8 标称吞吐远高于 FP16。

**展开讲：** 再说一件反直觉的：**量化对"算力富余、带宽吃紧"的端侧尤其划算**。我这条链路正踩在这个点上——三核各只有 49% 负载，说明 NPU 一半时间在等数据，少搬四分之三就直接生效。反过来，模型小到全塞进 cache、算力才是瓶颈时，量化收益就会打折。板子标称 6 TOPS 是 **INT8 口径**（3 核 × 2.0 TOPS INT8），**FP16 的标称值我不引用，因为我没测过**。

### Q：RKNN 的 PTQ 流程是怎样的？`dataset.txt` 里放什么？

**一句话答案：** 四步——`rknn.config()` 定预处理口径和目标芯片、`rknn.load_onnx()` 读图、`rknn.build(do_quantization=True, dataset=...)` 做量化、`rknn.export_rknn()` 出文件；`dataset.txt` 里就是**一行一张校准图片的路径**。

**展开讲：** 第二到第三步之间没有"训练"：工具链把校准图一张张喂进去做前向，记录每层激活的 min/max，据此反推 `scale` 和 `zero_point`，再把权重转成 INT8、重写整张图。**全程不反向传播、不改权重**，所以这套流程叫 PTQ（训练后量化），跟 QAT 是两回事。

三个踩过的细节，都是"不看文档绝对想不到"的：

- **`dataset.txt` 里必须写绝对路径。** 写相对的 `calib/xxx.jpg`，工具链会按清单所在目录去拼，最后拼成 `.../calib/calib/xxx.jpg`，报找不到文件。
- **`quantized_iteration` 是 1.x 的参数，2.x 传了直接 `ValueError`。** 版本升级时这类废弃参数会静默变成崩溃点。
- **依赖版本必须精确。** 我钉死的是 numpy 1.26.4 / onnx 1.14.1 / protobuf 3.20.3 / onnxruntime 1.16.0 / scipy 1.13.1 / opencv 4.9.0.80；numpy 2.x、onnx 1.19、protobuf 6.x 装上后是**运行即崩**，不是报错就是段错误。

**如果被追问「转换为什么在板子上做，不用 PC？」：** 因为 rknn-toolkit2 2.x 在 `packages/arm64/` 下就带了完整的 aarch64 wheel，板子 Debian 11 自带 Python 3.9.2，正好是 cp39。整个转换在板上约 **3.5 分钟**（161 层 × 3 轮量化，A76 上单线程），不用配任何交叉环境，一块板子自给自足。

### Q：校准阶段到底在校什么？为什么说它决定生死？

**一句话答案：** 校的是**每层激活值的取值范围**——一张张真实图喂进去，统计每个张量的 min/max，据此定出那层的 `scale`；范围一旦定错，模型就只在这个范围内负责，超出的部分全部饱和。

**展开讲：** 关键在"统计"两个字：不是"看看像不像"，是"取极值"。所以它对**校准集里的异常值和缺失分布极其敏感**：

- 校准集里有极端亮度、极端尺寸的图 → min/max 被拉宽 → 分辨率被摊薄。
- 校准集里**根本没有某类目标** → 那一支的激活分布被压得极窄 → 真实数据一进来就整段饱和。

两条合起来的后果就是：同一份模型、同一套 toolkit 2.3.0、同一个算法 `normal`、同一台板子，**我只换了校准集**，top-1 平均分从 0.5000 跳到 0.8072。**校准集比量化算法重要，这不是感觉，是这一组对照实验说的。**

### Q：校准集翻车那次，具体是怎么回事？

**一句话答案：** 我最早拿 **60 张合成色块图**（纯色矩形 + 纯灰底）当校准集，转出来的模型在真实画面上**框还是对的**，但 9 张真实图的置信度**全部精确等于 0.5000**；换成 170 张真实校准集后回到 0.8072（FP32 是 0.8125）。

**展开讲：** 按时间顺序还原，因为"我怎么发现的"比结论更有价值：

- **第一眼是"一切正常"。** 转换成功、模型能加载、推理有输出、框的位置和 FP32 差不到 1 px。所有自动化检查都是绿的，我一度认为量化已经做完了。
- **第二眼发现"分数全一样"。** 打印置信度时 9 张图**全精确等于 0.5000**——不是"接近 0.5"，是每一位都相同。正常检测器不可能在 9 张不同的图上给出同一个分数。
- **顺着 0.5 反推。** `0.5 = sigmoid(0)`，也就是 sigmoid 的输入全是 0；再往前，是 cls 分支的 logits 被量化成了**同一个常数**。
- **量一下框，确认只有一支坏了。** box 分支坐标和 FP32 差 **< 1 px**——回归那一支完全正常。

这个"只有分类坏、只有框正常"的反差直接指向根因：**cls 分支的激活分布，校准集里根本没覆盖**。合成色块里没有一个人，cls 在标定时从没见过"有人"的激活值，`scale` 被定在极窄区间；真实画面一进来就整体饱和到同一个码点。而 box 分支回归的是几何距离，分布相对稳定，不吃校准集分布，所以它活下来了。

**如果被追问「换成什么样的校准集就好了？」：** 170 张：**50 张板端双摄实拍 + 100 张光照/对比度/伽马/噪声增强 + 20 张合成**。核心是那 50 张实拍——它们决定"有人的画面长什么样"能不能被覆盖；增强的 100 张把量程往外撑，防止极端光照被削平；20 张合成留着，是为了不让量程完全被实拍的窄场景绑死。

### Q：只换校准集，数字到底差多少？

**一句话答案：** 9 张真实图 top-1 平均分：FP32 **0.8125** → 真实校准集 **0.8072（−0.65%）** → 旧合成校准集 **0.5000（−38.5%）**；检出率三组都是 9/9。

**展开讲：** 这张表是所有量化结论里最干净的一组对照，因为**只改了一个变量**：

| 模型 | 校准集 | 检出率 | 平均 top-1 分数 | 与 FP32 偏差 |
| :--- | :--- | :---: | ---: | ---: |
| FP32 ONNX | 不涉及 | 9/9 | 0.8125 | — |
| INT8（NEW） | 170 张真实为主 | 9/9 | 0.8072 | −0.0053（−0.65%） |
| INT8（OLD） | 60 张合成色块 | 9/9 | 0.5000 | −0.3125（−38.5%） |

注意一个极易忽略的细节：**OLD 组检出率也是 9/9**。如果只统计"检出没检出"，这个模型会被判成完全可用——**框都在、位置都对、就是分数全错**。这就是我后来做评测一定看"分数"和"mAP"而不看"检出率"的原因。

**如果被追问「这组数能当精度结论吗？」：** 不能。它是 **9 张静态图、单一场景（宿舍）、top-1 分数统计，不是 mAP**。它的作用是**证明校准集这个变量有多大杀伤力**，不是证明模型精度。真正的精度结论在下面 mAP 那几问。

### Q：余弦相似度 0.9965，为什么是反面教材？

**一句话答案：** 因为那个分类头已经整段塌缩成常数 0.5 的模型，**特征图余弦相似度恰好还有 0.9965、MAE 0.418，按当时的判据全部 PASS**——它对"单个分支塌缩"完全不敏感。

> 【费曼讲解】什么是塌缩，为什么余弦看不见它
>
> ① 生活类比：合唱团 80 个人，79 个唱得和原来一模一样，只有 1 个从头到尾拖长音。你站台下听"整体像不像原来的歌"，感觉几乎没变；但真看演出效果，那个拖长音已经毁了整首歌。
> ② 不懂的人会怎么错想：0.9965 就是 99.65% 像，几乎无损啊，还能有什么问题？
> ③ 一句话戳破：**余弦相似度是"整张特征图求一个平均"，对平均敏感、对局部失效迟钝**；80 个通道里 1 个整段变成常数，整体余弦几乎不动，可那 1 个通道恰好是分类头要用的全部信息。
> ④ 回到术语：塌缩指某个分支的输出退化成常数（方差归零），它的**信息量归零**，但在特征图里只占一小块面积，所以逐层的余弦、MAE 这类指标完全测不出来。

**展开讲：** 这里有三层问题，一层比一层致命：**它是逐层的，不经过后处理**（不落到"框"上，也不管 NMS 之后还剩几个目标）；**它被大量通道的平均表现主导**（cls 那一支全废，其余近似原样，整体依然 0.99）；**它和任务不对齐**（检测在乎框和类别对不对，余弦在乎张量像不像）。所以我现在对这套指标的态度是：**余弦当哨兵，mAP 当裁判**。哨兵能快速发现"这层完全对不上"，但它飘绿不代表模型能用。我也会主动说这指标本身的价值——不是没用，是我用错了地方。

**如果被追问「那你怎么知道 0.9965 那版是坏的？」：** 打置信度打出来的。9 张真实图全部精确等于 0.5000，这不是"精度差"，这是常数。**指标是绿的时候，得有一个"结果长什么样"的检查兜底**，这是我的教训。

### Q：真 mAP 是怎么测的？口径为什么要和 PC 侧完全一致？

**一句话答案：** 用带标注的公开集 **COCO128**（128 张 / **929 个 GT 框** / 71 个类别出现），PC 侧 ONNXRuntime 跑 FP32 基准、板端跑 INT8 导预测，**两边用同一个脚本算 mAP**；口径是 letterbox 640（灰边 114）、conf 0.01、NMS IoU 0.45 class-aware、COCO 101 点插值、IoU 阈值 0.5。

**展开讲：** 我强调"口径一致"，因为 mAP 对**阈值、NMS 策略、坐标逆变换**极其敏感，两边任何一处不同，算出来的差值就不是量化的贡献了。做法是把"算"收拢到一处：PC 端 `convert/eval_map.py` 既算 FP32、也能读板端导出的预测 `txt` 再算 INT8；板端只负责 `deploy/cpp/bench/eval_dump.cpp` 导预测，不参与计算。这样**同一份 GT、同一个 AP 实现**，唯一的变量就是模型。

### Q：FP32 0.6087 → INT8 0.6002，这个掉点怎么看？

**一句话答案：** 掉 **0.0085 个绝对 mAP**，相对 **−1.4%**，落在 INT8 PTQ 的常见区间里；我报"−0.85 个点"也报"−1.4%"，因为换算关系必须当场对得上。

**展开讲：** 这个说法里有两个刻意选择。第一，**绝对值也报、相对值也报**——只报"−1.4%"像在修饰，只报"−0.85 点"又要人自己换算。第二，**两个数分开说**，因为面试官拿计算器一除必须对得上；要是说"只掉了 1%"，被追问就露馅了。

还有三条局限我主动讲，不等人家问：

- **COCO128 是 YOLOv8n 的训练子集**，模型"见过"这些图，绝对 mAP 偏乐观，不能对外说"我在 COCO val2017 上做到 0.61"（官方 val2017 约 0.644）。
- 但**对"量化掉点"这个结论影响很小**：FP32 和 INT8 用同一模型、同一批图，"见过"在两侧同时存在，做差就抵消了。所以我只引用**相对掉点**，不引用绝对值。
- 仍然是 128 张、单一公开集，**不是自建场景集**。要证明"在我的宿舍/实验室也能用"，得自己标一批。

**如果被追问「掉 1.4% 算好还是差？」：** 从公开经验看属于较好水平（INT8 PTQ 常见 1~3%），但我不说"优秀"，因为**不同模型、不同任务的下限差很多，我没做过跨模型对比**。我能确定的是：这个掉点在我的检测任务上可接受，因为框位置偏差 < 1 px、检出率没有下降。

### Q：12.2 MB 到 4.34 MB，能说"压缩了 65%"吗？

**一句话答案：** 不能。12.2 MB 是原始 **FP32 ONNX**，4.34 MB 是图手术之后的 **INT8 RKNN**，中间跨了「量化」和「图手术」两步改造，**把两步收益合进一个减法对外说，是偷换口径**。

**展开讲：** 正确的拆法是把两个变量分开，各说各的：

| 口径 | 数值 | 说明 |
| :--- | ---: | :--- |
| 原始 FP32 ONNX | 12.2 MB | 改造前的起点 |
| 旧 84ch 模型 INT8 | 6.22 MB | **量化这一步**做完 |
| DFL-Free INT8 | 4.34 MB | **图手术这一步**做完，−30.2% |

所以我的标准说法是两句话，绝不合并成一句：**「量化把模型压到 INT8 口径；图手术在 INT8 口径上再从 6.22 MB 降到 4.34 MB，这一步收益是 −30.2%。」** 我不说"从 12.2 压到 4.34、压缩了 65%"，因为那个数字里混着两个不同性质的动作，面试官问一句"这两步各占多少"就穿帮。

**如果被追问「为什么不干脆说合并后的数？」：** 因为合起来那句话没有信息量——**既不告诉别人量化值多少，也不告诉别人图手术值多少**，只有一个凑出来的大数字。而且 ONNX 文件除权重还有图结构和常量开销，"文件小几倍"和"权重少几倍"本来就不是一回事。**能做减法的地方才做减法。**

### Q：为什么 RKNN 的混合量化（hybrid）不是万能的？

**一句话答案：** 因为它只治一种病——"误差集中在少数几层"。做法是把敏感层**回退成 FP16**、其余留 INT8，但**回退的层同时失去 INT8 加速**，而且图会被切成 INT8/FP16 两段、边界要插精度转换，**切得越碎，融合和连续调度的收益掉得越多**。它不是"更好的量化"，是"拿速度换精度的一次重新分配"。

**展开讲：** 敏感层有比较稳定的画像：**网络第一层卷积**（3 通道输入、动态范围最宽，离群通道通常出在这里）、**最后一层输出**（直接决定类别分数或框，误差没有下游可以吸收）、以及**激活动态范围特别大的层**（一个离群值就能把这个张量的 `scale` 拉宽，把其余数值全挤到零附近）。把这些层换回 FP16，等于给它们单独开一条通路。

代价是两条，必须讲清楚：一是这些层不再吃 NPU 的 INT8 MAC 阵列，那段耗时回到 FP16 的水平，**优化收益被吃掉一部分**；二是两段之间要做 INT8 与 FP16 的精度转换，数据得落地一次，NPU 子图被切碎之后算子融合和图级调度都会变差。所以它换来的是**精度的重新分配，不是免费的午餐**。

**如果被追问「那什么时候才该用？」：** 判断依据很硬：**先跑出每层量化误差报告、确认误差确实集中在可数的几层，并且当前掉点已经压不进业务预算**。两个条件缺一个，混合量化就是在用复杂度赌概率。

### Q：你这个项目为什么没走混合量化？

**一句话答案：** 因为**精度预算够用、收益不可测**——真 mAP 只掉 0.85 个点（0.6087 → 0.6002，−1.4%），在这个预算内做混合量化是负收益：**多花工程时间，换不到能测出来的精度提升**。我是评估过、没落地，不是不知道有这条路。

**展开讲：** 三条实话：

- **动机不足**：0.85 个点的掉点在我可接受的范围内，而混合量化的收益上限也只是"把这 0.85 个点救回来一部分"，救回来仍落在测量噪声附近。
- **成本是真的**：要跑每层误差报告、按层排序挑敏感层、反复重转重测，每改一次都得重跑一次真 mAP（板端导预测加 PC 侧算）。这个工程量远超它可能带来的收益。
- **我不会凭感觉挑层**：没跑报告就回退，等于又回到"看着像"的老路——那正是余弦 0.9965 教给我的教训。

**如果被追问「未来什么情况下会做？」：** 两个触发条件：业务把掉点预算压进 0.5 个点以内，或者换更大的模型、更难的场景后量化掉点冲到 3 个点以上。**而且第一步很清楚：先跑量化误差报告，按层排序定位敏感层，再决定回退哪几层。**

### Q：`toolkit` 和 `runtime` 版本倒挂，撞上了会怎样？

**一句话答案：** 官方不支持，实测会**一颗都检不出来**——旧那版模型是 toolkit 1.6.0 转的、喂给 runtime 1.5.2，阈值降到 0.05 输出仍是 0 个框。

**展开讲：** 最坑的是它**和校准集问题叠在了一起**，同时有两个病：合成校准集 + 版本倒挂。当时症状是"一张都检不出"，很容易归因成"量化把模型搞坏了"，其实是两个因叠加。后来板端 runtime 一路升到 2.3.0，才谈得上做干净的对照实验。

所以它给了我一条很硬的规矩：**排查量化问题先确认版本链，再谈算法**。版本链有三层——toolkit 转模型、runtime 加载执行、驱动进硬件，其中 **toolkit 和 runtime 必须配对**。我也在转换脚本里加了 `check_version()`：发现 toolkit 版本高于板端 runtime 就打印"官方不保证推理正确性"的警告。**让"版本不配"自己喊出来，而不是靠人记得。**

## 三、这一章的"记忆锚点"

- **量化是配尺子**：`q = round(x/scale) + zp`、`x ≈ (q-zp)×scale`；板上输入实测 `INT8 / NHWC / zp=-128 / scale=1/255`。
- **一把尺子 256 格**：量程和分辨率是同一块蛋糕，`scale` 定死就不再自适应，超量程即饱和。
- **权重 per-channel、激活 per-tensor**：卷积各通道数值差得远，共用一把尺子会把小通道压成 0。
- **INT8 快不是因为整数便宜**：是权重 4 字节变 1 字节（搬运降到四分之一）+ NPU 的 INT8 MAC 阵列更密。
- **校准集决定生死**：60 张合成色块 → cls 塌缩成常数 **0.5（= sigmoid(0)）**，box 仍差 < 1 px；换 170 张真实校准集，top-1 **0.5000 → 0.8072**（FP32 0.8125）。
- **余弦 0.9965 是反面教材**：它对单分支塌缩不敏感，我拿它当精度指标判过 PASS。**余弦当哨兵，mAP 当裁判。**
- **真 mAP 才是结论**：COCO128 / 929 GT / 71 类，FP32 **0.6087** → INT8 **0.6002**，−0.85 点 / −1.4%，conf 0.01 / IoU 0.45。
- **12.2 与 4.34 不能相减**：中间跨了量化和图手术两步；能单独成立的是 **6.22 → 4.34 MB（−30.2%）**这一步。

# 第 11 章 ReAct Agent 设计

> 一句话心智模型：ReAct 不是"让模型变聪明"，而是**让模型在每一步都能看到自己上一步干出了什么后果**——2B 小模型自己想不明白没关系，只要它肯看一眼观测再决定下一步，就够了。

## 一、先建立心智模型

一条自然语言进来，模型不是"一次想清楚全部答案"，而是走一条**边看边想**的路：想一步 → 调一个工具 → 拿到真实数据 → 再想一步。这个循环最多 5 轮，直到它不再要工具、开始说人话。

```
用户     "看看板子状态，有没有告警，灯该不该报警"
      │
      ▼
Thought  ──► 吐 XML: <tool_call><function=get_system_health></function></tool_call>
      │                                              ↑ Qwen3.5 原生格式是 XML，不是 JSON
      ▼
Action    ──► C++ 拦截，真调硬件：读 sysfs / 连 9000 收 248B 帧 / 写 LED
      │
      ▼
Observation ──► 必须回填成严谨 JSON 数组 [{"soc_temp_c": 34.23, ...}]
      │                                     ↑ 对象、空串、带换行 → runtime 直接报错
      ▼
   （回到 Thought，直到模型输出不带 <tool_call> 的自然语言 = Final Answer）

出错时先分两层，别一上来就改 prompt：
   ┌─ 模型幻觉？   → 补知识 / 加约束
   └─ 感知层错了？ → 修工具代码        （我 3 个真实缺陷里 2 个是这一层）
```

**记住这一个比喻**：老中医看病，是**边问诊边开方**——先问你哪儿疼，你说了，他再按一下，按了疼，他再换个方向问。他绝不会在你刚坐下的时候就直接开出一个疗程的全部药方。**ReAct 就是给模型装上"按一下"和"听你说疼"这两个动作。**

## 二、问答正文

### Q：ReAct 是什么？为什么不是"一次把计划全生成完"？

**一句话答案：** ReAct = **Reasoning + Acting 交替**，Thought → Action → Observation 三步循环，用真实观测纠偏，而不是靠模型在脑子里推演到底。

**展开讲：** 我的实现就是 `while (max_steps-- > 0)` 这个循环（`lab/agent/rkllm_embodied_agent.cpp:813`）：① `rkllm_run` 一次，把本轮输出攒下来；② 扫输出里有没有 `<tool_call>`，有就**执行全部工具调用**并把结果合成一个 JSON 数组；③ 以 `role="tool"` 再 `rkllm_run`，把 Observation 喂回去；④ 如果这一轮输出里没有 `<tool_call>`，说明模型开始说人话了，跳出循环，那就是 Final Answer。

要理解为什么必须这么做，把三种范式摆在一起比：

| 范式 | 怎么干活 | 致命问题 |
|---|---|---|
| 一次生成完整计划 | 让模型先输出"第一步调 A，第二步调 B，第三步……"再统一执行 | **计划是凭空生成的**，一旦第一个工具返回的数据和模型预想的不一样，后面全错；而且它没有机会改 |
| 纯 CoT | 只在脑子里推理，不调任何工具 | **它拿不到任何真实数据**，只能编。端侧 Agent 里这等于让模型猜板子温度 |
| **ReAct** | 想一步、做一步、看一眼结果，再决定下一步 | 步数变多、时延变长（我的实测就是 106.5~123.9 s）；但**每一步都被真实数据纠偏过** |

ReAct 的代价是**轮数**，收益是**每一轮都踩在真实数据上**。对我来说这个交换非常划算，因为端侧数据全是"读一次才知道多少"的物理量——温度、帧率、事件数，没有一样是模型能提前猜对的。

**如果被追问「Observation 是模型自己生成的还是你喂的？」：** 我喂的。模型只负责**提出**要调哪个工具，执行是我的 C++ 代码干的，结果也是我的代码拼成 JSON 再回填。**模型全程没有"访问硬件"的能力，它只有"申请访问"的能力。** 这个边界是安全设计的一部分，不是限制。

### Q：为什么端侧比云端更需要 ReAct？

**一句话答案：** 因为 2B 模型的"内部推演"能力不够可靠，但它"照着数据改口"的能力是够的——**与其指望它想对，不如让它每步都看一眼再想**。

**展开讲：** 这条是我这个项目最核心的一个判断，而且有实证支撑。第 11 章讲的那三个缺陷里，第二个最典型：模型拿到的数据全是真的（SOC 49 °C 是真的、事件日志里"温度超过 20.00 °C 阈值"也是真的），它推出来的结论却是"SOC 温度长期偏高，存在硬件降频甚至永久损坏的风险"。这不是它笨，是它**缺一个领域锚点**（RK3588 多少度才算热）。这种问题在大模型上靠"多想想"能缓解，在 2B 上靠"多想想"没用——它的参数容量就那么多。

但反过来，如果给它一个工具，让它去读"当前 SOC 温度"，它**照着数字改口**的能力是完全够用的。所以在端侧，正确的工程策略不是"逼模型想清楚"，而是：

- **把不确定的东西全变成可以查的东西**（温度、帧率、事件数、灯态，都做成工具）；
- **让它每一步都查一次**，用观测替它承担推演；
- **只在"判断"上用它，不在"取数"上用它**。

一句话：**小模型不缺语言能力，缺的是可靠的内部世界模型；ReAct 用"外部世界"替代"内部世界"。**

> 【费曼讲解】ReAct 就像老中医。他可以坐在那儿闭眼推演"你这应该是肝火旺"（这是纯 CoT），也可以直接搭脉、看舌苔、按肚子（这是工具调用），按到哪儿你喊疼，他立刻改方子（这是 Observation 纠偏）。
> 不懂的人会想："让模型一次把计划全排好不是更高效吗？"——错在这里：**效率和正确性在信息不完整时是矛盾的**。老中医不可能在见你第一面就开出整个疗程，因为第一个脉象就可能推翻他的初判。
> 一句话戳破：**不知道的事，问一次比想十次便宜。**
> 回到术语：Thought 是初判，Action 是搭脉，Observation 是"按到这儿疼"，ReAct 就是把这三步串成闭环，而不是让初判一路走到黑。

### Q：5 个工具分别是什么？参数和返回值长什么样？

**一句话答案：** 四个只读 + 一个可写。只读的负责"把物理世界翻译成 JSON"，可写的 `control_led` 是唯一真会动硬件的手，给了白名单 + 逐写入检查 + 写后回读三重保护。

**展开讲：** 这是我用 `rkllm_set_function_tools` 注册的工具表，`description` 字段是给模型看的——**它不是注释，是 UI 文案**，模型靠这段文字决定什么时候调谁，所以每一句都要写成"什么场景下调我"。

| 工具 | 参数 | 返回什么 | 关键设计 |
|---|---|---|---|
| `get_system_health` | 无（`properties: {}`） | 物理温度（SOC/CPU/NPU 各温区）、NPU 三核实时利用率、可用内存、指示灯当前状态 | 一次给全"体检快照"，避免模型为了拼一个结论连调三次 |
| `get_led_status` | 无 | 当前工作模式（heartbeat/alarm/on/off）与亮度 | **纯读，永不写 sysfs** |
| `control_led` | `mode`：枚举 `heartbeat` / `alarm` / `on` / `off`，必填 | 成功或结构化错误（`invalid_mode` / `led_readonly_mode` / `sysfs_write_failed` / `readback_mismatch`） | 白名单 + 逐写入检查 + 写后回读；**唯一有副作用** |
| `get_vision_telemetry` | 无 | 最新检测框坐标（x/y/w/h）、类别、置信度、数据新鲜度（`fresh` / `frame_id`） | 248 B 定长帧 + 双采样判新鲜 |
| `get_patrol_events` | `tail`：最近多少条，默认 10、最大 50（字符串类型） | 按时间排序的事件列表（`ts` / `type` / `summary`） | 只读尾部 N 行，内存 O(n)、与文件大小无关 |

工具表的 `parameters` 是 JSON Schema，`control_led` 那个枚举更狠——直接在 schema 里把四个合法值列出来（`"enum": ["heartbeat", "alarm", "on", "off"]`），**让模型在生成阶段就受到约束**，而不是等它生成了非法值再拒绝。

**如果被追问「为什么 `tail` 是字符串不是整数？」：** 这是个我留下的瑕疵。schema 里写的是 `"type": "string"`，但语义上是数字。后果是模型可能传 `"10"` 也可能传 `"twenty"`，解析端得自己做容错。更规范的做法是 `integer` + `minimum`/`maximum`。这个不影响功能，但属于"接口契约不够严"的地方。

**如果被追问「返回值为什么必须是合法 JSON？」：** 因为**解析失败整个循环就崩**。Observation 不是给人看的，是回填给 `rkllm_run` 当 `role="tool"` 消息的输入——runtime 内部会用 chat_template 解析它，解析器要求根节点是数组。传对象直接被拒，报 `E rkllm: Please provide a valid JSON format string. example: [{"temperature": 26.1}], do not include extra newlines, trailing commas, or any characters outside the JSON array.` **模型这一轮就直接断了，后面什么都不用谈。** 所以我的做法是：每个工具的返回剥掉外层方括号、内部拼成一个数组，多工具并发时也只有一个合法数组；字符串值先 trim 再拼，避免 `"\nalarm\n"` 这种脏输入。

**如果被追问「有副作用的那一个为什么特殊？」：** 因为另外四个搞错了最多是"读到错的数据"，`control_led` 搞错了是**真的把硬件状态改了**。所以它多了三重：① 白名单校验在写之前做，非法值**一个 sysfs 节点都不碰**——校验必须在写之前，不能先写再回滚；② 每一步写都查返回值，失败报 `sysfs_write_failed` + 具体是哪个节点；③ 全部写完后**回读实际状态**，与请求比对，不符报 `readback_mismatch`。**只信回读值，不信写入返回值。**

> 【费曼讲解】为什么副作用工具必须这么保守？把它想成你拿着一个没有屏幕的遥控器，按下去之后看不见电视有没有换台。
> 不懂的人会想："按了没报错，那就是成功了呗。"——错在这里：`write()` 返回字节数只代表"内核收下了我的字符串"，不代表"硬件切过去了"。我真实踩过的例子：往 `trigger` 写 `timer`，`ofstream` 不抛异常、`write` 也不报错，程序认为成功了，**灯根本没变**——因为这块板的内核 5.10.110 压根没编 `CONFIG_LEDS_TRIGGER_TIMER`，`timer` 这个值对 sysfs 是非法输入。
> 一句话戳破：**没有反馈通道的系统里，"我以为我做了"和"我真的做了"是两件事。**
> 回到术语：这就是为什么 `control_led` 要白名单前置校验 + 写后回读，也是为什么它必须在 Agent 里单独被当成"危险工具"对待。

### Q：Prompt 是怎么写的？2B 小模型怎么让它稳定输出规定格式？

**一句话答案：** 系统提示词分四块——**角色与硬件规格、世界知识、工具使用纪律、汇报纪律**；格式的稳定性**不靠 prompt 喊话，靠 runtime 的模板解析 + 参数 schema 约束 + 代码端容错**三层兜底。

**展开讲：** 我的 `sys_prompt` 是 `lab/agent/rkllm_embodied_agent.cpp:891` 起的那一大段，结构很清楚：

**第一块：角色 + 硬件规格。** 开门见山"你是一个部署在 Rockchip RK3588 边缘嵌入式计算设备上的智能具身运维 Agent"，紧接着把 8 核 ARM（4×A76 @ 2.4GHz + 4×A55 @ 1.8GHz）、NPU 3 核总峰值 6.0 TOPS、8 GB LPDDR4x、Debian 11 / kernel 5.10.110、板载 LED 路径 `/sys/class/leds/work/`、视觉服务在 9000 端口——全列出来。**为什么要把这些写进 prompt？** 因为模型不知道自己在哪台机器上，而这个信息决定了它怎么解读工具返回的数据。

**第二块：世界知识。** 这是最见功力的一段，第 11 章那个缺陷二就是它修好的：「RK3588 的 SOC 正常工作温度为 30~65 °C，超过 75 °C 才算过热告警，85 °C 以上才需要担心降频/损坏。若巡检事件的温度阈值明显偏低（如 20 °C），说明守护进程是用评测阈值在跑验收，**不要据此判定设备真的过热**」。**没有这三句话，49 °C 就会被汇报成"长期偏高、存在永久损坏风险"。**

**第三块：工具使用纪律。** 明确写清每个工具什么时候用（"查询指示灯状态请调用 get_led_status，改变指示灯才调用 control_led"），并且加了一条硬约束：「遇到条件指令或需要多步研判的任务，必须先调用 get_system_health、get_vision_telemetry、get_patrol_events 等感知工具拿到全量真实数据，再决策下一步动作；**绝对不能跳过感知直接执行动作**」。这条是防"一步到位型幻觉"的——小模型有个很强的倾向：听到"如果画面里有人就报警"，它会直接去调 `control_led(alarm)`，跳过看画面。

**第四块：汇报纪律 + 停止条件。** 「严禁捏造虚假硬件数据」「汇报时只陈述工具真实返回的字段，不要臆测工具的内部实现」「若工具返回 `success:false` 或任何 error（如 `led_readonly_mode` / `invalid_mode`），必须如实告知该操作已被拒绝及原因，**绝对不能声称操作已成功执行**」。

至于"怎么让 2B 稳定输出规定格式"，我给的是三层，**没有一层是"在 prompt 里多写几遍"**：

- **格式层靠 runtime**：Qwen3.5 的 `<tool_call><function=name><parameter=key>val</parameter></function></tool_call>` 是模型的原生输出格式，不是我发明的约定——顺着它比逆着它省力得多。
- **约束层靠 schema**：能枚举的枚举（`control_led` 的四个 mode），能不给参数的就不给参数（四读工具全是空 properties）。
- **容错层靠代码**：解析出来的参数一律 trim 再比对白名单；解析失败要有明确报错，不能静默当成功。

**如果被追问「为什么用 JSON 而不是自由文本？」：** 因为下游是机器不是人。自由文本我要写正则去抠数字，正则一脆弱整个链路就脆；JSON 有明确的解析器、明确的失败信号。而且这不是我的选择——**runtime 强制要求数组格式的 JSON**，我想用自由文本也用不了。

**如果被追问「prompt 写了这么多，2B 记得住吗？」：** 这是真实的代价。这段 prompt 有相当长度，它会一直占着上下文窗口（对着 `max_context_len = 8192` 算是有感的），而且小模型对超长 prompt 的"注意力"是有衰减的——所以我把最要紧的两条用【最高优先级】标出来，把可省的（比如 7 个温区全量）砍掉只留研判需要的两三个。

### Q：循环怎么控制？模型一直调工具不撒手怎么办？

**一句话答案：** 三道闸——**最大步数 5**（硬闸门）、**stall_rounds 连续两轮相同签名**（提前刹车）、**工具自身超时**（单次调用不卡死）；步数耗尽必须**明确报"任务未完成"**，不许硬凑答案。

**展开讲：** 三个层次的防线，失败模式各不相同：

**第一道：`max_steps = 5`。** 这是**防死循环的硬闸门**——LLM 完全可能反复调同一工具、或永远觉得信息不够，没上限就是无限烧 NPU。5 是实测经验值：正常巡检 3~4 步收敛（第二幕实测连续调用 4~5 个不同工具），再多就是在打转。

**第二道：`stall_rounds`。** 记录每轮触发的**工具名 + 参数签名**，连续两轮签名完全相同就判"原地打转"，提前收束并打印警告（`lab/agent/rkllm_embodied_agent.cpp:835`）。步数上限是最后一道闸，这个是提前刹车——差别在于**一个跑满 5 轮才发现，一个第二轮就停**。

**第三道：工具自身的超时。** `get_vision_telemetry` 连 9000 端口有 `SO_RCVTIMEO`（读一帧 300 ms 超时上限），`get_patrol_events` 只回退固定字节数读日志。**任何单个工具都不允许无限期阻塞**，否则整个循环卡在一个工具里，步数闸门根本轮不到生效。

**终止条件只有两个**：模型输出不带 `<tool_call>` 的自然语言（Final Answer），或者步数耗尽。耗尽时的处理是这段代码里我最在意的一处细节（`lab/agent/rkllm_embodied_agent.cpp:846`）：

```
if (g_step_output.find("<tool_call>") != std::string::npos) {
    std::cout << "[警告] [Agent] 工具执行轮数已达上限，任务未完成。" << std::endl;
}
```

**必须明确报"任务未完成"。** 因为 Agent 最危险的失败模式不是报错，是**"没做完但报告得很圆满"**——用户看到一段流畅的中文总结，完全不知道它其实任务没走完。这一条比看起来重要得多。

**如果被追问「工具调用失败怎么重试？」：** 分两类。**暂时性失败**（网络抖动、socket 超时）由工具自己内部处理，对外只报最终状态（`offline` / `timeout`），因为重试逻辑写进 Agent 循环会让模型看见中间的抖动、徒增混乱。**业务性拒绝**（`invalid_mode`、`led_readonly_mode`）**不该重试**，而且要在返回值里明确说出来——我加的 `hint` 字段就是干这个的："do NOT retry control_led with another mode; the gate rejects every mode in read-only mode"。**把"别再试了"变成机器可读的返回值**，模型才知道停。

**如果被追问「有总超时吗？」：** 没有做进程级的全局 deadline，这是我的一个缺口。现在的保护是"每步都有限"（工具超时 + 步数上限），但**最坏情况的墙钟时间是没有上界的**——5 轮 × 单轮生成时间，实际观测到 123.9 s 的长尾就是证据。要补的话很简单：在循环里记 `steady_clock` 起始点，超阈值就停止调度并报"超时未完成"。

### Q：失败模式有哪些？三个已知缺陷分别是什么？

**一句话答案：** 三个都是真跑出来的、有 trace 有日志的缺陷——**① 爆闪的报警灯被读成"熄灭"，模型据此编了个错误因果；② 模型不知道"20 °C 是演示阈值"，把正常温度判成过热；③ `--no-led` 下模型把四种模式挨个试了一遍，白跑 4 轮推理**。其中第 1 个是感知层 bug，第 2 个是知识缺口，第 3 个是接口没表达清楚——**没有一个的根因是"模型太小"**。

**展开讲：** 这三个按发现顺序讲最有冲击力，因为它们一个比一个隐蔽。

**缺陷一：演示全绿，但 Agent 在说假话。** 第二幕多步演示跑完，**12 项断言全 PASS**。我不放心去翻 trace，发现汇报里写着「LED 始终熄灭…这导致硬件层面的过热保护逻辑被抑制。」——**而那个灯正在 100 ms 爆闪报警。**

怎么判断这不是幻觉？**分层定位。** 我把整条 trace 的 Observation 全拉出来逐条对齐物理事实：`obs[1]` 和 `obs[16]`（两次 `get_led_status`）**都写着 `"current_mode": "off", "brightness": 0`**。同时用 shell 连采 `cat /sys/class/leds/work/brightness`，拿到 `0 255 0 0 255 255 ...`——物理上在闪。两边一对照：**输入错、推理对。不是它编的，是我喂错了。**

根因是三件事叠加：① 本板内核 5.10.110 没编 `CONFIG_LEDS_TRIGGER_TIMER`，`alarm` 只能用**用户态爆闪**（fork 一个 shell 循环，100 ms 亮 / 100 ms 灭）；② 既然是用户态爆闪，`trigger` 永远是 `none`，靠 trigger 判断模式的老逻辑直接失效；③ **爆闪是对称方波，单点采样落在灭相的概率约 50%**。两次独立采样都撞上大约 25%——**这不是小概率事件，是必然会发生的事**。更阴险的是 `off` 是个**合法值**，任何"字段有没有、格式对不对"的检查都发现不了。

修法两层：**主路是确定性判据**（读 pid 文件 `/tmp/edgevision_led_alarm.pid`，`kill(pid, 0)` 确认进程存在，再读 `/proc/<pid>/cmdline` 必须包含 `brightness`——第二个校验不能省，`kill(pid,0)` 成功只代表"存在且有权限发信号"，排除不了僵尸和 pid 复用）；**兜底是概率判据**（pid 文件缺失时做 12 次 × 15 ms 多点采样，共 180 ms 覆盖 1.8 个爆闪周期，出现亮暗交替就判 `alarm_blink`）。**确定性判据优先，概率判据兜底。**

**缺陷二：模型不缺智商，缺常识。** LED 修好后，汇报变成「SOC 温度长期偏高（>40 °C）…存在硬件降频甚至永久损坏的风险」，还加了一段「若系统内部逻辑 `0=off`, `1=heartbeat`, `2=alarm`, `3=on`（**推测**）…」。

这次**不是幻觉**——这是最关键的一句。模型拿到的**全是真数据**：SOC 49 °C 是真的，事件日志里写着"温度超过 20.00 °C 阈值"也是真的（我演示时压的阈值）。它的问题不是编数据，是**不知道 RK3588 多少度才算热**：手里只有"有个告警"+"阈值 20 度"，于是合理倒推出"超过 20 度就危险"。**它是缺世界知识，不是缺智商。**

修法是往 `sys_prompt` 补两条：① 温度常识（30~65 °C 正常 / 75 °C 告警 / 85 °C 以上才担心）；② 禁止臆测（"不要臆测工具的内部实现，如猜测 `control_led` 的枚举值编码"）。同一场景立刻变成「SOC 49.9 °C，正常（30~65 °C）」「这些是低阈值演示事件，而非真实过热」，那段枚举推理**整段消失**。

为什么"禁止臆测"也要写进 prompt？因为模型有个很强的倾向：**遇到不确定的地方，它会补一段看起来很专业的猜测，而不是承认不知道。** 这在产品里是灾难——用户看不出哪句是数据、哪句是脑补。**与其要求它"猜得准"，不如明确禁止它猜。** 工程启示一句话：**不是让模型更聪明，是补上它缺的那块世界知识。**

**缺陷三：`--no-led` 下白跑 4 轮推理。** 快慢双系统里慢层 Agent 是只读的（`--no-led`），因为 LED 写权归守护进程。但模型不知道这个"软约束"：用户一说"把灯调成报警"，它就去调 `control_led(mode=alarm)` → 被拒 → 换个模式再试 → 再拒……**heartbeat / on / alarm / off 四种模式挨个试了一遍，白跑 4 轮 NPU 推理**，还把上下文污染了一堆无用失败记录。

为什么它不一次就放弃？因为拒绝的返回里**只说了"被拒绝"，没说"别再试了"**。模型看到 `success:false` 的合理反应就是换参数重试——**这是它在训练里学到的正确行为，问题在我的接口没表达清楚。**

修法两层都要：① 工具返回加 `hint` 字段，明确写"do NOT retry control_led with another mode"；② `sys_prompt` 追加最高优先级只读约束。效果是 **`control_led` 调用从 4 次降到 1 次**。两层都要的理由是分工：**sys_prompt 是事前预防（不犯错），`hint` 是事后止损（犯错了立刻停）。** 只靠 prompt 不可靠（可能忽略、可能被用户话术带偏），只靠 hint 也不够（它会先试一次）。**冗余是故意的。**

**如果被追问「这三个缺陷有什么共同点？」：** 有，而且是我最想讲的一句：**两个是我喂错了数据 / 接口没表达清楚，只有一个勉强算模型的能力问题（缺知识）。** 所以遇到"Agent 给出离谱结论"，正确的排查顺序是：**先分层定位"是模型幻觉，还是我喂给它的数据本来就是错的"，再谈调 prompt。** 顺序反了会浪费大量时间在 prompt 上打补丁，而且补不干净——根因还在。

**如果被追问「12 项断言全 PASS，那你的测试有什么用？」：** 有用但不够用，我承认得很干脆。**断言能保证"流程正确"，保证不了"事实正确"**——它验的是"有没有调工具 / 参数对不对 / JSON 合不合法"，验不了"工具返回的那个 0 是不是真的 0"。这次是**人工翻 trace、把汇报和物理事实逐条对齐**才抓到的。改进方向也明确：把"物理事实"变成可断言的量——比如灯不再信"程序自述"，改成实测占空比。

### Q："具身（embodied）"到底特殊在哪？

**一句话答案：** 特殊在**输出会改变真实世界的硬件状态**——别的 Agent 说错话最多是误导用户，我这个 Agent 说错话会**真的点亮或熄灭一盏灯**，而这盏灯在工业场景里可能就是告警信号。

**展开讲：** 我给它起名叫"具身智能体"，不是因为这个词好听，是因为它的动作**真的落到物理层**：`control_led` 那一路最终是往 `/sys/class/leds/work/brightness` 和 `trigger` 写值，写下去灯就变了。这带来三条和纯软件 Agent 完全不同的设计要求：

**第一，副作用工具必须可逆。** 四个 mode 里 `heartbeat` 就是"恢复默认"，任何时刻都能一键回到安全状态。这不是巧合，是设计——**一个不能回到原状的执行器，不应该交给模型控制。**

**第二，必须有状态查询来确认。** 所以 `get_led_status` 和 `control_led` 是一对：**改完必须能查，查了才敢信。** 而且 `control_led` 自己内部也要回读（`readback_mismatch` 那条分支），因为"写成功 ≠ 生效"。

**第三，不能一次批量执行多个副作用动作。** 我的循环里其实允许一轮返回多个 tool_call（规范上支持），但工具集里**只有 `control_led` 一个是有副作用的**，所以"批量"这件事天然被工具设计限制住了——**不会出现"模型一口气连改三样硬件，第二样失败第一样已经改完"这种部分成功状态。** 这是用工具集结构换来的安全性，比在代码里写"禁止并发副作用"更可靠。

还有一条是**权限边界**：快慢双系统里 LED 的写权归守护进程，Agent 用 `--no-led` 只读。这本身就是个可演示的能力边界——"能感知、能研判，但不能乱动别人正在管的执行器"。它返回的是：

```
[{"success": false, "error": "led_readonly_mode",
  "note": "patrol daemon owns LED; agent is read-only",
  "hint": "do NOT retry control_led with another mode; the gate rejects every mode in read-only mode"}]
```

**如果被追问「那你的 Agent 算不算有权限系统？」：** **不算，这点必须说清楚。** 工具是全权限的，能做只读是因为我加了 `--no-led` 这个命令行开关，不是因为有真正的权限/鉴权机制。也没做并发多用户隔离。这是个明确的未做项。

## 三、这一章的"记忆锚点"

- **ReAct = Thought → Action → Observation 循环**，实现就是 `while (max_steps-- > 0)`，直到模型输出不带 `<tool_call>` 的自然语言。
- **三种范式对比**：一次生成完整计划（幻觉无法纠错）/ 纯 CoT（拿不到真实数据）/ ReAct（用观测纠偏，代价是轮数和时延）。
- **端侧更需要 ReAct 的根本原因**：2B 模型的内部推演不可靠，但"照着真实数据改口"完全够用——**用外部世界替代内部世界。**
- **5 个工具四读一写**：`get_system_health` / `get_led_status` / `get_vision_telemetry` / `get_patrol_events` 只读；`control_led` 是唯一有副作用的，白名单前置 + 逐写入检查 + 写后回读。
- **Observation 必须是合法 JSON 数组**：单对象会被 runtime 拒，一个工具也成为长度 1 的数组，否则整个循环当场断掉。
- **三道闸**：`max_steps=5` 硬闸门、`stall_rounds` 连续两轮相同签名提前刹车、工具自身 `SO_RCVTIMEO` 超时；耗尽必须**明确报"任务未完成"**。
- **三个缺陷没有一个是"模型太小"**：① 爆闪灯被单点采样读成 `off`（感知层）；② 不知道 30~65 °C 是正常（缺世界知识）；③ `--no-led` 下把四种模式试一遍（接口没表达"别再试"）。修完 `control_led` 4 次 → 1 次。
- **实测**：端到端 **106.5~112.2 s**（三次独立测量，另有 123.9 s 长尾）、连续 **4~5 个不同工具**、Observation **20~29 条全合法 JSON**、汇报 1315~1350 字、回归 **12/12 连续三次全绿**。

## 四、面试官可能从哪下刀（预演）

| 他可能问 | 你怎么接 |
|---|---|
| 「ReAct 不就是让模型多调几次工具吗，有什么难的？」 | 难点全在失败路径上：格式必须是数组、参数要 trim、既要防死循环又不能硬凑答案、有副作用的工具要可逆可回读。**跑通一次很容易，跑到 12/12 连续三次全绿很难。** |
| 「三个缺陷听起来都是你代码的 bug，跟 Agent 有什么关系？」 | 这恰恰是 Agent 工程的核心——**Agent 的可信度上限 = 它拿到的 Observation 的可信度**。模型再聪明也救不了一个喂错的传感器，所以做 Agent 一大半时间在修感知层和接口契约，不是在调模型。 |
| 「12 项断言全过了，你怎么知道它没在骗你？」 | 演示判 PASS ≠ 没问题，这是我自己踩出来的。断言验的是流程正确，验不了事实正确。抓到那句"灯灭了导致过热保护被抑制"，是人工翻 trace 把汇报和物理事实逐条对齐的结果。改进是把物理事实变成可断言的量，比如灯改测占空比。 |
| 「为什么上限是 5 步？为什么不是 10 步？」 | 5 是实测经验值：正常巡检 3~4 步收敛，再多就是在打转。而且每轮约 10 s 量级（这是总时长÷轮数的估算，不是打点实测），10 步意味着最坏两分钟以上。这是"够用 + 可接受时延"的取舍，不是理论推导。 |
| 「模型一直调同一个工具你怎么办？」 | 两道机制：`stall_rounds` 记录每轮工具名+参数签名，连续两轮完全相同就判原地打转提前收束；`max_steps=5` 是最后一道硬闸。**关键是耗尽时必须明确报"任务未完成"**，最危险的失败不是报错，是没做完却报告得很圆满。 |
| 「你说具身，具体特殊在哪？」 | 输出会改真实硬件状态。所以三条纪律：副作用工具可逆（heartbeat 就是恢复默认）、必须有状态查询确认（改完能查，查了才信，内部还要回读）、不批量执行多个副作用动作（工具集里只有一个是写操作，结构上就排除了部分成功）。 |
| 「这套东西拿到工业场景能直接用吗？」 | 不能。没做权限隔离（工具全权限，只读靠 `--no-led` 开关）、没测并发多用户、没有进程级总超时、5 步上限撑不住长链路任务。它是"验证了闭环可行"的原型，不是产品。 |
| 「换个大模型是不是这些坑就都没了？」 | 一个都修不了。LED 读错是采样问题，`--no-led` 重试是接口没表达清楚，温度误判是领域知识不在预训练语料里。**换 7B 照样不知道这块板子多少度算热；prompt 里补 30 个字比换大三倍的模型有效。** |

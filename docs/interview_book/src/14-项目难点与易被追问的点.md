# 第 14 章 项目难点与易被追问的点

> 一句话心智模型：这一章不讲"我做了什么"，只讲"哪里差点翻车、我怎么发现的、对方再压一层我还能不能站住"。前面几章让你会讲，这一章决定你能不能被连问三层还接得住。

## 一、先建立心智模型

我把面试里的追问想成一把**往下钻的钻头**，每一层都比上一层更靠近"你到底有没有亲自做过"。

```
                    追问的钻头，越往下越难编
  第 1 层  结果层   "多少毫秒？"            背数字就能过
  第 2 层  方法层   "你怎么测的？"          要说清仪器、口径、样本量
  第 3 层  归因层   "为什么是这个原因？"    要有证据链，不能靠"我觉得"
  第 4 层  边界层   "换个条件还成立吗？"    要知道方法的失效点
  第 5 层  价值层   "你哪里没做好？"        要真诚，编不了
```

**记住这一个比喻**：你的每个结论是一根**链条**，不是一颗**珠子**。珠子只能拿在手里展示，链条可以被人从任何一端拽——拽不断才叫结论。这一章就是补链条，顺便告诉你哪几根本来就短，被拽就该断，断了要立刻承认。

## 二、五个真难点

它们难不在写代码，而在**第一直觉全部是错的**，我是被数据打脸之后才改的口径。

### Q：37 毫秒到底是不是 NPU 慢？

**一句话答案：** 不是。用 `RKNN_FLAG_COLLECT_PERF_MASK` 把一次推理拆成 125 个算子：NPU 上 115 个合计 19.23 ms（51.0%），回退到 CPU 的 10 个合计 18.44 ms（49.0%）——将近一半的时间根本没在 NPU 上跑。

**展开讲：** 起点是"官方说 5.5 到 7 毫秒，我实测 37.19"。第一反应永远是驱动有问题、板子降频、模型不对，三件都查过全正常，问题于是变成"这些算是不是都给了 NPU"。最慢三个算子 `model.22/dfl/Transpose` 在 CPU 9181 微秒、`exSoftmax13` 4467 微秒、`Reshape` 2660 微秒，合计 18.02 ms，几乎就是那 18.44，全来自 YOLOv8 的 DFL 检测头：16 个 bin 加权求和，形状变换太频繁，工具链只能切出来丢给 CPU。真正确认"是放置问题不是算力问题"的对比是：`dfl/Transpose` 回退到 CPU 要 9181 微秒，`dfl/Transpose_1` 留在 NPU 只要 1475 微秒，同算子同数据量差 6 倍。

**如果被追问「49% 会不会是测量误差？」：** 115 个落在 51%、10 个落在 49%，是双峰不是抖动；反证是图手术后省 21.24 ms，比 18.44 还多，因为回退不只自己慢，还打断了 NPU 的连续调度。

**如果被追问「那 NPU 上那 19 毫秒正常吗？」：** 不正常，是另一类问题：MAC 利用率低，首层 3 通道卷积只有 2.33%，大量 Conv 在 5% 到 22%。所以对官方数我做完手术仍差 2.3 到 2.9 倍，这部分差距我承认没消掉。

### Q：三核为什么不是 3 倍？

**一句话答案：** 因为"三核给一个 context"和"三个 context 各绑一核"是两件事。前者 35.97 ms，只比单核快 3.3%；后者 300 帧墙钟 5058 ms、聚合 59.3 FPS，是单核 26.9 FPS 的 2.21 倍。

**展开讲：** 我第一次做三核想得很简单：掩码设三核，速度就该接近 3 倍，结果只有 3.3%。原因很朴素：**一个 context 内部，三颗核不是给同一次推理并行的，是给多次推理之间轮转用的**；一次 forward 层与层之间串行依赖，摊不开。要吃满三核，必须三个独立 context 各硬绑一核、跑三路数据。另一个必须一起报的数是：**三核满载时每颗核负载都只有 49% 左右**（Core0 49%、Core1 49%、Core2 50%）——不是"三核在拼命只是协调不好"，而是"每核一半时间在等" CPU 侧的采集、CSC 和 IO 搬运。

> 【费曼讲解】为什么"一个 context 用三核"没有 3 倍？
> 生活类比：一家餐厅三个灶。一个 context 三核等于**一个厨师同时看三个灶**，他还是要按菜谱一步步来，切菜时另两个灶只能空着；三个 context 各绑一核，等于**三个厨师各占一个灶**。
> 不懂的人会怎么错想：以为 NPU 核像 CPU 多线程，任务丢进去自动分摊，于是把掩码设成三核、测出 35.97，得出"三核并行没意义"的错误结论。
> 一句话戳破：并行粒度必须落在能独立推进的工作单元上；一次推理的层间是依赖，摊不开，多次推理之间才独立。
> 回到术语：所以正确做法是 `rknn_init` 三次拿三个 context，各 `rknn_set_core_mask` 绑死 Core0、Core1、Core2，配三线程三队列，这叫 data parallel。

**如果被追问「2.21 倍的并行效率怎么算？」：** 59.3 FPS 除以（3 乘 26.9 FPS）等于 73.5%，没吃到的部分一半来自每核 49% 负载，一半来自三条线程抢同一份内存带宽。

### Q：量化精度为什么要跑真 mAP，余弦相似度不行吗？

**一句话答案：** 不行，我在这上面栽过一次大的。旧版用 60 张合成色块当校准集，量化后余弦相似度仍有 0.99651，看着"几乎无损"，但分类分支已被压成常数 0.5——恰好等于 sigmoid(0)——等于分类头彻底废了，而余弦完全看不出来。

**展开讲：** 量化完比 FP32 与 INT8 输出，余弦 0.99651，我判断掉点可忽略；真实图片一验，9 张真实图 top-1 只有 0.5000，FP32 是 0.8125。去看输出才发现 INT8 所有类别置信度**精确等于 0.5**，一位小数都不差——不是掉点，是输出变成常数。为什么是 0.5？分类分支最后是 sigmoid，说明所有 logit 被量化成了 0；为什么是 0？校准集是合成纯色块，激活分布极窄，工具链统计出的 scale 很小，真实图片进来大量激活落在区间外被**饱和**削平。修复很直接：换 170 张校准集（50 实拍、100 增强、20 合成），9 张真实图 top-1 从 0.5000 回到 0.8072（FP32 是 0.8125），然后才用 COCO128 跑真 mAP：FP32 0.6087、INT8 0.6002，掉 0.85 点、相对 1.4%。

**如果被追问「余弦为什么没发现？」：** 它算的是整张特征图的整体形状相似度，8400 格点乘 80 类一平均，单个分支塌缩贡献很小。**余弦对"少数通道彻底坏掉"几乎不敏感**，所以我的口径是**余弦当冒烟，mAP 当验收**。

### Q：大模型和视觉模型抢 NPU 怎么办？

**一句话答案：** 快慢双系统。巡检守护是独立 C++ 进程、5 秒周期，**压根不加载 LLM**，只读温区、NPU 负载和视觉遥测，状态翻转才写事件；需要大模型判断时只写一行进 `llm_pending.jsonl` 留给慢层。

**展开讲：** 冲突是物理事实：视觉线要三个 context 吃满三颗核，Qwen3.5-2B（W8A8，2.8 GB）一加载也占 NPU，而且一占就是好几秒连续推理，同时要则视觉帧率掉、Agent 时延涨。**快层不加载 LLM** 的三条理由各自独立成立：一是 NPU 竞争，守护的本质是永不失职，任何让它排队的设计都是错的；二是时延，LLM 单轮十秒量级，守一个五秒周期逻辑上不成立；三是可靠性，快层只链标准库和 pthread，连 `rknn_api` 都不链，NPU 驱动挂了它也照样活着。慢层接口顺带解决了并发：`llm_pending.jsonl` 是单写者多读者，天然无写入竞态。

**如果被追问「那快层怎么知道该报警？」：** 靠规则不靠模型。温度进 75 度、视觉连续 5 次没检出人，这是阈值判断；阈值也不是为演示写死的，是 `--temp-enter`、`--temp-exit` 参数，默认 75 和 70，带 5 度回差。

### Q：大模型输出不可靠，你怎么敢让它上生产？

**一句话答案：** 我不相信它的输出，只相信**协议边界和回归用例**。三层：工具返回必须是我定义的合法 JSON 数组、模型吐的工具调用必须能手工解析成结构化字段、12 条回归用例含故障注入，挂一条就不算通过。

**展开讲：** 按不可靠的层次分三类，正好对应三层防护。格式层：模型吐参数会带空白，本该 `alarm` 给你 `"\nalarm\n"`，不 trim 永远匹配不上白名单，所以进业务逻辑前强制 trim，LED 模式做白名单校验。约定层：RKLLM 的结果回填接口很挑，传空串报 `The tool_response_str cannot be empty`，传 JSON 对象被拒、必须是数组，所以 Observation 一律由我这边序列化再回填。行为层：模型会重复调用失败的工具、会原地打转，防护是 `max_steps=5` 限步数加连续无新信息就强制收尾。

**如果被追问「12 条用例怎么证明不是自说自话？」：** 用例是我写的，我不遮掩。补偿是断言写成行为契约而非文案匹配：`tool_called`、`tool_arg`、`tool_order`、`obs_json_valid`、`any_of`、`exit_clean` 组合使用，T05 用 `any_of` 允许三条合法路径。局限我自己先说出来：断言基于 stdout 正则、时延含 ssh 和模型加载，而且**它验流程不验事实**，验证不了模型那句"灯在爆闪"是不是真的。

## 二之续：二十个追杀问题

**答的时候记住：先给结论，再给证据，最后主动交代边界。**

### Q：你说 2.21 倍，为什么不是 3 倍？第三个核的瓶颈到底是什么？

**一句话答案：** 不是第三个核慢，是三个核都只跑到一半——每核负载 49% 左右。瓶颈在喂数据的 CPU 侧：CSC 33.583 ms、letterbox、IO 搬运，全在 NPU 之外串行发生。

**展开讲：** `rknpu/load` 读到 Core0 49%、Core1 49%、Core2 50%，三个数几乎一样，说明调度是均匀的，缺的是活。往下一层：一路数据一圈 40 毫秒左右，其中 NPU 只占 16 毫秒，剩下都在 CPU 上做准备和收尾。多开几路能把 NPU 负载拉上去，但整机吞吐不会线性涨，因为 CPU 侧没那么多核可分——三路稳态 43.7、44.2、44.0 ms 已经在说 CPU 快满了。

### Q：DFL 图手术会不会在别的模型或别的检测头上失效？

**一句话答案：** 会，而且失效得很彻底——它完全依赖"YOLOv8 的 DFL 头结构固定、16 个 bin 的加权和可在 CPU 等价重算"这个前提，换检测头，切的位置就对不上。

**展开讲：** 我做的是结构手术：`yolov8n.onnx` 从 262 节点 1 输出（84 通道）改成 228 节点 2 输出（`raw_box` 64 通道加 `cls_sig` 80 通道），两个输出都停在卷积之后、形状变换之前，DFL 加权求和挪到 CPU 用 C++ 算。前提三条：头是 DFL（64 通道等于 4 角点乘 16 bin）、网格固定 8400 点可静态申请内存、分类 sigmoid 已在模型内做完。换模型就变：YOLOX 那种不用 DFL 的头没有可重算的东西，带 anchor 的头输出维度对不上，DETR 那类 query 机制连"网格"概念都没有。

**如果被追问「那等价性怎么保证？」：** 两层。数值层：同一张图手术前后对齐，box 最大绝对误差 0.000122 像素、cls 最大绝对误差 0；代码层：C++ 解码器与 numpy 参考实现跑同一份输出，最大差 6.1e-05 像素，都在 float32 极限附近。

**如果被追问「有坑吗？」：** 有。DFL 的 16 bin 加权和算出来是格子内相对坐标，必须再乘 stride，我第一次漏乘，框大小正好差 8 倍，看起来像模型精度崩了，靠打印中间值一层层对才定位到。

### Q：你的 mAP 只有 0.6，工业上能用吗？

**一句话答案：** 这个项目里不需要，因为我做的不是精度竞赛，是同一模型 FP32 与 INT8 的**相对掉点**。0.6087 掉到 0.6002 说明量化路径可用；工业精度靠换更大模型或换数据解决，不靠我的量化调优。

**展开讲：** 先承认：0.60 的 mAP@0.5 在真实工业检测里确实不够，YOLOv8n 本就是小模型，我选它是为了单板三核跑出可用帧率。所以结论边界是：**只能证明量化掉点 1.4%，不能证明这个模型能落地某条产线**——前者对照组是我自己的 FP32，干净；后者要场景数据、标注、产线验收，一件没做。真要提精度，顺序是换更大模型先看 NPU 扛不扛得住、再用真实场景数据微调，最后才是量化调优，顺序不能反。

### Q：COCO128 只有 128 张图 929 个 GT，凭什么说只掉 1.4%？

**一句话答案：** 凭"相对掉点"这个口径成立，并主动交代绝对值不可信。COCO128 是训练子集，绝对 mAP 必然偏乐观（官方 YOLOv8n 在 val2017 上约 0.644），所以我只拿它比 FP32 与 INT8 的差。

**展开讲：** 三条局限我写在文档里也主动说：一是训练子集，模型见过这些图，0.6087 偏乐观，不能对外说"在 COCO 上做到 0.61"；二是 128 图 929 GT 统计效力有限，跑两次会抖，所以我不拿小数点后两位说事；三是它不是自建场景验证集。那为什么还有用？因为两边是**完全相同的 128 张图、929 个 GT、同一套 letterbox 与 NMS 参数**（conf 0.01、IoU 0.45、class-aware），唯一变量是量化。为什么不用 val2017：5 千张图在单板上跑，每张二十毫秒，加标注比对和 101 点插值，一轮时间成本很高，而我要的只是"量化掉了多少"。

### Q：Agent 12 个用例怎么证明不是过拟合？用例是谁写的？

**一句话答案：** 用例是我写的，这是事实，我不美化。防护只有三条：断言写成行为契约而非文案匹配、`any_of` 与子序列允许合法路径多样、含一条真实故障注入。但整套测试**验流程不验事实**，这是边界。

**展开讲：** 最难堪的先说：回归是写完实现之后写的，天然有"按实现写断言"的风险。补偿是把断言做成通用谓词而不是写死某句输出：T07 只校验调用顺序的**子序列**，模型多想一步不误报，但把 `get_led_status` 放到 `control_led` 后面就报错；T12 是真去 `stop` 掉服务验证视觉离线。改进方向也清楚：断言换成结构化事件比对、wall clock 换成模型侧打点、再加一组"问它灯的状态然后真去读 sysfs 对答案"的事实用例。

### Q：2B 模型幻觉那么多，怎么保证它不乱调工具？

**一句话答案：** 保证不了"不想"，但保证"想了也做不成"。三层：参数白名单校验、未知工具直接拒绝、危险操作写后回读。它想乱来最多乱在嘴上，动不了灯。

**展开讲：** `control_led` 是五个工具里唯一有副作用的，防护最厚：模式必须在白名单、每次写 sysfs 查返回值、写完立刻回读。它曾试图设 `trigger=timer`，而 kernel 5.10.110 没编 `CONFIG_LEDS_TRIGGER_TIMER`，写下去恒 EINVAL，旧代码不验返回值就等于"假成功"。另一层是 hint 字段：工具拒绝时返回明确提示，加上系统提示里最高优先级的只读约束，把一个场景的 4 次无效调用压到了 1 次。至于误判真的发生过——它把 SOC 49°C 判成"永久损坏风险"，根因不是算错，是**没有世界知识**。补上"正常 30 到 65 度"后它能说出"SOC 49.9°C 正常"。**模型缺的不是智商是常识，常识得你喂。**

### Q：如果摄像头断了，你的系统会怎样？

**一句话答案：** 三层反应。视觉线采集失败但链路不崩、按超时继续转；守护的视觉遥测把状态标成 offline 或 timeout，翻转时写一条事件；Agent 读到 offline，不会拿到假的新鲜帧。

**展开讲：** 这套行为不是设计文档写的，是**测出来的**：T12 真去 `systemctl stop edgevision.service`，验证视觉被识别为离线，`finally` 里再 `start` 回来并回读，恢复失败就终止整场，不让"假恢复"混过去。遥测状态枚举五种：online、offline、timeout、partial_frame、malformed_frame；收帧按 248 字节定长收满，超时上限 300 毫秒。快层更克制：采样失败时冻结计数器，视觉断流不触发"恢复"，温度读不到就保持告警。服务层靠 `Restart=always` 5 秒自愈；设备层不一定，有些 UVC 拔插后要重新枚举，得靠 udev，我没做到那层。

### Q：为什么不用 ROS？

**一句话答案：** 因为 ROS 解决的是多节点、消息拓扑频繁变化的问题，而我是**一块板子、一条固定管线、一个 5 秒守护**，拓扑基本不变。收益接近零，成本是启动时间、依赖体积和一层我控制不了的中间件。

**展开讲：** 这是典型用错工具的陷阱：ROS 在机器人领域太标准，以至于很多人觉得做边缘视觉就该用。但它值钱的是节点发现、消息总线、tf 树、rviz，我一样都用不上。我的进程结构是：一个 C++ 主程序（采集、预处理、三个推理、推流线程）、一个独立守护、一个可选网页预览，通信是共享内存加 TCP，每一字节我都说得清。以后真要做多机协同会重新评估 ROS2 的 DDS，但那时做的是"加一层通信"，不是"把现有链路重写成 ROS 节点"。

### Q：这个项目里最难的部分是哪个？

**一句话答案：** 不是任何技术点，是**证明我的判断是对的**。具体说是发现"余弦相似度 0.99651 是个陷阱"的那一刻——它逼我承认自己用了一个看起来专业、实际抓不住关键错误的指标。

**展开讲：** 技术难点都有路径：硬解慢就换 MPP、三核不线性就拆 context、精度掉了就换校准集。难的是**方向本身就错、而且错得看起来很对**：0.99651 摆在面前，任何人第一反应都是"量化基本无损"，要推翻它，需要一个不信邪的念头"为什么真实图 top-1 只有 50%"。第二难的是承认 37 毫秒不是 NPU 慢，因为"NPU 就这水平"是个很舒服的结论。第三难是把每处"觉得没问题"变成"测过没问题"：以为 `cap.get` 回读 25 就是 25 帧，实测只有 20。

### Q：如果给你 3 个人 2 个月，怎么做成产品？

**一句话答案：** 先把"已验证的部分"和"产品需要的部分"分开算账，按"能不能被客户验收"排序：第一个月只做一件事，干掉 CSC 那 33.58 ms 并补看门狗与远程升级；第二个月做场景适配和交付物。

**展开讲：** 我的判断是**离产品最近的短板在可靠性和部署，不在算法**。0.60 的 mAP 对"有人/没人"这类粗粒度巡检够用，而拔网线、断电重来、远程升级这些坑一个都还没有。第一个月：一人做 RGA 硬件 CSC 加零拷贝（唯一能把 55.84 ms 明显压下去的路），一人做可靠性（看门狗、掉电自恢复、日志轮转、升级回滚），我做场景适配。第二个月做交付形态：配置化加热加载、健康检查接口、最后 72 小时压测。精度提升不做，因为它没有终点，而产品验收的是"客户场景下漏检率达标"，这中间需要数据不是时间。

### Q：你的方案和瑞芯微官方 demo 有什么区别？

**一句话答案：** 官方 demo 证明"这块芯片能跑"，我做的是"这条链路能跑多久、慢在哪、哪段可以砍"。三个具体差别：拆到算子级并归因、做了 DFL 图手术这种模型侧改造、做了快慢双系统这种资源编排。

**展开讲：** 不贬低官方 demo，它把路铺得很直：编译好的模型、例程、性能数字。问题是那个数字是"最佳条件下的一次推理"，而我要交付一个跑在 `systemd` 下的常驻服务。归因深度上，官方给端到端一个数，我给 125 个算子逐层耗时，能指出 `dfl/Transpose` 9181 微秒这个病灶，这个差别决定"能不能优化"。模型侧改造要求同时理解模型结构和部署链路。资源编排上，快慢双系统、三 context 绑核、有界队列背压丢帧，都是系统设计。地平线那套我没用过，不会假装比较；但方法论——先测再改、逐层归因、真指标验收——是跨平台可迁移的。

### Q：你说零拷贝不是瓶颈，怎么证明的？

**一句话答案：** 对照实验：同一模型，一次输入走 `pass_through=1`（原生直喂，省掉格式转换和拷贝），一次走正常 UINT8 转换，结果 37.05 ms 对 37.19 ms，差 0.4%。

**展开讲：** 设计逻辑是：如果输入侧搬运真是瓶颈，去掉它应该看到明显下降，差 0.4% 等于没有。佐证是输入数据每帧 1.17 MB，而瓶颈那 18.44 ms 花在 DFL 形状变换上——是纯计算不是搬运。所以手术顺序是"先砍 CPU 回退，再考虑零拷贝"。架构里写零拷贝是因为接口抽象和帧缓冲生命周期确实留了位置，但代码没落地，边界表里明确写着未实现；下一步是把 MPP 输出的 NV12 通过 DMA-BUF 的 fd 直接传给 RGA 和 RKNN，要等 RGA 那条路先通。

### Q：量化的 scale 是谁定的？校准集怎么选的？

**一句话答案：** scale 不是我定的，是工具链在校准集上统计的激活范围决定的——`q = round(x / scale) + zp`。校准集两版：旧版 60 张合成色块（灾难），新版 170 张，其中 50 实拍、100 增强、20 合成。

**展开讲：** 最容易误解的是以为量化参数可以手工调。实际 PTQ 流程是 `rknn.config(target_platform='rk3588')` 声明平台、`load_onnx` 载图、`build(do_quantization=True, dataset='dataset.txt')` 跑校准统计每层激活分布、`export_rknn` 导出。**校准集决定 scale，scale 决定什么范围会被饱和**。

> 【费曼讲解】量化里的 scale 到底是什么？
> 生活类比：把精确到小数点后六位的价格牌改写成"以 5 毛为单位"的整数价签。商品都在 3 到 8 块之间时用 5 毛做单位刚好；突然来一件 500 块的，你要么给个离谱数字，要么截断——这就是饱和。
> 不懂的人会怎么错想：以为 scale 是工程师拍的、可以凭经验调，像调学习率，于是手工改 scale，然后发现有的层好了有的更糟。
> 一句话戳破：scale 是"你给工具链看了哪些数据"的**结果**，不是"你希望它多少"的**输入**；要改 scale 只能改校准集。
> 回到术语：所以 `build(do_quantization=True, dataset=...)` 是量化的全部要害，区间外的值被 clamp 到端点，这就是饱和损失。

**如果被追问「170 张够吗？」：** 偏少，官方建议几百张，我是被算力和时间逼的。方向上是对的：**校准集必须来自真实分布**，这比数量重要。

### Q：NPU 三核怎么绑定？和 CPU 亲和性是一回事吗？

**一句话答案：** 不是。CPU 亲和性是 `sched_setaffinity` 或 `taskset`，管**谁来跑这段代码**；NPU 核绑定是 `rknn_set_core_mask`，管**这次推理交给哪颗 NPU 核**。一个在操作系统调度层，一个在推理运行时层。

**展开讲：** 两者失效方式完全不同。CPU 亲和性用错的表现是"数字骗人"：不绑核时同一程序 p50 3.45 ms，但 mean 会飘到 6.38 到 8.15 ms、p95 到 15.78 至 17.20 ms，因为线程被调度到小核，所以性能测试全部带 `taskset -c 6` 固定大核。NPU 绑定用错的表现是"以为并行了其实没有"：掩码设三核给一个 context 只有 35.97 ms。另外三个 NPU 核是三个独立计算单元、共享同一块内存和同一条总线，所以上限不只受核数限制，还受内存带宽限制。

### Q：你的 Agent 怎么做并发？

**一句话答案：** 现在**没有做并发**，是单请求串行系统，多请求会排队。这是我知道的边界，也是从演示走向产品必须补的一块。

**展开讲：** RKLLM 推理是同步的，一次 `rkllm_run` 要占住 NPU 好几秒，期间视觉线也抢同一块 NPU，所以连"两个请求同时跑"的物理条件都不具备。要做的话三条路按代价排：请求队列加单 worker（串行化，牺牲吞吐保正确）、限并发 2 并做 NPU 时间片轮转（会和视觉线抢，得先做优先级）、把 LLM 放到另一块板子物理隔离。我倾向第一条，因为 Agent 场景请求本就不密。

### Q：系统连跑一周会不会出问题？内存泄漏怎么查？

**一句话答案：** 我没有连跑一周的数据，不敢说"不会"。能说的是：进程挂在 `systemd` 下、`Restart=always`、5 秒自愈；泄漏我只有静态视角的把握（RAII、无裸 new、有界队列），没有 Valgrind 跑过的证据——板子是 aarch64，我还没把 Valgrind 交叉编过去。

**展开讲：** 这题考诚实。我说"跑一周没问题"，下一句一定是"你跑了多久"，答"半小时"就露了。真做过的三件事：服务挂 `systemd` 死了 5 秒自起；所有队列有界（推流队列 32，满了丢最旧帧）；线程与句柄 RAII 管理、SIGTERM 优雅退出按序释放。没做的是长时压测、Valgrind 或 ASan、内存增长曲线。现在就要查的话：`/proc/<pid>/status` 的 VmRSS 定时采样画曲线看是平台还是斜坡，`/proc/<pid>/fd` 数句柄变化，缓慢增长就自己包一层分配器打点；精确定位要靠 Valgrind 或 eBPF，这两个在板子上都还没跑通。

### Q：为什么用 C++ 不用 Python？开发效率怎么办？

**一句话答案：** 生产链路要稳定帧率、真并行和确定的资源生命周期，这三件 Python 都给不了；效率我用分工解决——算法验证、量化、mAP 评测全用 Python，生产链路用 C++。

**展开讲：** 效率我不装：C++ 调后处理比 numpy 慢多了。第一版 DFL 解码 Python 三行写完，翻成 C++ 花一下午还得自己写测试对数值。换来三件事：三核能真并行（GIL 会让计算线程串行）、每帧没有解释器开销（单帧预算只有二十毫秒量级）、服务化时资源生命周期确定。两边一致性靠逐位比：同一份输出，C++ 解码器与 numpy 最大差 6.1e-05 像素。

### Q：你测的这些数字，换一块板子还成立吗？

**一句话答案：** 绝对数字不成立，**结论方向成立**。换一块 RK3588 同款板，1.03、15.95、59.3 会变；但"DFL 头会回退到 CPU""单 context 三核不线性""合成校准集会毁掉分类分支"这三条是结构性的，换板子照样成立。

**展开讲：** 属于这块板子的：绝对毫秒、温度、帧率，受主频、内存带宽、散热影响。属于规律的：DFL 头在 RKNN 上大概率回退，因为形状变换太多；一个 context 用多核不会线性加速，因为层间依赖；校准集分布决定量化成败，这是 PTQ 原理决定的；MPP 硬解对 MJPEG 是压倒性优势，对 H.264 未必。具体幅度不知道，但有方法：同一套 bench、同一套绑核口径、同一套样本量，换板重跑就能得到可比的数。**方法可迁移，数字不可迁移。**

### Q：你觉得这个项目最大的缺陷是什么？

**一句话答案：** **没有真实场景的精度验证，也没有长时稳定性数据**。前者意味着我不能说这个模型能落地某条产线，后者意味着我不能说这个服务能连跑一年。这两条都不是靠短期优化能补的。

**展开讲：** 很多人会挑技术细节当缺陷，比如零拷贝没做。但零拷贝没做只是少一个优化，而"没有场景验证"是**结论的地基缺了一块**：mAP 在 COCO128 上算，是训练子集，绝对数偏乐观，也没针对"人形检测"这个真实用途做过采集标注验证，所以只能说"量化掉点 1.4%"，不能说"检测准确率 60%"。技术层面最想解决还没解决的是 CSC 走 CPU 要 33.583 ms、占生产链路六成，根因是 CPU 在读 uncached DRAM。

### Q：如果现在让你重做一遍，你会怎么改？

**一句话答案：** 三个改动按后悔程度排：第一天就上真 mAP 和真实校准集，别在余弦相似度上浪费一周；第一天就检查 `CMAKE_BUILD_TYPE`；一开始就把性能探针做成可复用工具。

**展开讲：** 三条的共同点不是"技术能力不够"，而是"流程顺序错了"。第一条代价最大：0.99651 给了我错误的安心感，基于它的下游结论要全部重验。第二条是纯粹浪费：一个多月所有绝对数都是 O0 的数。第三条是效率：`--perf` 逐层剖析把"猜"变成"看"。唯一不会改的是顺序：先学习线、再推理链路、最后叠 Agent，系统的复杂度和底层能力必须匹配。

## 三、这一章的"记忆锚点"

- **五个难点的共同形状**：第一直觉全错，我是被数据打脸之后才改口径的，这句话本身就是最好的开场。
- **两条铁证**：同一算子在 CPU 上 9181 微秒、在 NPU 上 1475 微秒（差 6 倍）；余弦 0.99651 而分类输出精确等于 0.5。
- **2.21 倍的分解**：单 context 三核 35.97 ms 只快 3.3%，三 context 各绑一核才 59.3 FPS，每核 49% 负载，并行效率 73.5%。
- **量化的要害是校准集**：旧 60 张合成色块让 top-1 掉到 0.5000，新 170 张回到 0.8072。
- **回答追杀问题的节奏**：先结论，再证据，最后主动交代边界；边界不丢人，编才丢人。

# 第 7 章 视觉推理流水线与后处理

> 一句话心智模型：这条链路是一根六节的管子，流速由最窄的那一节决定；而"最窄的那一节"会随着你把别的节改粗而搬家——我这一路的瓶颈从摄像头搬到 NPU，再搬到 CPU 的 CSC，每搬一次都要重新定位。

## 一、先建立心智模型

一帧画面从摄像头进来到变成一行检测结果发出去，要过六道手：**采集、硬解、预处理、推理、后处理、推流**。每一道手都有一个专职单元：摄像头和 USB 走 UVC，压缩帧走 VPU 硬解，格式转换和缩放走 CPU（原本该走 RGA，我没用），卷积走 NPU，解码和 NMS 只能走 CPU，最后打包走 TCP。**记住每一道手是谁在干、大概多少毫秒**，面试时你就不会把"NPU 快"错当成"整条链路快"。

```
  一帧数据的六道手（单位 ms，均为板端实测；口径见每个数字旁标注）

  [1] UVC 摄像头       1280x720 MJPEG，显式设 30fps 后 33.33 ms 出一帧
        |
  [2] MPP 硬解         p50 1.027 ms（VPU）      vs OpenCV 软解 7.761 ms
        |                                        -> 7.6 倍
  [3] CPU 侧 CSC       51~65 ms，Release 后 33.583 ms   <- 当前第一瓶颈
        |               NV12 -> RGB888，定点 BT.601 full-range
  [4] letterbox 640    1.0~3.4 ms，等比缩放 + 灰边 114
        |
  [5] NPU 推理         15.95 ms（DFL-Free，单核）  三独立 context 聚合 59.3 FPS
        |
  [6] 后处理           1.53（输入输出搬运）+ 3.09（DFL 解码 + NMS）
        |               合起来就是 bench 口径的 20.58 ms = 15.95 + 1.53 + 3.09
  [7] TCP:9000         248 字节定长帧（8B 头 + 10 x 24B BBox）
```

**记住这一个比喻**：这不是一条"传送带"，是一条**六个不同工种的接力赛**。每一棒都有自己的速度，交接的时候还要停一下。你优化的是"某一棒"，你感受到的是"整场比赛"——所以我每次只改一段，并且一定要留一组"这段理论上不该变"的对照组，否则你根本不知道快是哪儿快出来的。

## 二、问答正文

### Q：这条链路你能用 30 秒讲清楚吗？

**一句话答案：** UVC 摄像头出 MJPEG，MPP 走 VPU 硬解成 NV12，CPU 做颜色转换和等比缩放补灰边到 640×640，三个独立 context 各绑一个 NPU 核并行推理，CPU 做 DFL 解码和 NMS，最后按 248 字节定长帧推到 TCP 9000 端口。

**展开讲：** 我会在讲的时候顺手把每段的耗时带上，因为**光讲架构听不出你做过**：硬解 p50 1.027 ms、纯推理 15.95 ms、后处理 3.09 ms、CSC Release 后 33.583 ms。一句话里带三个数字，对方立刻知道你量化过。

还有一个细节值得主动说：**这条链路上只有第 5 段跑在 NPU 上**，其余五段要么是硬件单元（VPU），要么是 CPU。这也是为什么"NPU 优化完了还慢"——因为 NPU 早不是瓶颈了。

**如果被追问「为什么不是端到端 20 ms？」：** 因为 20.58 ms 是"推理 + 后处理"这一段，不含视频解码、CSC、letterbox。加上这些，生产链路的真实数字是 55.84 ms。这两个口径我下面单独讲，绝不混着说。

### Q：20.58 ms / 48.6 FPS 和 55.84 ms / 17.9 FPS，到底哪个是真的？

**一句话答案：** 两个都是真的，口径不同。20.58 ms 是 bench 口径（推理 + IO 搬运 + DFL 解码 + NMS），55.84 ms 是生产二进制口径（多算了 MPP 硬解、CSC、letterbox）。

**展开讲：** 这一题我建议主动讲，因为它是面试官最容易一击致命的地方——你报了两个数，他只要问一句"这俩怎么差这么多"，混着答的人当场塌。

拆开就清楚：

- **bench 口径 20.58 ms**：`15.95`（纯推理）+ `1.53`（输入输出搬运）+ `3.09`（DFL 解码 + NMS）。用 `bench_dflfree` 跑，输入是 `real_000.jpg`，不含视频解码、CSC、letterbox、画框。
- **生产口径 55.84 ms / 17.9 FPS**：`edgevision_pro_rknn` 全链路，含 MPP 硬解 + CSC + letterbox + NPU。这是 CMAKE 改成 Release 之后的数字，之前是 76.928 ms / 13.0 FPS。
- 还有一个中间口径：**bench 层全链路 16.21~16.26 ms / 61.7 FPS**（O3、`taskset -c 6`），O0 时是 18.91~19.06 ms / 52.6 FPS。这组是"编译优化"的 A/B，别和上面两组混。

三组数字对应三个仪器，就像你不能拿体重秤上的数说身高。

**如果被追问「那对外宣传你用哪个？」：** 讲生产口径，因为那是用户实际感受到的。20.58 ms 只在解释"模型本身多快"时用，并且一定带前缀"纯推理加后处理这一段"。

**如果被追问「为什么生产口径里 CSC 那么贵，bench 里没有？」：** 因为 bench 直接读一张 JPG，用 `cv::imdecode` 出 RGB，绕开了"从 DRM 的 NV12 转 RGB888"这一段。生产链路里这一段是 CPU 读 uncached 内存，实测 memcpy 只有 188 MB/s。

### Q：摄像头这段你踩过什么坑？

**一句话答案：** 我以为摄像头物理上限就是 20 fps，其实是**代码从来没设过帧率**，V4L2 默认协商到 20。补一行 `cap.set(cv::CAP_PROP_FPS, 30)` 之后，两台摄像头都能稳定跑 33.33 ms/帧。

**展开讲：** 这个坑分三层，每层都在推翻上一层：

第一层，查硬件能力。`v4l2-ctl --list-formats-ext` 一打，1280×720 MJPG 明确写着 `Interval: Discrete 0.033s (30.000 fps)`——硬件支持 30。

第二层，查当前生效值。`--get-parm` 报 `Frames per second: 20.000`，而源码三处（`lab/vision/edgevision_gateway.cpp:133-134`、`lab/vision/edgevision_preview_real.cpp:259-260`、`lab/drafts/bench_cam_fps.cpp:11-13`）**都只设了 FOURCC 和分辨率，一处都没设帧率**。

第三层，显式请求再看实测。请求 30 得到回读 30.00、实测 33.32 ms/帧 = 30.0 fps；请求 25 得到**回读 25.00，实测仍然 50.00 ms/帧 = 20.0 fps**。这一行是全场最坑的：**回读值会骗人**，它只是软件层记下的期望值，不是硬件的实际出帧节奏。

改完之后跑 400 帧长测，两台都是均值 **33.33 ms**，p95 分别是 33.50 / 33.39，最大偏差 **0.76 ms**，零抖动。

**如果被追问「那这个改动对系统意味着什么？」：** 意味着**整条链路的预算从 50 ms 变成 33.3 ms**。原来 50 ms 的帧周期里，有 15.6 ms 是在"等摄像头出帧"，不是我在算。改完之后这层缓冲没了，处理链路必须真的跑进 33.3 ms，否则就掉帧——所以这个"提速"其实是对后面每一段的加压。

**如果被追问「方法论上你学到什么？」：** 两条。① **"默认值"不是"上限"**：测上限之前先确认所有可调参数都调到了最大。② **软件层的"我以为"和硬件的"实际"之间差一个实测打点**：凡是"我设了它应该就是了"的地方，都要再测一次真实节奏。

### Q：MPP 硬解为什么比 OpenCV 软解快 7.6 倍？

**一句话答案：** 因为它用的是 VPU 这个专用硬件单元，JPEG 解码的熵解码和反变换在硅片里做完了；软解是在 A76 上用通用指令一条条算，还要占 CPU 时间和缓存带宽。

**展开讲：** 实测 **p50 1.027 ms（≈1.03）vs OpenCV `cv::imdecode` 7.761 ms**，7.6 倍。再拆细一点：`decode_put_packet` p50 1.015 ms、`get_frame` 约 0.017 ms——**时间几乎全花在"提交给硬件并等它做完"上，不在搬数据上**。这告诉你一件事：硬解再优化也没多少空间了，它的成本主要是"往返硬件的固定开销"，不是"处理像素"。

正确性我不是靠"看着对"验收的：200/200 帧全部有效，9 张真实图的 Y-PSNR 在 **49.9~77.2 dB**。

为什么快，有三个具体原因，面试可以顺着说：① 专用单元做专用变换，不需要用通用 ALU 模拟 DCT 和 Huffman；② 不占 CPU，7.76 ms 是实打实占着一个 A76 的；③ 不占内存带宽去做中间 memcpy——这一条在我这块板子上特别值钱，因为内存总线是全系统共享的。

**如果被追问「那硬解有没有代价？」：** 有。多了层间耦合：你的代码从此依赖 MPP 的库和内核里的 `mpp_service` 驱动，两者版本要匹配——这正是我下一个坑。

### Q：MPP 那个 -1012 是什么坑？

**一句话答案：** `decode_put_packet` 恒返回 **-1012（`MPP_ERR_BUFFER_FULL`）**，但我把所有参数都试遍了都没用；根因是**系统预装的库与内核驱动的 ioctl 语义版本倒挂**，用源码编译静态库、一行代码不改，直接通。

**展开讲：** 这个坑的排查过程比结论值钱：

1. 先确认用法没错：对着官方 demo 逐行比，配置、模式、输入格式都对。
2. 再换参数：`split_parse`、各种 CFG、预分配 frame buffer、`KEY_OUTPUT_FRAME` meta，全试了，**返回的都是同一个 -1012**。
3. 然后去读源码：翻 `mpp/mpp.c` 里 `mpp_put_packet` 的错误传播路径，确认是 `mpp_poll` 在输入端口就被拒了，根本没走到解码逻辑。
4. 最后做对照：用 MPP 源码编一个静态库，**代码一行不改**，出帧正常。

到这里根因就锁定了：系统里那个 `/usr/lib/aarch64-linux-gnu/librockchip_mpp.so.0` 是 **2021-05-20** 编的，板上 `mpp_service` 内核驱动的 ioctl 语义跟它对不上。库太老，问问题的方式驱动已经听不懂了。

**如果被追问「你怎么不早点怀疑版本？」：** 因为前 3 小时我都在"参数里找答案"，而错误码一直在说同一件事。这就是我总结的那条规矩：**参数怎么调都返回同一个错误码，优先怀疑层间版本，别继续翻参数。**

**如果被追问「这个坑对面试有什么用？」：** 它证明一件事——**"调用失败"不一定是"我调错了"**。很多人的排查止步于"我按文档写了还是不 work，可能文档不对"，真正的定位要求你去读调用链、找到拒绝发生在哪一层，然后用"换一个已知正确的实现"来做对照。

### Q：你的 CSC 为什么在 CPU 上做？RGA 不是干这个的吗？

**一句话答案：** RGA 就是干这个的，我也评估过——本板 RGA 用户态库是 **2.1.0，不支持 full CSC**，实测颜色偏差约 ±13%，检测模型吃颜色，我不敢上生产，所以主动放弃，CPU 自己写定点 BT.601 full-range 转换。

**展开讲：** 这一题必须答成"**评估过但判断不划算**"，绝不能答成"我做了 RGA 硬件 CSC"。

我掌握的事实三条：① 零拷贝的 NV12 转 RGBA 加缩放，RGA 实测能做到 **2.03 ms**，比 CPU 快一个数量级，看着非常香；② 但本板 RGA 2.1.0 **不支持 full CSC**，颜色偏差约 **±13%**，而且我**没有量化到底偏在哪、偏多少**；③ 这个缺陷是**本板 2.1.0 用户态库的特性**，升级 librga 有可能解除，但我没做。

判断：CSC 这一段我做的是"全色域转换"，颜色是模型的输入；13% 的系统性偏移意味着**我后面所有的精度结论都要重测一遍**，而它带来的收益只是把 33.583 ms 变成 2.03 ms。这个收益很大，但**在没验证颜色之前搬上生产，等于拿一个没测过的精度换一个测过的速度**。

现在生产链路走的是自写 CPU 定点转换，Release 后 **33.583 ms**（原 52.016 ms，1.549 倍），仍然占全链路 **60%**，是第一瓶颈。正确性我验过：CSC 输出和 cv2 参考的灰度相关性 **1.0000**。

**如果被追问「那你为什么不做量化验证再上？」：** 因为当时优先级排序里，还有一件收益更确定的事——砍掉 DFL 头那 18.44 ms 的 CPU 回退。同样是一个下午，改模型导出的收益是可验证的（box max|Δ| = 0.000122 px），改 RGA 的收益要先花时间建立一套颜色偏差的评测口径。我选了确定的那条。

**如果被追问「13% 这个数你测的？」：** 是评估阶段的实测现象，但没有系统量化，所以我每次说都带"约 ±13% 且未量化"这个限定。

### Q：letterbox 为什么必须做？直接把 1280×720 拉成 640×640 不行吗？

**一句话答案：** 不行。硬拉伸会把目标在竖直方向压扁，宽高比从 16:9 变成 1:1，模型看到的人全变成胖子——这会直接把 mAP 打下去。

**展开讲：** 摄像头是 1280×720（16:9），模型输入是 640×640（1:1）。两种对齐方式：

- **直接 resize**：宽高各按各的比例缩，画面被非等比拉伸，目标的形状变了。模型是拿正常比例的人训出来的，你一压缩，它的特征响应就会漂。
- **letterbox**：按 `scale = min(640/w, 640/h)` 等比缩放，剩下的地方补灰边（我的代码里补的是 **114**）。

我选 letterbox，代价是"有效像素变少了"——640×640 里有一大块是灰边，模型要在这个灰边框里找目标。但**形状正确**，而形状对检测模型比"像素多"重要。

具体到 1280×720 进 640：按 `scale = min(640/w, 640/h)`，宽这一维先顶满，所以 **scale 由宽度决定**，缩放后的画面比正方形矮，于是**上下各留一条灰边**（左右没有）。这个比例的算法写在公式里，不在常数里——你换个输入分辨率，它就变了。真正写在代码里的常数只有填充值 **114**。

验收方式也不含糊：letterbox 后的 buffer 拉回 PC 和参考实现对比，灰度相关性 **0.9995**（这个数还顺带证明了通道序没有 RGB/BGR 弄反）。

> 【费曼讲解】letterbox 到底在保护什么
>
> ① 生活类比：你要把一张 16:9 的照片塞进一个正方形相框。你可以硬拉成正方形（人就变胖了），也可以等比例缩小、留白边（人还是那个人，只是周围空了）。
> ② 不懂的人会怎么错想：模型反正会 resize 到 640×640，我提前自己 resize 不是多此一举？反正最终都是 640 个像素。
> ③ 一句话戳破：**最终都是 640 个像素，但"像素代表什么形状"变了。** 模型学的是"这个人的长宽比大概是多少"，你改了长宽比，等于改了它判断的依据。
> ④ 回到术语：这就是检测里的长宽比失真问题。letterbox 保留原始几何关系，同时通过 scale 和 pad 把几何信息完整记录下来，让输出坐标能一对一映射回原图。

**如果被追问「灰边为什么是 114？」：** 114 是 YOLO 系列常用的填充灰，我的训练/评估口径也用这个值，关键是**训练和部署必须一致**。另外 114 也是我合成输入时用的填充值（bench 里就填 114），这样测出来的延迟和真实输入的量级一致。

### Q：检测框怎么从 640×640 映射回原始 1280×720？

**一句话答案：** 预处理时把 `scale`、`pad_x`、`pad_y` 三个量记下来，后处理时反着算一遍：`(x - pad_x) / scale`。

**展开讲：** 具体代码是这样的：

```cpp
// 预处理：等比缩放 + 居中补灰边
lb = cv::Mat(640, 640, CV_8UC3, cv::Scalar(114, 114, 114));
pad_x = (640 - nw) / 2;
pad_y = (640 - nh) / 2;
resized.copyTo(lb(cv::Rect(pad_x, pad_y, nw, nh)));

// 后处理：逆变换回原图坐标
float ox1 = (d.x1 - pad_x) / scale;
float oy1 = (d.y1 - pad_y) / scale;
```

要点是：**这三个量必须跟着这帧图一起传下去**。我的 `RawFrame` 结构里就带着 `orig_w / orig_h / scale / pad_x / pad_y`，谁拿这帧图谁都能算回原图，不依赖全局状态。

顺便说个我特意不背的数：padding 的具体值是 `(640 - nh) / 2` 算出来的派生量，输入分辨率一变它就变——**要背的是公式，不是那个数**。真正在文档里有记录的是：我做 O0/O3 对比时用的是 640×640 的图，那次的 `scale` 正好是 **1.000**，没有填充。

**如果被追问「逆变换最容易错在哪？」：** 两个。① 忘了减 pad 就先除 scale，框会整体平移；② x/y 和 w/h 混用——如果你的框存的是 x1/y1/x2/y2，逆变换就逐点算；如果存的是中心点加宽高，就得先转换再算。我统一用 x1/y1/x2/y2，减少歧义。

### Q：三个 NPU context 在流水线里怎么摆？

**一句话答案：** 抓帧线程往任务队列里塞，3 个推理线程各持一个 context、各绑一个核，从同一个队列抢图；推流线程从结果队列取。两个队列都有容量上限，满了丢旧的。

**展开讲：** 结构上有三条不变量：

- **一个线程一个 context**：三个线程各持一个 context，各自 `rknn_set_core_mask` 绑 Core0/1/2。上下文不共享，避免锁竞争。
- **队列削峰填谷**：抓帧比推理快的时候队列会涨，所以入队要设上限；我的推流队列策略是 `size >= 2` 就丢最旧的，另外**上位机重连的瞬间清空存量**。
- **几何元数据跟着图走**：`RawFrame` 里带 `frame_id / scale / pad_x / pad_y`，推理线程不需要问别人这帧图是怎么预处理的。

这套结构跑出来的数：**40.8 ms/路，聚合 59.3 FPS，2.21 倍**，墙钟 5058 ms 跑完 300 帧，三路各自 4081~4089 ms，**差 8 ms**，负载几乎完全均衡。

**如果被追问「为什么不是 3 倍？」：** 三核各只跑到 49% 负载，NPU 有一半时间在等人；而且每路延迟从 37.27 ms 涨到 40.8 ms，三条路在抢同一条内存总线。加核解决算力，解决不了喂不饱。

**如果被追问「队列丢旧帧会不会丢检测结果？」：** 会，但那正是我要的。这是实时巡检，**旧帧的结果比没有结果更糟**——它会让上位机看到 3 秒前的人。丢旧保新是实时系统里的标准取舍。

### Q：DFL 是什么？为什么它要单独拿出来讲？

**一句话答案：** DFL 是 YOLOv8 检测头解框的方式：它不直接回归一个距离，而是把距离表示成 16 个 bin 的概率分布，做 softmax 之后对 `[0..15]` 求期望。这套东西在 NPU 上算子不被支持，全落在 CPU 上，占了 49% 的时间。

**展开讲：** 我在流水线里的位置是第 6 段（后处理），它做的事是：把 NPU 吐出来的原始张量，翻译成"框在哪、是什么类"。

这个翻译为什么贵？因为 DFL 那条链是 `Transpose` + `Softmax` + `Reshape` 三个操作串起来的，逐层剖析（125 个算子）显示：**NPU 上 115 个算子 19.23 ms（51.0%），CPU 上 10 个回退算子 18.44 ms（49.0%）**。最慢的三个正是 DFL 的：`model.22/dfl/Transpose` 9181 µs、`model.22/dfl/Softmax` 4467 µs、`model.22/Concat_3_swap_concat_reshape` 2660 µs。

详细的数学推导和"我怎么把它从图里砍掉"在第 8 章。这里你只需要记住**它在流水线里的角色和代价**：它是一段"必须做、但做得很慢"的翻译工作，而且因为它在 CPU 上，NPU 会停下来等它。

> 【费曼讲解】DFL 到底在算什么
>
> ① 生活类比：让你猜一个人的身高，你不直接报 175，而是给一张表——"160 的可能性 5%，165 的 10%，170 的 30%，175 的 35%，180 的 20%"，然后按概率加权平均算出一个数。DFL 就是这么干的，只不过它的表是 16 个格子（bin），格子间距是一个 stride。
> ② 不懂的人会怎么错想：回归就是一个数，直接输出一个数不就行了，搞成 16 个数不是更麻烦？
> ③ 一句话戳破：**输出一个分布再求期望，等于让网络可以表达"我不太确定、可能是这两档之间"，比逼它押一个数更容易训。** 代价是推理时多做一次 softmax 和一次加权求和。
> ④ 回到术语：这就是 Distribution Focal Loss 的思路——把框的四个距离分别建模成离散分布，用积分（加权和）取回连续值；而**这个加权和得到的是格子单位（0~15），必须再乘 stride 才是像素**，我第一版漏了这步，框整体差 8 倍。

**如果被追问「你砍掉它之后怎么保证等价？」：** 数值等价，不是"看着对"：拿原模型 84 通道输出当基准逐元素比，box 的 `max|Δ|` = **0.000122 px**、cls 的 `max|Δ|` = **0**；C++ 解码器和 numpy 参考再交叉验证一次，`max|Δ|` = **6.1e-05 px**。0.000122 已经是 float32 在 640 量级上的精度极限。

### Q：什么叫"算子回退"？为什么它比"慢"更严重？

**一句话答案：** 回退就是 NPU 不认识某个算子，编译器把它切下来扔给 CPU 算。它比"慢"严重得多，因为 CPU 和 NPU 之间要来回搬张量，NPU 还得停下来等。

**展开讲：** 我这 10 个回退算子占 18.44 ms，但砍掉整个 DFL 头省下来的不只是 18.44 ms——纯推理直接从 37.19 ms 掉到 **15.95 ms（−57.1%）**，省了 21.24 ms。多出来的那部分，就是"停下来等数据搬运"的调度损失，它从来没被单独记在一行里。

> 【费曼讲解】回退算子是什么
>
> ① 生活类比：一条流水线上六个工位，第五个工位突然说"这活儿我不会"，于是半成品被搬到楼下另一个车间做完再搬回来。楼下那个人可能做得也不慢，但**来回搬运和排队**把时间吃掉了。
> ② 不懂的人会怎么错想：既然 CPU 算得也不慢，那就让它算呗，反正最后结果对。
> ③ 一句话戳破：**问题不在它算得慢，在它破坏了"所有计算都在一个地方、一次做完"这件事。**
> ④ 回到术语：这叫子图回退（subgraph fallback）。NPU 编译器按算子支持表切图，不支持的就切出去给 CPU；每次切换都是一次张量落地内存、一次同步、一次调度。所以我优化的方向是**从模型导出端消灭回退**，而不是"把 CPU 那 10 个算子写快一点"。

**如果被追问「你怎么知道哪些算子回退了？」：** `rknn_init` 时传 `RKNN_FLAG_COLLECT_PERF_MASK`，跑完用 `rknn_query(RKNN_QUERY_PERF_DETAIL)` 拿每层的耗时和它跑在哪个单元上。我把它封成 `bench_npu 模型 1 --perf`，一条命令出全表。

### Q：NMS 的参数为什么是 conf 0.01 / IoU 0.45？

**一句话答案：** 因为要和 PC 侧评估**同一口径**。我的 mAP 是在这个口径下测的，部署换了阈值，两边数字就不可比了。

**展开讲：** 这两个值不是拍脑袋调的，是"评测口径"的组成部分：letterbox 640 灰边 114、conf 0.01、NMS IoU 0.45 且 class-aware、COCO 101 点插值。PC 侧 `convert/eval_map.py` 和板端 `bench/eval_dump.cpp` 用的是同一套，所以 COCO128 上 **FP32 mAP@0.5 = 0.6087 → INT8 = 0.6002（−0.85 点 / −1.4%）**这个结论才成立。

conf 0.01 明显低于实际使用阈值，这是 mAP 评测的惯例：低阈值只影响候选框数量，不影响 PR 曲线的端点，但能避免漏掉低分真阳性。

**如果被追问「那实际部署也用 0.01 吗？」：** 不。评测用 0.01 是为了算 mAP；生产推流给上位机的框会按显示需要过滤。**这是两个用途，不是两个标准。**

**如果被追问「那你展示的 19.2 FPS 是哪个阈值？」：** 那个 19.2 FPS 是上位机稳定接收真实活流的帧率，和阈值无关——阈值只影响每帧里的框数（上限 10 个），不影响出帧节奏。

### Q：推流为什么自己定义 248 字节定长帧，不用 RTSP？

**一句话答案：** 因为我要传的是**结构化检测结果**，不是视频流。RTSP 传的是压缩视频，我的上位机要的是"这一帧有几个框、什么类、多少分、什么坐标"——定长帧刚好一一对应，还天然解决粘包。

**展开讲：** 协议就两个结构体，`#pragma pack(push, 1)` 压紧，内存直接推：

```cpp
struct BBox { int32_t class_id; float score; float x, y, w, h; };    // 24 字节
struct DetectionHeader { uint32_t frame_id; uint32_t bbox_count; };  // 8 字节
struct FrameResult { DetectionHeader header; BBox boxes[10]; };      // 8 + 240 = 248 字节
```

**为什么定长天然解决粘包**：接收端不需要找分隔符、不需要解析长度字段，更不需要猜"这个 JSON 完了没有"——它只要**一直收到攒够 248 字节**就是一帧，剩下的字节是下一帧的开头。这个设计还被我复用到了 Agent 的 `get_vision_telemetry` 工具里：**收满 248 字节才算成功**，于是"离线、超时、半帧、畸形帧"能被区分开，而不是笼统报一个失败。

> 【费曼讲解】粘包到底粘的是什么
>
> ① 生活类比：TCP 是一条水管，不是一封封信。你倒了五杯水进去，另一头可能接到的是"两杯半"或者"三杯"，它不保证"一杯一次"。
> ② 不懂的人会怎么错想：我 `send` 一次，对方 `recv` 一次，不就是一条消息吗？
> ③ 一句话戳破：**TCP 保证"字节按顺序到"，不保证"按你 send 的边界到"。** 边界是你自己的事。
> ④ 回到术语：所以应用层协议要么带长度前缀、要么带分隔符、要么定长。定长是最省事的一种——接收端只需要一个计数器。

**如果被追问「RTSP/WebRTC 为什么不做？」：** 没做，这是诚实边界。我的场景不需要把画面推给远端的播放器，需要的是把检测结果交给上位机做验证和展示。真要做视频推流，那是另一条技术栈（RTP 打包、时间戳、重传），和当前目标不是一回事。

**如果被追问「248 这个数怎么来的？」：** 8 字节头加 10 个 24 字节的 BBox，**上限 10 个框**是产品决策——一帧画面里真正需要关注的目标不会超过 10 个，定了 10 个框长就固定了，于是整帧长度固定。上限一变，协议就跟着变。

### Q：上位机重连时 10800+ FPS 是怎么回事？

**一句话答案：** 那是我把**历史积压**一次性吐出来了，不是真的跑得快。队列里堆了几千帧旧结果，客户端一连上就全速发，看起来像 10800 FPS。修法是入队限容量丢旧 + 建联瞬间清空存量。

**展开讲：** 这个 bug 特别值得讲，因为它是典型的"指标好看但系统有病"：如果只看那个 FPS，你会以为性能起飞了；实际是**延迟雪崩**——客户端收到的是几分钟前的画面。

两个修法对应两个失效点：① 结果队列 `size >= 2` 就丢最旧的，保证队列里的永远是新鲜的；② 客户端建联的瞬间清空存量，从"当前帧"开始推。修完之后上位机稳定接收 **19.2 FPS** 真实活流。

**如果被追问「这个 FPS 和 48.6 FPS 差在哪？」：** 差在口径和端到端位置。48.6 是 bench 层的"推理 + 后处理"，19.2 是**上位机实际收到的帧率**，中间隔着 MPP 解码、CSC、letterbox、网络和客户端的处理。19.2 更接近"用户感受到的速度"。

### Q：这条链路的瓶颈搬过几次家？

**一句话答案：** 三次。先是摄像头（以为是 20 fps 上限）、然后是 NPU（37.19 ms 看着像 NPU 慢）、现在是 CPU 的 CSC（33.583 ms 占 60%）。

**展开讲：** 这个"搬家史"是我最喜欢讲的叙事，因为它展示的是**定位能力而不是运气**：

- **第一次**：全链路 50 ms/帧，看着像处理慢。查下来是摄像头默认协商 20 fps，设 30 之后帧周期 33.3 ms。**瓶颈是"等帧"，不是"算得慢"。**
- **第二次**：单帧 37 ms，看着像 NPU 慢。逐层剖析后发现 **49% 的时间在 CPU**（DFL 头的回退算子 18.44 ms），NPU 主体只有 19.23 ms。**瓶颈是模型导出，不是硬件。**
- **第三次**：把 DFL 砍掉、纯推理 15.95 ms，NPU 已经很快了。这时候瓶颈变成 CSC **51~65 ms**——CPU 读 uncached DRM 内存，memcpy 只有 188 MB/s。**瓶颈是内存访问模式。**

每一次搬家都伴随一次"我以为"被推翻。所以我不太相信"凭经验看哪里慢"——**必须拆层**。

**如果被追问「你现在还觉得哪里能再快？」：** CSC。Release 之后 33.583 ms 仍是全链路 60%。正解是 RGA，但本轮判断不划算，理由我前面讲了。另外 MPP 硬编我实测过，比软编还慢，已经从路线图上划掉了。

**如果被追问「你怎么保证下一次定位还是对的？」：** 靠两条：每个数字标口径，每个改动配对照组。比如做 O0/O3 时我特意留了三个"理论上不该变"的量——纯推理（14.79~14.88 到 14.90~14.95，没变）、MPP 硬解（1.250→1.322 ms，+5.8%）、letterbox（1.184→1.222 ms，+3.2%）。三个没变，唯一自有的热点 CSC 却快了 1.549 倍——这才叫闭环。

## 三、这一章的"记忆锚点"

- **六道手**：采集 → 硬解 → 预处理 → 推理 → 后处理 → 推流；只有第 5 段在 NPU 上，其余都是硬件单元或 CPU。
- **两个口径不许混**：bench 20.58 ms / 48.6 FPS（推理 + IO + 解码 + NMS），生产 55.84 ms / 17.9 FPS（含硬解 + CSC + letterbox）。
- **摄像头 20 fps 不是上限**：`cap.set(CAP_PROP_FPS, 30)` 一行，33.33 ms/帧、p95 33.50、零抖动；**回读值会骗人**（请求 25 回读 25，实测仍 20）。
- **MPP 硬解 p50 1.027 ms vs 软解 7.761 ms = 7.6 倍**；`-1012` 是层间版本倒挂，源码编静态库一行不改就通。
- **CSC 在 CPU 上是有原因的**：RGA 2.1.0 不支持 full CSC、偏差约 ±13%，评估过、判断不划算、没做。Release 后 33.583 ms，仍占全链路 60%。
- **letterbox 保形状**：`scale = min(640/w, 640/h)`、补灰 114、逆变换 `(x - pad_x) / scale`；不这么做会把目标压扁，mAP 掉。
- **DFL 落在 CPU**：125 个算子里 115 个在 NPU（19.23 ms），10 个回退在 CPU（18.44 ms，49%）；砍掉后纯推理 37.19→15.95 ms。
- **248 字节定长帧**：8B 头 + 10×24B BBox，定长天然抗粘包；背压丢旧 + 建联清空，修掉 10800+ FPS 的历史积压雪崩。

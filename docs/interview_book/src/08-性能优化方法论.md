# 第 8 章 性能优化方法论

> 一句话心智模型：性能优化不是"把代码写快"，而是"先证明时间到底花在谁身上，再只动那一个地方，最后用一组不该变的对照组证明你真的动了它"。

## 一、先建立心智模型

这一章讲的是我这条链路从**纯推理 37.19 ms** 掉到 **15.95 ms**、单帧全链路从 **37.19 ms / 26.9 FPS** 变成 **20.58 ms / 48.6 FPS** 的过程。但比那几个数字更值得背的是**顺序**：我在动手之前先做了一次逐层剖析，发现 37.19 ms 里只有 **19.23 ms** 在 NPU 上，另外 **18.44 ms** 是 NPU 编译器切给 CPU 的 10 个算子。这一步如果没做，后面所有"听起来很专业"的动作——绑三核、做零拷贝、开多线程、上 `-O3`——都会打在一个并不缺的地方上。

```
一帧 37.19 ms 的账，是怎么被拆开、又被拆掉的（板端实测，单核 Core0 口径）

  第 0 步｜直觉          "NPU 太慢"  ->  手先伸向 core_mask / 零拷贝 / 多线程
        |
  第 1 步｜测量          bench_npu --perf，125 个算子逐个记账
        |                NPU 115 个   19.23 ms  (51.0%)
        |                CPU  10 个   18.44 ms  (49.0%)   <- 真凶，全是 DFL 头
        |
  第 2 步｜证伪          把"听起来很合理"的假设一个个排掉：
        |                核绑定？  35.97 ms（AUTO 37.27）-> 不是调度
        |                喂数据？  37.05 vs 37.19（0.4%）-> 不是拷贝
        |                那剩下的只能是图里那 10 个算子
        |
  第 3 步｜动手          一次只改一个变量：
        |                图手术砍 DFL   -> 纯推理 15.95 ms（-57.1%）
        |                访存顺序       -> 解码 3.19 -> 1.79 ms
        |                编标志 Release -> CSC 52.016 -> 33.583 ms（1.549x）
        |
  第 4 步｜验收          每个结论都配"本该不动"的对照组：
                         NPU 纯推理 O0/O3 都是 14.7~15.0 ms -> 测量没漂
                         MPP 硬解 +5.8%、letterbox +3.2%     -> 不是负载波动
                         CSC 1.549x                         -> 确实命中自有代码
```

**记住这一个比喻**：优化像看一个"头疼"的病人。你不能一进门就开止痛药，得先做检查（测量），把"牙齿、颈椎、睡眠"一个个排掉（证伪），最后才对那一个病因下药（单变量改动）；复诊时还要看几个"本来就不该有变化的指标"（对照组）——如果连血压都跟着乱跳，那说明你的检查本身不可信，而不是药有效。

## 二、问答正文

### Q：37.19 ms 一帧，你当时第一反应是哪里慢？

**一句话答案：** 第一反应是"NPU 算力不够"，这是错的——逐层一拆才发现，49% 的时间根本不在 NPU 上，而在 NPU 编译时被切给 CPU 的 10 个算子上。

**展开讲：** 起点数字是单核 Core0 上 200 次推理的均值 **37.19 ms**，折 26.9 FPS，**p99 40.28 ms**（p50 37.07、p95 37.30）。我为什么第一反应会错？因为官方对这个模型给的量级是 5.5~7.0 ms，我实测 37.19 ms，差 5 倍以上。人在"差了 5 倍"的时候，第一反应一定是"我哪里没配对"——核没绑上？数据没直喂？单线程没并行？这三个念头对应的动作分别是调 `core_mask`、做 DMA-BUF 零拷贝、上多线程。我都做了对照实验，三个全被数据否掉，这才是这一章真正的价值：**先证伪，再动手**。

顺带说清楚一件事：37.19 ms 这个数和我后面讲的 15.95 ms 是**同一个口径**（`rknn_inputs_set + rknn_run + rknn_outputs_get` 的推理引擎边界，输入是合成 640×640 灰图），不含视频解码、CSC、letterbox。这也是我为什么一直强调口径——换个口径比数字，等于没比。

**如果被追问「那你怎么知道不是 NPU 慢？」：** 两条独立证据。① 三种核绑定都测了：单核 37.19 ms、单 context 挂三核 mask 35.97 ms（只快 3.3%）、`AUTO` 37.27 ms，最快也就 35.97——**不是调度问题**。② 逐层剖析把 125 个算子逐个记账，NPU 那边 115 个总共 19.23 ms；如果 NPU 真是瓶颈，它该吃掉绝大部分时间，而不是 51%。

### Q：`bench_npu --perf` 是怎么把 37.19 ms 拆到算子级的？

**一句话答案：** `rknn_init` 时传 `RKNN_FLAG_COLLECT_PERF_MASK`，跑完后 `rknn_query(RKNN_QUERY_PERF_DETAIL)` 能拿到每个算子的耗时和它跑在哪个执行单元上，我把它封成 `./bench_npu <model> 1 --perf`，一条命令出全表。

**展开讲：** 拿到手的是 125 个算子的明细，按执行单元一汇总就分出阵营：

| 执行单元 | 算子数 | 合计耗时 | 占比 |
| :--- | ---: | ---: | ---: |
| NPU | 115 | 19.23 ms | 51.0% |
| CPU（回退） | 10 | 18.44 ms | 49.0% |
| 合计 | 125 | 37.67 ms | 100% |

逐层表的合计是 37.67 ms，和 200 次均值的 37.19 ms 略有出入——两个口径不同（逐层计时本身有开销），我引用时按各自出处标注，不混着说。

最慢的 8 个算子里，前 3 名全在 CPU 上，而且全是 `model.22` 的 DFL 段：

| 算子 | 执行单元 | 耗时 | 所属 |
| :--- | :--- | ---: | :--- |
| Transpose | CPU | 9181 us | `model.22/dfl/Transpose` |
| exSoftmax13 | CPU | 4467 us | `model.22/dfl/Softmax` |
| Reshape | CPU | 2660 us | `model.22/Concat_3_swap_concat_reshape` |
| ConvExSwish | NPU | 1857 us | `model.0/conv`（首层，3 通道） |
| Concat | NPU | 1687 us | `model.22/Concat_3` |
| Transpose | NPU | 1475 us | `model.22/dfl/Transpose_1` |
| Reshape | CPU | 941 us | `model.22/Concat_3_0_unsqueeze1` |
| Reshape | CPU | 765 us | `model.22/Concat_0_unsqueeze0` |

光前三个（9181 + 4467 + 三个 Reshape 合计 4366）就是 **18.02 ms**。而整个 backbone 的 NPU 时间也才 19.23 ms——**检测头的一小段解码，吃掉了和整个骨干网差不多的钱**，这就是我当时看到表的第一感受。

**如果被追问「以后加了个新模型，你怎么知道它有没有同样的问题？」：** 一条命令。`./bench_npu <model> 1 --perf`，然后看两个数：CPU 回退算子的个数、以及回退耗时的占比。回退占比超过 20% 就值得动图，低于 5% 就先看别处。**这个探针比任何"感觉快了"都可靠，因为它是幂等的、可复现的。**

### Q：什么叫算子回退？为什么它比"慢"更严重？

**一句话答案：** 回退是 NPU 的编译器不认识某个算子，把这一段子图切下来扔给 CPU 算。它比"慢"严重得多，因为 CPU 和 NPU 之间要来回搬张量，NPU 还得停下来等。

**展开讲：** 我这 10 个回退算子自己算 18.44 ms，但砍掉整个 DFL 头之后，纯推理从 37.19 ms 掉到 15.95 ms，**省了 21.24 ms**——比 18.44 ms 还多。多出来的这一截，就是"停等"和"搬运"的调度损失，它**从来没被单独记在任何一行的耗时里**，所以只看报表你永远看不到它。

> 【费曼讲解】为什么"算得慢"不是回退最贵的地方
>
> ① 生活类比：你要在 A 楼做三道工序、B 楼做两道。B 楼那两道其实做得很慢，也就 5 分钟；但 A、B 之间每来回一趟要打包、等电梯、签字交接，一趟 8 分钟。你最后抱怨"B 楼那两道工序好慢"，其实你亏在电梯上。
> ② 不懂的人会怎么错想：既然回退的算子只占 18.44 ms，那我拼命优化它也最多省 18.44 ms，天花板就摆在那儿。
> ③ 一句话戳破：**回退的代价 = 那 10 个算子自己的时间 + 它造成的每一次"停等"**，后者不记账，但它按趟吃掉了墙钟。
> ④ 回到术语：这叫子图回退（subgraph fallback）。在 NPU 上它表现为一个个同步点——NPU 提交完前面的算子，中间张量要落到共享内存，CPU 读完算完写回去，NPU 再读进来续跑。所以我的方向定成"**从图里消灭回退**"，而不是"把那 10 个算子写快一点"。

**如果被追问「怎么知道哪些算子会回退？」：** 不用猜，`RKNN_QUERY_PERF_DETAIL` 直接把每个算子的执行单元列出来了。另外把 `.rknn` 的图层结构和算子支持表一对照，规律很清楚：卷积、Concat 这类 NPU 天生会；`Transpose` / `Softmax` / `Reshape` 这类纯形状变换 + 特殊激活，在 `(1, 64, 8400)` 这种"通道在中间"的布局上支持很差。

### Q：DFL 到底在算什么？为什么不能直接回归一个距离？

**一句话答案：** YOLOv8 的检测头对每个边不输出一个距离，而是输出 16 个 bin 的概率分布，再对 `[0..15]` 求期望把分布"压"回一个连续值；这一步是 softmax 加加权求和，不是一个卷积，所以在图里显得又碎又难融合。

**展开讲：** 从张量形状看得最清楚。切点处的 `raw_box` 是 `(1, 64, 8400)`：64 = 每条边的 16 个 bin × 4 条边，8400 是三个尺度（stride 8/16/32）的锚点拼起来的总数。对其中任意一条边：

```
   z = [z0, z1, ..., z15]            # 16 个 bin 的原始 logit
   p = softmax(z)                    # 变成分布，sum(p) = 1
   d = p0*0 + p1*1 + ... + p15*15    # 期望，即 "积分"
   dist_px = d * stride              # 格子单位 -> 像素
```

`d` 的取值范围是 0~15，单位是"格子"，必须再乘 stride 才是像素——我第一版就是漏了这一步，框整体偏大、**刚好差 8 倍**（stride=8 那一路）。这个坑的排查方法很土但很有效：把 `dist` 的范围打出来，正确应该是 0~120 像素量级，我打出来是 0~15，一眼就知道量纲错了。

为什么网络要这么设计？因为直接回归一个数，等于逼网络对"到底 3 还是 4"押一个值；输出分布再取期望，允许它说"我觉得 3 的可能性 0.6、4 的可能性 0.4"，训练时更好收敛。代价就是推理时多一次 softmax 和一次加权和。

### Q：那这堆数学能不能合并掉？为什么"求期望"可以塞进一个卷积？

**一句话答案：** 能。因为期望对概率是线性的，`Σ p_i·i` 等价于用一个权重固定为 `[0, 1, ..., 15]`、没有 bias 的 1×1 卷积去卷 softmax 的输出；固定权重卷积恰好是 NPU 最擅长的算子。

> 【费曼讲解】为什么"求期望"其实是一次卷积
>
> ① 生活类比：一群人投票选 0 到 15 号档位，票数就是概率。你想要"平均档位"，就是让每个档位乘上它的票数再相加。注意——**那把尺子是固定的**：刻度永远是 0,1,2,...,15，不会因为今天投票的人变了而变。
> ② 不懂的人会怎么错想：求期望里又有乘法又有加法，前面还挂着 softmax，这么一堆东西拼起来，NPU 不认识太正常了。
> ③ 一句话戳破：**难点从来不是"求期望"，是它前面那两个形状变换**。加权求和本身是一组常数权重，常数权重的一次矩阵乘，就是一次 1×1 卷积，NPU 算这个比算什么都熟。
> ④ 回到术语：`d = Σ p_i · i` 可以写成 `d = conv1x1(p; W=[0..15], b=0)`，即"16 通道进、1 通道出、权重固定"的卷积。真正卡住编译器的是 `Reshape` 和 `Transpose`（把 `(1,64,8400)` 拆成 `(1,4,16,8400)` 再转置），以及那个 `(1,4,16,8400)` 布局下的 `Softmax`。

**展开讲：** 这条数学等价关系告诉我一件很重要的事：**DFL 不是"不可融合的原罪"，它之所以回退，是因为编译器在形状变换上认输了。** 所以有两条路可走：

- 方案 A（融合在图里）：把期望换成 1×1 卷积留在图中，让 NPU 吃掉；但 `Reshape` / `Transpose` / 那个布局下的 `Softmax` 仍然要处理，能不能全融进去要看编译器版本，风险不确定。
- 方案 B（切出来，我自己做）：干脆把整个 DFL 从图里切掉，只导出 `raw_box` 和 `cls_sig` 两个原始张量，解码由我自己的 C++ 完成。

**我实际落地的是方案 B**，理由是它的收益可算、风险可控：解码在 A76 上做完只要 1.79 ms（优化后），而方案 A 还得赌编译器的融合行为。这一点我在面试里会主动讲清楚——**方案 A 我评估过、没落地，说"我把它融成卷积了"是不诚实的。**

### Q：图手术具体切在哪？怎么保证切点找得对？

**一句话答案：** 完全不碰训练、也不改模型结构，直接对 ONNX 图做拓扑裁剪：从两个张量处截断，只导出 `raw_box (1,64,8400)`（未 softmax 的 box 分布）和 `cls_sig (1,80,8400)`（模型内已 sigmoid 的类别概率），DFL 解码和 NMS 搬到 C++。

**展开讲：** 两个切点是按**图拓扑**定位的，不依赖中间张量的 shape（ultralytics 导出的图通常没写 value_info）：

- `raw_box`：找 name 里含 `/dfl/` 的第一个 `Reshape` 节点，它的 `input[0]` 就是三个尺度 box 分布 concat 之后那个张量，来自 `/model.22/Concat_output_0`。
- `cls_sig`：找 `/model.22` 下最后一个 `Sigmoid` 的输出，即 `/model.22/Sigmoid_output_0`。

然后用反向 BFS 从这两个输出往回收集所有依赖，按原顺序保留节点（ONNX 要求拓扑有序），只保留被用到的 initializer，重建 value_info。结果：**节点 262 → 228，输出从 1 个 84 通道变成 2 个原始张量**。

注意切点选在 `Sigmoid` **之后**是个刻意的选择：原始输出本来就在 sigmoid 之后，我只是把它搬出来，不做任何数值变换——所以 cls 那一支的等价误差**精确等于 0**，一点舍入都没有。如果切在 sigmoid 之前，我就得自己在 CPU 上补一个 sigmoid，误差就不再是零了。

**如果被追问「为什么不重新训一个不带 DFL 的模型？」：** 因为重新训练会改权重，我现有的全部精度基线（FP32 mAP 0.6087、9 张真实图 0.8125 那些）都要重测，链路上一串结论全部作废。而切图这件事在数学上是恒等变换，能证明到 `max|Δ|` 是 float32 极限，**风险量级完全不同**。能用一个可验证的恒等变换解决的问题，不该动到训练。

### Q：怎么证明你没砍错？这是最关键的一问。

**一句话答案：** 不看代码看数据——拿原模型 84 通道输出当基准，和新模型两个输出加我的 numpy 解码逐元素比：**box 的 `max|Δ|` = 0.000122 px，cls 的 `max|Δ|` = 0**。

**展开讲：** 这里的验收标准是"能不能算出误差"，不是"看起来对不对"。0.000122 px 在 640 这个量级上已经是 **float32 的精度极限**（末位舍入），换句话说：这个差异不是我的解码引入的，是浮点数本身就存不下更多位。cls 直接是 0，因为那一支我只是把 sigmoid 之后的张量搬出来，什么都不做。

再多做一层交叉验证：C++ 解码器和 numpy 参考再对一遍，`max|Δ|` = **6.1e-05 px**，框数和类别完全一致。**两套独立实现（numpy 和 C++）、两个方向（对新图和原图）都收敛到同一个量级**，这才叫等价。

**如果被追问「只在你这几张图上对，能说明什么？」：** 逐元素比不是"挑几张图看着像"，它检验的是**整个数值映射**：同一张输入，两条路径的输出逐元素作差取最大绝对值。这个检验和"用哪张图"关系不大——差异上界落在浮点精度内，就说明两条路径在数学上是同一个函数。要更强的证据得对输入域随机采样再比，这一步我没做，我主动说。

### Q：解码从 3.19 ms 降到 1.79 ms，同样的算法为什么能差一倍？

**一句话答案：** 因为瓶颈不在算，在访存顺序。原来的循环每读一个数就跳 33.6 KB，80 个类别跳完跨 2.7 MB，cache 全废。

**展开讲：** `cls` 输出是 `(80, 8400)` 的行主序布局。按"anchor 外循环、类别内循环"遍历时，内层每取一次 `cls[c*8400 + a]`，地址就跳过一个 8400 元素的距离（33.6 KB），80 个类别跑一遍等于跨了 2.7 MB——**每次读都是一个新 cache line，前面搬进来的全浪费了**。

两个改动，加起来 1.78×：

- 换循环顺序：类别外循环、anchor 内循环，内层地址连续，顺着摸。
- 先按阈值筛 anchor，只对通过的做 softmax——避免 8400 次 softmax 全做一遍。

> 【费曼讲解】什么是 cache 局部性
>
> ① 生活类比：仓库里 80 个箱子、每箱 8400 个小件。你按"箱"取，一趟抱一箱，80 趟；你按"小件编号"取，为了拿 1 号小件要跑遍 80 个箱子，每趟只拿一件，8400 趟。
> ② 不懂的人会怎么错想：访问的总数据量完全一样（都是 80 × 8400 个数），算法也没变，那耗时应该差不多啊。
> ③ 一句话戳破：**CPU 拿数据不是按"个"拿的，是按块拿的**——你第一次摸到某个地址时，它旁边一整块已经被搬进 cache 了；顺着摸是白送，跳着摸是每次都白搬。
> ④ 回到术语：这就是空间局部性。同一个算法，只要把"内层循环走在连续地址上"，在 ARM 上就能差一倍。所以我的经验是：**看到"数据量不大但就是慢"，先怀疑 cache，别怀疑算法。**

**如果被追问「1.79 ms 和后来编译优化测的 0.62 ms 对得上吗？」：** 对不上，而且它们本来就不是同一组数，我会分开说。3.19 → 1.79 ms 是**改代码结构**（访存顺序）的 A/B，两次都是 O0、板端 20 次平均；3.44~3.51 → 0.62~0.63 ms 是**开编译优化**的 A/B，两次都是同一份优化后的代码、`taskset -c 6`、bench 灰图输入。**两个实验的变量不同、程序版本不同，绝对值不能串成一条链**，只有各自的倍率成立。

### Q：单 context 挂 3 核 mask 为什么没用？

**一句话答案：** 因为 `core_mask` 说的是"这个 context 允许用哪几个核"，不是"把一帧拆成三份并行算"；单帧内部的计算有数据依赖、天生串行，三颗核只能分段接力，中间还要同步，同步开销把并行收益吃光了——实测 **35.97 ms**，只比单核 37.19 ms 快 **3.3%**。

**展开讲：** 我量了三种绑法，三个数：

- 单核 Core0：37.19 ms / 26.9 FPS（Core1 37.32、Core2 37.36，三组几乎重合，说明"不调 mask 时就是一个核在算"）。
- 单 context 绑 `CORE_0_1_2`：**35.97 ms / 27.8 FPS**，只快 3.3%。
- `RKNN_NPU_CORE_AUTO`：37.27 ms，和单核没区别——**"交给运行时自动调度"并不会帮你把三核用起来**。

这一组实验的价值不在"省了 3.3%"，而在于它**排除了一个假设**：如果慢是因为核没用上，那最快的绑法应该接近官方量级；事实是最快的 35.97 ms 离 5.5~7.0 ms 差得远。于是嫌疑被推回到图里——这也是我下一步去做逐层剖析的直接原因。

**如果被追问「三核到底怎么才能用起来？」：** 3 个独立 context、3 个工作线程各绑一核、各跑一张不同的图，从同一个任务队列抢活。实测 **59.3 FPS / 2.21 倍**。并行需要"三条独立的活"，而不是"三个核抢一条活"。

### Q：3 个独立 context 跑到 2.21 倍，为什么不是 3 倍？

**一句话答案：** 因为三颗核各只跑到 **49%** 负载——NPU 有一半时间在等 CPU 喂数据、等内存返回。加核只解决"算力不够"，解决不了"喂不饱"。

**展开讲：** 三个线程、三个 context、各绑一核，200 帧级别的实测是：

| 配置 | 单帧延迟 | 聚合吞吐 | 加速比 |
| :--- | ---: | ---: | ---: |
| 单线程基线（仅 Core0） | 37.27 ms | 26.8 FPS | 1.00x |
| 3 线程 / 3 context（Core0+1+2） | 40.8 ms/路 | 59.3 FPS | 2.21x |

墙钟 5058 ms 跑完 300 帧，三路各自 4081~4089 ms，**差 8 ms**——负载几乎完美均衡，所以"2.21 倍"不是有哪一路偷懒。真正的两个原因：① 三条路抢同一条内存总线，**每路延迟从 37.27 ms 涨到 40.8 ms（单路慢了 9%）**；② 前处理、DFL 解码、NMS 这些段在 CPU 上还是串行的，NPU 算完要等 CPU 收尾才能进下一帧。

并行效率 = 实测聚合吞吐 ÷ 理论上限 = 59.3 ÷ (3 × 26.9) = **73.5%**（换 `2.21 ÷ 3` 是 73.7%，差 0.2 个百分点只是单核基线取 26.9 还是 26.8 FPS 的口径差异）。对外我就说"约 73.5%"。

**如果被追问「三颗核为什么有一半时间是闲的？」：** 因为 NPU 不是自己会找活干的单元，它要等 CPU 把数据准备好、提交任务、再把结果搬走。三核各 49% 负载这个数，本质上就是"三个工人在等同一台送料的推车"的工时统计。这也解释了为什么我后面不再折腾 NPU，而是去动 CPU 侧和编译标志——**瓶颈已经搬到另一侧了**。

### Q：`CMAKE_BUILD_TYPE` 为空这件事，你是怎么发现的？

**一句话答案：** 准备做 Release 优化时先去查现状，`build_native/CMakeCache.txt` 里 `CMAKE_BUILD_TYPE:STRING=` 后面是空的，`flags.make` 里 `CXX_FLAGS = -std=gnu++17`——**一个 `-O` 都没有，等于全程 `-O0`**。

**展开讲：** 影响面比想象大：项目此前记录的全部 CPU 侧耗时——MJPG 软解 7.76 ms、letterbox、DFL 解码 3.09 ms、CSC 51~65 ms——**全是在无优化构建下测出来的悲观值**。也就是说，这些数字不是"性能上限"，是"没开优化"。

为什么一个月没人发现？三条叠加，每条都值得记：

- CMake 在 build type 为空时**不报错、不警告**，只是不追加任何优化标志。编译成功、程序能跑、结果正确——**功能测试永远发现不了这类问题**。
- bench 工具是手工 `g++ -O2` 编的，跑出来的数（比如解码 1.79 ms）看着挺正常，于是形成了"整体应该没问题"的错觉。
- **两套构建口径混用，互相掩盖了对方的缺陷**。

修的时候踩了 CMake 自己的一个坑，很经典：构建摘要第一版恒为空、还误报"没有 `-O`"。因为 `CMAKE_BUILD_TYPE` 的值是 `Release`（大小写混合），而标志变量是全大写 `CMAKE_CXX_FLAGS_RELEASE`；直接拼 `CMAKE_CXX_FLAGS_${CMAKE_BUILD_TYPE}` 得到 `CMAKE_CXX_FLAGS_Release`，`DEFINED` 为假，读到空值。**CMake 变量名大小写敏感，必须 `string(TOUPPER ...)` 再拼。**

最终的修法里有一步比"加 `-O3`"更重要：**configure 结束时打印构建摘要，并检查 flags 里匹配不到 `-O[0-9s]` 就打 `message(WARNING)`**。让"没开优化"自己喊出来，而不是靠人记得去看。

### Q：改了编译标志，凭什么说 1.549× 是真的、不是测量噪声？

**一句话答案：** 因为在同一批测量里，我特意留了两组"理论上绝对不该变"的对照组：MPP 硬解（跑在硬件上）**+5.8%**、letterbox（走 OpenCV 预编译库）**+3.2%**，两个都没动；而唯一属于我自己写的 CPU 热点 CSC **恰好提速 1.549×**。

**展开讲：** 用同一张 `real_000.jpg`、同一个模型、两个生产二进制各跑 5 次，`taskset -c 6` 绑大核：

| 层 | O0（`build_native`） | O3（`build_release`） | 变化 | 判读 |
| :--- | ---: | ---: | :--- | :--- |
| MPP 硬解 decode | 1.250 ms | 1.322 ms | +5.8% | **对照组①**，硬件层，编译优化物理上碰不到 |
| NV12→RGB888 CSC | 52.016 ms | 33.583 ms | **1.549×** | 自己写的定点转换循环，优化直接命中 |
| letterbox（`cv::resize`） | 1.184 ms | 1.222 ms | +3.2% | **对照组②**，OpenCV 预编译库，`-O3` 作用不到 |
| NPU + DFL 解码 | 22.480 ms | 19.708 ms | −2.77 ms | 与 bench 口径的 −2.78 ms 吻合 |
| 全链路合计 | 76.928 ms | 55.836 ms | **−27.4%（1.378×）** | 13.0 → 17.9 FPS |

这里的门道是：**两个对照组是两种不同性质的"不该变"**——一个跑在硬件上（`rkvdec`），一个跑在别人早就编译好的 `.so` 里。两种不同机制同时纹丝不动，才排除了"今天机器心情好"这种解释。

> 【费曼讲解】对照组为什么是实验设计的核心
>
> ① 生活类比：想知道一种新肥料有没有用，就种两排——一排施肥、一排不施肥，其他条件全一样。如果两排**旁边的杂草长得一样高**，说明这块地本身没变；要是连杂草都突然窜高，那说明今年这块地整体变好了，跟肥料没关系。
> ② 不懂的人会怎么错想：优化前测一遍、优化后测一遍，快了，那就是优化的功劳。
> ③ 一句话戳破：**快，可能是你的改动带来的，也可能是机器今天心情好**；只有"不该变的也没变"，才能把后者排除掉。
> ④ 回到术语：这叫阴性对照（negative control）。bench 口径里我用的阴性对照是"纯推理 `rknn_run`"——O0 是 14.79~14.88 ms、O3 是 14.90~14.95 ms，差不到 1%，因为它跑在 NPU 硬件上，主机侧编译优化根本碰不到它。它稳住了，第③④项的变化才可以归因。

**如果被追问「那 1.549× 到底指什么？是不是全链路提速 1.55 倍？」：** 不是，这两个数一旦混着说就会被计算器拆穿。**1.549× 是 CSC 单层的**；全链路是 **−27.4%（1.378×）**，13.0 → 17.9 FPS。我会主动补一句局限：CSC 之外还有很多不归编译优化管的部分（NPU 时间、MPP 硬解、OpenCV 里的 letterbox），所以单层 1.55× 摊到全链路只剩 27.4%，而且**即使 O3 之后 CSC 仍占全链路 60%（33.58 ms），它还是第一瓶颈**。

**如果被追问「bench 口径的 5.5× 怎么又对不上了？」：** 口径不同，两组我都报：bench 口径（`bench_dflfree`，不含 CSC / letterbox / JPEG）里 DFL 解码 + NMS 是 **3.44~3.51 → 0.62~0.63 ms（5.5×）**，全链路（IO 周期 + 解码）**18.91~19.06 → 16.21~16.26 ms（−14.6%，52.6 → 61.7 FPS）**；生产二进制口径是上面那张表（含 CSC，所以绝对秒数大得多，全链路 76.928 → 55.836 ms）。**同一件事的两个观察窗口，倍率方向一致，绝对值不能互推。**

### Q：MPP 硬编明明走通了、参数都对了，你为什么把它从路线图划掉？

**一句话答案：** 因为它比软件编码更慢——1280×720 上 **7.24 vs 6.65 ms（1.07~1.09×）**，唯一优势是 CPU 占用从 **99.7% 降到 8.2%**；而单路 30 fps 下 CPU 根本不是瓶颈，拿 0.6 ms 的延迟损失换 6 ms 的 CPU 空闲是亏的。

**展开讲：** 先说它没坏：NV12 入、输出标准 baseline JPEG，9 张真实图 Y-PSNR **42.46 dB**，1280×720 **49.27 dB**，`file` 认证合法。所以这不是"做不成"，是"做成了但不划算"。

慢的原因是**结构性**的，不是写法问题。对分辨率扫描做线性拟合，得到两个延迟模型：

```
  硬编  t(ms) ≈ 0.35 + 7.0e-6 × 像素数
  软编  t(ms) ≈ 0    + 7.5e-6 × 像素数
```

每像素的边际算力两者基本打平（硬编甚至略优），但硬编每帧要多付 **0.35 ms 固定开销**——`ioctl` 提交 + 等中断往返。分辨率越小，这 0.35 ms 摊得越不利，所以 64×64 那档输得最惨；1280×720 时固定开销被摊薄，差距才压到 1.07×。其他口径也全是输：640×640 慢 1.13~1.20×；64×64 到 960×540 全部档位更慢，没有一个赢的；4 路并行时软编快 **1.88×**（软编能吃满 8 个 A76/A55，硬编只有 4 个 jpege 硬件核）。

**「真的走了硬件」这件事我也验了**，因为"硬编慢"最容易的第一猜测就是"其实悄悄软回退了"。查 `/proc/interrupts` 的中断增量：`fdba0000.jpege-core` 四个核跑前是 21485 / 2735 / 1566 / 820，跑后是 25038 / 3438 / 1953 / 987，增量 **+3553 / +703 / +387 / +167**，其余 jpege / rkvenc / rkvdec 核**全部 0 变化**。硬件确实在干活，慢是真的慢。

**如果被追问「负结论有什么好讲的？」：** 因为它证明了两件事。第一，**我会用数据否掉自己写在路线图上的假设**——"硬解快了 7.6 倍，那硬编也该快"听起来非常合理，但它是错的。第二，负结论有**明确的后续动作**：把"MPP 硬编省 7.2ms"从路线图划掉，CPU 侧优化改做 RGA CSC。**没有负结论的项目，通常意味着你根本没做够对照实验。**

**如果被追问「是不是你代码写得不好才慢？」：** 三条排除：① 正确性过了（PSNR 42~50 dB、`file` 认证）；② 真走了硬件（中断增量）；③ 慢的原因是结构性的——0.35 ms 固定开销来自提交/中断往返，不是我的循环写法。要证明是我写错，得先解释这个 0.35 ms 从哪来。

### Q：这套东西总结下来，性能优化到底该按什么顺序做？

**一句话答案：** 先测量再动手、一次只改一个变量、每个结论配一个"不该变"的对照组、所有数字都要能说出测法和复现命令。

**展开讲：** 五条，每条都配一个我踩过的反例：

- **先测量，别先动手。** 反例：我一开始想动的是 `core_mask` 和零拷贝，两样都被实测否掉（三核 mask 只快 3.3%；INT8 直喂 37.05 vs 转换 37.19，差 0.4%）。真正的瓶颈是图里的 10 个算子。
- **一次只改一个变量。** 图手术、访存顺序、编译标志是三个独立实验，每个都有自己的前后 A/B。要是三个一起改，最后那个 −57% 你根本不知道是谁的功劳。
- **留对照组。** 反例的反面就是最好的例子：如果当初没测"纯推理 O0 vs O3 不变"，那 1.549× 我永远说服不了任何人，包括我自己。
- **记录复现命令。** `BENCHMARKS` 每一节末尾都有能直接粘到板子上跑的 bash。我宁可写"未测"，也不给一个拿不出命令的数。
- **区分"感觉快"和"测出来快"。** 反例：不绑核测 DFL 解码，O0 的 p50 还是 3.45 ms（和绑核一模一样），但 mean 被拖到 6.38~8.15 ms、p95 冲到 15.78~17.20 ms——**5.5× 的真实差距，不绑核量出来只有 2×**。均值反映的是调度噪声，不是代码差异，所以我所有性能表都标了 `taskset`。

还有一个口径上的自检口诀：**性能表里如果两个不同口径给出完全相同的数字，一定是口径定义错了，不是巧合。** 我第一版测速表里"全周期 IO"和"全链路"两栏一模一样，查出来是 `t5 - t0` 把 release 也算进去了（release 在 decode 之后）。重定义成纯推理 `t2-t1`、IO 周期 `t3-t0`、解码 `t4-t3`、全链路 `t4-t0` 之后，`15.95 + 1.53 + 3.09 = 20.58` 才自洽。

## 三、这一章的"记忆锚点"

- **先看账，别先看算力**：37.19 ms 里 NPU 只有 19.23 ms（51.0%），CPU 回退 18.44 ms（49.0%），125 个算子逐个记账。
- **砍 18.44 省 21.24**：回退的代价不只是那 10 个算子自己的时间，还有一次次"停等"的调度损失，后者从来不单独记账。
- **图手术是恒等变换**：切在 Sigmoid 之后，节点 262 → 228；box `max|Δ|` = 0.000122 px（float32 极限）、cls `max|Δ|` = 0（精确为 0）。
- **三个数三个结论**：单核 37.19 ms / 单 context 三核 35.97 ms（−3.3%）/ 3 context 三核 59.3 FPS（2.21×）；三核各 49% 负载，所以不是 3×。
- **访存顺序能差一倍**：解码 3.19 → 1.79 ms，跳着读跨 2.7 MB，顺着读就对了。
- **一个 `-O` 都没有**：`CMAKE_BUILD_TYPE` 空了一个月，功能测试永远发现不了；修完 CSC 1.549×、全链路 −27.4%（1.378×）。
- **两个对照组同时成立**：MPP +5.8%、letterbox +3.2% 都不动，才有资格说 CSC 的 1.549× 是编译优化带来的。
- **负结论也是结论**：MPP 硬编慢 1.07~1.09×，唯一优势 CPU 8.2% vs 99.7%，因为单路 30 fps 下 CPU 不是瓶颈，划掉。

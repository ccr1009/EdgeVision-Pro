# 第 4 章 多线程与并发同步

> 一句话心智模型：多个线程**共享同一块内存**——这是它比进程便宜的原因，也是所有并发 bug 的唯一来源；所以这一章只讲两件事：共享数据的读写怎么被打断，以及用什么把它重新变回"不会被打断"。

## 一、先建立心智模型

```
进程 = 资源分配单位（一个地址空间、一张 fd 表）
线程 = CPU 调度单位（共享上面那堆东西，只有自己的栈和寄存器）

            进程（共享：全局变量 / 堆 / fd / 代码段）
   ┌──────────────────────────────────────────────────────┐
   │  ┌──────────┐   ┌──────────┐   ┌──────────┐         │
   │  │ 线程 0   │   │ 线程 1   │   │ 线程 2   │         │
   │  │ 私有:栈  │   │ 私有:栈  │   │ 私有:栈  │         │
   │  │   寄存器 │   │   寄存器 │   │   寄存器 │         │
   │  └────┬─────┘   └────┬─────┘   └────┬─────┘         │
   │       └──────────────┼──────────────┘               │
   │                ┌─────▼─────┐                        │
   │                │ counter++ │  ← 谁都能写，谁都可能被打断│
   │                └───────────┘                        │
   └──────────────────────────────────────────────────────┘

   一次 counter++ 在 CPU 眼里是三条指令：
       ① load  counter → 寄存器      ② add  寄存器, 1      ③ store 寄存器 → counter
   两条线程的这三条指令可以任意交错 → 后写的覆盖先写的 → 丢数据

   我的项目里线程/进程是这样分工的（单路摄像头，不是多路）：

   [摄像头采集线程] ──push──► g_raw_queue（界 2，满了丢旧）
                                    │
                    ┌───────────────┼───────────────┐
              [worker 0]       [worker 1]       [worker 2]
              绑 NPU core0     绑 core1         绑 core2
                    └───────────────┼───────────────┘
                                    │ push（界 2，满了丢旧）
                              g_stream_queue
                                    │
                          [TCP 推流线程] ──send──► 上位机 :9000
```

**记住这一个比喻**：线程像**同一间厨房里的几个厨师**——锅碗瓢盆（全局变量、堆、fd）全是共用的，每个人只有自己的围裙和菜刀（栈和寄存器）。所以他们干活特别快（不用搬厨房），但只要有两个人同时伸手去抓同一口锅，就一定会打架。锁就是那口锅的**使用牌**：谁拿到牌谁能动锅，其他人只能等。

## 二、问答正文

### Q：线程和进程到底差在哪？为什么线程"便宜"？

**一句话答案：** 进程是资源分配单位（独立地址空间、独立 fd 表），线程是 CPU 调度单位（共享进程的全部资源）；进程切换要换页表、刷 TLB，线程切换只换栈和寄存器。

**展开讲：** 便宜的地方在于"不用换地址空间"。地址空间一换，CPU 的 TLB（地址翻译缓存）大面积失效，接下来几百条访存全要重新走页表——这才是进程切换贵的真正原因，不是那几条寄存器保存指令。

代价也正来自"共享"：进程之间出事，各死各的；线程之间出事，一个线程写坏堆，整个进程一起崩。我项目里 3 个 NPU worker 共享同一个任务队列，只要有一个 worker 在没加锁的情况下动队列，另外两个立刻就跟着受害——这是线程模型天生的耦合。

**如果被追问「那什么时候该用多进程？」：** 需要隔离和容错的时候。我的巡检守护就是个独立进程而不是一个线程，因为它必须做到"网关崩了我还活着"，线程做不到这一点——同一个进程里的线程没有这种隔离。

**如果被追问「线程有自己的什么东西？」：** 栈、寄存器上下文（含程序计数器和栈指针）、线程 ID、errno、信号掩码、调度优先级。除此之外——堆、全局变量、代码段、fd 表、当前工作目录——全是共享的。

**面试怎么讲：** 先给"资源分配单位 vs 调度单位"这句定义，再补"贵在 TLB 而不是寄存器"，最后用"巡检守护必须是独立进程"落地。三层说完就不会被追问倒。

### Q：`pthread_create` 第四个参数为什么要传 `&ids[i]` 而不是 `&i`？

**一句话答案：** 因为参数是**地址**，线程真正去读这个地址的时候，主线程的循环可能已经跑完了；传 `&i` 的话三个线程最后拿到的都是 `i` 的终值。

**展开讲：** `pthread_create` 的签名是 `int pthread_create(pthread_t*, const pthread_attr_t*, void*(*)(void*), void*)`，最后那个 `void*` 是**指针**。你传 `&i`，传的是"变量 i 在哪"，而不是"i 现在等于几"。

竞态的窗口在于：主线程 `for (i = 0; i < 3; i++) pthread_create(..., &i)` 这一圈可能几十微秒就跑完了，而新线程被调度上 CPU 可能要几毫秒。等它真正去 `*(int*)arg` 的时候，`i` 早就变成 3 了——于是三个线程都以为自己是最核心 3（越界）。这就是典型的**共享了栈上变量**的 bug。

正确做法是让每个线程有自己的数据：定义 `int ids[3] = {0,1,2}`，传 `&ids[i]`，数组在主线程 join 之前一直有效。

**如果被追问「那如果我非要用循环变量呢？」：** 那就得把值本身塞进指针里（`(void*)(intptr_t)i`），或者在堆上 `new` 一份再传，或者用 `pthread_create` 之前先拷贝到一个稳定位置。三种都能用，但都别传栈上循环变量的地址。

**面试怎么讲：** 这题的关键词是"**传的是地址，不是值**"，再加一句"线程真正读的时候主线程可能已经跑完了"。说出这条时序，就说明你不是背的。

### Q：两个线程各做 100 万次 `counter++`，为什么结果是 1000093 而不是 2000000？

**一句话答案：** 因为 `counter++` 不是一条指令而是"读—加—写"三条，两个线程的指令交错之后，后写的会把先写的覆盖掉；我实测 100 万 + 100 万只得到 **1000093**，丢了 **9907** 次。

**展开讲：** 这是 D9 那个实验的真实结果。期望 200 万，实测 1000093。丢掉的 9907 次不是"随机丢"，每一次都对应一次具体的覆盖：

```
线程 A                      线程 B
load  counter(=5)  → 寄存器
                            load  counter(=5)  → 寄存器
add   寄存器, 1    → 6
                            add   寄存器, 1    → 6
store 6 → counter
                            store 6 → counter   ← A 的那次 +1 被吃掉了
```

两次自增，结果只涨了 1。这台机器上丢掉的概率大约千分之五，取决于两个线程被调度到不同的核上撞车的频率——所以这个数字**换个负载就会变**，别把它当成一个常数记。

同一次实验里，加上 mutex 之后 200 万次结果精确；`std::atomic` 跑 200 万次也**不丢**。

**如果被追问「编译器优化会不会让情况更糟？」：** 会。`-O2` 之后编译器可能把这个变量提到寄存器里循环，最后只写回一次，那结果可能反而"看起来对了"，但语义完全是错的。这种"优化后 bug 消失"最容易骗人。

**如果被追问「那你为什么不干脆全都上 atomic？」：** 见后面那题。`atomic` 只能保证**单个变量的一次操作**原子，保证不了"几个变量必须一起变"。

**面试怎么讲：** 直接报数字：期望 200 万、实测 1000093、丢 9907。然后一句话解释"三条指令 + 覆盖"。这个题的价值全在这个具体数字上，说"会丢一些"就废了。

> 【费曼讲解】把 `counter++` 想成**两个人轮流在同一个记账本上改一个数字，但中间要去里屋拿笔**。A 看了本子上写着 5，进里屋拿笔；B 也看了本子上写着 5，也进里屋；A 出来写上 6，B 出来也写上 6。两个人各记了一次，本子上只多了 1。不懂的人通常把 `counter++` 当成一个"瞬间完成的动作"，因为它在源码里就是一个符号。一句话戳破：**C 语言里的一行，在 CPU 眼里是三条指令，中间那两条之间的空隙，就是别人插队的地方。** 回到术语：这段空隙叫临界区，让三个人都不许插队的办法就是加锁——把"看本子"和"写字"锁成一个不可分割的整体。

### Q：mutex 加锁为什么能解决？它底层真的是每次都要进内核吗？

**一句话答案：** 锁把"读—改—写"包成一个临界区，同一时刻只允许一个线程进；底层是 futex——**无竞争时在用户态一条原子指令搞定，只有在真有竞争时才进内核挂起**。

**展开讲：** 这一点常被误解成"加锁就是系统调用"，那会得出"加锁必然很慢"的错误结论。futex（fast userspace mutex）的设计就是把快路径留在用户态：

- **无竞争**：对锁变量做一次原子 CAS（`0 → 1`），成功了就直接进临界区，全程没有系统调用。
- **有竞争**：CAS 失败，说明锁被占着，这时候才调 `futex(FUTEX_WAIT)` 进内核把自己挂到等待队列上，让出 CPU。
- **解锁**：先把锁变量原子写回 0，再看有没有等待者，有就 `FUTEX_WAKE` 唤醒一个。

所以我那台机器上 mutex 版跑 200 万次计数器，结果精确，而且总耗时完全可接受——因为绝大多数次都是无竞争的快路径。

**如果被追问「那原子指令是什么？」：** ARM 上是 `LDXR/STXR`（独占加载 + 独占存储，配对使用，中间只要有人碰过这块内存 STXR 就失败重试），新的 ARMv8.1 还有 LSE 原子指令（`LDADD` 之类）可以一次做完。x86 上是带 `LOCK` 前缀的指令。都是**硬件保证**，不是软件模拟。

**如果被追问「那把锁会不会很慢？」：** 会。持锁线程被调度走了，其他线程全在等，等于把多线程退化成单线程。这就是"锁粒度"那题要解决的。

**面试怎么讲：** "无竞争走用户态、有竞争才进内核"这一句一定要说，它能把"加锁很慢"这个常见误解直接顶回去。再补一句 ARM 上是 LDXR/STXR，可信度就够了。

### Q：锁粒度怎么选？你项目里是怎么做的？

**一句话答案：** 临界区里只放**必须原子**的操作，越短越好；我项目里是"抢到任务后立刻解锁"，锁里只做一次 `pop`，绝不在锁里跑推理。

**展开讲：** 我做过对照实验：3 个 NPU worker 从同一个任务队列抢单。

- **锁住整个过程**（拿到锁 → 从队列取任务 → 跑完推理 → 放回结果 → 解锁）：三个 worker 实际上变成串行，因为它们抢的不是任务，是那唯一一把锁。
- **抢到就立刻解锁**（锁里只做 `pop`，拿到任务马上 `unlock`，然后无锁地跑推理，最后再单独加锁 `push` 结果）：吞吐**明显高于**前者。

原因很直白：推理一次是几十毫秒（三核实测每帧 43.7 / 44.2 / 44.0 ms 这个量级），而 `pop` 一次是纳秒级。把 40 毫秒的活放进锁里，等于让另外两个核干等 40 毫秒。

这就是为什么网关里那两个队列各有**一把独立的锁**（`g_raw_lock` 和 `g_stream_lock`）：采集线程和推流线程在操作不同的队列，不该互相排队。**能拆成两把锁，就别用一把大锁。**

**如果被追问「锁变多了会不会死锁？」：** 会，所以要么保证"同一时刻只持有一把锁"，要么给所有锁规定一个全局顺序。我这里几条路径都是单锁操作，不存在嵌套。

**面试怎么讲：** 不要只说"临界区要短"，要说"我做过 A/B：锁住推理 vs 只锁 pop，后者快得多"，并给出量级对比（纳秒级 pop vs 几十毫秒推理）。有对照、有量级，才叫实测。

### Q：死锁的四个必要条件是什么？破坏了哪一个最实用？

**一句话答案：** 互斥、持有并等待、不可剥夺、循环等待，四个同时成立才会死锁；工程上最实用的是**固定加锁顺序**，直接破坏"循环等待"。

**展开讲：** 这四个条件是必要条件不是充分条件——四个都满足也可能不死锁（只是"有可能"）。所以防守思路是"随便破坏一个"：

- 破坏**互斥**：改成无锁结构（不是所有场景都能改）。
- 破坏**持有并等待**：一次性申请所有锁（`std::lock` 就是这么做的），或者拿不到就全放开重来。
- 破坏**不可剥夺**：用带超时的 `try_lock_for`，超时就放弃并释放已持有的锁。
- 破坏**循环等待**：给所有锁编号，永远按编号从小到大加。

我项目里目前没有嵌套加锁的路径（每条路径只持一把锁），所以死锁风险是"结构上就不存在"，而不是"靠纪律避免"——**这是更好的防守：让错误无法表达**。

**如果被追问「那条件变量和 mutex 一起用会不会死锁？」：** 会，如果两个线程各自持有一把锁再去抢对方的锁。所以条件变量那套的标准写法是"一个 mutex 配一个条件变量，`cond_wait` 内部会临时放锁"。

**面试怎么讲：** 四个条件报完，重点讲"我选固定顺序，因为最容易落地"，再补一句"我的架构上干脆没有嵌套锁"。能说到"让错误无法表达"这一层，就是加分项。

### Q：`std::atomic` 什么时候够用，什么时候不够？

**一句话答案：** 只有**单个变量的简单操作**（自增、置位、CAS）够用；一旦需要"几个东西一起变"，`atomic` 就不够了，必须 mutex。

**展开讲：** 判断标准是"**有没有不变量跨越多个变量**"。比如"队列的 size 和队列里的元素"就是一对——你不能只把 size 做成原子而元素不是，那样别的线程可能看到一个 size 为 1 但数组还没写进去的瞬间。

我的实测结论很干脆：`std::atomic` 跑 200 万次**不丢**，而无锁的普通 `int` 必丢（1000093 那次）。所以原子操作确实是硬件支持的，不是软件模拟。

**如果被追问「原子操作能替代锁吗？」：** 能替代"单个变量"，替代不了"临界区"。`atomic` 保证的是"这一条指令不可分割"，不是"这几条指令不可分割"。

**如果被追问「那无锁队列呢？」：** 原理上可以（CAS 循环 + 单生产者单消费者甚至不需要 CAS），但我**没在这个项目里实现过无锁队列**，我用的就是互斥锁加有界队列——因为队列操作频率远低于推理频率，锁的开销在这里根本不构成瓶颈。**选简单的、能证明对的，而不是选听起来高级的。**

**面试怎么讲：** "单变量 vs 跨变量"这个判据先给，再甩 200 万 vs 1000093 的对照，最后主动说"我没做无锁队列，因为不需要"——诚实且显得有判断力。

### Q：内存序（memory order）到底在讲什么？

**一句话答案：** 讲的是"你写的代码顺序，和 CPU 实际执行/别的线程实际看到的顺序，可能不是同一个顺序"，`memory_order` 就是你对编译器和 CPU 说"这几条重排没关系，那几条绝对不行"。

**展开讲：** 有两个层级的重排：

- **编译器重排**：编译期把没有数据依赖的语句换位置。你写的 `a = 1; flag = 1;` 可能变成 `flag = 1; a = 1;`。
- **CPU 重排**：CPU 有 store buffer、乱序执行，两个核看到的内存写入顺序可能不一致。ARM 是弱内存模型，比 x86 更容易观察到这种重排——这也是为什么"在 PC 上跑对了、在板子上跑错了"这种事真的会发生。

`memory_order_relaxed` 只保证这一个原子变量本身的原子性，不提供任何跨变量的顺序保证；`memory_order_acquire/release` 提供"一个线程的 release 写之前的操作，对 acquire 读之后的另一个线程可见"，这是写"标志位通知"最常用的配对；`memory_order_seq_cst` 是默认值，最强也最慢。

**如果被追问「你项目里实际用了哪个？」：** 老实说：我项目里的同步几乎全走 mutex 和条件变量，它们本身已经隐含了完整的内存屏障，所以我**没有单独去调 `memory_order`**。这部分我是"理解原理但没在项目里手写过弱序代码"。

**如果被追问「那为什么要懂它？」：** 因为读别人代码时会遇到。比如一个 `std::atomic<bool> stop_flag` 用 relaxed 写，配上一个依赖它来传递的普通指针，就是经典的数据竞争。

**面试怎么讲：** 先讲"两层重排"，再讲 acquire/release 是配对使用的，最后**主动说"我没手写过弱序代码"**。装作精通是最容易被追穿的，主动划边界反而加信任分。

> 【费曼讲解】内存序像**几个人对着同一块白板写字，但每个人手里的便利贴会延迟贴上去**。你写完"任务好了"（写数据），又写了"我举手了"（写标志），但在别人眼里可能先看到你举手、后看到任务内容。不懂的人通常以为"我代码里先写 A 再写 B，别人就一定先看到 A 再看到 B"。一句话戳破：**CPU 为了快，允许把写操作"先揣在兜里"；你能保证的只有"我自己写完了一定能读到自己写的"，保证不了"别人什么时候看到"。** 回到术语：这就是为什么需要 release/acquire 配对——release 相当于"把兜里所有东西倒出来再举手"，acquire 相当于"看到举手之后再看白板，保证内容已经到了"。

### Q：条件变量为什么必须配 mutex？

**一句话答案：** 因为"检查条件"和"进入睡眠"这两步必须**原子**——否则生产者可能正好在你检查完"队列是空的"、还没睡着的那一瞬间塞进任务并发出信号，那个信号就丢了，你会永远睡下去。

**展开讲：** 想象去掉 mutex 的代码：

```
消费者：if (queue_empty())  ← 检查，成立
                              ← 这时候生产者 push 了任务，cond_signal()，但你在"准备睡"状态，信号没人接
         cond_wait()          ← 睡下去，永远不醒
```

信号的本质是"一次通知"，它不记录历史——你不在等待队列里的时候发来的信号就是**丢了**。所以必须让"检查条件 + 入队等待"成为一个不可分割的动作。`pthread_cond_wait` 就是靠"传入 mutex"来做到这一点的：它的内部实现是在持锁状态下把当前线程挂到条件变量的等待队列，然后**在同一把锁的保护下**释放 mutex。中间没有缝。

这也解释了它的**三步语义**：先**解锁** mutex（让别人能进来改条件）、再**睡眠**、被唤醒后**重新加锁**再返回。第 ① 步和第 ② 步是原子的。

**如果被追问「那 cond_wait 醒来之后锁是谁的？」：** 是你的。`cond_wait` 返回前会重新加锁，所以返回后你依然在临界区里，可以直接检查条件、直接动队列。

**如果被追问「生产者为什么要先加锁再 signal？」：** 严格说修改共享数据必须持锁，signal 本身可以在持锁时发（常见写法）也可以在解锁后发（性能略好，减少"唤醒后抢不到锁"的空转）。我在网关里用的是**持锁中 signal**，简单、正确、不容易错。

**面试怎么讲：** 一定要讲出那个"丢信号"的时序图：检查完 → 生产者插入并 signal → 你睡下 → 永远不醒。把这段时序讲清楚，条件变量就没得问了。

> 【费曼讲解】条件变量配 mutex，像**去银行办业务拿号**。你要先看"现在叫到几号了"（检查条件），如果还没到你就得坐下等（睡眠）——但如果"看号码"和"坐下"之间没有柜台帮你锁住，可能出现：你看的时候还没到你，你抬头那一瞬间号已经叫过了，你却没在座位上（信号丢了），于是你永远坐在那里等一个已经过去的号。不懂的人通常以为"条件变量就是自己会等，跟锁没关系"。一句话戳破：**条件是"别人改的"，你要么在锁里检查完直接睡（中间不给别人插队的机会），要么就永远有可能错过通知。** 回到术语：mutex 保护的是"条件变量对应的共享状态"，`cond_wait` 把它和解锁/加锁绑成一个原子动作，才让"检查—睡眠"无缝衔接。

### Q：为什么 `cond_wait` 必须用 `while` 包，不能用 `if`？

**一句话答案：** 因为**醒来不代表条件成立**——可能是虚假唤醒，也可能醒来后任务被别的线程抢走了；用 `if` 只检查一次就会拿着空队列往下跑。

**展开讲：** 我跑过这个对比实验，结论很直接：`if` 版从空队列里读出了垃圾值 `0`，`while` 版正确地睡回去了。

"醒来条件不成立"有两个来源：

- **虚假唤醒**（spurious wakeup）：POSIX 明确允许 `cond_wait` 在没有 signal/broadcast 的情况下返回。这不是 bug，是为了实现效率做的让步（有些实现里信号处理、线程取消都可能造成提前返回）。
- **条件被抢**：`cond_broadcast` 唤醒所有等待者，但锁只有一个——抢到锁的那个把任务拿走了，剩下的线程醒来一看，队列又空了。

`while` 的写法就是把"醒来"重新当成"再检查一次"：

```
pthread_mutex_lock(&lock);
while (queue.empty() && running) {
    pthread_cond_wait(&cond, &lock);   // 每次醒来都回到这里重新判条件
}
task = queue.front(); queue.pop();
pthread_mutex_unlock(&lock);
```

**如果被追问「那 `if` 具体错在哪？」：** 不是"偶尔错"，是"条件不成立时它也往下跑"，于是 `queue.front()` 在一个空队列上被调用——这是未定义行为，读到什么都有可能。我在实验里读到的就是 0。

**如果被追问「唤醒后要不要重新检查 running 标志？」：** 要。我网关里 worker 的循环条件写的是 `while (queue.empty() && g_running)`，退出时主线程先置 `g_running = 0` 再 `broadcast`，worker 醒来发现队列空且已停止，就 break 出去——不然 join 会一直挂着。

**面试怎么讲：** 这是最高频的追问，标准答案是"虚假唤醒 + 条件被抢，所以醒来要重判"。能再补一句"我的循环条件里还带了退出标志，否则优雅退出时 join 会挂住"，就是实战过的人。

> 【费曼讲解】用 `if` 包 `cond_wait` 像**你排队等叫号，被叫醒一次就以为轮到自己了，直接冲进柜台**。但叫醒你的可能不是"到你号了"，而是"有人咳嗽了一声"（虚假唤醒），或者"叫的是别人的号，只是你在同一个大厅"（broadcast 唤醒所有人）。不懂的人通常把 `cond_wait` 当成"睡到条件成立为止"。一句话戳破：**`cond_wait` 只承诺"我让你睡，有人喊你你就醒"，从来不承诺"你醒的时候条件一定成立"。** 回到术语：所以等待必须写成"循环检查条件"的形式，`while` 是这段代码的正确性前提，不是风格选择。

### Q：生产者—消费者为什么要用有界队列？队列无限长会怎样？

**一句话答案：** 无限队列在"生产快、消费慢"时会让内存无界增长，最终 OOM；有界队列会把压力反向传回生产者，逼它降速或丢帧——这就是背压。

**展开讲：** 这是我在推流网关里真吃过的亏，细节放在第 5 章讲，这里只说结构上的道理。

队列的作用是**削峰填谷**：把两个速度不匹配的环节解耦，让快的不用等慢的。但"解耦"不等于"免费"——它把"速度不匹配"这个矛盾转化成了"队列长度"。如果队列没有上限，这个矛盾就被推到内存里去，等到内存撑不住的那一刻一起爆发。

有界队列做了另一件事：**它让"慢"这件事变得可见、可控**。队列满了，生产者立刻知道消费者跟不上，可以：

- **阻塞等待**（把压力传回上游，最保守）；
- **丢最旧的**（保实时性，我的推流队列就是这么做的，容量 2，满了先 pop 再 push）；
- **丢最新的**（保完整性，适合日志类）。

三种都是合法设计，但**必须显式选一个**，不能默认"队列无限长"。

**如果被追问「丢帧不会丢数据吗？」：** 会，但实时系统里"推一天的旧画面给上位机"比丢帧糟糕得多。用户要看的是"现在"，不是"十分钟前"。

**如果被追问「背压和限流有什么区别？」：** 背压是"下游慢导致上游被反压"，是被动的、由队列满触发的；限流是上游主动按令牌桶/漏桶限制速率。前者是系统自我保护，后者是业务约束。

**面试怎么讲：** 别背书，讲因果链："队列无界 → 生产快消费慢 → 内存涨 → OOM"。然后说"我有界队列 32，满了丢最旧，实测 300 帧丢 0 帧"——用数据证明"有界"不是牺牲。

### Q：RK3588 的 3 核 NPU 怎么真正并行？为什么不是 3 倍？

**一句话答案：** 必须**开 3 个独立的 context、每个绑一颗核**，而不是对一个 context 调 `rknn_set_core_mask(CORE_0_1_2)`；实测单 context 三核 mask 只从 37.19 ms 降到 **35.97 ms（−3.3%）**，3 个独立 context 才聚合到 **59.3 FPS（2.21×）**。

**展开讲：** 这一点我在 W2 里记了很久，因为它反直觉：`core_mask` 看起来很像是"把三颗核都给它"，但它是让**一个**推理任务在内部用多核去切同一张图——YOLO 这种网络层间是串行依赖的，切分收益非常有限，所以只快了 3.3%。

真正的并行要**任务级**：3 个 context，各自绑 core0 / core1 / core2，每个 context 独立跑完整的一次推理。这样三张图真的在三个核上同时跑。

为什么只有 2.21× 而不是 3×？因为**三核跑满时每颗核只有 49% 负载**——NPU 在等数据。瓶颈在 CPU 侧：DFL 头那段 Transpose/Softmax/Reshape 回退到 CPU 执行，占了整帧约 49% 的时间，NPU 主体只占 19.23 ms。

**如果被追问「那你怎么优化？」：** 先改模型导出，把 DFL 头从图里去掉（DFL-Free 后处理），纯推理从 37.19 ms 降到 15.95 ms；**不要先去做零拷贝**，因为瓶颈根本不在拷贝上。

**如果被追问「3 个 context 有什么代价？」：** 每个 context 都占自己的 NPU 内存和权重，3 个 context 的内存占用是单份的 3 倍。这也是为什么巡检守护坚决不加载 LLM——NPU 已经被这 3 个 context 占着。

**面试怎么讲：** 顺序是"错的做法 + 它的实测数字（−3.3%）→ 对的做法 + 它的实测数字（2.21×）→ 为什么不是 3×（49% 负载，CPU 回退）"。这三个数字连起来就是一个完整的技术判断故事，非常加分。

> 【费曼讲解】三核不是 3 倍，像**三家银行网点但只有一条运钞车道**。你开了三个窗口（三个 context 绑三颗核），客户分流也做得很好，但每个窗口每办完一笔业务都得等运钞车来一趟（CPU 侧的后处理、DDR 带宽），三个窗口只能一起等。不懂的人通常会错想成"三颗核 = 三倍速度，没跑到三倍就是没用对"。一句话戳破：**并行度不是由"最宽的环节"决定的，是由"最窄的环节"决定的；你只加宽了三颗核，没有加宽那条共享的通道。** 回到术语：59.3 FPS 相对单核 2.21×，这个比值叫加速比；它卡在这里是 CPU 回退和 DDR 带宽拖的，不是 NPU 算力不够——所以正确的优化动作是"砍 CPU 侧的后处理"，不是"再想办法榨 NPU"。

### Q：线程数怎么定？为什么不用线程池？

**一句话答案：** 线程数由**瓶颈资源的并行度**决定，不是越多越好；用线程池是因为线程创建/销毁有开销，而且线程数必须可控，否则几百个线程互相抢 CPU 反而更慢。

**展开讲：** 我项目里线程数的来源很明确：

- **3 个 NPU worker**：因为只有 3 颗核，第 4 个 worker 只能排队，纯属浪费栈内存和调度开销。
- **1 个采集线程**：摄像头只有一路。
- **1 个推流线程**：一条 TCP 连接。

如果换成 CPU 密集型的活，经验值是"核数或核数 + 1"；IO 密集型可以更多，因为线程大部分时间在等。但这些都是起点，真正的答案永远是**测出来的**——我测过 3 核各自只有 49% 负载，说明瓶颈不在线程数上。

关于线程池：我这里的线程是**长期驻留**的（进程活多久它们活多久），本质上已经是一个"固定大小的池"。真正需要线程池的场景是"任务源源不断地来、量不确定"，那时才需要一套"有活就派、没活就等"的分派机制（W2 的 D11 就是 3 worker 抢单的最小线程池）。

**如果被追问「线程不 join 会怎样？」：** 漏资源，类似僵尸进程。`join` 是"父等子并回收线程资源"，`detach` 是"自己跑完自己回收"。既不 join 也不 detach，线程结束后的资源就一直挂着。

**如果被追问「那你 join 的时候卡住了怎么办？」：** 这就是为什么要让 worker 的循环条件里带 `g_running`，退出时先置标志再 broadcast，不然 `join` 会永远等一个睡在条件变量上的线程。

**面试怎么讲：** 先给"瓶颈资源的并行度"，再给"我的 3 个 worker 是因为只有 3 颗核"，最后补一句"线程池在我的场景里就是固定驻留的线程，不需要分派层"。这样就既懂原理，又不是硬套八股。

## 三、这一章的"记忆锚点"

- 线程共享地址空间，只有栈、寄存器、errno 是私有的；进程切换贵在 **TLB**，线程切换不换地址空间。
- `counter++` 是"读—加—写"三条指令，2 线程各 100 万次实测 **1000093**（丢 **9907**）；加锁或 `std::atomic` 后 200 万次精确。
- mutex 底层是 **futex**：无竞争在用户态一条原子 CAS，有竞争才进内核挂起；ARM 上是 `LDXR/STXR`（或 LSE 指令）。
- 锁粒度：**只锁必须原子的那一步**。我项目里锁里只做 `pop`，几十毫秒的推理放在锁外；两个队列两把锁，不共用。
- 死锁四条件：互斥、持有并等待、不可剥夺、循环等待；最实用的是**固定加锁顺序**。
- `cond_wait` 三步：解锁 → 睡眠 → 被唤醒后重新加锁，前两步原子；必须配 mutex，否则**信号会丢**。
- 必须 `while` 不能 `if`：虚假唤醒 + 条件被抢；我用 `if` 版实测从空队列读出垃圾值 `0`。
- 3 核 NPU 要**3 个独立 context 各绑一核**；单 context 加三核 mask 只快 **3.3%**（37.19 → 35.97 ms），独立 context 才有 **2.21×**（59.3 FPS），因为每核只有 **49%** 负载、瓶颈在 CPU 回退。

## 四、面试官可能从哪下刀（预演）

| 他可能问 | 你怎么接 |

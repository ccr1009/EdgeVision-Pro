# 第 17 章 端侧 AI 部署方向：简历逐条对应

> 一句话心智模型：端侧 AI 面试官只信"你自己量出来的数"，不信"我用了什么框架"；这一章把简历上每个数字都配上口径、测量边界和对照实验。

## 一、先建立心智模型

先直接回答你那个问题：这本问答详解能不能用在这份简历上？能，而且这份端侧 AI 简历是覆盖率最高的一份——书里第 1 到第 14 章几乎能一条一条对回它的每一句话，覆盖度约 90%。但"书里讲到了"和"简历上这么写就对"是两件事。简历是被压缩过的文本，一句话里常塞进三个数字，而面试官会随手挑一个往下钻。所以这一章干的活是把简历翻回它的实测现场：它省掉的测量条件，我给你补回来；它写得含混的地方，我给你一个改过的说法。

你会发现一个规律：真正会被当场抓住的，从来不是"数错了"，而是"这个数的外延比你以为的大"。你心里想的是"纯推理那一段的耗时"，嘴上说的是"提速 57%"；你心里想的是"这一层自己写的代码快了 1.55 倍"，写在简历上跟"全链路缩短 27.4%"排在同一行。数字本身一字不差，但外延被人接错，就变成了另一种意思。

```
一个数字要经得起三层追问，缺一层它就只是口号

  简历上的一行字："纯推理 37.19 -> 15.95 ms（提速 57%）"
        |
  第 1 层｜怎么测的 ── 计时窗口从哪到哪？反复几次？报均值还是分位数？
        |                -> rknn_inputs_set .. rknn_outputs_get，200 次，均值 + p50/p95/p99
        |
  第 2 层｜对照是什么 ── 同一口径下，哪些量"本该不动"？它们真的没动吗？
        |                -> O0/O3 下纯推理 14.7~15.0 ms 不动；MPP +5.8%、letterbox +3.2%
        |
  第 3 层｜边界在哪 ─── 这个数不含什么？换硬件、换模型、换数据还成立吗？
        |                -> 不含硬解/CSC/letterbox；INT8 口径另算；换板子必须重量
        |
  三层都答得上来 -> 叫数据。任何一层答不上来 -> 叫宣传。
```

**记住这一个比喻**：报数字就像报体重——你得说清是早上空腹称的（怎么测的）、用的是不是同一台秤（对照是什么）、瘦的是脂肪还是水分（边界在哪）。面试官问的从来不是"多少斤"，而是"我凭什么信你这杆秤"。

**30 秒口述版 · 统一口径与性能剖析。** 我第一版也觉得是 NPU 慢，因为官方给这个模型的量级是 5.5~7.0 ms，我测出来 37.19 ms。但我没先改代码，先做了逐层剖析：125 个算子里 115 个在 NPU 上跑，合计 19.23 ms；另外 10 个被切回 CPU，合计 18.44 ms，占 49%。计时口径是 `rknn_inputs_set` 到 `rknn_outputs_get` 这一段，200 次取均值，同时看 p50/p95/p99。绑核、直喂数据、开多线程这三条"听起来很合理"的路我都做了对照实验，全被数据否掉，所以我才敢确定问题在图里。

**30 秒口述版 · 计算图重构与 C++ 优化解码。** 那 10 个回退算子全是 DFL 头的 Transpose/Softmax/Reshape。DFL 数学上就是每个格子 16 个 bin 求期望，而求期望可以塞进一个 1×1 卷积，于是我把整个头切掉，把模型改成双输出：`raw_box` 64 通道、`cls_score` 80 通道，节点从 262 降到 228。切完之后纯推理 37.19 → 15.95 ms。解码器我自己用 C++ 重写，先跟 numpy 参考实现对数值，坐标 `max|Δ|` 是 6.1e-05 px；顺手把类别循环挪到外层，解码 3.19 → 1.79 ms。全链路口径是 20.58 ms / 48.6 FPS。

**30 秒口述版 · INT8 量化与真 mAP。** 量化是 PTQ 四步：`rknn.config` 定平台和 mean/std，`load_onnx`，`build(do_quantization=True, dataset=...)`，`export_rknn`。校准集 170 张，50 张板端双摄实拍、100 张光照对比度伽马噪声增强、20 张合成。精度我不敢用余弦相似度交差，因为 0.9965 那个数看着漂亮而模型其实是废的，所以我跑真 mAP：COCO128，128 张图 929 个 GT 框，FP32 0.6087、INT8 0.6002，掉 0.85 个百分点。最值钱的是那个反面教材：用合成色块当校准集，分类头 scale 崩掉，输出恒等于 0.5000，看起来检出率还是 9/9。

**30 秒口述版 · 三核 NPU 并行与构建体系。** 一个 context 挂三核 mask 没用，只快 3.3%；要并行必须起 3 个独立 context，分别绑 Core 0/1/2，跑出 59.3 FPS，是单核 26.9 FPS 的 2.21 倍。注意是三核各约 49% 负载，不是线性 3 倍——每路自己反而慢到 40.8 ms，聚合吞吐才是收益。构建那块更有意思：跑了一个多月，`CMAKE_BUILD_TYPE` 是空的，一个 `-O` 都没开。改成 Release 之后 CSC 单层 52.016 → 33.583 ms，全链路 76.928 → 55.836 ms。

**30 秒口述版 · MPP 硬解与网络推流。** 硬解 p50 1.03 ms，OpenCV 软解 7.76 ms，差一个量级，因为 VPU 是专用单元，DCT 和熵解码在硅片里做。中途踩了个大坑：出厂预装的动态库跟 5.10 内核的驱动接口协议不兼容，`put_packet` 恒返回 `-1012`，最后是自己源码编了个静态库才通。推流我没上 RTSP，自己定了 248 字节定长帧加 `#pragma pack(1)`，定长天然抗粘包，再加队列丢旧和建联清空解决延迟雪崩。

**30 秒口述版 · 纯端侧大模型底座与 Tool Calling 闭环。** 大模型是 RKLLM runtime v1.3.1 加 Qwen3.5-2B 的 W8A8 版，权重 2.8 GB，纯板端离线跑，加载完系统的 `MemAvailable` 还有 6.1 GB 量级——注意是可用量不是余量，6.1 加 2.8 超过 8 GB 就是最好的解释。工具链解析 Qwen 原生的 XML `<tool_call>`，回填必须是严格 JSON 数组，一个工具也得是长度 1 的数组，传对象 runtime 直接拒。五个硬件原子工具覆盖温度、NPU 负载、LED、视觉遥测、巡检事件，串成"巡检、研判、执行、汇报"的多步闭环，三次独立测量是 106.5、112.2、123.9 秒。

**30 秒口述版 · 快慢双系统与外设、系统自愈。** 快层是不加载 LLM 的 C++ 守护，5 秒周期状态机加迟滞判决，只在状态翻转时写 `llm_pending.jsonl` 交给慢层——为什么坚决不让快层碰模型？因为 NPU 上已经有一路 YOLOv8 在跑，再挤进去就是一锅端。12 项用例回归全绿，含故障注入和自动恢复。外设那块：双摄 V4L2 两路 1280×720，默认协商成 20fps 是没显式设帧率的根因，修完 33.33 ms/帧、30.0 FPS 零抖动；双麦走 ALSA 的 `hw:5,0` 和 `hw:6,0`、16 kHz S16_LE；服务化用 `daemon(0,0)` 加 systemd `Restart=always` 5 秒自愈，`sigaction` 收 SIGINT/SIGTERM，全链路屏蔽 SIGPIPE。

## 三、简历上 4 处必须掰正的口径（最重要）

这一节有 6 个 Q。为什么上面说"4 处"？因为 6 处措辞问题里，真正属于**数字口径错位**的是前 4 处（体积、掉点、提速、加速比），它们错在把不同性质的量放进同一个句式里；后 2 处（6.1 GB、7.6 倍）属于**测量定义模糊**，数没错，是"这个数指的是什么"没说清。两类都会被当场抓住，但挨刀的方式不同：前 4 处是"你这算法不对"，后 2 处是"你这命令我怎么复现不出来"。

### Q：简历写"模型体积缩减 64%（12.2 MB → 4.34 MB）"，这句话有什么问题？

**一句话答案：** 12.2 MB 是原始 FP32 ONNX，4.34 MB 是做完图手术的 INT8 RKNN，中间跨了「量化」和「图手术」两次性质完全不同的改造；把两步收益合进一个减法里对外说 −64%，面试官问一句"这两步各占多少"就露馅。

**展开讲：** 正确的说法是三行而不是两行：

| 口径 | 数值 | 这一步做了什么 |
| :--- | ---: | :--- |
| 原始 FP32 ONNX | 12.2 MB | 改造前的起点 |
| 旧 84ch 模型 INT8 | 6.22 MB | **量化**这一步做完 |
| DFL-Free INT8 | 4.34 MB | **图手术**这一步做完，−30.2% |

所以我念的话是两句，绝不合并：先说"量化把模型压到 INT8 口径"，再说"图手术在 INT8 口径上从 6.22 MB 降到 4.34 MB，这一步是 −30.2%"。BENCHMARKS 里我自己写过一句提醒——不能合成一个减法对外说 −64%，这句话就是写给你现在用的。

**如果被追问「那你能不能直接说压缩到 1/3？」：** 不能，因为 4.34 / 12.2 这个比值同样跨口径，和 −64% 是一个错误的两种写法。能被除的是同一口径下的两个数，比如 6.22 → 4.34。

**如果被追问「量化到底省了多少？」：** 12.2 → 6.22 MB 是量化的贡献，但这里要老实补一句：ONNX 文件里除了权重还有图结构和常量，所以"文件小了几倍"不完全等于"权重少了几倍"，我不拿文件体积反推权重压缩率。

> 【费曼讲解】为什么"12.2 → 4.34 缩小 64%"不能这么讲
>
> ① 生活里对应的场景：有人跟你说"我今年变富了 64%"，你追问一句，他说"一半是涨薪，一半是这个月开始自己做饭省了钱"。这两件事能加成一个大数吗？涨薪是收入端、省饭钱是支出端，它们连同一个会计科目都不是。
>
> ② 不懂的人会怎么错想：会想"反正最后体积确实小了嘛，报总数有什么错"。错在总数**不含信息**：它既不告诉别人量化值多少，也不告诉别人图手术值多少，只有一个凑出来的大数字。而且它让人误以为"做一个动作就能得到这个收益"。
>
> ③ 一句话戳破：能做减法的，只有同一把尺子量出来的两个数；换了尺子还相减，那不叫减法，叫编故事。
>
> ④ 回到术语：12.2 MB 是 FP32 ONNX 的文件口径，4.34 MB 是图手术后 INT8 RKNN 的文件口径，中间经过了量化（精度从 FP32 变 INT8）和图重构（算子从 262 个变 228 个）两个独立变量。单变量原则要求一次只留一个变量在动，所以体积也得拆成两段报。

### Q：简历写"COCO128 mAP@0.5 仅微损 0.85%"，0.85 是百分比还是百分点？

**一句话答案：** 是**百分点**。0.6087 掉到 0.6002，绝对差 0.0085，也就是 0.85 个百分点；换成相对值是这个数的 1.4%，即 −1.4%。写成"微损 0.85%"会被读成"相对只掉 0.85%"，等于把损失说小了 1.6 倍。

**展开讲：** 我的标准说法是一句带两个数，顺序固定——"mAP@0.5 从 0.6087 掉到 0.6002，掉了 0.85 个百分点，相对是 −1.4%"。先绝对后相对，因为绝对值是原始事实，相对值是换算结果；反过来先报相对，听着像在挑一个好看的数。这么报还有一个好处：面试官拿计算器一除必须对得上，敢当场被人验算的数字才是真数字。

同一个坑还埋在别处：这个 0.85 是 mAP@0.5 的掉点，不是"精度掉了 0.85%"，也不是"准确率 99.15%"。mAP 是 0 到 1 之间的连续量，不是通过率。

**如果被追问「那到底算好还是差？」：** 从公开经验看，INT8 PTQ 掉 1~3% 是常见区间，我这个算比较好。但我不说"优秀"，因为不同模型不同任务的下限差很远，我没做过跨模型对比。我能确定的是：在这个检测任务上可接受，因为框位置偏差不到 1 px、检出率没有下降。

**如果被追问「只报一种行不行？」：** 不行。只报"−1.4%"像在修饰，只报"−0.85 个点"又要对方自己换算，而且一换算就容易算错——这个坑我自己踩过。

> 【费曼讲解】百分点和百分比，差的那一个字是什么
>
> ① 生活类比：一只股票从 100 块跌到 97 块，你可以说"跌了 3 个点"，也可以说"跌了 3%"。这两个数在这一刻刚好相等，纯属巧合——因为起点正好是 100。如果它从 200 跌到 194，那就是跌了 6 个点，但只跌了 3%。
>
> ② 不懂的人会怎么错想：看到"0.85"和"−1.4%"，第一反应是"这俩矛盾了吧""哪个是真的"。其实两个都是真的，只是**分母不同**：百分点的分母是 1（一个完整刻度），百分比的分母是基准值 0.6087。
>
> ③ 一句话戳破：百分点是两个百分比**相减**得到的东西，百分比是两个百分比**相除**得到的东西；一个是减法一个是除法，永远别混着说。
>
> ④ 回到术语：mAP 本身就是个 0~1 的数，所以它的差天然是"点"而不是"百分比"。0.6087 − 0.6002 = 0.0085 = 0.85 个百分点；0.0085 ÷ 0.6087 = 1.4%，这才是相对下降。报"0.85%"等于在说相对下降 0.85%，那是把 0.6087 掉到 0.6035 才有的幅度。

### Q："纯推理提速 57%"和"37.19 → 15.95 ms"，哪个说法更安全？

**一句话答案：** 后一个安全，因为它自带口径和两个原始数；"提速 57%"是不严谨的措辞——57% 是**耗时降幅**，等价提速是 37.19 除以 15.95，也就是 2.33 倍。说"提速 57%"的人，其实想说的是"耗时减少 57%"。

**展开讲：** 这里有个中文语感陷阱。"提速"在口语里既可以指"时间变短了百分之多少"，也可以指"吞吐变成原来的几倍"，而这两个数完全不同：耗时降 57%，对应速度快 2.33 倍。面试官听到"提速 57%"，如果按第二种理解，心里会算成 1.57 倍，一除发现是 2.33，就会觉得你这人不是不会算就是故意含糊。

我的标准说法是："纯推理从 37.19 ms 降到 15.95 ms，耗时降了 57%，等价吞吐 2.33 倍。"三个信息一次给全：两个原始值、降幅的口径、换算后的倍数。同理，全链路那句是"单帧 20.58 ms / 48.6 FPS，时延降 44.7%、吞吐 +81%"——也是同一套三段式。

**如果被追问「2.33 倍和 2.21 倍是什么关系？」：** 两个口径，不能相乘也不能混。2.33 倍是**单核、纯推理**这一段自己变快的倍数（同一个 context、同一份输入，只是图变了）；2.21 倍是**三核聚合吞吐**相对单核的倍数（26.9 FPS → 59.3 FPS）。前者是"每个核变强了"，后者是"核多用了但没线性"。要说清它俩，只要说清一句话：2.33 是纵向的时间轴优化，2.21 是横向的资源轴并行。

**如果被追问「那你简历上为什么还写 57%？」：** 因为它跟着原始数一起出现，`37.19 → 15.95 ms（−57%）` 这个写法是安全的——括号里的百分比是那两个数的注解，不是独立结论。危险的写法是把百分比单独拎出来当卖点。

### Q：简历同一段里写"CSC 1.55 倍加速"和"全链路缩短 27.4%"，面试官会不会听成"全链路 1.55 倍"？

**一句话答案：** 会，而且这是六处里最容易被误听的一处。1.549 倍只属于 CSC 那一个函数（52.016 → 33.583 ms），全链路是 76.928 → 55.836 ms，也就是 −27.4%、1.378 倍。两个数摆在一起不加限定，听的人一定会以为是同一件事的两个视角。

**展开讲：** 为什么差这么多？因为 CSC 只是全链路里的一段。全链路里还有硬解、letterbox、NPU 推理、DFL 解码、NMS，Release 只加速了"我自己写的、吃 CPU 的那部分"。当时那组对照表恰好把这件事说得很清楚：CSC 1.549 倍是唯一被显著改善的，MPP 硬解从 1.250 变 1.322 ms（+5.8%）、letterbox 从 1.184 变 1.222 ms（+3.2%）、NPU 纯推理在 O0 和 O3 下都是 14.7~15.0 ms 不动。这些"本该不动"的项没动，才证明 1.549 是真命中而不是噪声。

所以我的说法是把它拆成两句，中间加一句限定："1.549 倍是 CSC 单层的，只作用于我自己写的 C++；全链路是 −27.4%，因为 CSC 只占其中一段，其余段不受编译标志影响。"再加一句更硬的：CSC 优化完仍有 33.583 ms，占全链路 60%，所以它现在就是瓶颈本身。

**如果被追问「那 1.378 倍是怎么来的？」：** 76.928 除 55.836，就是 1.378。我把这个倍数和 −27.4% 一起说，因为有人喜欢看倍数、有人喜欢看降幅，两个必须能对上。

**如果被追问「那你为什么只优化了 CPU 那部分？」：** 因为当时瓶颈就在那儿。硬解和 NPU 都不吃编译标志，letterbox 那 1.184 ms 也不值得动。优化要打在最大的一块上，不是打在好看的一块上。

### Q："模型加载后系统可用内存冗余超 6.1 GB"——这个 6.1 GB 是怎么测出来的？拿什么命令？

**一句话答案：** 读 `/proc/meminfo` 里的 `MemAvailable`——等价于 `free -m` 那一行的 available 列——在 `rkllm_init` 成功返回之后、还没跑推理的时候读一次。它说的是"模型加载完，系统还能给新进程匀出多少内存"，不是"空着的容量"，也不是"冗余"。

**展开讲：** 三个细节决定这个数能不能被复现。第一，看 `MemAvailable` 而不是 `MemFree`：Linux 会主动拿空闲内存做 page cache，所以 `MemFree` 天然偏小且抖动，`MemAvailable` 才是"不用换出就能拿到的量"。第二，读取时机要在 `rkllm_init` 之后：模型是 mmap 加载的，加载前读出来是加载前的数，没有意义。第三，要连读几次看稳定，单点采样会撞上缓存回收的瞬间。

配合上下文报才完整：板子 8 GB 内存、模型权重 2.8 GB、加载完 `MemAvailable` 稳定在 6.1 GB 量级。这三个数摆在一起，听的人自己就能核对逻辑。

**如果被追问「6.1 加 2.8 都 8.9 了，超过 8 GB，你不觉得矛盾？」：** 这正是"6.1 不可能是剩余总容量"的证据，问得好。8 GB 是标称，内核、CMA 保留、系统服务都要先吃掉一块，所以"标称 8 GB 减去权重 2.8 GB"这个算法根本得不出可用值；而且 6.1 是 `MemAvailable`，是"可分配"不是"未使用"。所以我从来不说"剩余 6.1 GB"或"冗余 6.1 GB"。

**如果被追问「这个数有什么用？」：** 它决定架构成不成立。NPU 上还要同时跑一路 YOLOv8，视觉链路自己也要内存，所以测试计划里写的终止条件就是 `MemAvailable` 低于 1 GB 就停实验。6.1 GB 是"两个模型能共存"的前提，不是一句好听的余量。

### Q："较软解提速 7.6 倍"这个数经得起验算吗？

**一句话答案：** 经得起验算，但会被算出一个略小的数——按 p50 相除，7.76 除 1.03 大约是 7.5 倍。7.6 偏高了 1% 左右，方向没错但别再加码，也别说 8 倍。最安全的说法是直接给两个原始值加口径："硬解 p50 1.03 ms，OpenCV 软解 7.76 ms"。

**展开讲：** 倍数是最脆弱的表述，因为分子分母任一端口径动一点，倍数就漂。软解那个 7.76 ms 会随分辨率、CPU 频率、是否开 `-O` 变；硬解那个 1.03 ms 是 p50，p99 会更高。这两个数一旦换条件重量，倍数就会变成 6 倍或 8 倍。而给绝对值的人不怕被问：你可以当场说"这是 1280×720 的 MJPEG 帧，同一条码流，同一块板子，p50"。

硬解为什么能差一个量级，机理也要说得出：VPU 是专用单元，DCT 反变换和熵解码在硅片里做，不占 A76 也不占通用缓存带宽；拆开看，那 1.03 ms 里几乎全花在提交任务和等硬件上，解码本身不是开销。

**如果被追问「那 7.6 到底能不能写？」：** 能，但要加"约"字，并且旁边摆原始值。我更愿意写"约 7.5×"，因为任何人拿你给的两个数一除就是这个结果，自洽比好看重要。

**如果被追问「换个分辨率还成立吗？」：** 没测过，所以我只对 1280×720 这个口径负责。硬解的收益随分辨率上升通常是变大的，但我不拿"应该更大"当结论——没测就是没测，这是边界。

## 四、书里原来没展开、但简历写了的 4 块（补齐）

这一节补的四块，前三块书里散在第 8、第 9 章，但没有"从头到尾说一遍"的版本；第四块"零依赖"是新问题——它能被问倒，不是因为答不出来，是因为大部分人没准备。

### Q：你怎么证明自研 C++ 解码器没算错？max|Δ| = 6.1e-05 px 这个数是怎么来的？

**一句话答案：** 让两条互相独立的实现吃同一份输入，逐一比输出。我把图手术前模型 84 通道的原始输出 dump 成二进制文件，numpy 写一份参考解码（慢但对、逻辑直白），C++ 解码器读同一个文件，两边各导出框表，逐框逐坐标取绝对差的最大值，得到 6.1e-05 px；框数和类别完全一致。

**展开讲：** 这个实验的设计有三个要点，缺一个就不成立。第一，**输入必须是同一份**：不能让两边各自跑一遍模型，那样比的就不只是解码器，还混进了推理的非确定性。第二，**参考实现要足够笨**：numpy 那份就老老实实循环，不优化、不复用、不玩指针，它越慢越蠢越好，因为它的价值是"容易看出对不对"。第三，**比的是逐元素最大差**，不是检出框数量、不是 IoU、不是肉眼看图——那些指标对单个坐标的小偏差不敏感。

6.1e-05 px 这个量级不是"差不多就行"，它是有来历的：float32 的尾数只有 23 位有效位，在 640 这个坐标量级上，相邻两个可表示数的间隔本身就在 10⁻⁵ 到 10⁻⁴ 像素这个档。也就是说，6.1e-05 已经贴着 float32 的地板了，再往下不是"更准"，是"换精度"。

**如果被追问「只对一张图能说明什么？」：** 说明的不是这张图，是整个数值映射。我比的是"同一份张量输入经过两个函数后的输出差"，和图像内容无关，随便换一份 dump 结果都该在这个量级。真要抬杠，可以把验证集每张图都 dump 一遍跑，结论是同一条。

**如果被追问「C++ 和 numpy 差 6.1e-05，那到底谁对？」：** 都对，差异来自浮点运算顺序（numpy 走 SIMD、C++ 走标量循环，累加顺序不同）。这也是为什么我不追求 0 误差——追求 0 反而说明我偷偷用了同一段代码，那验证就失去意义了。

> 【费曼讲解】max|Δ| 为什么能证明"没砍错东西"
>
> ① 生活类比：两台不同的血压计量同一个人，一台 122/78、一台 121/79。你不会问"哪个是真的"，你会问"差多少、差得正常吗"。差 1 mmHg 叫仪器误差，差 30 mmHg 叫有一台坏了。
>
> ② 不懂的人会怎么错想：会以为"证明没砍错"就是"跑一遍看看框画得准不准"。可人眼看图对小偏差极不敏感——框偏半个像素你根本看不出来，但下游做测距、做跟踪累积起来就会飘。所以"看着对"是最弱的证据。
>
> ③ 一句话戳破：要证明的是**两个函数在这份输入上输出几乎相同**，不是**结果看起来合理**；前者是数学命题，后者是主观感受。
>
> ④ 回到术语：这叫数值等价验证。取 `max|Δ|` 而不是均值，是因为均值会把一个离群的错框摊薄到看不见；取最大值等于"最坏的那一个元素也不许超阈值"。所以 6.1e-05 的含义是：最坏情况下，我的 C++ 解码器和一个完全独立写的参考实现在坐标上只差 6.1e-05 像素。

### Q：简历里"max|Δ| < 1e-4 px"和你实际测的 1.22e-4 px、6.1e-05 px 是什么关系？为什么 < 1e-4 这个写法会被抓？

**一句话答案：** 它们是两个不同比较对上的数：1.22e-4 px 是**图手术前后**的 box 误差（原 84 通道输出 vs DFL-Free 双输出），6.1e-05 px 是**C++ 解码器 vs numpy 参考**的误差。1.22e-4 比 1e-4 大，所以"max|Δ| < 1e-4 px"套在第一个比较上是不成立的——这就是会被抓的地方。

**展开讲：** 两个实验各证明一件事，不能混：

| 比较对 | 验证什么 | 实测 max\|Δ\| |
| :--- | :--- | :--- |
| 原 84ch 输出 vs DFL-Free 双输出（box） | 图手术没砍错 | 1.22e-4 px |
| 原 84ch 输出 vs DFL-Free 双输出（cls） | 图手术没砍错 | 0 |
| C++ 解码器 vs numpy 参考 | 解码器实现没算错 | 6.1e-05 px |

所以正确写法是两个分句："图手术前后 box 坐标 `max|Δ|` 约 1.2e-4 px、cls 完全为 0；C++ 解码器与 numpy 参考 `max|Δ|` 为 6.1e-05 px。"如果非要写不等式，只有后一个能写 `< 1e-4`。

**如果被追问「1.22e-4 是不是说明手术有问题？」：** 不是，它同样是 float32 精度极限的量级，而且可复现。判据不是"小不小"，是"和精度极限同量级 + cls 精确为 0 + 框数类别完全一致"。三个条件同时成立，说明差的只是末位舍入，不是逻辑错。

**如果被追问「那你为什么不干脆写成 1e-4 量级？」：** 那是最稳的写法，我现在的说法就是"约 1.2e-4"和"6.1e-05"分开报。写"< 1e-4"的毛病在于它把两个实验压成一个结论，而且第一个实验其实越界了——这种"差不多"的写法，遇到真会算的人就是送分题变送命题。

### Q：INT8 非对称 PTQ 的完整流程，从校准集到 rknn 文件，一步一步说？

**一句话答案：** 四步：`rknn.config()` 定目标平台、mean/std、量化算法；`rknn.load_onnx()` 读图；`rknn.build(do_quantization=True, dataset=...)` 用校准集跑一遍统计每层的动态范围；`rknn.export_rknn()` 出 `.rknn`。非对称的意思是激活的 `zero_point` 不一定落在 0，`scale = (max − min) / 255`。

**展开讲：** 关键细节全在参数和数据集上：

```
1. rknn.config(target_platform='rk3588', mean_values, std_values, 量化算法)
2. rknn.load_onnx(model='yolov8n_dflfree.onnx')
3. rknn.build(do_quantization=True, dataset='dataset.txt')   # 170 张校准图
4. rknn.export_rknn('yolov8n_dflfree_int8.rknn')
```

`dataset.txt` 里一行一张图的**绝对路径**——写相对路径会被拼成 `.../calib/calib/xxx.jpg` 然后报找不到。转换在板端做，161 层 × 3 轮，A76 单线程，约 3.5 分钟。依赖必须钉死，numpy 1.26.4 / onnx 1.14.1 / protobuf 3.20.3 / onnxruntime 1.16.0 / scipy 1.13.1 / opencv 4.9.0.80。还有一个版本坑：`quantized_iteration` 是 toolkit 1.x 的参数，2.x 传进去直接 `ValueError`。

校准集 170 张不是随便凑的：50 张板端双摄实拍保证真实分布，100 张做光照、对比度、伽马、噪声增强保证覆盖，20 张合成补边角。为什么这么讲究——因为校准集错一次，模型直接变成常数输出。

**如果被追问「不对称会不会更慢？」：** 不会，NPU 内部对非对称量化有专门通路，激活的 zero_point 是逐层编译进去的常数。真正会拖慢的是 per-channel 和混合精度，那是另一回事。

**如果被追问「为什么权重对称、激活非对称？」：** 权重分布近似以 0 为中心对称，对称量化能省一个偏置项；激活经过 ReLU 之后全部非负，强制对称等于把一半码点浪费在负数区间，量程和分辨率都亏。

> 【费曼讲解】非对称量化的 scale 和 zero_point 为什么这么要命
>
> ① 生活类比：你有一把 256 格的尺子，要把一段长度画上去。`scale` 决定"一格代表多少"，`zero_point` 决定"0 刻度画在第几格"。量程和分辨率是同一块蛋糕：格子总共 256 个，你把量程拉宽，每格就变粗。
>
> ② 不懂的人会怎么错想：会觉得"量化就是把浮点数四舍五入成整数"，像把 3.7 变成 4 那样简单。真按这个理解，校准集随便给几张图就行了——反正都是舍入。
>
> ③ 一句话戳破：量化参数是从**数据分布**里统计出来的，不是从数值范围里猜的；你给什么图，就决定了尺子怎么画。给一堆色块，尺子就按色块画；画完去量真实照片，全挤在几格里，分辨率全没了。
>
> ④ 回到术语：`scale = (max − min) / 255`，`zero_point = round(−min / scale)`。如果激活全落在 [0, 6]、你校准集却是色块的 [0, 255]，那 scale 就被拉宽 40 倍，真实数据全挤到最左边几格，反量化回来就是一个趋同的值——这就是我那次分类头输出恒等于 0.5000 的机理，0.5000 正好是 sigmoid(0)。

### Q：简历写"零依赖 PC/云端"，你怎么证明真的零依赖？

**一句话答案：** 分三层证：运行时不联网（断网、`ss` 无外连）、模型和运行库都在板子本地（`ls` 看 2.8 GB 的 `.rkllm` 文件、`ldd` 看本地 `librkllmrt.so`）、工具全是本机资源（sysfs、本机 8088 和 9000 端口）。三层都在板子上，才叫零依赖。

**展开讲：** 但必须先自己说清一个边界，不说就会被抓：**"执行零依赖"不等于"构建零依赖"**。`.rkllm` 文件是在 PC 上转换出来的，转换脚本还没进仓库——这是已知缺口，我会主动提。换句话说，我保证的是"部署之后不需要任何外部服务"，不是"从零开始不碰电脑"。

证法是可以现场做的：把网线拔了（板子 WiFi 本来就是关的），跑完一整轮多步 Tool Calling 闭环，五类工具全部正常返回；同时在另一个终端 `ss -tunp` 看，除了本机 8088 和 9000 的连接看不到任何出网连接。这一步做完，"零依赖"就从形容词变成了可复现的操作。

**如果被追问「那模型文件是怎么来的？」：** PC 上转的，转换脚本没进仓库，这是我没补齐的一块。但转换是一次性动作，运行是永久的，两件事要分开说。

**如果被追问「没有云端，模型的通用能力不就没了？」：** 对，这就是取舍。我要的不是通用问答，是"在断网环境下也能巡检、研判、执行、汇报"。代价是它只能干这五类工具覆盖的事，也更容易产生幻觉——这三条我在第 11 章列成已知缺陷了。

## 五、这一章的"记忆锚点"

- **一个数字三层皮**：怎么测的 → 对照是什么 → 边界在哪。三层齐了叫数据，缺一层叫口号。
- **三核是 2.21 倍，不是 3 倍**：59.3 FPS 对 26.9 FPS，三核各约 49% 负载，并行效率 73.5%。谁说线性 3 倍，谁没量过。
- **57% 是耗时降幅，提速是 2.33 倍**：两个都对，混着说就是措辞事故。
- **0.85 是百分点，−1.4% 是相对值**：先绝对后相对，顺序别反，敢让人拿计算器验算。
- **12.2 / 6.22 / 4.34 是三行不是两行**：量化一步、图手术一步，永远不合成 −64%。
- **1.549× 只属于 CSC 单层**：全链路是 −27.4%（1.378×），CSC 优化完仍占全链路 60%。
- **7.6 倍是约数**：1.03 和 7.76 是原始值，p50 口径；倍数让别人自己除，别加码到 8 倍。
- **6.1 GB 是加载后 `MemAvailable`**：不是剩余容量、不是冗余；6.1 加 2.8 超过 8 就是最好的解释。
- **max|Δ| 有两个比较对**：手术前后 1.22e-4、C++ 对 numpy 6.1e-05，只有后者能写"小于 1e-4"。
- **七个词不能碰**：RGA 硬件 CSC、DMA-BUF 零拷贝、RTSP-WebRTC、H.264-H.265 硬解、ByteTrack 进 C++、整机功耗、ASR——全部没做，只能说"评估过、没落地"。

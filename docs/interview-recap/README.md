| **35.97 ms（−3.3%）** | 单 context 三核 mask，几乎无收益 | `BENCHMARKS.md` 2.2.2 |
| **59.3 FPS / 2.21×** | 3 独立 context 真并行（**不是线性 3×**） | `BENCHMARKS.md` 2.2.2 |

| 数字 | 含义 | 出处 |
|---|---|---|
| **1000093** | 2 线程百万次无锁自增实测结果（丢了 9907 次） | D9 |
| **247** | 板子在跑进程数（D5 遍历 `/proc`） | `/root/lab/w1_e5` |
| **60.3 FPS / 丢 0 帧** | 网关聚合吞吐（有界队列 32） | D20 实跑 |

> ### 🔥 余弦相似度 0.99651 的正确用法：它是「反面教材」，不是「精度成绩」
> 本项目做过对照实验：旧合成色块校准集训出来的模型，cls 分支整体塌缩成常数 **0.5（= sigmoid(0)）**、
> 分类头彻底失效，而它当时的特征图余弦相似度**恰好还有 0.9965**。
> 换成真实校准集后，9 张真实图 top-1 平均分从 **0.5000 → 0.8072**（FP32 是 0.8125）。
>
> **面试讲法**：「我一开始也拿余弦相似度当精度指标，0.9965 就 PASS 了；后来发现这个数会骗人——
> 特征图整体相似不影响单个分支塌缩。真精度得跑 mAP，我用 COCO128（929 GT 框）测的真实掉点是
> 0.6087 → 0.6002，−1.4%。」这套自打脸的过程比任何一个漂亮数字都更值钱。

## 诚实边界：现在到底哪些能做、哪些不能

面试官最爱从这里下刀。**主动说「还没做」，比被问穿强一百倍。**

⚠️ **下面这张表在 2026-10-25 做过一次大修正**——原来写的 4 条「还不能吹」，
**有 3 条其实早就做完了**，照旧的背会主动把功劳让出去。

| 能力 | 现状 | 面试怎么说 |
|---|---|---|
| 真实摄像头输入 | ✅ **已接入** UVC 摄像头，MPP 硬解 MJPEG | 「输入是真实摄像头活流，不是仿真」 |
| NMS 后处理 | ✅ **已实现**（conf 0.01 / IoU 0.45，与 PC 侧 eval 同口径） | 可直接讲 |
| MPP / V4L2 硬解 | ✅ **已落地生产链路**，p50 1.03ms，7.6× 于软解 | 是本项目亮点之一 |
| 端到端延迟 | ✅ **有**：单帧全链路 20.58ms / 48.6 FPS（bench 口径）；生产链路 55.84ms / 17.9 FPS（含 CSC） | **必须说清是哪个口径**，别混用 |
| RGA 硬件 CSC | ❌ **未实现**（本板 RGA 2.1.0 不支持 full CSC，颜色偏差 ±13%） | 「跨平台框架搭好了，但这块板的 RGA 不支持，硬上颜色会偏，我判断不划算」 |
| DMA-BUF 零拷贝 | ❌ **未实现**（架构设计了，代码没落地） | 「做了对照实验证明现在输入侧不是瓶颈（差 0.4%），所以我优先砍 CPU 回退，零拷贝是下一步」——**这个回答反而加分** |
| RTSP / WebRTC | ❌ 未实现（用的是 TCP:9000 自定义 248B 定长帧） | 「推流是自己定义的定长帧协议，不是 RTSP」 |
| H.264 / H.265 硬解 | ❌ 未实现（只有 MJPEG 硬解） | 「摄像头出的是 MJPEG，所以只做了 MJPEG 硬解」 |
| ByteTrack 进 C++ 链路 | ❌ 未实现（只在 Python 侧做过仿真） | 「跟踪这块还没进 C++ 网关」 |
| 整机功耗 | ❌ **没测过** | 「功耗没测，不敢给数字」——**千万别编 9.5W 这种数** |
| 语音入口（ASR） | ❌ 未实现（只做了选型方案：sherpa-onnx + SenseVoice） | 「选型做完了，板端还没实测 RTF」 |

**判断原则**：上表 ❌ 的项目，**可以讲"为什么决定不做"或"下一步怎么做"，但不能讲成"已经做了"**。
面试官最看重的不是做全，是**清楚自己做到哪**。

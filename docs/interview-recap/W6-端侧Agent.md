# 第 6 周：端侧 Agent（RKLLM / Tool Calling / 快慢双系统 / 可靠性）

> **一句话心智模型**：Agent 出错时，**先别急着改 prompt** —— 先分层问一句「是模型在编，还是我喂给它的数据本来就是错的」。我这个项目三个真实缺陷，两个都不是模型的锅。

---

## 一、心智模型

```
一条自然语言进来，发生了什么（ReAct 循环，最多 5 步）

  👤 "看看板子状态，有没有告警，灯该不该报警"
        │
        ▼
  🤖 Thought ──► 输出 XML: <tool_call><function=get_system_health></function></tool_call>
        │
        ▼
  ⚙️ Action ──► C++ 拦截，调用真硬件（读 sysfs / 连 9000 收 248B 帧 / 写 LED）
        │
        ▼
  🔍 Observation ──► 必须回填成严谨 JSON 数组 [{"soc_temp_c": 34.23, ...}]
        │                                    ↑ 对象、空串、带换行 → 运行时直接报错
        ▼
  （循环回 Thought，直到模型输出 Final Answer 自然语言）

出错时先分两层：
  ┌─ 模型幻觉？   → 改 prompt / 加约束
  └─ 感知层错了？ → 修工具代码      ★ 我 3 个缺陷里 2 个是这一层
```

**一句话记住**：**Agent 的可信度上限 = 它拿到的 Observation 的可信度。** 模型再聪明，也救不了一个喂错的传感器。

## 二、八股 Q/A

### 2.1 RKLLM 部署

**Q：端侧大模型怎么跑起来的？**
> Rockchip **RKLLM runtime v1.3.1**，原生 C++ 接口（`librkllmrt.so`），加载 **Qwen3.5-2B 的 W8A8 量化版**，权重 **2.8 GB**。板子 8 GB 内存，加载完实测**可用内存还有 6.1 GB** 量级 —— 这个余量很关键，因为 NPU 上还有一路 YOLOv8 在 7×24 跑。
> 流程：`rkllm_createDefaultParam()` → `rkllm_init()` → `rkllm_run()`，输出是**流式回调**（`RKLLM_RUN_NORMAL` 逐段吐字，`RKLLM_RUN_FINISH` 收尾）。

**Q：怎么用上 NPU 和 CPU 的？**
> 两件事：① RKLLM 默认把矩阵运算放到 **NPU 3 核协同**；② **A76 大核绑定** —— 用 `taskset` 把进程钉在 4 个 A76 上，避免被调度到 A55 小核拖慢 decode。
> 为什么大核重要：LLM 推理是**逐 token 串行**的，每个 token 都卡在最慢那一步，调度到小核就是直接翻倍。

**Q：`max_context_len` 踩过坑吗？**
> 踩过，典型的「一开始能跑、跑复杂任务就崩」。默认 **2048**，多步研判一轮要回填 3~4 个工具 Observation（光事件列表就 1.5 KB），直接挤爆，运行时报 **`The context is not enough!`**；提到 **8192**（模型头上限 16384）才够。
> 教训：**Agent 的上下文预算要按「最坏一轮塞几个工具结果」算，不是按聊天长度算。**

### 2.2 Tool Calling 原理

**Q：`rkllm_set_function_tools` 三个参数是什么？**
> 签名 `rkllm_set_function_tools(handle, sys_prompt, tools_json, tool_response_str)`，后三个是关键：
> 1. **`sys_prompt`**：**Agent 的「人格 + 世界知识 + 操作纪律」，全项目最重要的一段字符串。**
> 2. **`tools_json`**：OpenAI Function Calling 风格的工具说明书数组，每个给 `name` / `description` / `parameters`(JSON Schema)。**description 是给模型看的 UI 文案，不是注释** —— 模型靠它决定什么时候调谁。
> 3. **`tool_response_str`**：工具结果回填的**包装标签**，我传 `"<tool_response>"`。**它不能为空串**：传 `""` 时 API 直接返回 **-1**，报 `E rkllm: The tool_response_str cannot be empty`。

**Q：为什么工具结果必须是 JSON 数组 `[{...}]`，不能是对象？**
> 传对象（`{"temperature": 26.1}`）会被拒：
> `E rkllm: Please provide a valid JSON format string. example: [{"temperature": 26.1}], do not include extra newlines, trailing commas, or any characters outside the JSON array.`
> 根因：runtime 把结果包进 chat_template 的 `role="tool"` 消息，**解析器要求根节点是 Array** —— 这是 OpenAI Function Calling 的规范（一次可返回多个工具结果，天然是数组）。**所以「一个工具也必须是长度 1 的数组」。** 我的做法是把每个工具的返回剥掉外层方括号、内部拼成一个数组，多工具并发时也只有一个合法数组。

**Q：Qwen 的工具调用格式长什么样？手写解析踩过什么坑？**
> Qwen3.5 原生输出是 **XML 不是 JSON**：无参 `<tool_call><function=get_system_health></function></tool_call>`；带参 `<tool_call><function=control_led><parameter=mode>alarm</parameter></function></tool_call>`。
> 我在 C++ 里用字符串定位 `<function=` / `<parameter=` / `</parameter>` 手工解析 —— **不是炫技，是 runtime 只把文本吐给你，不负责解析**。
> 坑：模型常把参数包在换行里，实际吐 **`"\nalarm\n"`**，直接比白名单 `!= "alarm"` 就被判非法，**解析完必须 trim**。本地看着能跑、一到真实输出就偶发失败。

**Q：ReAct 循环具体怎么实现的？**
> `Thought → Action → Observation` 循环，直到模型输出不带 `<tool_call>` 的自然语言（Final Answer）。实现是 `while (max_steps-- > 0)`：
> ① `rkllm_run` 一次攒下本轮输出；② 扫有没有 `<tool_call>`，有就**执行全部工具调用**并合成 JSON 数组；③ 以 `role="tool"` 再 `rkllm_run` 把 Observation 喂回去；④ 没有 `<tool_call>` 就跳出。

**Q：`max_steps=5` 的作用？步数耗尽怎么办？**
> 它是**防死循环的硬闸门** —— LLM 完全可能反复调同一工具、或永远觉得信息不够，没上限就是无限烧 NPU。5 是实测经验值：正常巡检 3~4 步收敛（第二幕实测 4~5 个不同工具），再多就是在打转。
> 耗尽时**必须明确报「任务未完成」**：循环结束后再检查一次输出里还有没有 `<tool_call>`，有就打印 `⚠️ [Agent] 工具执行轮数已达上限，任务未完成`。
> 这条比看起来重要：**Agent 最危险的失败模式不是报错，是「没做完但报告得很圆满」。**

**Q：还有别的防打转机制吗？**
> 有，`stall_rounds`：记录每轮触发的**工具名 + 参数签名**，连续两轮签名完全相同就判「原地打转」提前收束。步数上限是最后一道闸，这个是提前刹车。

### 2.3 五个硬件工具

**Q：这 5 个工具分别干什么？**
> | 工具 | 干什么 | 关键设计 |
> |---|---|---|
> | `get_system_health` | 温度 / NPU 三核负载 / 可用内存 / 当前灯态 | 一次给全「体检快照」 |
> | `get_led_status` | 只读查灯 | 纯读，永不写 sysfs |
> | `control_led` | 改灯 | 白名单 + 逐写入检查 + 写后回读 |
> | `get_vision_telemetry` | 从 9000 端口抽一帧检测结果 | 248B 定长帧 + 双采样判新鲜 |
> | `get_patrol_events` | 读巡检守护的事件黑匣子 | 只读尾部 N 行，内存 O(n) |

**Q：温度工具读几个温区？**
> 读 **`thermal_zone0` / `zone1` / `zone2`**（zone0 当 SOC、zone2 当 NPU，读不到就用 SOC 兜底），`/1000.0` 换算（sysfs 是毫摄氏度）。
> 板子实际有 **7 个温区**，全量遍历 `thermal_zone0~6` 是我第 1 周的综合练习和早期 8088 端口那个 C++ RPC 服务干的活。**Agent 工具只取研判需要的那两三个** —— 不是不能读全，是没必要把 7 个数字都塞进模型上下文。

**Q：`control_led` 为什么要白名单 + 写后回读？**
> 因为**这是唯一真会动硬件的写操作**。白名单只有 `heartbeat` / `alarm` / `on` / `off`，非法值走 `invalid_mode` 分支、**一个 sysfs 节点都不碰** —— 校验必须在写之前，不能先写再回滚。
> 回读是因为**写成功 ≠ 生效**：sysfs `write()` 返回字节数、`ofstream` 不抛异常，都不代表硬件切过去了。真实案例：写 `trigger=timer` 返回 EINVAL，旧代码不检查返回值 → 工具返回 `success: true`，灯根本没变。
> 现在的做法是每步查返回值（`sysfs_write_failed` + `failed_node`），全写完后**回读实际状态**，不符报 `readback_mismatch`。**只信回读值，不信写入返回值。**

**Q：视觉工具怎么保证数据是「活的」？**
> 三层：
> ① **收满 248 字节**（8B 包头 + 10×24B BBox），循环 `recv` 直到够数，防 TCP 半帧；
> ② **五种状态显式区分**：`online` / `offline`（连不上）/ `timeout`（连上没数据）/ `partial_frame`（收一半断流）/ `malformed_frame`（`bbox_count` 超协议上限，只报头不读框，**严禁越界读**）；
> ③ **双采样比 `frame_id`**：立刻再抓一帧，两次不同 = `fresh:"true"`，相同 = `"false"`（网关可能在停推），第二次失败 = `"unknown"`。
> **为什么要判新鲜**：网关挂了但 socket 还留着旧缓冲，你能收到帧、但那是几秒前的，不比 `frame_id` 根本发现不了。
> 另外 `get_patrol_events` 要小心：日志轮转单份能到 **5 MB+**，整文件读进内存就是自杀。用 `seekg` 从**文件尾**只回退 `n × 1024` 字节再取尾部 N 行，**内存 O(n)、与文件总大小无关**，单行超 1 KB 视为畸形跳过。

### 2.4 快慢双系统（架构题）

**Q：什么是快慢双系统？**
> 快层是常驻 C++ 守护 `edgevision_patrol_daemon`，每 5 s 采温度 / NPU / 视觉帧，**状态机 + 迟滞**判断，状态翻转就写事件日志 + 控 LED；慢层是 Agent（RKLLM + Qwen3.5-2B），**只在需要研判/汇报时被叫起来**，秒级到十几秒。**快层负责"反射"，慢层负责"思考"。**

**Q：为什么快层刻意不加载 LLM？三条理由。**
> ① **NPU 竞争**：三颗 NPU 核已被 9000 网关的 YOLOv8 7×24 占着，快层再加载几 GB 的 LLM 会抢时片，**直接威胁推流帧率**。这不是理论风险，我用 `bench_contention_sampler.py` 做过三场景采样。
> ② **时延**：LLM 单次几百 ms 到秒级、调度不可控；而「温度超限 → 闪灯」是**毫秒级反射**，`if (temp > 75.0)` 成本约等于 0。这个位置放模型是纯亏。
> ③ **可靠性**：告警是安全行为，必须**可预测、可回归**；LLM 输出不确定，可能幻觉、拒绝、超时。快层零模型依赖、只链 std + pthread，连 `rknn_api` 都不链接，**和主业务故障域完全隔离**。
> **一句话：该用 if 的地方不要用 LLM。**

**Q：状态机 + 迟滞具体怎么设的？**
> 两个**独立**子状态 PERSON 和 THERMAL，任一激活灯就是 `alarm`，都恢复才回 `heartbeat`。
> - PERSON：分数 ≥ 0.5 **连续 2 次**才进（防单帧误检），连续 **5 次**不到才出。
> - THERMAL：**75 °C 瞬时进**（安全侧不等待），**70 °C 连续 3 次（15 s）才出** —— 5 °C 回差就是迟滞。
> **为什么进快出慢**：进是防灾，晚一步就晚了；出是复位，早一步就会在阈值附近抖动、灯抽风、日志刷爆，人对告警脱敏比不报警更糟。

**Q：失败安全怎么处理的？**
> 采样失败时**冻结对应计数器**，不推进状态机：视觉断流 → **不触发恢复**（数据缺失 ≠ 现场没人）；温度读不到 → 若已在告警则**保持告警**（fail-safe，宁可误报不可漏报）。

**Q：为什么写两份日志？为什么不需要锁？**
> `patrol_events.log` 是人看的全量黑匣子（`DAEMON_START` / `PERSON_ALERT` / `THERMAL_ALERT` / `RECOVER`），**只在状态翻转时追加** —— 5 s 一次平着写，一晚上就是几万行垃圾。
> `llm_pending.jsonl` 是**给慢层的契约**，四字段 `{"ts","type","summary","raw"}`，type 只 3 类。**关键设计：快层是唯一写者（O_APPEND），慢层只读 —— 单写者多读者，天然无竞态，一个锁都不用。**

**Q：为什么默认阈值 75/70 而演示用 20/18？**
> 板上 SOC 实际才 **30~45 °C**，用 75 °C 演示永远不触发，演示就成了"什么都没发生"。我把阈值做成命令行参数（`--temp-enter/--temp-exit/--person-score`），演示压到 20 °C，**走的是和真实过热完全相同的代码分支**，只是触发条件不同；默认仍是 75/70，**不为演示写死**。
> 这是我最坚持的一条：**可以降低触发门槛，但不能为演示加一条假的代码路径。**

### 2.5 缺陷一：演示全绿，但 Agent 在说假话（本项目最高潮）

**Q：先讲现象。**
> 第二幕多步演示跑完，**12 项断言全 PASS**。我不放心去翻 `trace.json`，发现汇报里有一句：「LED 始终熄灭…这导致硬件层面的过热保护逻辑被抑制。」
> **而那个灯正在 100 ms 爆闪报警。**

**Q：你怎么判断这是不是模型幻觉？**
> **分层定位。** 我先把整条 trace 的 Observation 全拉出来逐条对齐物理事实 —— `obs[1]` 和 `obs[16]`（两次 `get_led_status`）**都写着 `"current_mode": "off", "brightness": 0`**。
> 也就是：**模型忠实地推理了一个错误的输入。不是它编的，是我喂错了。**
> 这一步判断极其关键 —— 当时如果直接改 prompt（"注意灯可能在闪"），就是把**感知层的 bug 转嫁给模型**去兜，永远修不到根上。

**Q：物理事实怎么确认的？**
> `cat /sys/class/leds/work/brightness` 连采是 **`0 255 0 0 255 255 ...`**，清清楚楚在闪；而 `cat /sys/class/leds/work/trigger` 恒为 **`[none]`**。

**Q：根因到底是什么？**
> 三件事叠加：
> ① 本板内核 5.10.110 **没编 `CONFIG_LEDS_TRIGGER_TIMER`**，`alarm` 不能用内核定时器，只能**用户态爆闪**：fork 一个 shell 循环 `echo 255 → sleep 0.1 → echo 0 → sleep 0.1`；
> ② 既然是用户态爆闪，**`trigger` 永远是 `none`**，靠 trigger 判断模式的老逻辑直接失效，只能退化成"读一次 brightness"；
> ③ **爆闪是 100 ms 亮 / 100 ms 灭的对称方波，单点采样落在灭相的概率约 50%。**
> **周期性物理量用单点采样去定性 = 抽样定理里的混叠。**

**Q：「混叠」这个词用在这里合适吗？**
> 完全合适。信号是 **5 Hz 方波**（200 ms 周期），按奈奎斯特采样率要 **> 10 Hz** 才能重建；单点采样等价于采样率趋近 0，**不但采不到真值，还会得到一个稳定但完全错误的结论**。更阴险的是它返回的 `off` 是个**合法值**，任何"字段有没有、格式对不对"的检查都发现不了。

**Q：修法两层，分别是什么？为什么两层？**
> **第一层（确定性判据，主力）**：`led_user_blink_alive()` —— 读 pid 文件 `/tmp/edgevision_led_alarm.pid`，再做两次校验：`kill(pid, 0)` 确认进程存在；读 `/proc/<pid>/cmdline` **必须包含 `brightness`**。
> 第二个校验不能省：`kill(pid,0)` 成功只代表"存在且有权限发信号"，**排除不了僵尸进程，也排除不了 pid 被内核复用**。cmdline 一比对，两者都能排除。命中直接返回 `alarm_blink`，**与 trigger 内容无关**。
> **第二层（兜底）**：pid 文件缺失或被清理时，做 **12 次 × 15 ms 多点采样（180 ms，覆盖 1.8 个爆闪周期）**，只要出现 **`hi > 0 && lo > 0`**（既亮过又灭过）就判 `alarm_blink`。
> **为什么两层**：第一层依赖 pid 文件这个**外部状态**，可能被清理、被误删（回归脚本收尾就留下过陈旧 pid）；第二层不依赖任何外部状态，只看物理量本身。但第二层是**概率性**的，所以它是兜底、不是主力。**确定性判据优先，概率判据兜底。**

**Q：面试官会追问「为什么不干脆把采样窗口拉到 1 秒？」**
> 因为这是**工具调用链路上的同步读**，窗口拉长直接加到每次 `get_led_status` 的延迟上，而模型一轮可能调好几次；180 ms 已覆盖 1.8 个周期，再长边际收益很小。
> 更根本的是：**不该用采样去推断一个可以直接查询的状态**（pid 在 = 在爆闪）。采样是兜底，不是主路。

**Q：还有连带问题吗？**
> 有，而且更阴 —— 回归脚本收尾的**"假恢复"**：
> ① `restore_led_heartbeat()` 只 `echo trigger=heartbeat`，**没清爆闪子进程**，循环还在覆写 brightness，看着"恢复了"其实没恢复；
> ② 判据写的是 `"heartbeat" in cat_trigger` —— 但 **trigger 候选列表里每个模式名都含 heartbeat 字样**，`[none]` 时这行里也有，**判据恒真**。
> 修法：先停爆闪子进程 + 清 pid；判据改成匹配**带方括号的生效标记 `[heartbeat]`**，并校验 `blink_left == 0`。
> **教训：验收判据必须指向「物理事实」，不能指向「文本里出现过某个词」。**

**Q：这次 debug 给你的方法论是什么？**
> 一条：**Agent 给出离谱结论时，先分层定位「模型幻觉」还是「感知层喂错数据」，再谈调 prompt。** 顺序反了会浪费大量时间在 prompt 上打补丁，而且补不干净 —— 根因还在。

**Q：这次还暴露了测试体系什么问题？**
> **演示判 PASS ≠ 没问题。** 我的 12 条断言验的是「有没有调工具 / 参数对不对 / JSON 合不合法」，**验不了「工具返回的值对不对」**。
> 换句话说：**断言能保证流程正确，保证不了事实正确。** 这种"绿色但撒谎"的失败模式，只能靠**人工翻 trace 把汇报和物理事实对齐**才能抓到。

### 2.6 缺陷二：模型不缺智商，缺常识

**Q：灯修好之后又出了什么问题？**
> 同一场景，汇报变成：「SOC 温度长期偏高（>40 °C）…存在硬件降频甚至**永久损坏**的风险。」还加了一段：「若系统内部逻辑 `0=off`, `1=heartbeat`, `2=alarm`, `3=on`（推测）…」

**Q：这次是幻觉吗？**
> **不是。** 这是最关键的一句。模型拿到的**全是真数据**：SOC 49 °C 是真的，事件日志里写着「温度超过 **20.00 °C** 阈值」也是真的（我演示时压的阈值）。
> 它的问题不是编数据，是**不知道 RK3588 多少度才算热**。手里只有「有个告警」+「阈值 20 度」，于是合理倒推出「超过 20 度就危险」→ 40 多度当然「长期偏高」。**它是缺世界知识，不是缺智商。**

**Q：修法是什么？修完效果如何？**
> **往 sys_prompt 里补世界知识**，两条：
> ① 温度常识：「RK3588 的 SOC 正常工作温度 **30~65 °C**，**超过 75 °C** 才算过热告警，**85 °C 以上**才需担心降频/损坏。若巡检事件温度阈值明显偏低（如 20 °C），说明守护是用评测阈值跑验收，**不要据此判定设备真的过热**。」
> ② 禁止臆测：「只陈述工具真实返回的字段，**不要臆测工具的内部实现**（如猜测 `control_led` 的枚举值编码、猜测 sysfs 数值含义）。拿不准就说不确定或直接省略。」
> 同一场景立刻变成：「SOC **49.9 °C** ✅ 正常（30~65 °C）」「**这些是低阈值演示事件，而非真实过热**」，那段臆测的枚举推理**整段消失**。

**Q：为什么"禁止臆测"这条也要写进 prompt？**
> 因为模型有个很强的倾向：**遇到不确定的地方，它会补一段看起来很专业的猜测，而不是承认不知道。** 这在产品里是灾难 —— 用户看不出哪句是数据、哪句是脑补。**与其要求它"猜得准"，不如明确禁止它猜。**

**Q：工程启示是什么？（这句一定要说）**
> **不是让模型更聪明，是补上它缺的那块世界知识。**
> 很多人第一反应是"换个更大的模型"。但换个 7B 上来，它照样不知道你这块板子多少度算热 —— 这是**领域知识，不在预训练语料里**。**prompt 里补 30 个字的常识，比换大三倍的模型有效。**

### 2.7 缺陷三：`--no-led` 下白跑 4 轮推理

**Q：这个缺陷是什么？**
> 快慢双系统里慢层 Agent 是**只读**的（`--no-led`），因为 LED 写权归守护进程。但模型不知道这个"软约束"：用户一说"把灯调成报警"，它就去调 `control_led(mode=alarm)` → 被拒 → 换个模式再试 → 再拒……
> **heartbeat / on / alarm / off 四种模式挨个试了一遍，白跑 4 轮 NPU 推理**（每轮约 10 s 量级），还把上下文污染了一堆无用失败记录。

**Q：为什么它不一次就放弃？**
> 因为拒绝的返回里**只说了"被拒绝"，没说"别再试了"**。模型看到 `success:false` 的合理反应就是换参数重试 —— 这是它在训练里学到的正确行为，**问题在我的接口没表达清楚**。

**Q：修法？为什么两层都要？**
> ① **工具返回加 `hint` 字段**，明确写「`do NOT retry control_led with another mode; the gate rejects every mode in read-only mode`」—— **把"别再试"变成机器可读的返回值**；
> ② **sys_prompt 追加最高优先级只读约束**：「当前运行在 `--no-led` 只读巡检模式，指示灯控制权归属常驻巡检守护进程……你绝对不要调用 `control_led`」。
> 效果：**`control_led` 调用从 4 次降到 1 次。**
> 两层都要：sys_prompt 是**事前预防**（不犯错），`hint` 是**事后止损**（犯错了立刻停）。只靠 prompt 不可靠（可能忽略、可能被用户话术带偏），只靠 hint 也不够（它会先试一次）。**冗余是故意的。**
> 这不算给模型打补丁，是**在接口契约里表达业务约束** —— `--no-led` 是系统状态，模型看不见，就必须通过 prompt 和返回值告诉它。

### 2.8 回归测试体系

**Q：12 个用例分别测什么？**
> T01 问温度（必须调 `get_system_health`，且**不能**顺手调 `control_led`）；T02 只查灯态；T03 报警（`mode=alarm` + `success`）；T04 恢复心跳；T05 非法模式（`any_of` 三种可接受行为，**但绝不允许灯真的变成非法值**）；T06 在线视觉；T07 综合巡检（多工具按**指定顺序**出现，子序列断言）；T08 条件决策（`any_of`）；T09 REPL `/clear` 后仍能答（上下文清理不破坏系统提示词）；T10 长上下文边界（~800 字逼近上限，`exit_clean`）；T11 REPL 连续两次控灯（on → alarm 参数不串扰）；T12 **故障注入**（停视觉服务，看它是否如实报离线）。

**Q：断言类型有哪些？为什么要这么多种？**
> `tool_called` / `tool_not_called` / `tool_arg` / `tool_order`（子序列）/ `obs_json_valid` / `any_of` / `exit_clean` / 回复关键词。
> 因为 **Agent 输出不是确定性的 —— 同一个问题可以有多条合法路径**。**该强制的强制**（T07 用 `tool_order` 子序列，保证"先感知后决策"顺序不能反），**该宽松的宽松**（T05/T08 用 `any_of`，接受多条路径但每条都必须合法）。写死单一预期会因模型措辞变化而假失败，写太松又会漏掉真错 —— **这个度是设计出来的**。

**Q：故障注入怎么保证不把板子搞坏？**
> 一套很严的协议，因为它会真 `systemctl stop edgevision`：
> ① 不带 `--with-faults` 时 T12 直接 **SKIP**；② 注入前确认 `edgevision` 是 active，否则 SKIP；③ stop 后跑用例，**无论成败、超时还是异常，`finally` 里一律 start 并回读状态**；④ 恢复失败 → 打印 70 列 `!` 大警告 + 手动恢复命令 + **立即终止整场回归**；⑤ 整场结束（无论成败）把 LED trigger 写回 `heartbeat` 并回读验证。
> **原则：故障注入的恢复必须写在 finally 里，不能写在成功路径里。**

**Q：指标口径和局限？**
> 两个别混：**工具决策正确率** = 「调了正确工具且参数正确」的用例数 / 该维度适用用例数；**端到端成功率** = 断言全过的用例数 / **实际执行数（SKIP 不计分母）**。
> 时延 `wall_s` 我明确标注：**从 PC 侧发起 ssh 到进程退出，含 ssh 握手 + 逐 token 生成 + 板端 timeout** —— **不能当 NPU 时延引用**，只做纵向趋势对比。这个声明必须写，否则别人会拿它当推理延迟。
> 局限里最要紧的三条：① **stdout 解析对文案敏感**（靠三条正则抓契约行，改一个字测试就崩）；② wall-clock 含 ssh + `rkllm_init` 好几秒冷启动；③ 最根本的 —— **验的是「流程对不对」，验不了「事实对不对」**（就是 2.5 暴露的盲区）。

### 2.9 必背数字

**Q：这套系统一句话报多少？**
> **12/12 回归全绿**（连续三次）；两幕演示端到端 **106.5~112.2 s**（另有三轮跑出 **123.9 s** 长尾）；一条自然语言串起 **4~5 个不同工具**；**Observation 20 条全为合法 JSON**；LED 告警期**占空比 20.0% → 49.7%（+29.7 pp）**，6 s 内 brightness 翻转 **73 次**；`control_led` 调用 **4 → 1**。

**Q：占空比这个判据怎么来的？**
> 因为 **heartbeat 本身就在闪** —— 用"看到亮度跳变"判断报警**根本无效**，实测 heartbeat 基线占空比就是 **20.0%~25.3%**（呼吸灯亮的时间本来不短）。而 100 ms 对称方波理论占空比 50%，所以判据改成**告警期占空比 ≥35% 且相对基线抬升 ≥15 pp**；实测 alarm 期 **49.7%~50.0%**、抬升 **+24.7~29.7 pp**，区分度很清楚。
> **采样间隔必须 0.02 s** —— 用 0.1 s 正好与 200 ms 方波同频，**混叠**，会误判成常亮或常灭。这个坑和 2.5 是同一个根。

### 2.10 边界（主动说）

**Q：语音入口和演示的服务化做了吗？**
> 都**没做**。语音只出了选型方案 `docs/VOICE_ASR_PLAN.md`：主选 **sherpa-onnx + SenseVoice Small int8**（官方中文 CER 7.81%），备选 Paraformer，**待板端实测** —— 原话是"只做了选型，没落地"。
> 两幕演示现在是手工跑的脚本，**没固化成 systemd 服务**；巡检守护本身也是独立进程，也还没做开机自启。已知依赖：演示要求 `edgevision.service`（视觉网关）保持 active。

**Q：Agent 的能力上限？**
> **5 步，硬上限。** 超了明确报"任务未完成"，不会硬凑答案。5 步对"巡检 → 研判 → 执行 → 汇报"够用，但对需要长链路工具编排的任务（比如逐区排查 10 个故障点）**不够** —— 这是设计取舍，不是没想到。

**Q：还有哪些没做？**
> 与 W5 一致的那几条：RGA 硬件 CSC / DMA-BUF 零拷贝 / RTSP / H.264-H.265 / 整机功耗 —— 全**没做**。
> Agent 侧另外两条：**没测过并发多用户**、**没做权限隔离**（工具是全权限的，能做只读是因为我加了 `--no-led`，不是因为有权限系统）。

## 四、踩过的坑（都是真踩）

- **`tool_response_str` 传空串** → API 返回 -1，`The tool_response_str cannot be empty`。
- **工具结果回填成 JSON 对象** → runtime 拒，必须数组，**单个工具也得是长度 1 的数组**。
- **参数值没 trim** → 模型吐 `"\nalarm\n"`，白名单比对失败，偶发不生效。
- **`max_context_len` 用默认 2048** → 多步研判回填几个工具结果就 `The context is not enough!`。
- **以为 `echo timer` 成功** → 本板没编 `CONFIG_LEDS_TRIGGER_TIMER`，返回 EINVAL，不检查返回值 = 假成功。
- **周期性物理量单点采样** → 爆闪的灯被读成 `off`，Agent 据此汇报"灯灭了导致过热保护被抑制"。
- **`kill(pid,0)` 当存活判据** → 排除不了僵尸和 pid 复用，必须再查 `/proc/<pid>/cmdline`。
- **只 fork 不 exec** → 子进程继承 NPU 的 DMA 映射，父进程退出后孤儿把 NPU 内存钉死，`rkllm_init` 报 `ENOMEM`（free 显示还有 6 GB）。
- **爆闪子进程继承 stdout 管道** → 回归用例卡死 **270 s** 被强杀，修复后 **21 s**；修法 = exec 前把 0/1/2 都重定向 `/dev/null`。
- **收尾"假恢复"** → 只写 trigger 不清爆闪子进程；判据 `"heartbeat" in trigger` 对 `[none]` 也判真（候选列表里每个名字都含 heartbeat）。
- **sys_prompt 里没写领域常识** → 49 °C 被汇报成"长期偏高、存在永久损坏风险"。
- **没把业务约束写进返回值** → 只读模式下模型把 4 种模式挨个试，白跑 4 轮 NPU 推理。

## 五、面试官可能从哪下刀

**Q1：「演示全绿，你说它其实在撒谎。那你的测试到底有什么用？」**
> 有用但不够用，我承认得很干脆。**断言能保证「流程正确」，保证不了「事实正确」** —— 它验有没有调工具、参数对不对、JSON 合不合法，验不了工具返回的那个 0 是不是真的 0。
> 这次是**人工翻 trace、把汇报和物理事实逐条对齐**才抓到的。改进方向也明确：把「物理事实」变成可断言的量 —— 比如灯不再信"程序自述"，改成实测占空比，我现在就是这么做的。

**Q2：「你怎么 100% 确定是感知层错、不是模型幻觉？」**
> 我把整条 trace 的 Observation 全拉出来：两次 `get_led_status` 的返回里**都写着 `current_mode: "off"`**，模型的每句结论都能在 Observation 里找到出处 —— **它没编任何东西**。同时我用 shell 连采 `brightness`，拿到 `0 255 0 0 255 255`，物理上在闪。两边一对照：**输入错、推理对**，这个判断我敢下。

**Q3：「两次都读到 off，概率上说不通吧？」**
> 说得通。对称方波占空比 50%，单次落灭相就是 50%，两次独立采样都撞上约 25% —— **这不是小概率事件，是必然会发生的事**。更麻烦的是它返回的 `off` 是个**合法值**，格式检查、字段检查全过，所以特别隐蔽。

**Q4：「那你多读几次 `brightness` 不就解决了？」**
> 因为**采样是概率性的，pid 才是确定性的**。爆闪进程在跑 = 灯在报警，这是一个可以直接查询的**状态**，根本不需要靠采样去推断。所以多点采样放在**兜底**（12 次 × 15 ms 覆盖 1.8 周期），主力判据是查 pid + 校验 cmdline。**能用状态判断的，就不要用采样推断。**

**Q5：「模型说要永久损坏，是不是模型太小？换 7B 会好？」**
> 不会。**它缺的不是智力，是「RK3588 多少度算热」这条领域知识** —— 换个更大的模型照样不知道，因为这块板子的温度规格不在预训练语料里。
> 证据：它拿到的数据**全是真的**（49 °C、20 °C 阈值都是真的），推理链也合理，**唯一缺的是「正常范围是多少」这个锚点**。我在 sys_prompt 补了 30 个字，同一场景立刻变成「49.9 °C ✅ 正常（30~65 °C）」。**补知识比换模型便宜三个数量级。**

**Q6：「为什么快层不用 LLM？现在不是都讲 LLM 做决策吗？」**
> 三条理由，任一条单独成立就不该用：**NPU 被占满**（三核在跑 YOLOv8）、**时延不对等**（毫秒级反射 vs 秒级推理）、**安全行为必须可预测**（告警不能靠一个可能幻觉的东西）。
> 我的原则是：**该用 if 的地方不要用 LLM。** 慢层的价值在「研判和汇报」，不在「触发告警」。

**Q7：「你这个 12 条回归，覆盖率够吗？」**
> 不够，我不吹。它覆盖 **5 个工具的主路径 + 1 条故障注入**，没覆盖并发多用户、权限隔离、长时间运行的上下文漂移，以及最根本的「工具返回值正确性」。
> 但它有一个我很满意的点：**故障注入的恢复写在 finally 里**，恢复失败立刻终止整场并报警 —— **测试工具本身不能把环境搞坏**，这是底线。

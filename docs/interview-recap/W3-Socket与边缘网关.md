# 第 3 周：Socket 与边缘网关

> **一句话**：TCP 是**字节流**不是消息流，所以「一帧从哪到哪」得**你自己定义**。

---

## 一、心智模型

```
服务端                                 客户端
socket()   拿到"总机" fd                 socket()
bind()     绑定 IP:端口
listen()   变成"能接客"的状态
accept()  ── 阻塞等人来 ──►             connect()
   返回一个新的 fd（这条连接专用的）
   ↓                                        ↓
recv()/send()  ◄──────── 双向数据 ──────── recv()/send()
```

**关键认知：`accept` 返回的是「新 fd」，原来那个监听 fd 继续接客。**
这就是「迎宾员 + 服务员」模型 —— 迎宾员（listen fd）只管在门口迎客，进来之后交给一个专属服务员（conn fd）。

## 二、八股 Q/A

### TCP 基础

**Q：`socket/bind/listen/accept` 各干什么？**
> `socket` 建 fd；`bind` 绑地址端口；`listen` 把 fd 变成被动监听（内核开始接连接队列）；`accept` 从队列里取一个完成的连接，返回**新的 fd**。

**Q：为什么要 `setsockopt(SO_REUSEADDR)`？**
> 避免服务重启时 `bind: Address already in use`（上个进程的连接处于 `TIME_WAIT`）。

**Q：TCP 三次握手、四次挥手为什么是 3 和 4？**
> 握手 3 次是为了**双方都确认对方能收能发**；挥手 4 次是因为 TCP 是**全双工**，两个方向要**各自关闭**（一方说「我没数据了」不等于「我不能再收」）。

**Q：`TIME_WAIT` 为什么存在？**
> 主动关闭方要等 `2MSL`，保证最后那个 ACK 能重传、并让旧连接的重复包在网络里消失。**服务端主动关连接会堆积 `TIME_WAIT`，所以一般让客户端先关。**

**Q：TCP 和 UDP 怎么选？**
> TCP：可靠、有序、有流控，但建立连接有延迟、有重传。UDP：无连接、低延迟、可丢包。
> **我们的选型**：固件升级用 TCP（绝对不能丢）；无人机摇杆用 UDP（慢一帧不如丢一帧，重传反而更糟）。

### 粘包 / 半包（核心考点）

**Q：什么是粘包？为什么会粘？**
> TCP 是**字节流**，没有消息边界。发送方两次 `send` 的数据，接收方可能一次 `recv` 全收到（粘），也可能一条消息分两次到（半包）。

**Q：怎么解决？**
> **定长包头 + 长度字段**：先发 8 字节（帧号 + 目标数），接收端先读满 8 字节，算出包体长度，再读够那么多字节。

**Q：光有长度字段够吗？**
> 不够。**`recv` 不保证一次读完**，包头也可能分两次到。必须**循环收**：
> `while (已收 < 需要的字节数) { n = recv(...); 已收 += n; }`

**Q：为什么结构体要 `#pragma pack(1)`？**
> 编译器默认按**内存对齐**往结构体里塞填充字节（比如 int 后补 4 字节），板端和 PC 端算出来的大小可能不同 → **一序列化就错位**。`pack(1)` 关掉对齐，保证两端布局一致。

**Q：为什么用二进制结构体，不用 JSON？**
> JSON 每帧要**解析字符串**（CPU 开销大）、体积膨胀 2~3 倍。结构体是**内存直发**，几乎零成本。高频固定格式数据没有理由用 JSON。

### 字节序

**Q：为什么要 `htonl/htons`？**
> 网络字节序是**大端**，x86/ARM 默认**小端**。端口号、IP、协议里的整数字段必须转成网络序，否则对端读出来是错的。

**Q：结构体里的 `float` 也要转吗？**
> 严格说要（`htons` 只处理整数）。工程上常见做法是**约定两端都是小端**（同架构）就不转，但跨平台时必须显式处理。**面试时说出这个取舍**，比说「不用转」强。

### 阻塞 / 非阻塞 / epoll

**Q：阻塞 `accept` 有什么问题？**
> 没有客户端来，整个线程卡死，**主循环全停**。我做过 A/B 对比：阻塞版把 AI 推理主循环整个冻住。

**Q：`fcntl(O_NONBLOCK)` 之后 `accept` 返回什么？**
> 没连接时立刻返回 `-1`，`errno = EAGAIN`（或 `EWOULDBLOCK`）。**这不是错误，是「现在没有」，要区分对待。**

**Q：非阻塞轮询有什么缺点？**
> 空转烧 CPU。所以要用 **epoll/select** 让内核在「有事件」时才唤醒你。

**Q：select / poll / epoll 的区别？**
> - `select`：fd 数上限 1024，每次调用要把整个集合从用户态拷进内核，**O(n)**
> - `poll`：去掉 1024 上限，但一样要全量拷贝
> - `epoll`：**内核里维护红黑树 + 就绪链表**，只返回就绪的 fd，**O(1)**，适合上万连接

**Q：epoll 的 LT 和 ET？**
> LT（水平触发）：只要还有数据没读完，就一直通知你，**不容易漏**。
> ET（边缘触发）：只在状态变化时通知一次，**必须一次读到 `EAGAIN` 为止**，否则丢事件。ET 效率高但难写对。

### 边缘网关架构（你项目里的）

**Q：为什么要「NPU 线程算、推流线程发」两条线？**
> **背压（backpressure）**。如果 NPU 线程自己 `send`，网络卡 100ms，这个线程就阻塞在 `send` 上，**NPU 空转** —— 算力被网络拖死。
> 分开之后，网络的抖动被队列吸收，推理不受影响。

**Q：队列无限长会怎样？**
> 网络一直慢、NPU 一直产 → 队列无限涨 → **内存爆掉（OOM）**。
> 所以队列必须**有界**（我设 32），满了**丢最旧的帧**。实时系统里**丢帧比堆积好** —— 推一天的旧画面给上位机毫无意义。

**Q：`send` 的返回值要不要检查？**
> 必须。不检查的话，对端断开了你还一直写 → 触发 `SIGPIPE`，**进程直接被信号杀掉**。
> 正确做法：`send(..., MSG_NOSIGNAL)` + 检查返回值 + 处理半包（`send` 也可能只发出去一部分）。
> 我实测过：客户端断开后，板端立刻打出「send 失败, 断开客户端」并干净收尾。

## 四、踩过的坑

- **不检查 `send` 返回值** → 对端断开后进程被 `SIGPIPE` 杀掉。
- **`recv` 只调一次就 unpack** → 网络抖一下就解出乱码。
- **结构体没 `pack(1)`** → 两端大小不一致，数据错位。
- **阻塞 `accept`** → 主循环冻住。
- **队列无上限** → 内存缓慢增长，跑几小时 OOM。

# 第 2 周：多线程与并发

> **一句话**：多个线程**共享同一块内存**，这是它比进程快的原因，也是所有 bug 的来源。

---

## 一、心智模型

```
进程 = 资源分配单位（一个地址空间、一堆 fd）
线程 = CPU 调度单位（共享上面那堆资源，只有自己的栈和寄存器）

    进程
   ┌──────────────────────────────┐
   │  共享: 全局变量 / 堆 / fd / 代码 │
   │  ┌──────┐ ┌──────┐ ┌──────┐  │
   │  │线程0 │ │线程1 │ │线程2 │  │
   │  │栈+寄存器│ │栈+寄存器│ │栈+寄存器│  │
   │  └──────┘ └──────┘ └──────┘  │
   └──────────────────────────────┘
```

**一句话记住**：**线程之间没有秘密**，所以对共享数据的任何「读-改-写」都可能被打断。

## 二、八股 Q/A

### 线程基础

**Q：线程和进程的区别？**
> 进程有独立地址空间，线程共享进程的地址空间；进程切换要换页表（贵），线程切换只换栈和寄存器（便宜）；进程间通信要走 IPC，线程直接读写全局变量（但**必须加锁**）。

**Q：`pthread_create` 的参数怎么传？为什么容易错？**
> 第四个参数是 `void*`。新手常写成 `&i`（循环变量地址）—— **3 个线程最后拿到的可能都是 `i` 的终值**。
> 正确做法：定义一个数组 `int ids[3] = {0,1,2}`，传 `&ids[i]`。

**Q：`join` 和 `detach` 的区别？**
> `join` = 父等子，**并回收子线程资源**（相当于线程版的 `waitpid`）。`detach` = 分离，线程自己跑完自己回收，父线程不能再 `join`。
> **不 `join` 也不 `detach` 会漏资源**（类似僵尸）。

### 竞争与锁

**Q：什么是竞态条件？**
> 多个线程**同时**对共享数据做「读-改-写」，而这三步不是原子的，中间可能被切走。最终结果取决于调度顺序。

**Q：你实测的多线程丢数据是怎么回事？**
> 2 个线程各做 100 万次 `counter++`，期望 200 万，**实测只有 1000093** —— 丢了 9907 次。
> 原因：`counter++` 编译成「读内存 → 加 1 → 写回」三条指令，两个线程的指令可能交错，后写的覆盖先写的。

**Q：加锁为什么能解决？锁的底层是什么？**
> 锁把「读-改-写」包成**临界区**，同一时刻只允许一个线程进。
> 底层是 **futex**（fast userspace mutex）：无竞争时在用户态一条原子指令搞定（快），有竞争时才进内核挂起（慢）。

**Q：死锁的四个必要条件？**
> ① 互斥 ② 持有并等待 ③ 不可剥夺 ④ 循环等待。
> 破坏任意一个即可。工程上最常用：**固定加锁顺序**（破坏循环等待）。

**Q：锁粒度怎么选？**
> 我做过对照：**抢到任务后立刻解锁**（锁里只做 `pop`，不做耗时操作），3 个 NPU worker 的吞吐明显高于「锁住整个推理过程」。
> 原则：**临界区里只放必须原子的操作，越短越好。**

### 原子操作

**Q：`std::atomic` 和 `mutex` 怎么选？**
> `atomic` 只适合**单个变量的简单操作**（自增、置位、CAS），无锁、开销极小。
> 一旦要保护**多个变量的一致性**（比如「金额和余额同时改」），`atomic` 不够，必须 `mutex`。

**Q：`atomic` 是硬件支持的吗？**
> 是。底层靠 CPU 的原子指令（ARM 上是 `LDXR/STXR` 或 `LSE` 原子指令），不是软件模拟。
> 我实测过：`std::atomic` 跑 200 万次**不丢**，而无锁的普通 `int` 必丢。

### 条件变量

**Q：条件变量为什么要配合 mutex 用？**
> 因为「判断条件」和「睡眠」必须**原子**。否则生产者在你判断完「队列空」、还没睡着的时候塞了任务、发了信号，**信号丢失，你永远等不到**。

**Q：`pthread_cond_wait` 内部做了哪三步？**
> ① **解锁** mutex（让别人能进来放任务）
> ② **睡眠**（挂到条件变量的等待队列）
> ③ 被唤醒后**重新加锁** 再返回
> ①②是原子完成的，中间没有缝。

**Q：为什么必须用 `while` 而不是 `if` 包住 `wait`？**
> 因为**醒来不代表条件成立**：可能是虚假唤醒（spurious wakeup），也可能醒来后任务被别人抢走了。
> 用 `if` 只检查一次 → 会拿着**空队列**继续跑 → 读到未初始化内存甚至崩溃。
> 我跑过对比实验：`if` 版从空队列里读出了垃圾值 `0`，`while` 版正确地睡回去了。

### 线程池与 NPU 调度

**Q：为什么要线程池，不是来一个任务开一个线程？**
> 线程创建/销毁有开销；而且线程数必须可控（**核数决定并行上限**），否则几百个线程互相抢 CPU，反而更慢。

**Q：RK3588 的 3 核 NPU 怎么真正用起来？**
> **不是**对一个 context 调 `rknn_set_core_mask(CORE_0_1_2)`。
> 必须**开 3 个独立 context，每个绑一颗核**。
> 实测：单 context 三核 mask 只从 37.19ms 降到 **35.97ms（-3.3%）**；3 个独立 context 聚合到 **59.3 FPS（2.21x）**。

**Q：为什么不是 3 倍？**
> 三核跑满时每颗核只有 **49% 负载** —— NPU 在等。瓶颈在 CPU 侧的检测头解码（DFL 头回退，占 49% 时间）。**加速比卡在 2.21x，是被 CPU 和 DDR 拖的，不是 NPU 不够。**

## 四、踩过的坑

- **传 `&i` 给 `pthread_create`** → 所有线程拿到同一个终值。
- **用 `if` 包 `cond_wait`** → 虚假唤醒后拿空数据。
- **锁里做耗时操作**（比如锁着跑推理）→ 其他线程全排队，等于单线程。
- **忘了 `join`** → 线程资源泄漏。
- **以为 `counter++` 是原子的** → 编译器优化后更乱。

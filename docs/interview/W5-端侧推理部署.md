# 第 5 周：端侧推理部署（RKNN 量化 / 图手术 / 三核 / 编译优化 / MPP）

> **一句话心智模型**：端侧推理的瓶颈**八成不在 NPU 算力**，在「模型图里有多少算子跑在 CPU 上」和「你的测量方法有没有骗你」。

---

## 一、心智模型

```
一帧图像进板子，时间到底花在哪（实测，优化前 37.19 ms）

  ┌───────────────────────────── NPU 115 个算子  19.23 ms (51%)
  │   Conv / Concat / Transpose ...
  └────────────────────────────────────────────────────────
  ┌───────────────────────────── CPU 回退 10 个算子  18.44 ms (49%)  ← 真凶
  │   DFL 头：Transpose 9.18 / Softmax 4.47 / Reshape 4.37
  └────────────────────────────────────────────────────────

  动作：把 DFL 解码链从 onnx 图里切掉，搬到 CPU 手写
        ↓
  纯推理 37.19 → 15.95 ms（−57%）
  全链路 20.58 ms / 48.6 FPS（原 26.9 FPS）
```

**一句话记住**：**先看「哪些算子没被 NPU 接住」，再谈算力、零拷贝、多核。**顺序反了就是白干。

## 二、八股 Q/A

### 2.1 RKNN 量化

**Q：PTQ（训练后量化）的流程是什么？校准图在做什么？**
> 四步：① `rknn.config(mean_values/std_values, target_platform='rk3588')` 定预处理口径和芯片；② `rknn.load_onnx()` 读图；③ `rknn.build(do_quantization=True, dataset='dataset.txt')` —— **这一步就是量化本体，dataset 是校准集清单**；④ `rknn.export_rknn()` 出 `.rknn`。
> 我整个转换是在**板子上**跑的（toolkit2 的 2.x 有 aarch64 wheel），venv 在 `/root/rknn_env`，版本 2.3.0。不是必须用 x86 PC。
> 校准图不是"训练"，是**统计每一层激活值的分布范围**：一张张喂进去，记录每个 tensor 的 min/max，据此定量化参数。**全程不反向传播、不改权重。**

**Q：非对称量化到底怎么算？**
> 仿射映射：`q = round(x / scale) + zp`，反量化 `x ≈ (q - zp) × scale`。
> 非对称的意思是零点不一定是 0（`zp` 可正可负），好处是能覆盖「全正」或「全负」的分布（比如 ReLU 之后的激活全非负），对称量化会浪费一半码点。
> 板上模型的输入属性实测就是 `INT8 / NHWC / zp=-128 / scale=1/255`。

**Q：为什么 scale 是「按校准集定的」这件事很要命？**
> 因为 **scale 一旦定死，模型就只对这个范围内的数值负责**。数值超出范围 = 饱和（全被夹到同一个码点），也就是信息直接丢光。
> 校准集窄 → scale 小 → 真实数据一进来就饱和。这就是"校准集决定生死"的机理。

**Q：那你踩到的具体是什么坑？**
> 我最早用**合成色块图**做校准（纯色矩形 + 纯灰底，60 张）。转出来的模型在真实画面上**框还是对的**，但 9 张真实图置信度**全部精确等于 0.5000**。
> `0.5 = sigmoid(0)` —— 分数全是同一个常数，说明 **cls 分支被量化整体塌缩成常数了**，分类头彻底失效，只剩框分支还能用。
> box 分支没坏，是因为回归值的分布相对稳定，不吃校准集分布的影响。

**Q：数字对比是多少？**
> 9 张真实图 top-1 平均分：FP32 **0.8125** → 换真实校准集 **0.8072**（−0.65%）→ 旧合成校准集 **0.5000**（−38.5%）。
> 新校准集 170 张：50 张板端双摄实拍 + 100 张光照/对比度/伽马/噪声增强 + 20 张合成。

**Q：余弦相似度 0.9965 为什么不能当精度指标？**
> 这是我最想讲的一条：那个坏掉的模型，**特征图余弦相似度还有 0.9965，MAE 0.418，按当时的判据全部 PASS**。
> 原因：余弦相似度是**整张特征图**的整体形状相似度，被大量通道的平均表现主导。**单个分支塌缩对整体余弦的贡献很小** —— 80 个通道里 cls 分支全废了，其余通道还近似原样，整体依然 0.99。
> 而且它是**逐层统计**，不经过后处理、不落到检测框上，跟"能不能检出目标"隔着一层。
> **教训：一个指标 PASS 不代表模型可用。指标必须和任务对齐、而且要落到端到端产物上。**

**Q：那真精度怎么测的？**
> 用带标注的公开集 **COCO128**（128 张 / **929 个 GT 框** / 71 类）跑真 mAP@0.5。
> 口径两侧完全一致：letterbox 640（灰边 114）、conf 0.01、NMS IoU 0.45 class-aware、COCO 101 点插值。
> 结果：**FP32 0.6087 → INT8 0.6002，绝对掉 0.85 个百分点，相对 −1.4%**。
> 工具：PC 端 `convert/eval_map.py`，板端 `deploy/cpp/bench/eval_dump.cpp` 只负责导预测。

**Q：这个 mAP 有什么局限？必须一起说。**
> 三条，我会主动讲：
> ① **COCO128 是 YOLOv8n 的训练子集**，模型"见过"这些图，所以**绝对 mAP 偏乐观**，不能对外说"我在 COCO val2017 上做到 0.61"（官方 val2017 约 0.644）；
> ② 但 FP32/INT8 用的是**同一批图**，"见过"这个因素在两边同时存在、互相抵消，所以**相对掉点 1.4% 是成立的**；
> ③ 它仍然是 128 张公开集，**不是我自建场景的验证集**。要证明"在我的场景里也能用"，得自己标一批。

**Q：还叠了别的问题吗？**
> 叠了。旧那版模型是 **toolkit 1.6.0 转的，喂给 runtime 1.5.2**（版本倒挂，官方不支持）。它同时有「合成校准集 + 版本倒挂」两个病，实测在那个 runtime 下**一张都检不出**（阈值降到 0.05 仍为 0），所以它不能当基线。
> 后来板端 runtime 一路升到 2.3.0，才谈得上做干净的对照实验。

### 2.2 DFL 图手术

**Q：DFL 是什么？为什么它会在 CPU 上？**
> DFL（Distribution Focal Loss）是 YOLOv8 检测头里把"框的距离"表示成 16 个 bin 的分布、再做加权和的那一段。它由 **Transpose + Softmax + Reshape** 组成。
> RKNN 的 NPU 对这几个形状变换算子支持不好，直接**回退到 CPU** 执行 —— 而 CPU 和 NPU 之间要来回搬数据，这才是最贵的部分。

**Q：怎么发现它是瓶颈的？**
> 用 `RKNN_FLAG_COLLECT_PERF_MASK` 打开逐层计时，一次拿到 **125 个算子**的耗时：
> - NPU 侧 115 个，合计 **19.23 ms（51.0%）**
> - CPU 回退 10 个，合计 **18.44 ms（49.0%）**
> 最慢的三个：`model.22/dfl/Transpose` **9181 µs**、`model.22/dfl/Softmax` **4467 µs**、三个 Reshape 合计 **4366 µs**（2660+941+765）。光这三个就 18.02 ms。

**Q：然后怎么砍的？**
> 不去改模型训练，直接做**图手术**：把 ONNX 在 Sigmoid 之后切开，只导出两个原始输出。
> `yolov8n.onnx`（262 节点，1 输出 84 通道）→ `yolov8n_dflfree.onnx`（228 节点，2 输出）：
> - `raw_box`：`(1, 64, 8400)`，来自 `/model.22/Concat_output_0`
> - `cls_sig`：`(1, 80, 8400)`，来自 `/model.22/Sigmoid_output_0`
> 整个 DFL 解码链从计算图里消失，**解码改由我用 C++ 写**。

**Q：怎么证明你没砍错？这是最关键的一问。**
> 不看代码，**用数据证明等价**：拿原模型（84ch 输出）当基准，和新模型输出 + 我的 numpy 解码逐元素比：
> - box 坐标 **max|Δ| = 0.000122 px**
> - cls 分数 **max|Δ| = 0**
> 0.000122 在 640 这个量级上已经是 **float32 的精度极限**（末位舍入），说明切图没有引入任何语义损失。cls 直接是 0 —— 因为原始输出本来就在 Sigmoid 之后，我只是搬走。
> C++ 解码器再和 numpy 对一遍，max|Δ| = **6.1e-05 px**。

**Q：解码搬到 CPU 会不会更慢？收益具体多少？**
> 会多花时间，但远小于省下的：后处理从 0.3 ms 涨到 **3.09 ms**（DFL 解码 + NMS），换来 18.44 ms 的 CPU 回退被砍掉。
> - 纯推理 **37.19 → 15.95 ms（−57.1%）**
> - 模型 84ch INT8 **6.22 MB → 4.34 MB（−30.2%）**
> - 单帧全链路 **37.19 ms / 26.9 FPS → 20.58 ms / 48.6 FPS（−44.7% / +81%）**
> 全链路分解：15.95（推理）+ 1.53（IO）+ 3.09（后处理）= 20.58 ms。

**Q：为什么砍掉 18.44 ms 却省了 21.24 ms？省得比砍掉的还多。**
> 因为 DFL 那 10 个算子不只是自己慢，它**还额外拖累了 NPU 调度**：CPU 回退意味着 NPU 要停下来等数据搬来搬去，这段等待没有单独记账。所以图变干净之后，NPU 主体的 19.23 ms 也跟着变短了。

**Q：DFL 的 16 bin 加权和有个坑？**
> 有，而且我第一版就踩了：加权和得到的是**格子单位**（0~15）的距离，**不是像素**，必须再乘 stride；漏了这步框整体偏大、**刚好差 8 倍**（stride=8 那一路）。
> 怎么发现的：把 `dist` 的范围打出来就行 —— 正确应该是 0~120 像素量级，我打出来是 0~15。**跨量纲的地方一定要打印中间值**，一眼看出来，比读代码快十倍。

**Q：优化完还差官方多少？**
> 官方标称 5.5~7.0 ms，我实测 15.95 ms，还有 **2.3~2.9 倍**差距。差距在 **NPU 侧的 MAC 利用率**：首层 `model.0/conv`（3 通道输入）只有 **2.33%**，大量 Conv 在 5%~22%。
> 这说明瓶颈已经从"图不干净"变成"NPU 没被喂饱"，性质完全不同。

### 2.3 三核 NPU 调度

**Q：RK3588 的 3 个 NPU 核怎么用？**
> `rknn_set_core_mask()` 只能绑**一个 context** 使用的核。所以有两条路：
> ① 单 context 绑三核 `CORE_0_1_2`；
> ② 开 3 个独立的 context，每个绑一颗核，3 个线程各跑一个。
> 实测只有第 ② 条路有收益。

**Q：单 context 绑三核为什么没用？**
> 实测 **35.97 ms，只比单核 37.19 ms 快 3.3%**。`RKNN_NPU_CORE_AUTO` 更是 37.27 ms，和单核一样。
> 原因：**单帧内的计算是有依赖的、串行的**。三颗核只能把同一张图分段接力跑，中间要同步，**核间同步开销把并行收益吃掉了**。3 个核不等于 3 倍算力，除非你有 3 条独立的活儿。

**Q：3 个独立 context 呢？为什么不是 3 倍？**
> 单线程基线 37.27 ms / 26.8 FPS；3 线程 3 context 各绑一核 → **40.8 ms/路，聚合 59.3 FPS，2.21×**。墙钟 5058 ms 跑完 300 帧，三路各自 4081~4089 ms，**差 8 ms，负载几乎完全均衡**。
> 但不是 3 倍，因为**三颗核各只跑到 49% 负载**（Core0 49% / Core1 49% / Core2 50%）。NPU 有一半时间在**等人** —— 等 CPU 喂数据、等 DDR 返回；加核只解决"算力不够"，解决不了"喂不饱"。
> 而且路延迟从 37.27 涨到 40.8 ms（每路慢 9%），因为三条路在同一条内存总线上抢带宽。

**Q：并行效率怎么算？**
> `实测聚合吞吐 ÷ 理论上限` = **59.3 ÷ (3 × 26.9) = 73.5%**。
> 换个等价算法 `2.21 ÷ 3 = 73.7%`，两者差 0.2 个百分点只是因为单核基线取 26.9 还是 26.8 FPS（两个口径都存在）。**对外我就说"约 73.5%"。**

**Q：喂数据方式会影响吗？（很多人建议做零拷贝）**
> 我做了对照：**INT8 原生直喂（`pass_through=1`）37.05 ms vs UINT8 转换 37.19 ms**，差 0.4%。
> 因为输入只有 **1.17 MB/帧**，而且 NPU 是异步搬运的。**CPU 侧的输入格式转换不是瓶颈** —— 这也是我判断"先别做 DMA-BUF 零拷贝"的依据。

### 2.4 逐层剖析与访存优化

**Q：逐层剖析怎么做？**
> `rknn_init` 时传 `RKNN_FLAG_COLLECT_PERF_MASK`，跑完用 `rknn_query(RKNN_QUERY_PERF_DETAIL)` 拿每层的耗时和它跑在哪个单元上（NPU / CPU）。
> 我封在 `bench_npu <model> 1 --perf` 里，一条命令出全表。

**Q：「官方 5.5 ms、你实测 37 ms」怎么一步步归因的？**
> 四步，每步都排除一个假设：
> ① **先确认口径**：我测的是 `rknn_inputs_set + rknn_run + rknn_outputs_get` 全周期，官方 5.5 ms 大概率只算 `rknn_run`。先把边界对齐，再比数字。
> ② **再看核绑定**：单核 / 三核 mask / AUTO 三种都测，最快 35.97 ms —— **不是调度问题**。
> ③ **再看喂数据**：INT8 直喂 vs UINT8 转换，差 0.4% —— **不是拷贝问题**。
> ④ **最后拆层**：10 个 CPU 算子占了 49%，全是 DFL 头 —— **找到了**。
> 每一步都在排除一个"听起来很合理"的假设，最后剩下的才是真因。

**Q：解码为什么要改遍历顺序？**
> 原来 3.19 ms，太高了。cls 输出是 `(80, 8400)` 布局，按「anchor 外循环、类别内循环」遍历时，每读 `cls[c*8400 + a]` 要跨 33.6 KB，80 个类别跑一遍跨 **2.7 MB** —— **cache 全废**。
> 改成「类别外循环、anchor 内循环」，内层地址连续；再加上先按阈值筛 anchor、只对通过的做 softmax（避免 8400 次 softmax）。降到 **1.79 ms**，1.78×。
> **同样的算法，在 ARM 上访存顺序能差一倍。看到"数据量不大但很慢"，先怀疑 cache。**

### 2.5 测量方法论（面试官最吃这一节）

**Q：为什么性能测试必须 `taskset` 绑核？**
> 我在 RK3588 上实测过一组对照，这是我最想讲的一条：
>
> | 组 | mean | p50 | p95 |
> |---|---:|---:|---:|
> | 绑核 O0 | 3.44~3.51 ms | 3.44~3.48 | 3.48~3.71 |
> | **不绑核 O0** | **6.38~8.15 ms** | 3.44~3.47 | **15.78~17.20 ms** |
> | 绑核 O3 | 0.62~0.63 ms | 0.62~0.63 | 0.63~0.64 |
> | 不绑核 O3 | 2.71~2.93 ms | 2.71~2.89 | 2.73~3.16 |
>
> 看第二行：**p50 和绑核组一模一样（3.45 ms），但 mean 翻倍、p95 冲到 17 ms**。
> 原因：O0 代码跑得久，被调度器在大小核之间迁移的次数多得多，每次迁移都是一次长尾。
> 后果：**5.5× 的真实差距，不绑核量出来只有 2×**。你要拿这个数去汇报，直接自废武功。

**Q：所以为什么用 p50/p95/p99 而不是只看均值？**
> 均值会被长尾污染，**它反映的是调度噪声，不是代码差异**。实时系统真正在意"最差的那几次有多差"：p95/p99 才决定你会不会掉帧。我的报告里三个都写：p50 看典型、p95 看抖动、p99 看最坏。

**Q：对照组怎么设？还有哪两个对照组？**
> 设一个**"理论上绝对不该变"**的量。做 O0/O3 对比时选的对照组是**纯推理 `rknn_run`**：O0 **14.79~14.88 ms** vs O3 **14.90~14.95 ms** —— **无变化**。NPU 是硬件单元，主机侧编译优化根本碰不到它，它稳住才能证明其他层的差异是真实归因、不是测量漂移。
> 在生产二进制上做 O0/O3 时又设了两个：**MPP 硬解**（1.250 → 1.322 ms，+5.8%，硬件层不该变 ✔）和 **letterbox**（1.184 → 1.222 ms，+3.2%，OpenCV 预编译库我改不了 ✔）。
> **两个"不该变"的同时不动，唯一自有的 CPU 热点 CSC 恰好提速 1.55×** —— 这才叫闭环。

**Q：口径踩过什么坑？**
> 第一版测速表里「全周期 IO」和「全链路」两栏数字**一模一样**。查出来是我把「全周期」写成 `t5 - t0`，而 release 在 decode 之后，所以那栏其实**包含了解码**。
> 重定义：纯推理 `t2-t1`、IO 周期 `t3-t0`、解码 `t4-t3`、全链路 `t4-t0`。修正后 `15.95 + 1.53 + 3.09 = 20.58` 才自洽。
> **教训：性能表里两个不同口径给出相同数字，一定是口径定义错了，不是巧合。**

### 2.6 编译优化（一个静默失效的坑）

**Q：你发现的那个大坑是什么？**
> 项目跑了 20 多天，`build_native/CMakeCache.txt` 里 **`CMAKE_BUILD_TYPE` 是空的**，`flags.make` 里写的是 `CXX_FLAGS = -std=gnu++17` —— **一个 `-O` 都没有，等于全程 -O0**。
> 也就是说此前所有 CPU 侧数字（软解 7.76 ms、letterbox、DFL 解码 3.09 ms、CSC 51~65 ms）**全是未优化的悲观值**。

**Q：为什么一个月没人发现？**
> 三条叠加：
> ① CMake 在 build type 为空时**不报错、不警告**，只是不加优化标志 —— 编译成功、程序能跑，**功能测试永远发现不了**；
> ② bench 工具是手工 `g++ -O2` 编的，跑出来的数字看着正常，于是形成"整体应该没问题"的错觉；
> ③ **两套构建口径混用，互相掩盖了对方的缺陷**。

**Q：怎么修的？**
> CMakeLists 四处：① build type 为空时默认 `Release`；② 兜底 `if(NOT CMAKE_CXX_FLAGS_RELEASE)` 时强制 `-O3 -DNDEBUG`（以防外部 toolchain 覆盖）；③ 自动探测 `-mcpu=cortex-a76.cortex-a55`，失败降级 `-mtune`，再失败用通用；
> ④ **最关键：configure 结束时打印构建摘要，flags 里匹配不到 `-O` 就 `message(WARNING)`** —— 让"没开优化"自己喊出来，不能靠人记。

**Q：修的过程中踩了什么？**
> CMake 自己的坑：摘要第一版恒为空、还误报"没有 -O"。因为 `CMAKE_BUILD_TYPE` 的值是 **`Release`（大小写混合）**，而标志变量是全大写 **`CMAKE_CXX_FLAGS_RELEASE`**。直接拼 `CMAKE_CXX_FLAGS_${CMAKE_BUILD_TYPE}` 得到 `CMAKE_CXX_FLAGS_Release`，`DEFINED` 为假 → 读到空值。**必须 `string(TOUPPER ...)` 再拼。**

**Q：收益多少？口径说清楚。**
> 两组数字，必须分开说：
> - **bench 口径**（`taskset -c 6`，6 轮交替）：DFL 解码 + NMS **3.44~3.51 → 0.62~0.63 ms（5.5×）**；全链路 **18.91~19.06 → 16.21~16.26 ms（−14.6%，52.6 → 61.7 FPS）**；二进制 206,256 → 75,688 B（−63%）。
> - **生产二进制口径**（同图 `real_000.jpg`、同模型、各 5 次）：**CSC 52.016 → 33.583 ms = 1.549×**；**全链路 76.928 → 55.836 ms（−27.4%，13.0 → 17.9 FPS）**。

**Q：最容易被问穿的一句——「白捡 1.55×」到底指什么？**
> **1.549× 是 CSC 单层的，不是全链路。** 全链路是 **−27.4%（1.378×）**。
> 这两个数一旦混着说，面试官拿计算器一除就露馅。我现在的标准说法是：「CSC 单层提速 1.55×，但全链路只降 27.4%，因为 CSC 之外还有很多不归编译优化管的部分」。

**Q：这个 27.4% 有什么局限？**
> 三条：① 用的是 **640×640** 的图，letterbox scale=1.000，若换 1280×720 输入，CSC 的工作量大约翻 2.25 倍，占比会变；② 测量时 `w4_edgevision_gateway` 常驻，占 CPU 约 55%；③ 即使 O3 之后，**CSC 仍占全链路 60%** —— 它还是第一瓶颈，编译优化只是把它从"离谱"拉到"很大"。

### 2.7 MPP 硬解与硬编（一正一负）

**Q：MPP 硬解做到多少？**
> **p50 1.027 ms（≈1.03）vs OpenCV 软解 `cv::imdecode` 7.761 ms，7.6×**。
> 拆开看：`decode_put_packet` p50 1.015 ms、`get_frame` ≈0.017 ms —— 时间几乎全花在提交和等硬件。
> 200/200 有效帧，9 张真实图 Y-PSNR **49.9~77.2 dB**，全部 PASS。

**Q：硬解踩的最大的坑是什么？**
> `decode_put_packet` **恒返回 -1012（`MPP_ERR_BUFFER_FULL`）**，换遍所有参数（split_parse、各种 CFG、预分配 frame buffer、KEY_OUTPUT_FRAME meta）全部无效。
> 排查方法：读完官方 demo 确认用法没错 → 去读 `mpp/mpp.c` 里 `mpp_put_packet` 的错误传播路径，确认是 `mpp_poll` 输入端口被拒 → **用 MPP 源码重新编译静态库，一行代码都不改，直接出帧**。
> 根因：系统预装的 `/usr/lib/.../librockchip_mpp.so.0` 是 **2021-05-20** 编的，和板上 `mpp_service` 内核驱动的 ioctl 语义**版本倒挂**。
> **这类"参数怎么调都返回同一个错误码"的问题，优先怀疑层间版本，别继续翻参数。**

**Q：硬编呢？听说也做了？**
> 做了，而且完整验证正确（NV12 入 → 标准 baseline JPEG，9 图 Y-PSNR **42.46 dB**，1280×720 **49.27 dB**，`file` 认证合法）。
> **但实测比软编慢**：1280×720 mean **7.24 vs 6.65 ms（1.07~1.09×）**；640×640 慢 1.13~1.20×；分辨率从 64×64 扫到 960×540，**全部档位都更慢，没有一个赢的**；4 路并行软编快 **1.88×**。
> 唯一优势是 **CPU 占用 8.2% vs 99.7%**（每帧 0.59 vs 6.64 ms）。

**Q：为什么"用了硬件反而慢"？这题很值。**
> 对分辨率做线性拟合，得到延迟模型：
> - 硬编 `t ≈ 0.35 ms + 7.0e-6 × 像素数`
> - 软编 `t ≈ 0    ms + 7.5e-6 × 像素数`
> **每像素的边际算力两者基本打平（硬编还略优），但硬编每帧要多付 0.35 ms 的固定开销** —— `ioctl` 提交 + 等中断往返。
> 分辨率越小，这 0.35 ms 摊得越不利，所以 64×64 那档输得最惨；1280×720 才把差距压到 1.07×。
> 4 路并行输得更狠，因为**软编能吃满 8 个 A76/A55 核，硬编只有 4 个 jpege 硬件核**。

**Q：怎么证明它真的走了硬件，不是悄悄回退到软件？**
> 查 `/proc/interrupts` 里硬件核的中断**增量**：
> `fdba0000.jpege-core` 的 42/44/46/48 四个核：
> 跑前 `21485 / 2735 / 1566 / 820` → 跑后 `25038 / 3438 / 1953 / 987`
> 增量 **+3553 / +703 / +387 / +167**，其余 jpege / rkvenc / rkvdec 核**全部 0 变化**。
> 这就是硬件在干活的铁证。**一开始我以为是软回退，是这个证据推翻了它。**

**Q：那结论是什么？**
> **从路线图划掉，不做。** 单路 30 fps 下一次编码 6.65 ms，只占一个核的 20%（6.65/33.3），**CPU 根本不是瓶颈**，拿 0.6 ms 的延迟损失换 6 ms 的 CPU 空闲是亏的。
> **负结论也是结论** —— 用数据把写在路线图上的假设否掉，比硬凑一个"快了 5%"的数字有价值。

**Q：硬编还踩了什么值得说的坑？**
> 两个：
> ① `FIXQP` 模式下 `fps_in_denom=0` 导致 `rc_frm_check_drop` 断言除零，直接 **Segfault**；
> ② PSNR 只有 35.4 dB、画面偏暗：`cv::cvtColor` 出的是 **limited-range YUV（16~235）**，而 JPEG 要 **full-range**，MPP 原样写入。输入侧预展开 `(Y−16)×255/219` 后 **35.4 → 46.2 dB**。
> 更坑的是 `prep:range` / `set_color_range` 12 组组合**输出字节完全相同** —— **键存在但被实现忽略，又是个"假成功"**，只能靠端到端 PSNR 才发现。

### 2.8 边界（主动讲，别等问）

**Q：RGA 硬件 CSC 做了吗？**
> **没做。** 本板 RGA 用户态库是 **2.1.0，不支持 full CSC**，实测零拷贝 NV12→RGBA + 缩放能做到 2.03 ms（比 CPU 的 33.58 ms 快一个量级），但**颜色偏差约 ±13% 且没量化**，我不敢上生产。判断是纯性能优化、上板收益不确定，优先级排到了最后。

**Q：DMA-BUF 零拷贝呢？**
> **没做**，`rknn_inputs_set` 走的是普通内存拷贝。
> 但我做过对照实验证明**现在输入侧不是瓶颈**：INT8 直喂 37.05 vs UINT8 转换 37.19 ms，差 0.4%，每帧才 1.17 MB。所以**零拷贝是"优化一个不存在的问题"**，我先去砍 CPU 回退，那才是 49%。

**Q：RTSP / WebRTC 呢？**
> **没做。** 我推流用的是自己定义的 **TCP 9000 上的 248 字节定长帧**（8B 包头 + 10×24B BBox），不是 RTSP。选它是因为要跨机验证结构化检测结果，定长帧比 RTSP 简单可控。

**Q：H.264/H.265 硬解？**
> **没做。** 摄像头出的是 **MJPEG**，所以 MPP 只接了 MJPEG 解码这一条。H.264/H.265 要另外的码流输入源，项目里没有。

**Q：整机功耗多少？**
> **没测。** 没有功率计，我不给数字。**"没测"是唯一诚实的答案，编一个 9.5W 出去，被问一句"怎么测的"就完了。**

## 四、踩过的坑（都是真踩）

- **拿余弦相似度当精度指标** → 0.9965 PASS，而 cls 分支已经塌缩成常数 0.5。
- **用合成色块做校准集** → scale 被窄分布锁死，真实数据一进来就饱和。
- **DFL 的 16 bin 加权和忘了乘 stride** → 框整体差 8 倍。
- **以为 `rknn_set_core_mask(CORE_0_1_2)` 就能三倍加速** → 只快 3.3%。
- **不绑核测性能** → p50 一样，mean 翻倍、p95 冲到 17 ms，5.5× 变成 2×。
- **两个不同口径给出相同数字还以为是巧合** → 实际是计时点定义错了。
- **`CMAKE_BUILD_TYPE` 为空** → 全程 -O0，CMake 不报错不警告，功能测试永远发现不了。
- **`CMAKE_CXX_FLAGS_${CMAKE_BUILD_TYPE}`** → 变量名大小写敏感，拼出 `..._Release` 恒为空。
- **MPP `decode_put_packet` 恒 -1012** → 参数怎么调都没用，是系统库与内核驱动版本倒挂。
- **以为硬编一定比软编快** → 每像素算力打平，硬编白付 0.35 ms 固定开销。
- **以为硬编慢是软回退** → 查 `/proc/interrupts` 中断增量才推翻了它。

## 五、面试官可能从哪下刀

**Q1：「你说掉点只有 1.4%，凭什么信？COCO128 才 128 张图。」**
> 三重回答：① **929 个 GT 框 / 71 个类**，不是 128 个样本量的分类问题；② 我主动承认 **COCO128 是训练子集，绝对 mAP 偏乐观**，所以我不引用绝对值，只引用**同批图上的相对掉点** —— "见过"这个偏差在 FP32 和 INT8 两边同时存在，做差就抵消了；③ 要更强的结论，下一步是**自建场景验证集**，这个我明确说没做。

**Q2：「余弦相似度 0.9965 你说没用，那它在什么情况下有用？」**
> 它是**逐层、整体、不经过后处理**的粗筛指标，用来快速发现"这层完全对不上"很有效（比如 0.3 那种）。但它**不敏感于单分支塌缩** —— 80 个通道里 1 个废了，整体余弦几乎不动。所以正确用法是：**余弦当哨兵，mAP 当裁判**。

**Q3：「你砍 DFL 头，怎么保证不是只在你这几张图上对？」**
> 我证明的不是"看起来对"，是**数值等价**：拿原模型 84ch 输出当基准，逐元素比 —— box max|Δ| = 1.22e-4 px（float32 极限）、cls max|Δ| = 0。这个证明和"哪张图"无关，它是对**整个数值映射**成立的。而且 C++ 解码器和 numpy 又交叉验证了一遍（6.1e-5 px）。

**Q4：「三核只跑 2.21 倍，是不是你没优化好？」**
> 不是优化不足，是**已经到瓶颈的另一侧**。证据是三核各只有 **49% 负载** —— NPU 有一半时间在等人。加核只能解决算力不够，解决不了"喂不饱"。真要再往上，得从 DDR 带宽和 CPU 侧流水线下手，不是再调 NPU。

**Q5：「你说 1.549×，那全链路为什么只降 27.4%？」**
> 因为 CSC 只是其中一层，而且是**变慢的那部分之外**的一层。全链路里还有 NPU 时间（编译优化碰不到）、MPP 硬解（硬件）、letterbox（OpenCV 预编译库）。这几个加起来理论上就不该动，实测也确实没动（+5.8% / +3.2%，在噪声内）。**能把 27.4% 拆清楚、并且每一层都有对照，比报一个大数字可信。**

**Q6：「不绑核到底差在哪？给我一个数。」**
> 同一个 O0 二进制：绑核 p50 3.45 / mean 3.5 / p95 3.7；不绑核 p50 3.45（一样）/ mean 6.4~8.2（翻倍）/ p95 17 ms（四倍多）。**p50 不变而 mean 翻倍，说明差异全在长尾 —— 是调度迁移，不是代码。** 这就是为什么我所有性能表都标了 `taskset`。

**Q7：「MPP 硬编慢，是不是你代码写错了？」**
> 我专门排除了这个可能性。① 正确性过了：Y-PSNR 42.46 dB / 720p 49.27 dB，9/9 ≥35 dB，`file` 认证标准 baseline JPEG；② **真的走硬件**：jpege-core 四核中断增量 +3553/+703/+387/+167，不是软回退；③ 慢的原因是**结构性**的：拟合出 `0.35 ms + 7.0e-6×像素`，固定开销是硬件的提交/中断往返，不是我的循环写法。要证明是我写错，得先解释这个 0.35 ms 从哪来。

**Q8：「这些数字你怎么保证不是编的？」**
> 三层：① 每个数字都标了**测量口径**（纯推理 / IO 周期 / 全链路不混用）；② 每个结论都配**对照组**（NPU 纯推理、MPP 硬解、letterbox 三层"不该变"的）；③ **复现命令写进文档**，`BENCHMARKS.md` 每节末尾都有能直接粘到板子上跑的 bash。我宁可写"（未测）"，也不给一个拿不出命令的数。

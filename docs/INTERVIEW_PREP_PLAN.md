## 二、两分钟项目自述（逐字稿，背下来）

> 面试第一个问题 99% 是「介绍一下你这个项目」。**这段要背到能下意识说出来。**
> 语速放慢，别像背课文。

「我在一块 RK3588 开发板上做了一个端侧的 AI 推理和智能体系统。

一开始遇到的问题是：官方说这个模型在 NPU 上只要五六毫秒，我在板子上实测是 37 毫秒，差了六七倍。
我没有直接去猜原因，而是用 RKNN 的逐层剖析功能把 125 个算子全部拆开计时，
发现 NPU 主体只占 19 毫秒，另外 18 毫秒是 YOLOv8 检测头里的三个算子——Transpose、Softmax、Reshape——被回退到 CPU 上算了。
**所以瓶颈不是 NPU 算力不够，是 CPU 回退。**

于是我把这三个算子从 ONNX 计算图里剥掉，自己在 C++ 里写解码，
先证明数值等价——框坐标误差 1.2e-4 像素，已经是 float32 的精度极限了。
改完之后单帧纯推理从 37 毫秒降到 15.95 毫秒，模型也从 12 兆压到 4.3 兆。

量化这块我踩过一个比较有意思的坑：我一开始用特征图余弦相似度判断量化有没有掉精度，
算出来 0.9965，看起来非常好。但后来发现这个指标会骗人——
换回旧的合成校准集之后，分类分支整体塌缩成了一个常数 0.5，也就是 sigmoid(0)，
分类头其实已经彻底废了，而余弦相似度**照样是 0.9965**。
所以我改成跑真的 mAP：在 COCO128 上，FP32 是 0.6087，INT8 是 0.6002，掉了 0.85 个点、1.4%。

后面我又用 RKLLM 把 Qwen 2B 跑在板子上，做了个端侧智能体，
能调 5 个硬件工具——查温度、查 NPU 负载、查摄像头检测结果、控 LED、读巡检日志。
一条自然语言能跑完「巡检、研判、执行、汇报」。
这块最值钱的一次 debug 是：演示全部通过了，但我去翻执行记录，发现它汇报说灯灭了，
而那个灯其实正在报警爆闪。查下来不是模型幻觉，是我的感知层在骗它——
灯的亮度是 100 毫秒一个周期的方波，我只采样了一次，正好撞在灭的那一半。
**周期性物理量用单点采样去定性，这就是抽样定理里的混叠。**

整个项目所有数字都是板端实测的，测不出来的我就写「未实现」，
README 里专门有一张「明确未实现」的表。我觉得清楚自己做到哪，比做得全更重要。」

> **时长检验**：上面这段正常语速约 110 秒。如果面试官中途打断追问，就**顺着他的问题深入，别硬背完**。

## 三、五条杀手故事（每条都要能独立讲 90 秒）

面试官一天听八个候选人讲故事，**能被记住的只有「反常识 + 有数字 + 有方法论」的**。

### 故事 1：官方 5.5ms vs 实测 37ms —— 归因不靠猜
- **钩子**：「我没有信官方数字，也没有直接优化，而是先把它拆开。」
- **方法论**：`RKNN_FLAG_COLLECT_PERF_MASK` 拆 125 个算子 → NPU 115 个 19.23ms / CPU 回退 10 个 18.44ms
- **反常识**：`dfl/Transpose` 回退 CPU 要 9.18ms，但 `dfl/Transpose_1` 却在 NPU 上跑只要 1.47ms —— **同一个算子，位置不同结果差 6 倍**
- **结论**：瓶颈在算子放置，不在算力

### 故事 2：余弦相似度 0.9965 骗了我 —— 指标选错等于没测
- **钩子**：「我一开始用一个看起来很权威的指标，它给了我一个非常漂亮的数字，而那个数字是假的。」
- **证据**：合成色块校准集 → cls 分支输出**精确等于 0.5**（= sigmoid(0)，说明整体塌缩成常数）→ 而余弦相似度仍有 0.9965
- **转折**：换真实校准集 → 9 张图 top-1 平均分 0.5000 → 0.8072
- **落地**：改用真 mAP（COCO128 / 929 GT / 71 类）：0.6087 → 0.6002，−1.4%
- **加分**：主动说局限 ——「COCO128 是 YOLOv8n 的训练子集，绝对 mAP 偏乐观，不能对外说我在 val2017 上拿到 0.61；但 FP32 和 INT8 用同一批图，'见过'的因素两边抵消，所以**相对掉点**是成立的。」
- **学到什么**：指标必须能反映你真正关心的东西，否则测了等于没测

### 故事 3：演示全绿，但 Agent 在说谎 —— 分层定位幻觉 vs 感知层
- **钩子**：「演示判 PASS 了。我不放心，去翻了执行记录。」
- **现象**：Agent 汇报「LED 始终熄灭，这导致硬件层面的过热保护逻辑被抑制」——而灯正在爆闪
- **关键判断**：先问「是模型幻觉吗？」→ 逐条把 Observation 拉出来对齐物理事实 → **Observation 里写的就是 `current_mode: "off"`**
- **根因**：`get_led_current_mode()` 单点读 trigger 见 `none` 就读**一次** brightness，撞上 100ms 爆闪的灭相
- **修法两层**：① 查爆闪进程的 pid + `/proc/<pid>/cmdline` 含 `brightness` 才判活（排除僵尸和 pid 复用）→ 直接返回 `alarm_blink`；② 兜底 12 次 ×15ms 多点采样
- **学到什么**：**Agent 给出离谱结论时，先分层定位是「模型幻觉」还是「感知层喂了错数据」，再谈调 prompt。** 这次模型是忠实地推理了一个错误的输入。

### 故事 4：模型不缺智商，缺常识
- **钩子**：「上一条修好之后，它又开始说设备要永久损坏了。」
- **现象**：汇报「SOC 温度长期偏高（>40°C）…存在硬件降频甚至永久损坏的风险」，还臆测「若系统内部逻辑 0=off, 1=heartbeat…」
- **关键判断**：这次数据是对的（49°C），模型也读到了「超过 20.00°C 阈值」——**它只是不知道 RK3588 多少度才算热**
- **根因**：缺领域世界知识 → 只能按「有没有告警」倒推 → 把演示阈值当成了真实红线
- **修法**：sys_prompt 补世界知识（正常 30~65°C，>75°C 才算过热，85°C 才需要担心降频）+ 明确禁止臆测工具内部实现
- **修复后**：同一场景变成「SOC 49.9°C ✅ 正常（30~65°C）」「这些是低阈值演示事件，而非真实过热」
- **学到什么**：**不是让模型更聪明，是补上它缺的那块世界知识。** 这也是 prompt engineering 里最实的一课。

### 故事 5：MPP 硬编走通了，但我把它从路线图上划掉了
- **钩子**：「这件事我做完了、做对了，然后决定不用它。」
- **过程**：实现 MPP 硬件 JPEG 编码，输出合法 baseline JPEG，PSNR 42.46dB，全部验证通过
- **结果**：**比软编还慢 1.07~1.88×**，从 64×64 到 960×540 **所有分辨率都更慢**
- **关键证据**：一开始以为是走了软件回退，后来用中断计数证明**确实走了硬件**（`fdba0000.jpege-core` 四核中断 +3553/+703/+387/+167），推翻了误判
- **根因**：延迟模型 —— 硬编 = **0.35ms 固定 ioctl/中断往返** + 7.0e-6 × 像素；软编 = 0 + 7.5e-6 × 像素。**每像素算力打平，硬编白付固定开销**
- **唯一优势**：CPU 8.2% vs 99.7%（每帧 0.59ms vs 6.64ms）—— 但单路 30fps 下 CPU 不是瓶颈，不划算
- **学到什么**：**负结论也是结论。** 用数据把路线图上的假设否掉，比硬凑一个「快了 5%」的数字有价值。

> 五条故事里，**故事 3 和故事 5 最能打**——大部分候选人只有「我做了 X 效果变好 Y%」，
> 没有「我做了 X 发现它变差了所以我不做」和「我做完发现我之前判断错了」。

## 四、红线：这些话说出口就完了

### 绝对不要说的（说了必被追问穿）

| ❌ 千万别说 | 为什么 |
|---|---|
| 「端到端延迟 18 毫秒」 | 那是板子到货前的设计估算值。真实是 20.58ms（bench 口径）/ 55.84ms（生产链路） |
| 「三核 150+ FPS」 | 没有这个数。真实是 **59.3 FPS / 2.21×** |
| 「功耗 9.5W」 | **功耗从来没测过。** 问就说「没测」 |
| 「我做了 DMA-BUF 零拷贝」 | **没做。** 只能讲「做了对照实验证明输入侧不是瓶颈，所以优先砍 CPU 回退」 |
| 「我做了 RGA 硬件 CSC」 | **没做。** 本板 RGA 2.1.0 不支持 full CSC，判断不划算主动放弃 |
| 「RTSP 推流 / H.264 硬解」 | **没做。** 只有 MJPEG 硬解，推流是自己定义的 TCP 248B 定长帧 |
| 「4 路 1080P 实时」 | 讲不出口，没这个能力 |
| 「我用了 ByteTrack 做跟踪」 | 只在 Python 里做过仿真，**没进 C++ 链路** |
| 「余弦相似度 0.9965，说明量化几乎无损」 | **这是最典型的踩雷**。它恰恰是反例，见故事 2 |

### 高分说法（同一个事实，换个说法）

| 情况 | 低分说法 | 高分说法 |
|---|---|---|
| 某项没做 | 「这个还没来得及做」 | 「我评估过，结论是**不做**，原因是…」+ 讲理由和数据 |
| 数字不好看 | 换个口径让它好看 | 「这个口径下是 X，另一个口径下是 Y，我一般报 Y 因为更保守」 |
| 被问倒了 | 硬编一个答案 | 「这个我不确定，我当时的做法是 X，但没验证到那一层」 |
| 项目有短板 | 回避 | 「最大的短板是 RGA 没落地，CSC 走 CPU 要 33 毫秒，这是我现在最想解决但还没解决的」 |

## 五、被问倒了怎么办（这个必须练）

面试官一定会问到你不会的。**不会不是问题，慌了瞎编才是致命伤。**

### 三步走

1. **先确认问题**：「您问的是 A 还是 B？」—— 有一半情况你其实会，只是没听清方向
2. **给已有的最近答案**：「这块我没直接做过，但相关的 X 我做过，我的理解是…」
3. **明确边界**：「再深我就不确定了，不敢瞎说」—— **这句话比编一个答案强十倍**

### 三类必被问但你没做过的（提前想好）

| 可能的问题 | 怎么答 |
|---|---|
| 「用过 RGA 吗？DMA-BUF 呢？」 | 「RGA 查过也评估过，但这块板 RGA 2.1.0 不支持 full CSC，硬上颜色偏 ±13%，我判断不划算就没做；DMA-BUF 只做到架构设计，没落地。**不过我做对照实验证明了我现在的输入侧不是瓶颈**——原生直喂和转换喂差 0.4% 都不到，所以我优先去砍 CPU 回退，那才是 49% 的大头。」 |
| 「GDB / Valgrind 熟练吗？」 | 「GDB 用过，但不算熟练，主要用来抓过 segfault 定位到具体行；Valgrind 没在这块板上跑过 —— 板子是 aarch64，我还没交叉编过去。」**（注意：如果你这几天补了，就如实改成做过）** |
| 「多线程调度、锁粒度这些呢？」 | 这块**真的做过**，直接上 W2：2 线程百万次无锁自增实测 1000093（丢了 9907 次）、条件变量为什么必须配 mutex、为什么用 while 不用 if、3 核抢单线程池锁粒度最小化。 |

## 六、反问环节（问这些，加分）

面试最后「你有什么想问我的」**不是客套，是评分项**。别问「公司有食堂吗」。

- 「这个岗位平时部署的模型大概是多大、跑在什么芯片上？是偏优化还是偏业务集成？」
- 「团队现在端侧这块的瓶颈主要在哪 —— 是模型精度、还是内存/带宽这类硬件约束？」
- 「如果我进来，前一个月比较现实的目标是什么？」
- 「团队用 GDB / Valgrind / perf 这类工具排查性能问题，有比较固定的流程吗？」（**暗示你想学**）

## 八、心理准备（说点实在的）

1. **实习面试不会考到最深。** 你现在的深度（能讲清算子回退、能讲清混叠、能讲清负结论）已经超过大部分研一候选人了。
2. **大部分候选人只有一个项目，且数字是编的。** 你有五条能扛三轮追问的故事，这是真实优势。
3. **被问倒很正常。** 面试官问超纲问题是常态，考察的是你的反应，不是知识边界。
4. **「我不知道」是加分项**，前提是你能说清楚「我知道到哪一步、我猜可能是 X、但我没验证」。
5. 最后：**别为了显得厉害去提你没做的东西。** 你的核心竞争力是「数据是真的」，
   一旦掺了一个假的进去，整套东西的可信度就全塌了 —— 这个项目的价值就在「能当场复现」这四个字上。
